# 工具返回的结果太长怎么处理？

::: tip 一句话回答
原则是**工具只返回模型下一步需要的信息**。具体手段按顺序考虑：在工具里**过滤和裁剪字段**；对列表做**分页**，返回总数和"下一页"的游标；对大文本**截断**并明确告诉模型被截断了、怎么取剩下的；必要时用小模型**先摘要**；特别大的结果**存到外部**（文件、对象存储），只把路径或 ID 交给模型，让它按需读取。多轮之后，旧的工具结果还可以**清理或压缩**，别让它们一直占着上下文。
:::

## 详细解析

### 为什么不能整个塞进去

- **超出上下文**：一次数据库查询、一份日志、一个网页，动辄几万 token，直接把请求撑爆
- **成本和延迟**：工具结果会留在消息历史里，之后每一轮都要重新计费
- **效果变差**：关键信息被淹没在大量无关内容里，模型更容易漏看或答错，见 [上下文窗口是什么？长上下文有哪些问题](/ai/llm/04-context-window)
- **注入面变大**：外部内容越多，夹带恶意指令的机会越多，见 [间接提示注入](/engineering/security/02-indirect-injection)

### 在工具设计阶段解决

最有效的办法是让工具本身就返回得少：

- **只给需要的字段**：查用户返回姓名、状态、等级，而不是整张表的 40 个字段；去掉内部 ID、时间戳这类模型用不上的值
- **提供过滤参数**：日志工具接收 `level`、`keyword`、`since`，让模型自己缩小范围，而不是拉全量再看
- **分页**：默认返回前 20 条，附上 `total` 和 `next_cursor`
- **提供"概览"和"详情"两个粒度**：先返回文件列表或搜索摘要，模型选中后再调详情工具

### 运行时的兜底

工具设计得再好，也会遇到意外的大结果，所以执行层要有统一兜底：

1. 结果超过阈值（按 token 或字符数估算）就处理
2. **截断**：保留开头和结尾（日志的报错常在末尾），中间写明省略了多少
3. **告诉模型**：在结果里写"已截断，共 12000 行，只显示前 100 行和后 50 行，可以用 offset 参数查看其他部分"，模型才知道还有内容、怎么拿
4. **落盘**：完整结果写到文件或存储里，返回路径，模型可以再用读文件或搜索工具按需查看

### 已经用过的结果怎么办

长任务里，几十轮之前的工具结果大多不再需要。常见做法是把旧结果替换成一行占位（"此处原为 xx 工具的结果，已清理"），或者压缩成摘要。注意要保留工具调用和结果的配对结构，否则有的接口会报错。这部分和 [长任务 Agent 的上下文管理](/ai/agent/12-long-task-context) 相关。

## 代码示例

```ts
// 统一的结果兜底：超长就截断首尾，并告诉模型怎么取完整内容
function fitToolResult(text: string, maxChars = 4000, savedPath?: string): string {
  if (text.length <= maxChars) return text
  const head = text.slice(0, Math.floor(maxChars * 0.7))
  const tail = text.slice(-Math.floor(maxChars * 0.3))
  const omitted = text.length - head.length - tail.length
  const hint = savedPath
    ? `完整结果已保存到 ${savedPath}，需要时可以用 read_file 分段读取。`
    : '如需其他部分，请缩小查询范围后重新调用。'
  return `${head}\n\n[已截断：中间省略 ${omitted} 个字符。${hint}]\n\n${tail}`
}

const log = Array.from({ length: 2000 }, (_, i) => `line ${i}`).join('\n')
const out = fitToolResult(log, 200, '/tmp/tool-output/abc.log')
console.log(out.length < log.length, out.includes('已截断')) // true true
```

## 面试官可能追问

::: details 用小模型先摘要，有什么风险？
摘要会丢信息，而且丢什么不由主模型决定：主模型要找某个错误码，摘要模型可能恰好把它省掉了。摘要还会增加一次调用的延迟和成本。所以更推荐让工具支持过滤，或者落盘后让主模型自己检索；摘要适合网页正文这类"要大意"的内容。
:::

::: details 截断阈值怎么定？
按 token 估算而不是字符数更准，中文和代码的字符与 token 比例差别很大。阈值要结合上下文窗口和一个任务预计调用多少次工具来定：单个结果不应占掉太大比例。可以按工具分别设置，日志、网页给得紧一些，结构化查询结果给得宽一些。
:::

::: details 二进制或图片结果怎么办？
不要把 base64 直接塞进文本结果里，会占用大量 token 而且模型读不懂。支持多模态输入的模型可以用图片内容块传入；更多时候是在工具里先提取有用的信息（如 OCR 文字、表格），或者存储后返回链接。
:::

## 易错点

- 截断了却不告诉模型，模型会把残缺的结果当成全部，得出错误结论
- 只截开头。日志、命令输出的关键信息经常在末尾
- 只在运行时兜底，不改工具设计。应该先让工具支持过滤和分页
- 清理旧结果时把工具调用和结果的配对删坏了，导致接口报错
