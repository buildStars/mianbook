# 大模型为什么要一个 token 一个 token 地生成？投机解码是怎么加速推理的？

::: tip 一句话回答
大模型是**自回归**的：第 t 个 token 的分布依赖前面所有 token，所以只能逐个生成。每生成一个 token 都要把全部权重从显存读一遍，小批量下瓶颈是**显存带宽**而不是算力，GPU 大部分时间在等数据。**投机解码**让一个便宜的草稿模型先连续猜 k 个 token，大模型**一次前向并行验证**这 k 个位置，按概率接受一段前缀，拒绝处从修正后的分布重新采样。这套接受规则能保证**输出分布和大模型自己采样完全一致**，加速比取决于草稿的接受率。
:::

## 详细解析

### 为什么只能逐个生成，又为什么慢

模型建模的是 `P(x_t | x_1 ... x_{t-1})`，不知道第 t 个 token 就没法算第 t+1 个的分布（采样过程见 [生成与采样](/ai/llm/01-generation-sampling)）。

decode 阶段每步只处理 1 个新 token，计算量很小，却要读完所有权重和 [KV Cache](/ai/llm/08-kv-cache)。算力闲着、带宽占满，这叫**访存受限**。一次前向处理 1 个 token 和处理 5 个 token，读的权重一样多，耗时差不多。投机解码就是利用这一点：把"串行算 5 步"换成"串行猜 5 步（便宜）+ 并行验 1 次（贵但只一次）"。

### 流程

1. 草稿模型基于当前前缀，自回归地生成 k 个候选 token `d_1 ... d_k`，并记下每步的分布 q
2. 大模型对"前缀 + d_1 ... d_k"做**一次**前向，得到这 k 个位置以及第 k+1 个位置的分布 p
3. 从 d_1 开始依次验证：以概率 `min(1, p(d_i) / q(d_i))` 接受
4. 第一次拒绝时，从**残差分布** `norm(max(0, p - q))` 采样一个 token 替换它，丢掉后面的草稿
5. 如果 k 个全部接受，再从第 k+1 个位置的 p 额外采样一个 token

```text
草稿：  今天  天气  很  热  吗
验证：   ✓     ✓    ✓   ✗
输出：  今天  天气  很  [从残差分布重采样的 token]   -> 一次大模型前向产出 4 个 token
```

每轮至少产出 1 个 token（最差相当于普通解码），最多 k+1 个。

### 为什么输出分布和大模型一致

只看单个位置，记大模型分布为 p，草稿分布为 q。输出某个 token x 有两条路：

- 草稿恰好给出 x 并被接受：`q(x) · min(1, p(x)/q(x)) = min(q(x), p(x))`
- 草稿被拒绝后从残差分布采到 x：总拒绝概率是 `1 - Σ min(p, q) = Σ max(0, p - q)`，残差分布里 x 的概率是 `max(0, p(x) - q(x)) / Σ max(0, p - q)`，两者相乘得 `max(0, p(x) - q(x))`

两条路加起来：`min(q(x), p(x)) + max(0, p(x) - q(x)) = p(x)`。所以每个位置的输出都严格服从 p，草稿模型再差也只影响速度、不影响质量。贪心解码时更简单：草稿 token 等于大模型的 argmax 就接受，否则用 argmax 替换。

### 加速比取决于什么

- **接受率**：草稿和大模型越像，接受越多。单步接受率等于 `Σ min(p, q)`
- **草稿开销**：草稿模型越小越快，但通常越不像，要权衡
- **k 的取值**：k 太大，后面的猜测大多被拒，白算；k 太小，摊薄不够

假设每个 token 被接受的概率都是 α（理想化假设），每轮期望产出 `(1 - α^(k+1)) / (1 - α)` 个 token。比如 α = 0.8、k = 4 时约 3.4 个。

### 常见变体（只讲思路）

- **不用独立草稿模型**：在大模型上加几个额外的预测头，同时预测后面几个 token；或者让大模型跳过部分层来起草
- **用文本本身起草**：从提示词或已生成内容里找重复的 n-gram 作为草稿，适合代码修改、摘要这类大量复制原文的任务
- **树状验证**：一次给出多条候选分支，用特殊的注意力掩码一次验证整棵树，提高接受长度

这些方法都沿用"便宜地猜、并行地验"的框架，区别在草稿从哪来。

## 代码示例

用一个 4 个 token 的小词表验证接受规则，统计输出分布是否等于 p：

```js
const p = [0.5, 0.3, 0.15, 0.05] // 大模型分布
const q = [0.25, 0.25, 0.25, 0.25] // 草稿模型分布

function sample(dist) {
  let r = Math.random()
  for (let i = 0; i < dist.length; i++) {
    r -= dist[i]
    if (r < 0) return i
  }
  return dist.length - 1
}

function verify(x) {
  if (Math.random() < Math.min(1, p[x] / q[x])) return { token: x, accepted: true }
  // 拒绝：从 max(0, p - q) 归一化后的残差分布重新采样
  const residual = p.map((pi, i) => Math.max(0, pi - q[i]))
  const sum = residual.reduce((a, b) => a + b, 0)
  return { token: sample(residual.map((r) => r / sum)), accepted: false }
}

const N = 1_000_000
const count = [0, 0, 0, 0]
let accepted = 0
for (let i = 0; i < N; i++) {
  const r = verify(sample(q))
  count[r.token]++
  if (r.accepted) accepted++
}
console.log(count.map((c) => (c / N).toFixed(3)).join(' ')) // 约 0.500 0.300 0.150 0.050
console.log((accepted / N).toFixed(3)) // 约 0.700，即 Σ min(p, q)
```

## 面试官可能追问

::: details 投机解码在高并发场景下还有效吗？
效果会变小。批量大时 decode 已经能用上更多算力，不再严重访存受限，并行验证"白送"的算力变少；被拒绝的草稿还浪费了计算。所以它在低延迟、小批量的场景收益最明显（延迟优化总览见 [推理延迟](/engineering/deploy/07-latency)）。
:::

::: details 草稿模型有什么要求？
必须和大模型用**同一个词表**，否则 token 对不上无法验证。最好是同系列的小模型或从大模型蒸馏而来（见 [模型蒸馏](/ai/llm/15-distillation)），分布越接近接受率越高。
:::

::: details 和 KV Cache 有什么关系？
两者是叠加的。验证时大模型对 k 个草稿位置一起计算并写入 KV Cache，被拒绝位置之后的缓存要回滚丢弃。草稿模型也有自己的 KV Cache。
:::

## 易错点

- 认为投机解码会降低质量：用正确的接受规则时，输出分布和大模型完全一致，这是它和"直接用小模型"的本质区别
- 拒绝后不能直接从 p 重新采样，必须从 `max(0, p - q)` 归一化后的残差分布采样，否则分布会偏
- 认为它减少了大模型的计算量：总计算量没减少甚至更多，省的是**串行步数**
