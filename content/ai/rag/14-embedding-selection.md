# Embedding 模型怎么选？什么时候需要微调？

::: tip 一句话回答
选型看几个硬条件：**语言**（中文、多语言）、**最大输入长度**、**向量维度**（影响存储和检索成本）、**部署方式**（API 还是自部署）。公开榜单只能用来缩小范围，最后要用**自己业务的评测集**比较 Recall@k。通用模型在专业领域召回明显不够、而且已经调过切分和混合检索时，再考虑用**领域内的查询-文档对**加**难负例**做微调。换模型意味着全部向量要重算。
:::

## 详细解析

### 选型维度

| 维度 | 要看什么 |
| --- | --- |
| 语言 | 中文为主选中文效果好的模型；中英混合或跨语言检索选多语言模型 |
| 最大长度 | 超过上限的文本会被截断，后半段内容不进向量；块大小要在上限内 |
| 维度 | 维度越高存储和计算越多。部分模型支持截断到较低维度使用，可以用效果换成本 |
| 领域 | 法律、医疗、代码这类领域，通用模型可能分不清专业术语 |
| 非对称检索 | 有的模型要求查询和文档加不同的前缀或指令，不按要求用效果会下降 |
| 部署和成本 | API 方便但数据要出域；自部署要考虑 GPU 和吞吐 |

Embedding 的基础原理见 [Embedding 是什么](/ai/llm/07-embedding)。

### 为什么不能只看榜单

公开榜单的任务和数据与你的业务差别很大，排名靠前不代表在你的文档上最好。而且榜单的数据集可能被模型训练时见过。可靠的做法是：

1. 从真实查询里抽一批问题，标注每个问题对应的正确文档块（见 [RAG 系统怎么评估](/ai/rag/08-rag-eval)）
2. 候选模型各自把文档库向量化，跑同一批问题
3. 比较 Recall@k、MRR，按问题类型分组看差异
4. 同时记录向量化速度、检索延迟和存储成本

这个评测集后面做微调、换模型都能复用。

### 什么时候考虑微调

微调之前先排查其他环节，它们成本更低：

- 解析和切分有没有问题
- 加上 BM25 的 [混合检索](/ai/rag/05-hybrid-search) 和 [重排序](/ai/rag/06-rerank) 有没有用上
- [查询改写](/ai/rag/07-query-rewrite) 能不能弥补用户说法和文档说法的差异

这些做完，召回还是不够，而且失败案例集中在领域术语、内部说法上，微调才值得。

### 微调怎么做

- **数据**：查询和相关文档块组成的正样本对。来源可以是用户点击日志、人工标注，或者用大模型根据文档块生成问题
- **难负例**：和查询看起来相关、但其实不是答案的块，通常用当前模型检索出的高排名错误结果。只用随机负例，模型学不到细粒度的区分
- **训练目标**：常用对比学习，让查询靠近正例、远离负例
- **验证**：在留出的评测集上和原模型对比，同时检查通用查询有没有变差

微调后的模型就是新模型，整个库要重新向量化（见 [增量更新索引](/ai/rag/12-incremental-index)）。

## 面试官可能追问

::: details 维度越高效果越好吗？
不一定。效果主要取决于模型本身的训练，维度高只是表达空间大。维度高带来的是存储、内存和检索计算的线性增长。同一个模型如果支持多种维度，可以在评测集上对比，找效果和成本的平衡点。
:::

::: details 微调 Embedding 和微调重排模型，先做哪个？
重排模型直接看查询和文档的组合，对领域差异更敏感，微调后提升往往更直接，而且不用重建索引。如果问题是相关文档根本没进候选集，那就是召回的问题，要从 Embedding 下手。先用评测集判断是"没召回"还是"排序错"。
:::

::: details 用大模型生成训练问题，有什么风险？
生成的问题往往措辞规范、和原文用词很接近，跟真实用户的口语化提问不一样，训练出来的模型可能在真实查询上提升有限。可以让模型模仿真实查询的风格，并混入一部分真实日志数据；生成的数据也要抽检质量。
:::

## 易错点

- 只看公开榜单排名选模型，不在自己的数据上评测
- 文档块超过模型的最大长度，被截断却不知道
- 忽略模型要求的查询前缀或指令，效果打折
- 微调后只给新文档用新模型，新旧向量混在一起
