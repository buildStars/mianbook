# RAG 怎么做多租户隔离和权限过滤？

::: tip 一句话回答
原则是**检索阶段就过滤**，用户无权看的内容不能进入上下文，不能指望模型"不说"。多租户按隔离强度可以选**独立库、独立 collection 或共享 collection 加租户字段**；文档级权限把 ACL（允许访问的用户、部门、角色）写进块的元数据，查询时按当前用户身份带上过滤条件。权限变更要能及时同步到索引，缓存的 key 也要带上租户和权限。
:::

## 详细解析

### 为什么必须在检索时过滤

如果先检索、再让模型判断"这段用户能不能看"，内容已经进了 Prompt，模型可能直接复述，也可能被提示注入诱导说出来。权限是确定性的规则，要由代码执行，不交给模型（见 [敏感信息泄露](/engineering/security/04-data-leakage)）。

### 多租户的三种隔离方式

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 独立实例或库 | 每个租户一套向量库 | 隔离最强，可按租户单独备份、删除 | 成本高，租户多时运维困难 |
| 独立 collection | 同一个库，每个租户一个 collection | 隔离较好，查询时只需选对 collection | collection 数量有上限，小租户很多时浪费 |
| 共享 collection 加 tenant_id | 所有数据在一起，每个块带租户字段 | 资源利用率高，租户多也好管理 | 完全依赖过滤条件，一旦漏写就跨租户泄露 |

大客户或合规要求高的租户用独立库，大量小租户用共享加字段，混合使用也很常见。部分向量库提供原生的多租户或分区功能，可以优先使用。

### 文档级权限

企业知识库里，同一租户内不同人能看的文档也不同。做法：

1. 入库时从源系统（网盘、Wiki、文档系统）同步 ACL，写进块的元数据，比如 `allowed_groups: ["hr", "finance"]`
2. 查询时根据登录用户解析出他所属的用户组，构造过滤条件 `tenant_id = X AND allowed_groups 包含任一用户组`
3. 过滤条件由服务端根据身份生成，不能接受前端或模型传来的参数

用户组比逐个用户更好维护：人员变动时改组成员即可，不用改每个块的元数据。

### 前过滤和后过滤

向量检索加过滤有两种执行方式：

- **后过滤**：先取 top-k，再去掉无权限的。过滤比例高时，可能 k 条全被过滤，结果为空或很少
- **前过滤**：在检索过程中只考虑满足条件的向量，结果数量有保证，但对 ANN 索引的实现要求更高

权限过滤要的是"返回足够多的有权限结果"，优先用数据库支持的前过滤（或类似的过滤检索）。用后过滤时要放大 k，并检查返回数量。

### 容易漏掉的泄露点

- **权限变更延迟**：文档在源系统里收回了权限，索引里还是旧 ACL。要监听源系统的权限变更事件，或定期同步，并按敏感程度定同步频率
- **缓存**：语义缓存或结果缓存的 key 没带租户和权限，A 的答案被返回给 B（见 [语义缓存](/engineering/deploy/10-semantic-cache)）
- **摘要和派生数据**：GraphRAG 的社区摘要、预生成的 FAQ 混合了多篇文档的内容，权限要取所有来源的交集
- **日志和 trace**：记录的检索片段同样敏感，查看日志也要有权限控制

## 面试官可能追问

::: details 怎么验证权限过滤没有漏洞？
写专门的测试：构造不同权限的测试用户，用只有高权限文档才能回答的问题去查，断言低权限用户的检索结果里不出现这些文档。把这类用例放进回归测试，每次改检索代码都跑。线上可以对检索结果再做一次权限校验作为兜底，发现不一致就告警。
:::

::: details 用户删除账号或租户退出，数据怎么删干净？
共享 collection 按 `tenant_id` 批量删除向量、关键词索引、缓存和原文；独立库直接删库。还要覆盖备份、日志和评测集里的副本。隔离方式设计时就要考虑删除的成本，这也是合规要求高的租户倾向独立库的原因。
:::

::: details 权限很细，比如按段落控制，怎么处理？
切分时让一个块只属于一个权限范围，不要把不同权限的段落切进同一个块。ACL 跟着块走，过滤逻辑不变，只是元数据更细。
:::

## 易错点

- 先检索再让模型判断权限，内容已经进了上下文
- 过滤条件从请求参数里取，用户改一下参数就能看别的租户的数据
- 用后过滤但 k 没放大，有权限的结果被挤掉，看起来像"检索不到"
- 只同步了文档内容，没同步权限变更
