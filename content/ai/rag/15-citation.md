# RAG 的回答怎么做引用和溯源？

::: tip 一句话回答
常见做法是把检索到的块**编号**后放进 Prompt，要求模型在每个论断后标注来源编号，比如 `[2]`；后端把编号映射回**文档、页码和原文位置**，前端展示成可点击的引用，点开能看到原文并高亮。模型标的引用不一定可靠，要做**引用校验**：编号是否存在、引用的内容是否真的支持这句话。找不到依据时，宁可说"资料中没有提到"。
:::

## 详细解析

### 为什么要做引用

- **可验证**：用户能自己核对，不用完全相信模型
- **可排查**：答错时能看出是检索错了还是生成错了
- **约束模型**：要求每句话都有出处，模型凭空编造的空间变小

在企业知识库、法律、医疗这类场景，引用往往是硬需求（见 [企业知识库问答系统设计](/engineering/system-design/01-knowledge-base-qa)）。

### 基本做法：编号加标注

把检索结果整理成带编号的上下文：

```text
[1] 来源：员工手册.pdf 第 12 页
年假天数按工龄计算，满 1 年不满 10 年的为 5 天……

[2] 来源：休假制度补充说明.docx
……

要求：只根据上面的资料回答。每个论断后用 [编号] 标出依据；资料里没有的内容，直接说明没有找到。
```

编号用短的序号，不要让模型抄写长的文档 ID，抄错的概率更高。后端保存"序号到块"的映射，解析回答里的 `[n]`，替换成引用链接。

流式输出时，`[2]` 可能被拆在两个片段里，前端要等标记完整后再渲染成链接（见 [流式 Markdown 渲染](/engineering/streaming/05-markdown-streaming)）。

### 引用校验

模型标注的引用会出错：编号不存在、引用的块和这句话无关、一句话综合了多处却只标了一处。校验分几层：

1. **格式校验**：编号是否在本次上下文范围内，不在的直接去掉
2. **支持度校验**：把"句子 + 引用的块"交给 NLI 模型或 LLM 判断，块是否支持这句话。不支持的句子标为"无依据"，或者提示用户
3. **离线评测**：抽样统计引用准确率和引用覆盖率（有多少论断带了引用），作为评测指标之一（见 [RAG 系统怎么评估](/ai/rag/08-rag-eval)）

支持度校验会增加延迟和成本，可以只对高风险场景做，或者异步做、只用于监控。

### 定位到原文

只给出文件名不够，用户还要在几十页里找。入库时保留页码、段落位置，甚至字符偏移（见 [文档解析和入库](/ai/rag/11-multimodal-parsing)），前端就能：

- 跳到 PDF 对应页并高亮这个块
- 在引用卡片里直接显示原文片段
- 显示文档版本和更新时间，避免用户拿过期文档较真

更细的做法是让模型同时输出它依据的原文句子，再在块里做字符串匹配，定位到句子级。匹配不上说明模型改写或编造了，可以作为一个告警信号。

## 面试官可能追问

::: details 有些模型或平台提供原生的引用功能，和自己让模型标注有什么区别？
原生功能通常由平台在接口层面支持，返回结构化的引用位置，比让模型在文本里写 `[n]` 更规整、更容易解析。是否支持、返回什么结构各家不同。自己标注的方式通用、可控，换模型也能用；两种方式都需要校验。
:::

::: details 多个来源说法冲突时怎么处理？
在 Prompt 里要求模型遇到冲突时都列出来，并分别标注来源，不要自己挑一个。检索时可以把文档的版本、发布日期放进上下文，让模型优先采用较新的，并告诉用户依据的是哪一份。
:::

::: details 引用了就一定没有幻觉吗？
不是。模型可能给一句编造的话配上一个看起来相关的编号，或者把原文的意思改了。引用只是提供了核对的入口，是否真的支持要靠校验。
:::

## 易错点

- 只要求模型标注引用，不校验，错误的引用比没有引用更误导人
- 让模型抄写长 ID 或 URL，容易抄错甚至编造出不存在的链接
- 入库时没保留页码和位置，引用只能精确到文件
- 流式渲染时把半截的引用标记当普通文本显示
