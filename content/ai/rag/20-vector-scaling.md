# 向量数据量上亿时怎么扩展？分片、副本和索引构建怎么做？

::: tip 一句话回答
单机放不下就**分片**：按 ID 哈希分片数据均匀，但每次查询要**扇出到所有分片**，各取 top k 再合并；按租户分片能让查询只打一个分片，但要处理大租户和热点。**副本**解决读吞吐和可用性，不解决容量。上亿规模时索引构建本身就是难点：HNSW 构建慢、吃内存，频繁删改会让图质量下降，要靠分段写入、后台合并和定期重建；内存还不够就用 **DiskANN** 这类磁盘索引，内存只放压缩向量，原始向量和图放 SSD。
:::

## 详细解析

### 先确认瓶颈在哪

扩展前先分清三件事，它们的解法不同：

| 瓶颈 | 表现 | 主要手段 |
| --- | --- | --- |
| 容量 | 单机内存放不下向量和索引 | 分片、量化压缩、磁盘索引 |
| 查询吞吐 | QPS 上去后延迟升高 | 副本、缓存、降低每次搜索的候选数 |
| 写入和构建 | 导入慢、索引跟不上数据变化 | 分段构建、批量导入、后台合并 |

很多时候先做量化就能把容量问题推后一个数量级（见 [向量压缩](/ai/rag/19-vector-compression)），再考虑分片。

### 分片：按 ID 哈希还是按租户

**按 ID 哈希**：数据均匀分到 N 个分片。ANN 搜索不能只看一个分片，因为最近的向量可能在任何一个分片上，所以查询要发给所有分片：

```text
               查询 q，top k
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
     分片 1       分片 2       分片 3     各自搜出 top k（可多取一些）
       └────────────┼────────────┘
                    ▼
        合并：按相似度排序，取全局 top k
```

扇出的代价是：延迟取决于最慢的分片，分片越多尾延迟越高；每个分片都要做一次完整的图搜索，总计算量随分片数增加。所以分片数不是越多越好，够放下数据、留出余量即可。合并时要注意各分片的分数必须可比（同一模型、同一距离度量），否则不能直接排序。

**按租户分片**：多租户 SaaS 里，查询通常只在一个租户的数据里搜。把同一租户放在同一分片，查询不用扇出，也天然隔离了数据（权限过滤见 [权限过滤](/ai/rag/13-permission-filter)）。问题是租户大小差别很大：大租户要单独再拆分，小租户可以合在一个分片里，用租户 ID 做过滤。

### 副本：吞吐和可用性

每个分片放多个副本，查询可以打到任意副本，读吞吐近似随副本数线性增长；某个节点挂了，其他副本继续服务。代价是内存和写入成本成倍增加：每次写入要同步到所有副本，副本之间短时间不一致，刚写入的数据可能查不到。副本不增加容量，容量不够还得靠分片。

### 索引构建：上亿规模的真正难点

HNSW 插入一个点要先在图上搜索它的近邻再连边，构建时间随数据量和参数（每个点的邻居数、构建时的搜索宽度）上升，整个过程要把向量和图都放在内存里。上亿条数据的全量构建可能要几个小时，需要专门的大内存机器。

增删改对图索引也不友好：

- 删除一般只打标记，被删的点还留在图里占内存、参与遍历，删除比例高了召回和速度都会变差
- 更新等于删除加插入
- 大量增量插入后图的结构不如一次性构建的好

常见做法是像 LSM 一样**分段**：新数据写进小的可变段，小段先用暴力检索或小索引；段攒够大小后后台构建成不可变段，再定期把小段和带大量删除标记的段合并、重建。查询时同时搜所有段再合并。增量更新的流程见 [增量索引](/ai/rag/12-incremental-index)。

### 磁盘索引：内存放不下时

DiskANN 的思路是把图和原始向量放到 SSD 上，内存里只放 PQ 压缩后的向量。搜索时用内存里的压缩向量估算距离、决定往哪走，需要时从 SSD 读取节点的邻居和原始向量，最后用原始向量精排。它的图专门设计成搜索步数少，以减少随机读盘次数。代价是延迟比全内存索引高，对 SSD 的随机读性能有要求。

## 面试官可能追问

::: details 每个分片取 top k 再合并，结果和单机一样吗？
不完全一样。每个分片的 ANN 搜索本身是近似的，合并后的结果也是近似的。分片上取的数量正好等于 k 时，全局 top k 一定在各分片的 top k 之内（前提是各分片搜索是精确的）；但 ANN 会漏召回，所以常让每个分片多取一些候选再合并，用一点开销换召回。
:::

::: details 带过滤条件的查询在分片架构下有什么问题？
过滤条件很严格时，每个分片符合条件的数据都很少，HNSW 图上的遍历容易走不到它们，召回下降。如果过滤字段是租户这类高选择性的字段，最好直接按它分片或分区；其他情况要看数据库是否支持在遍历时过滤，以及过滤后数据量很少时是否会切换为暴力检索。
:::

::: details 换嵌入模型时，上亿数据怎么重建？
新模型的向量和旧的不能混用，只能新建一套索引。后台批量重新向量化并构建，期间新写入双写，评测通过后切换查询，旧索引留着回滚（见 [向量数据库选型](/ai/rag/03-vector-db)）。这时要按两套索引的内存和计算量规划资源。
:::

## 易错点

- 以为加副本能解决容量问题；副本只提升吞吐和可用性
- 分片数开得过多，扇出带来的尾延迟和总计算量反而拖慢查询
- 删除只打标记却从不合并重建，时间长了内存涨、召回降
- 合并多个分片或多个索引的结果时，混用了不同模型或不同距离度量的分数
