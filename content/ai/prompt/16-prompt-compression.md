# 提示词太长怎么压缩？会不会影响效果？

::: tip 一句话回答
先做无损的：**去掉冗余、精简改写**，删掉重复的规则和客套话；**示例少而精**，挑覆盖不同情况的几条；对话历史做**摘要**。不变的长前缀走**提示词缓存**，不用压缩也能省钱省时间。基于小模型删词的自动压缩（LLMLingua 一类）压缩率高，但可能删掉关键信息。任何压缩都会影响效果，**必须用评测集对比压缩前后**再上线。
:::

## 详细解析

### 先弄清楚长在哪里

压缩前先拆一下提示词的组成，按占比排序：

```text
系统提示（角色、规则、格式要求）   通常不变
少样本示例                         通常不变
检索到的文档 / 工具结果             每次不同，经常最长
对话历史                           随轮数增长
用户当前输入                        每次不同
```

不同部分的压缩方法不一样。不变的部分优先考虑缓存；变化的部分才需要真正压缩。

### 精简改写

系统提示经常越改越长，常见的冗余：

- 同一条规则在不同地方用不同说法写了好几遍
- 历史上为修某个问题加的补丁，问题早就不存在了
- 客套话和空话，比如"你是一个非常优秀、专业、认真负责的助手"
- 用一大段话描述格式，其实一个示例就能说清

做法：逐条问"删掉这句，输出会变吗"。拿不准的就保留，用评测验证后再删。也可以让模型帮你精简，见 [用模型优化提示词](/ai/prompt/15-meta-prompting)，但结果一样要过评测。

### 示例的数量和挑选

示例往往是最占地方的静态部分：

- 示例数量和效果不是线性关系，加到一定程度后收益很小
- 挑选覆盖不同类型、不同边界情况的示例，而不是好几条相似的
- 示例本身也可以缩短，只保留体现规律的部分
- 示例很多时，可以按当前输入动态检索最相似的几条，而不是全部放进去

示例的作用和写法见 [Few-shot 和思维链](/ai/prompt/02-few-shot-cot)。

### 静态部分走缓存

系统提示和示例每次都一样，可以放在提示词最前面，利用服务商的提示词缓存。缓存命中的部分计费更低、首字延迟更短。它不减少上下文长度，但解决了长提示词最主要的成本问题。细节见 [提示词缓存](/engineering/deploy/04-prompt-caching)。

要注意：压缩改写和缓存有冲突。如果每次都对静态部分做动态压缩，前缀就变了，缓存会失效。

### 动态部分的压缩

- **对话历史**：早期轮次做摘要，只保留最近几轮原文，见 [多轮对话的上下文管理](/ai/prompt/06-conversation-memory)
- **检索结果**：减少召回的块数，加重排只保留最相关的；块内只截取相关段落
- **工具结果**：只保留需要的字段，见 [工具结果太长](/ai/tools/12-long-tool-results)

### 自动压缩方法

LLMLingua 一类的方法用一个小语言模型给每个词打分，信息量低的词（模型很容易预测出来的词）删掉，保留信息量高的。它还会给指令、示例和问题分配不同的压缩比例，先整段筛掉不重要的示例，再逐词删减。后来的 LLMLingua-2 改成训练一个小的分类模型，逐词判断保留还是删除，速度更快。压缩后的文本人读起来不通顺，但大模型往往还能理解。

| 方面 | 说明 |
| --- | --- |
| 优点 | 压缩率高，不需要人工改写，适合长文档、检索结果 |
| 风险 | 可能删掉否定词、数字、专有名词这类关键信息；对格式要求、代码不适用 |
| 成本 | 多一次小模型推理，增加延迟 |
| 冲突 | 压缩结果每次不同，无法利用前缀缓存 |

适合压缩检索文档这类"信息密度低、容错较高"的内容，不适合压缩系统规则和输出格式要求。

### 用评测验证

压缩一定要有评测集兜底，见 [提示词版本管理](/ai/prompt/13-prompt-versioning)：

1. 准备覆盖主要场景和边界情况的评测集
2. 同时跑压缩前后两个版本，对比任务指标，不只看 token 数
3. 重点看失败样本：哪些情况压缩后变差了，对应删掉了什么

## 面试官可能追问

::: details 上下文窗口足够大，为什么还要压缩？
窗口大不等于效果好。内容越多，成本和延迟越高，关键信息被淹没的可能也越大，模型对中间位置内容的利用往往不如开头和结尾。压缩的目标是让模型看到的内容更精准，而不只是装得下。
:::

::: details 压缩后效果反而变好了，可能是什么原因？
原来的提示词有互相矛盾的规则，或者有很多无关内容在干扰模型。精简后指令更清楚，模型更容易抓住重点。这也说明提示词不是越长越好。
:::

::: details 怎么决定先压缩哪部分？
按"占比 × 可压缩空间 ÷ 风险"排序。检索结果和对话历史通常占比最大、容错较高，先处理；系统规则占比小、风险高，最后处理。静态部分先上缓存，再考虑压缩。
:::

## 易错点

- 只看 token 数降了多少，不跑评测就上线
- 对静态前缀做动态压缩，导致提示词缓存失效，反而更贵
- 用自动压缩处理系统规则和格式要求，删掉否定词、数字后行为改变
