# 让模型自我反思、自我修正真的有用吗？

::: tip 一句话回答
要看**反馈从哪里来**。有**外部信号**时很有用：代码跑测试、调用工具查结果、用校验规则检查格式，把具体的错误信息交给模型修改，通常能明显提升成功率。只让模型"检查一下自己的回答"、**没有任何新信息**时，效果有限，在推理题上甚至可能把对的改成错的。所以落地时的重点是**提供可靠的反馈**，并设置**轮数上限**控制成本。
:::

## 详细解析

### 常见的几种做法

| 做法 | 流程 | 反馈来源 |
| --- | --- | --- |
| Self-Refine | 生成 → 让模型写出改进意见 → 按意见修改，重复几轮 | 模型自己 |
| Reflexion | 尝试任务 → 根据失败结果写一段文字总结（"上次错在哪"）→ 把总结放进下一次尝试的上下文 | 环境给出的成败信号，加上模型自己的总结 |
| 生成者 + 评审者 | 一个提示词负责生成，另一个提示词（或另一个模型）按标准评审 | 另一个视角 |
| 工具验证 | 生成后运行测试、执行查询、做格式校验，把结果反馈给模型 | 外部环境 |

和 [Self-Consistency](/ai/prompt/02-few-shot-cot) 的区别：Self-Consistency 是独立采样多次再投票，不修改答案；反思类方法是在同一个答案上迭代修改。

### 为什么纯自我修正效果有限

模型第一次答错，往往是因为缺少知识或推理走偏。再问一次"检查一下"，它用的还是同样的知识和能力，很难发现自己的盲点。研究中观察到的现象：

- 没有外部反馈时，在数学、推理类任务上让模型自我修正，准确率常常没有提升，有时下降
- 模型会被"请检查错误"这类措辞暗示，以为一定有错，把正确答案改错
- 早期一些"自我修正有效"的结果，用了标准答案来决定什么时候停止，这在实际场景里是拿不到的

在写作润色、风格调整这类开放任务上，自我改进更有效，因为好坏标准模糊，按照明确的要求逐条检查确实能改进。

### 什么时候值得用

最有效的情况是**能自动判断对错**：

- **代码生成**：跑单元测试、类型检查、lint，把报错交给模型修
- **SQL 和数据查询**：执行一下，看有没有报错、结果是否合理
- **结构化输出**：用 Schema 校验，把具体的校验错误反馈回去
- **事实性回答**：用检索结果核对引用，见 [怎么让模型在不知道的时候说"不知道"](/ai/prompt/11-say-i-dont-know)

## 代码示例

带外部反馈的修正循环（`llm.chat` 是通用伪接口，`runTests` 由业务实现）：

```ts
// 反馈来自测试结果，而不是模型自评
async function generateWithTests(task: string, maxRounds = 3) {
  const messages = [{ role: 'user', content: task }]
  for (let round = 1; round <= maxRounds; round++) {
    const code = await llm.chat({ messages })
    const result = await runTests(code)
    if (result.passed) return { code, rounds: round }
    messages.push(
      { role: 'assistant', content: code },
      { role: 'user', content: `测试失败：\n${result.log}\n请分析原因后给出修正后的完整代码。` },
    )
  }
  return { code: null, rounds: maxRounds } // 超过轮数就停，交给人处理
}
```

编程 Agent 的核心循环就是这个模式的扩展，见 [编程 Agent 是怎么工作的](/ai/agent/08-coding-agent)。

## 面试官可能追问

::: details 用另一个模型来评审，比让模型自评好吗？
通常好一些：评审提示词可以只关注检查标准，换一个模型还能减少同样的盲点。但评审模型也会出错，有时偏好更长、更自信的回答。评审标准要具体可检查，并且定期用人工标注校准评审结果。
:::

::: details 反思循环什么时候停？
设硬性的轮数上限；外部检查通过就停；连续两轮输出没有实质变化或者同一个错误反复出现也停。停下后要么返回最好的一版，要么明确告诉调用方失败，交给人处理。
:::

::: details 推理模型还需要外部的反思循环吗？
推理模型在思考过程中已经会自我检查，对纯推理任务再套一层"请反思"的收益很小。但外部反馈仍然有价值：它没法在思考中运行你的测试或查你的数据库，所以"生成 → 执行 → 反馈"的循环依然适用，见 [思维链和推理模型是什么](/ai/llm/10-reasoning-models)。
:::

## 易错点

- 没有任何外部信息，只让模型"再检查一遍"，就期望准确率提升
- 反馈太笼统，比如"有错误请修改"，不给具体的报错信息
- 不设轮数上限，成本和延迟成倍增加
- 用标准答案来判断何时停止，评测结果在真实场景里无法复现
