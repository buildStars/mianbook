# 怎么用大模型做意图识别和文本分类？

::: tip 一句话回答
把分类写成一个约束严格的任务：**每个标签给出定义、边界和例子**，加几条容易混淆的**少样本示例**；输出**限定为枚举值**，留一个"其他"类兜底，需要时让模型给出置信度或理由。上线前用标注好的评测集算准确率并做**混淆分析**。大模型适合标签常变、样本少的场景；流量大、标签稳定时，可以用 Embedding 分类或训练小模型降成本。
:::

## 详细解析

### 标签设计是第一步

分类效果不好，很多时候是标签本身有问题：

- **标签之间有重叠**：比如"退款"和"售后"，用户问"商品坏了能退吗"该归哪个
- **标签只有名字**：模型只能按字面猜
- **没有兜底类**：闲聊、无关问题被硬塞进某个业务类

每个标签写清楚三件事：

```text
refund 退款
  定义：用户想把已支付的钱退回来
  包括：申请退款、查询退款进度、退款被拒
  不包括：只换货不退钱（归 exchange）；还没付款就取消（归 cancel_order）
```

"不包括"这一栏对区分相近标签最有用。

### 提示词和少样本示例

- 系统提示里列出全部标签和定义，用标签或分隔符和用户输入隔开，见 [XML 标签和分隔符](/ai/prompt/12-xml-delimiters)
- 示例优先放**容易混淆的边界样本**，而不是每类一条最典型的
- 多轮对话里识别意图，要带上必要的上文，比如上一轮在聊哪个订单

### 输出约束

```json
{
  "intent": "refund",
  "confidence": "high",
  "reason": "用户提到已付款，想退钱"
}
```

- `intent` 用枚举约束，最好用结构化输出能力保证只出现合法值，见 [稳定输出 JSON](/ai/prompt/04-structured-output)
- 必须有 `other` 类，并在定义里说明"拿不准时归 other"
- 置信度：模型自己说的置信度并不精确，做成 high / low 两档就够用；也可以采样几次看结果是否一致
- `reason` 方便排查，但会增加输出 token；流量大时可以只在评测阶段开启

低置信度或 `other` 的请求，交给追问澄清、通用对话或人工处理，而不是硬路由到某个业务流程。

### 和传统方法怎么选

| 方法 | 适合 | 不适合 |
| --- | --- | --- |
| 大模型 + 提示词 | 标签常变、样本少、需要理解上下文 | 极高流量、对延迟很敏感 |
| Embedding + 相似度或简单分类器 | 标签稳定、每类有一定样本、要求快且便宜 | 需要推理或上下文的复杂意图 |
| 训练专门的小模型 | 流量大、标签稳定、有足够标注数据 | 标签经常调整 |

常见组合：先用 Embedding 或规则处理高频、明确的意图，拿不准的再交给大模型。也可以用大模型给线上数据打标，积累数据后训练小模型，大模型只处理难例。

### 评测和混淆分析

1. 从线上真实问题里抽样，人工标注，组成评测集，每类都要有样本，边界样本多放一些
2. 算整体准确率，以及每个类别的精确率和召回率
3. 画混淆矩阵，看哪两类最容易混。通常是标签定义有重叠，改定义比加示例更有效
4. 每次改标签、改提示词、换模型都重跑，见 [提示词版本管理](/ai/prompt/13-prompt-versioning)

客服场景里意图识别在整体架构中的位置，见 [智能客服系统设计](/engineering/system-design/04-customer-service)。

## 面试官可能追问

::: details 标签有上百个，全部放进提示词效果不好，怎么办？
做分层分类：先分大类，再在大类内分细类，每一步的标签都不多。也可以先用 Embedding 召回最相近的十几个候选标签，再让大模型在候选里选。
:::

::: details 一句话里有多个意图怎么办？
改成多标签输出，`intents` 是数组，按出现顺序排列，后续流程逐个处理。也可以只识别主意图，其他的在回复里追问。具体取决于业务流程能不能同时处理多件事。
:::

::: details 怎么降低分类的成本和延迟？
用小模型，输出只要标签不要理由，系统提示和示例放在前面利用提示词缓存。流量更大时，用大模型打标的数据训练一个专门的分类模型，或者换成 Embedding 方案。
:::

## 易错点

- 标签只给名字不给定义和边界，模型在相近标签之间随机选
- 不设 `other` 类，无关问题被强行归到业务类，触发错误流程
- 只看整体准确率：类别不均衡时，小类别可能几乎全错，整体数字却很好看
