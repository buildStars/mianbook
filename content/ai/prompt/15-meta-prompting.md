# 怎么让大模型帮你写和优化提示词？

::: tip 一句话回答
分两步用。**起草**：把任务目标、输入输出示例、约束和使用者告诉模型，让它写出结构完整的初版提示词，比从零写快，也不容易漏要求。**优化**：在评测集上跑当前提示词，把**失败样例和评分标准**交给模型，让它分析原因并提出修改，再跑评测验证，循环几轮。关键是要有**评测集兜底**，用**留出集**防止过拟合，并由人审核修改，避免提示词越改越长、规则互相冲突。
:::

## 详细解析

### 起草：给模型足够的信息

模型写提示词的质量取决于你给的信息。只说"帮我写一个客服提示词"，得到的是空泛的模板。应该提供：

- **任务和目标**：要完成什么、给谁用、成功的标准是什么
- **输入输出示例**：几条真实输入和期望输出，包括边界情况
- **约束**：输出格式、语气、不能做的事、遇到什么情况要转人工
- **运行环境**：用在哪类模型上、有没有工具、上下文里会放哪些资料

可以让模型先就不清楚的地方提问，再动笔写。拿到初稿后自己通读一遍，删掉不需要的部分，写法原则见 [怎样写好一个 Prompt](/ai/prompt/01-prompt-principles)。

### 优化：基于失败样例迭代

```text
         ┌──────────────────────────────────────────────┐
         ↓                                              │
当前提示词 ──→ 在评测集上运行 ──→ 打分，挑出失败样例       │
                                       │                │
                                       ↓                │
           把提示词 + 失败样例 + 评分标准交给模型         │
           让它先分析失败原因，再给出修改后的提示词       │
                                       │                │
                                       ↓                │
                    在评测集和留出集上验证 ── 更好 ───────┘
                                       │
                                     更差 → 丢弃这次修改
```

几个要点：

1. **先诊断再修改**：要求模型说明每个失败样例错在哪、属于哪类问题，再针对性地改，而不是笼统地"优化一下"
2. **一次改一类问题**：改动小，效果好坏容易归因
3. **保留评分标准**：模型知道评价方式，提出的修改更有针对性
4. **留出集**：一部分样例只用来验证、不给模型看，防止它针对看到的样例"打补丁"

### 自动化的提示词优化

把上面的循环交给程序跑，就是自动提示词优化。思路大致有几类：

- **生成候选再挑选**：让模型生成很多版本的指令，在评测集上打分，保留最好的
- **把历史分数给模型看**：把过去尝试过的提示词和对应分数一起给模型，让它提出分数可能更高的新版本
- **框架化**：像 DSPy 这类框架把提示词看成可以优化的参数，按指标自动挑选指令和 few-shot 示例

自动化省人力，但对评测集质量的依赖更强：指标设计得不好，优化出来的提示词只是在"刷分"。

### 常见的问题

- **越改越长**：每个失败样例都加一条规则，提示词变成一长串特例，规则之间互相冲突。定期让模型或人做一次"合并、精简"
- **过拟合**：评测集上分数提高，线上没有变化甚至变差
- **换模型就失效**：为一个模型优化的提示词，换模型后要重新评测
- **把评测样例原样写进提示词**：分数好看，但这是作弊，泛化能力没有提升

修改结果上线前，按 [提示词怎么做版本管理和上线](/ai/prompt/13-prompt-versioning) 的流程回归和灰度。

## 面试官可能追问

::: details 用来优化提示词的模型，和实际运行提示词的模型，需要是同一个吗？
不需要。优化通常用能力更强的模型，因为分析失败原因和改写要求较高的推理能力；运行时可以用更便宜的模型。但评测一定要在实际运行的模型上做。
:::

::: details 自动优化出来的提示词看起来很奇怪，能用吗？
如果在留出集和线上灰度中都表现更好，可以用，但要先人工确认没有夹带评测样例的答案、没有违反业务规则。可读性差的提示词后续难以维护，能改写得更清楚而效果不降时，优先用清楚的版本。
:::

::: details 什么情况下不值得花时间优化提示词？
任务需要的知识模型本来就没有，这时应该补资料（RAG）；需要稳定的特定风格或格式、而且样本充足时，可以考虑微调，见 [微调、RAG 和 Prompt 工程怎么选](/ai/llm/09-finetune-vs-rag)。提示词已经清楚、失败来自模型能力上限时，换更强的模型或拆分任务更有效。
:::

## 易错点

- 没有评测集，只凭几个例子判断模型改得好不好
- 每个 bad case 都加一条特殊规则，提示词越来越长，互相冲突
- 优化和验证用同一批样例，看不出是否过拟合
