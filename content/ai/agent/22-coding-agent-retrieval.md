# Coding Agent 怎么找到要改的代码？代码库的上下文怎么检索？

::: tip 一句话回答
主流做法是让模型像开发者一样**用工具逐步探索**：先用 glob 看目录结构、用 grep 搜关键字，再按行号范围读文件，**由粗到细**缩小范围。**向量检索**适合"不知道叫什么名字"的语义查询，但对标识符的精确匹配不如 grep，还要维护索引。**符号索引和语言服务**（跳转定义、查引用）解决"这个函数在哪定义、谁调用了它"；**仓库地图**用很少的 token 给出全局轮廓。大仓库里通常组合使用。
:::

## 详细解析

### 工具式搜索

模型手里有几个简单工具：

- **glob / 列目录**：按文件名模式找文件，先了解项目结构
- **grep**：按正则搜内容，返回文件名和行号
- **读文件**：可以指定行号范围，只读需要的部分

它的优点是**无需预处理、结果总是最新的、精确**。代码里的名字往往是可猜的：报错信息里的字符串、路由路径、组件名、配置项，一搜就能定位。缺点是需要多轮调用，模型要会选关键词；搜一个很常见的词会返回大量结果，要配合文件类型过滤和结果数量上限。

### 向量检索

把代码切块后算向量，查询时按语义相似度召回。

| 维度 | grep 类工具 | 向量检索 |
| --- | --- | --- |
| 精确标识符 | 准 | 可能召回相似但不对的代码 |
| 语义查询（"处理支付回调的地方"） | 要靠模型猜关键词 | 擅长 |
| 新鲜度 | 永远是当前文件 | 代码改了要更新索引 |
| 预处理 | 无 | 切块、计算向量、存储 |
| 结果可解释性 | 高，命中就是包含 | 低，不清楚为什么召回 |

代码在 Agent 运行中会被它自己修改，索引很容易过期，所以很多 Coding Agent 以工具式搜索为主，向量检索作为可选的补充。代码切块要按函数、类等语法单元来切，不要按固定字数切断，原理见 [RAG 的文档怎么切块](/ai/rag/02-chunking) 和 [混合检索](/ai/rag/05-hybrid-search)。

### 符号索引和语言服务

grep 能找到字符串，但分不清"定义"和"同名的另一个东西"。语言服务（例如通过 LSP 协议接入的语言服务器）理解代码语义：

- **跳转定义**：这个函数、类型实际定义在哪个文件
- **查引用**：改一个函数签名之前，先找出所有调用方
- **类型信息和诊断**：变量是什么类型、哪里有类型错误

改公共接口时，查引用比 grep 可靠得多，能避免"改了定义漏了调用方"。代价是要启动对应语言的服务，大仓库里首次索引较慢。

### 仓库地图

仓库地图（repo map）是把项目里的文件、主要的类、函数签名提取出来，压缩成一份概览放进上下文。模型不用读源码就知道"用户相关的逻辑在 `services/user` 下，有 `createUser`、`updateProfile` 这几个函数"。生成时一般借助语法解析器提取定义，再按引用关系挑出最重要的部分，控制在固定 token 预算内。项目说明文件（例如 AGENTS.md）也起类似作用，见 [Agent 的项目说明文件怎么写](/engineering/harness/06-agent-instructions)。

### 由粗到细

1. 读项目说明和目录结构，确定大致在哪个模块
2. 用 grep 或符号搜索找到候选文件和行号
3. 只读命中位置附近的几十行，确认是不是目标
4. 需要改接口时查引用，找齐所有受影响的地方
5. 读相关的测试，了解预期行为

每一步只把必要的内容放进上下文。大仓库里还可以把"找代码"交给子 Agent，它探索完只回报文件路径和结论，主 Agent 的上下文保持干净，见 [子 Agent 是什么](/engineering/harness/04-subagents)。整体工作循环见 [编程 Agent 是怎么工作的](/ai/agent/08-coding-agent)。

## 面试官可能追问

::: details 为什么不把整个仓库都塞进上下文？
大多数仓库远超上下文窗口；即使放得下，成本和延迟很高，而且无关代码太多时模型更容易分心、引用错误的位置。按需检索既省钱也更准，见 [长任务的上下文怎么管理](/ai/agent/12-long-task-context)。
:::

::: details 模型搜不到想要的代码怎么办？
换关键词：试试英文同义词、驼峰和下划线两种写法、相关的报错文本；放宽范围，从目录结构入手；从已知入口（路由表、`main` 函数）顺着调用链往下读。多次搜不到时应该如实说明，而不是凭想象写一个新实现。
:::

::: details monorepo 里怎么控制检索范围？
先根据任务确定相关的包，把搜索限定在这些目录；排除 `node_modules`、构建产物和生成代码（通常遵循 `.gitignore`）；包之间的依赖关系可以从各包的配置文件里读出来，作为扩大范围的依据。
:::

## 易错点

- 认为向量检索一定比 grep 高级，忽略了精确匹配和索引新鲜度的问题
- 一上来就读整个大文件，上下文很快被占满
- 改函数签名只 grep 了函数名，漏掉通过别名、重新导出调用的地方
- 搜索时不排除依赖目录和构建产物，结果被大量无关命中淹没
