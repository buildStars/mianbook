# Deep Research 类 Agent 怎么设计？

::: tip 一句话回答
Deep Research 是让 Agent 花几分钟到几十分钟，围绕一个问题做多轮搜索、阅读和整理，最后交付一份**带引用的报告**。典型流程是**澄清需求 → 制定研究计划 → 多路并行检索和阅读 → 发现缺口再补搜 → 综合成文 → 核对引用**。架构上常用**编排者加子 Agent**：编排者拆子问题，子 Agent 各自搜索并只返回精简的发现和来源，主上下文不会被网页原文撑爆。难点在**什么时候停**、**来源可不可信**、**引用是否真的支持结论**，以及控制成本。
:::

## 详细解析

### 需求澄清

和普通搜索问答相比，它的输入是开放的问题，比如"对比几种向量数据库在我们场景下的取舍"，输出是一份结构化报告。动手前先澄清：

- 范围和深度：要覆盖哪些方面，要概览还是深入
- 时间范围、地区、语言、优先的来源类型（论文、官方文档、新闻）
- 交付形式：报告的结构、篇幅、要不要表格

一次问清这几点，比跑完再返工省得多。只回答单个事实的问题不需要 Deep Research，普通的 [AI 搜索](/engineering/system-design/09-ai-search) 就够了。

### 整体架构

```text
用户问题 ──▶ 澄清 ──▶ 编排者：制定研究计划（子问题列表）
                         │ 并行派发
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       子 Agent 1     子 Agent 2     子 Agent 3   （各自：搜索 → 筛选 → 阅读 → 提炼）
          │              │              │
          └──── 发现 + 来源（精简） ─────┘
                         ▼
               编排者：汇总，找出缺口和矛盾 ──▶ 不够就追加子问题，再派一轮
                         ▼
               写作：按大纲成文，每个论断挂引用
                         ▼
               引用核对 ──▶ 报告
```

子 Agent 的意义在于**隔离上下文**：每个子 Agent 读几十个网页，但只把结论和来源返回给编排者，见 [多 Agent 系统有哪些协作模式](/ai/agent/05-multi-agent) 和 [长任务 Agent 的上下文管理](/ai/agent/12-long-task-context)。

### 核心模块

- **规划**：把问题拆成相互独立、可以并行的子问题；计划写进外部笔记，后续按进度更新，见 [Agent 的规划能力](/ai/agent/03-planning)
- **检索**：每个子问题生成多个查询，换不同说法和语言；先看搜索结果的标题和摘要做筛选，再抓取正文，避免把时间花在无关页面上
- **阅读和提炼**：从正文里抽取和子问题相关的事实，每条事实记下来源 URL 和原文片段，这是后面引用的依据
- **综合**：编排者合并各路发现，去重，标出不同来源之间的矛盾，判断还缺什么
- **写作**：先出大纲，再按章节写；每个论断必须能对应到提炼阶段记下的某条事实

### 关键难点

| 难点 | 做法 |
| --- | --- |
| 什么时候停 | 设最大轮数、最大子 Agent 数和预算；编排者每轮判断"关键问题是否都有至少两个独立来源支持"，满足就停 |
| 来源可信度 | 优先一手来源（官方文档、论文、原始数据）；标注来源类型和日期；同一结论多个来源交叉验证；内容农场和转载降权 |
| 引用不支持结论 | 写作只能引用提炼阶段的事实；成文后逐条核对"引用的原文片段是否真的支持这句话"，不支持的删掉或改写 |
| 网页里的注入 | 抓取的内容只当数据，子 Agent 不给写操作工具，见 [间接提示注入](/engineering/security/02-indirect-injection) |
| 成本 | 子 Agent 用便宜一些的模型，编排和写作用强模型；缓存已抓取的页面；按问题复杂度决定派几个子 Agent |

### 扩展与优化

- **过程可见**：向用户实时展示正在搜什么、读了哪些来源，长时间等待时用户才有耐心，也能中途纠偏
- **中途介入**：允许用户审阅研究计划后再开跑，见 [人在回路怎么设计](/ai/agent/11-human-in-the-loop)
- **断点恢复**：任务长，要按步保存状态，见 [Agent 的状态持久化和断点恢复](/ai/agent/14-durable-agent)
- **私有数据**：除了网页搜索，还可以接入企业知识库作为另一个检索来源，和 RAG 的检索链路共用
- **评测**：准备一批有参考答案的研究题，评估要点覆盖率、引用准确率、事实错误数，以及耗时和费用，见 [怎么评估一个 Agent 的表现](/engineering/eval/10-agent-eval)

## 面试官可能追问

::: details 为什么要用多 Agent，单个 Agent 循环搜不行吗？
单个 Agent 也能做，但所有网页内容都堆在一个上下文里，几十个来源之后就会超出窗口或者注意力分散，而且只能串行。子 Agent 能并行，各自的上下文互不干扰，编排者只看提炼后的结果。代价是 token 总量明显增加，子 Agent 之间也看不到彼此的发现，可能重复搜索，所以子问题要拆得尽量不重叠。
:::

::: details 不同来源说法矛盾怎么办？
不要让模型悄悄选一个。报告里如实写出分歧，注明各自的来源、时间和可信度，能判断的给出倾向和理由。常见原因是时间不同（旧数据和新数据）或口径不同，把这一点指出来本身就很有价值。
:::

::: details 怎么防止报告里出现编造的引用？
引用只能从系统记录的来源里选，模型不能自己写 URL；每条引用附带原文片段。成文后再用一轮检查，逐条核对片段是否支持对应的句子，不支持的标出来或删掉。最后在前端渲染引用时也只认系统记录的来源 ID。
:::

## 易错点

- 不澄清需求就开跑，跑了二十分钟才发现方向不对
- 子 Agent 把网页原文整个返回给编排者，主上下文很快爆掉
- 没有停止条件，只靠模型自己觉得"够了"，结果要么太浅要么停不下来
- 让模型在写作阶段自由引用，出现来源和结论对不上，甚至编造链接
