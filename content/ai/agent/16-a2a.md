# Agent 之间怎么通信？A2A 协议解决了什么问题？

::: tip 一句话回答
同一个系统里的多个 Agent 可以共享代码和内存直接调用，但**不同团队、不同厂商、不同框架**写的 Agent 要协作，就需要一套公共协议。**A2A（Agent2Agent）** 就是这样一套开放协议：每个 Agent 用 **Agent Card** 公开自己的能力和接入方式，双方围绕**任务（Task）** 交换**消息（Message）**，产出结果叫**产物（Artifact）**，长任务通过**流式更新或回调通知**汇报进度。它和 **MCP 是互补关系**：MCP 解决 Agent 怎么调用工具和数据，A2A 解决 Agent 怎么和另一个 Agent 合作。
:::

## 详细解析

### 为什么需要 Agent 间协议

[多 Agent 协作](/ai/agent/05-multi-agent)讲的多是同一个系统内部：编排者直接调用子 Agent 的函数，共享状态。跨系统时情况不同：

- 对方是黑盒：你不知道它用什么模型、什么框架，也不该知道它的内部提示词和工具
- 任务可能很长：订机票、审合同这类任务要几分钟甚至几天，中间还可能要用户补充信息
- 每家各写一套私有接口，接 N 个 Agent 就要写 N 套适配

A2A 把"发现对方、交代任务、跟踪进度、拿回结果"这几件事标准化，让 Agent 像 Web 服务一样可以互相对接。

### 核心概念

| 概念 | 作用 |
| --- | --- |
| Agent Card | 一份 JSON 描述：名称、能做哪些事（skills）、服务地址、支持的能力（如流式、推送通知）、需要的鉴权方式。放在约定的 well-known 路径下，供客户端发现 |
| Task | 一次协作的单位，有 id 和状态：已提交、处理中、需要输入、需要鉴权、已完成、失败、已取消、已拒绝 |
| Message | 一轮对话内容，由若干 Part 组成，Part 可以是文本、文件或结构化数据 |
| Artifact | 任务产出的结果，如生成的报告、文件，和过程中的对话消息分开 |

调用方叫客户端 Agent，被调用方叫远程 Agent。远程 Agent 对外是"不透明"的：只暴露能力和任务状态，不暴露内部推理和工具。

### 一次协作的流程

```text
客户端 Agent                                远程 Agent
    | -- 读取 Agent Card，确认能力和鉴权方式 -->  |
    | -- 发送消息（创建任务）-------------------> |
    | <- 任务状态：处理中 ---------------------- |
    | <- 任务状态：需要输入（缺出发日期）-------- |
    | -- 补充消息（同一个任务 id）--------------> |
    | <- 流式更新 / 推送通知：产物分块 ---------- |
    | <- 任务状态：已完成 + Artifact ----------- |
```

规范定义了三种协议绑定：JSON-RPC 2.0、gRPC 和 HTTP+JSON（REST 风格），远程 Agent 在 Agent Card 里声明支持哪些。短任务直接同步返回；长任务可以流式推送状态和产物（基于 HTTP 的绑定用 SSE），或者由远程 Agent 向客户端注册的 webhook 发 POST 推送通知。复用 Web 的现成基础设施，网关、负载均衡、监控都能照用。

### 和 MCP 的分工

| | MCP | A2A |
| --- | --- | --- |
| 连接的对象 | Agent 和工具、数据源 | Agent 和 Agent |
| 对方的性质 | 能力明确的函数或资源，输入输出结构化 | 有自主性的黑盒，可能多轮追问 |
| 交互形态 | 多为一次调用一次结果 | 有状态的任务，可能持续很久 |

一个典型系统两者都用：旅行助手通过 A2A 把"订酒店"交给酒店方的 Agent，酒店 Agent 内部再通过 [MCP](/ai/tools/02-mcp) 查库存、调支付。判断标准很简单：对方只是执行一个确定的操作，用工具；对方需要自己理解、规划、追问，用 Agent 协议。

### 安全和鉴权

- Agent Card 声明鉴权方案，实际凭证走 HTTP 层的标准方式（如 OAuth 2.0、API Key），不放在消息正文里
- 必须用 HTTPS，客户端要校验服务端身份；有的场景会对 Agent Card 签名防篡改
- 远程 Agent 返回的内容是**不可信输入**，可能带着[间接提示词注入](/engineering/security/02-indirect-injection)，不能直接当指令执行
- 按最小权限授权：给对方的令牌只覆盖这一个任务需要的范围，敏感操作在本方加人工确认

## 面试官可能追问

::: details 既然有 MCP，把远程 Agent 包装成一个 MCP 工具不行吗？
简单场景可以，很多系统就是这么做的。但工具调用默认是"一问一答"，不擅长表达"处理中、需要你补充信息、过两小时再通知你"这类长任务和多轮交互；而且工具语义暗示调用方掌握控制权。对方真有自主性、任务又长时，用专门的 Agent 协议更自然。
:::

::: details 客户端怎么知道该把任务交给哪个远程 Agent？
先拿到候选 Agent 的 Agent Card，可以来自固定配置、内部注册中心或目录服务。然后根据 Card 里的 skills 描述做匹配，常见做法是让编排模型读这些描述来选，和从多个工具里选一个类似。选错的代价更高，所以关键业务通常配置白名单。
:::

::: details 远程 Agent 处理很久，客户端断线了怎么办？
任务有 id，状态保存在远程 Agent 那边。客户端重连后可以按 id 查询任务状态，或重新订阅更新；如果事先注册了推送通知地址，远程 Agent 完成时会主动回调。客户端自己也要持久化任务 id，参考 [Agent 的断点恢复](/ai/agent/14-durable-agent)。
:::

## 易错点

- 把 A2A 和 MCP 当成竞争关系。两者解决的是不同层的问题，常常一起用
- 以为 A2A 会让双方共享上下文和内部状态。远程 Agent 是黑盒，只通过消息和产物交流
- 把远程 Agent 的返回当成可信内容直接执行。跨组织的数据一律按外部输入处理
- 协议细节在演进中，方法名、字段名以官方规范当前版本为准，面试时讲清概念和分工就够了
