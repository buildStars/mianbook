# 多 Agent 系统常见的失败方式有哪些？怎么排查和避免？

::: tip 一句话回答
多 Agent 的失败大多不是某个模型"不够聪明"，而是**协作出了问题**：任务描述不清导致**重复或遗漏**，交接时**信息丢失**、结论**互相矛盾**，Agent 之间**无限互相委派**，没有人**验证**结果，一个环节的错误被下游当成事实**层层放大**。排查靠**完整的执行轨迹**和清晰的**职责边界**，定位"错误第一次出现在哪"；避免靠**结构化的交接约定**、明确的**终止条件**和**独立的验证环节**。
:::

## 详细解析

### 一个公开的分类

有研究（论文 "Why Do Multi-Agent LLM Systems Fail?"）分析了多个开源多 Agent 框架的执行轨迹，整理出一套失败分类 MAST，分成三大类：**系统设计问题**（角色和任务定义、流程设计）、**Agent 之间的不一致**（沟通和协调）、**任务验证**（缺少验证或提前结束）。这个划分很适合作为排查的检查清单。下面按工程上常见的表现展开。

### 常见失败方式

| 失败 | 典型表现 | 根因 |
| --- | --- | --- |
| 任务描述不清 | 两个子 Agent 查了同一批资料；某个方面没人负责 | 拆分时没写清范围、边界和产出格式 |
| 违背角色 | 负责检索的 Agent 开始写结论，负责审查的 Agent 自己改起代码 | 角色定义模糊，或工具权限没按角色收紧 |
| 信息丢失 | 用户的关键约束在第二次交接后消失 | 交接只传了一段摘要，约束没被带下去 |
| 结论互相矛盾 | 两个子 Agent 对同一事实给出不同说法，汇总时被直接拼在一起 | 没有冲突检测，汇总方不核对 |
| 无限委派 | A 交给 B，B 觉得不归自己又交回 A；或者不断派生新的子 Agent | 没有委派深度和总步数限制 |
| 提前结束或不结束 | 没做完就宣布完成；或者完成了还在反复"优化" | 没有可检查的完成标准 |
| 缺少验证 | 子 Agent 说"测试通过了"，主 Agent 就照单全收 | 把自述当事实，没有独立检查 |
| 错误级联 | 第一步检索到错误数据，后面所有分析都建立在它上面 | 中间结果没有校验，错误一路传播 |

### 排查思路

1. **先拿到完整轨迹**：每个 Agent 收到的输入、调用的工具、输出、交给谁，都要能按时间线回放，见 [Agent 怎么调试](/engineering/harness/05-agent-debugging)
2. **找错误第一次出现的位置**：从最终错误往回追，看是哪个 Agent 的哪一步最早引入了错误信息。修那里，而不是修最后一个环节
3. **对照职责边界**：这一步本该由谁负责？他拿到的信息够不够？是信息没传到，还是传到了没用上？
4. **区分是个例还是模式**：同类任务批量跑，统计失败落在哪一类，见 [Agent 怎么评测](/engineering/eval/10-agent-eval)

### 怎么避免

- **结构化的交接**：委派时写清目标、范围、不做什么、产出格式、完成标准；回报用固定结构（结论、依据、未完成的部分、不确定的地方），不要只传一段自由文本
- **约束随任务传递**：用户的硬性要求放在每次委派都会带上的字段里，不依赖中间摘要
- **终止条件**：限制委派深度、总步数、总预算；每个子任务有超时；禁止把任务原样交回给委派方
- **独立验证**：关键结论由另一个 Agent 或确定性检查复核，例如跑测试、核对引用原文；验证者拿到的是原始材料，而不是被验证者的摘要
- **冲突显式处理**：汇总时检测说法不一致的地方，要么追查来源，要么标注出来交给用户
- **少用几个 Agent**：能用一个 Agent 加工具完成的，就不要拆。每多一个 Agent 就多一处交接，协作模式和代价见 [多 Agent 系统有哪些协作模式](/ai/agent/05-multi-agent)

## 代码示例

一个带深度限制、禁止回传和结构化回报校验的委派函数：

```js
const MAX_DEPTH = 2

function delegate(task, { from, to, depth = 0, chain = [] }) {
  if (depth > MAX_DEPTH) return { ok: false, error: `委派超过 ${MAX_DEPTH} 层，停止` }
  if (chain.includes(to)) return { ok: false, error: `${to} 已经在委派链上（${chain.join(' -> ')}），疑似循环` }
  if (!task.goal || !task.doneWhen) return { ok: false, error: '任务缺少目标或完成标准' }
  return { ok: true, chain: [...chain, from, to].filter((v, i, a) => a.indexOf(v) === i), depth: depth + 1 }
}

function checkReport(report) {
  const missing = ['conclusion', 'evidence', 'unfinished'].filter(k => !(k in report))
  return missing.length ? `回报缺少字段：${missing.join('、')}` : '回报格式正确'
}

const task = { goal: '调研 A 方案的限制', doneWhen: '列出 3 条以上带来源的限制', constraints: ['只看官方文档'] }
const step1 = delegate(task, { from: 'lead', to: 'researcher' })
console.log(step1) // { ok: true, chain: [ 'lead', 'researcher' ], depth: 1 }
console.log(delegate(task, { from: 'researcher', to: 'lead', ...step1 }).error)
// lead 已经在委派链上（lead -> researcher），疑似循环
console.log(delegate({ goal: '随便看看' }, { from: 'lead', to: 'writer' }).error)
// 任务缺少目标或完成标准
console.log(checkReport({ conclusion: '...', evidence: [] }))
// 回报缺少字段：unfinished
```

## 面试官可能追问

::: details 为什么让另一个 Agent 验证有时也不管用？
如果验证者和执行者用同样的模型、看同样的摘要，它们容易犯同样的错，验证只是走过场。有效的验证要有独立的信息来源（原始材料、测试结果），或者不同的检查方法；能用确定性检查的优先用确定性检查。
:::

::: details 怎么判断失败是模型能力问题还是系统设计问题？
看轨迹：如果某个 Agent 拿到了完整、清楚的输入却给出错误结果，偏向能力问题，可以换模型或改提示；如果它拿到的输入本身就缺信息、有歧义，或者职责就没分清，是设计问题。实践中后者占的比例往往不小，改模型解决不了。
:::

::: details 子 Agent 之间要不要直接通信？
默认不要，让它们只和编排者交互，信息流清楚，也好排查。确实需要协商的场景（比如多方辩论）要限定轮数，并由编排者做最终裁决。跨系统的 Agent 通信见 [A2A 协议](/ai/agent/16-a2a)。
:::

## 易错点

- 把失败归因到最后输出错的那个 Agent，没有往回追错误最早出现的位置
- 委派时只写一句话的任务，没有范围、产出格式和完成标准
- 把子 Agent 的"已完成""测试通过"当成事实，不做独立核对
- 遇到效果不好就继续加 Agent，交接点越多，信息丢失和矛盾越多
