# 长任务 Agent 的上下文越来越长，怎么管理？

::: tip 一句话回答
长任务里每一步的工具调用和结果都会追加到上下文，很快就会变慢、变贵、效果下降，最后超出窗口。常用四种手段：**清理旧的工具结果**，只留调用记录；接近上限时做**压缩**，把历史总结成一段摘要后重新开始；让 Agent 把计划、进度和发现写进**外部笔记或文件**，需要时再读回来；把会产生大量中间信息的子任务交给**子 Agent**，它在自己的上下文里工作，只把结论返回。核心是区分哪些信息以后还要用：任务目标、关键决定、未完成的事项必须保留，原始的工具输出大多可以丢。
:::

## 详细解析

### 上下文为什么会膨胀

- 工具结果占大头：一次读文件、一次搜索就是几千 token
- 每一轮都要把全部历史重新发给模型，成本随步数累加
- 内容越多，模型越难注意到早期的关键信息，容易忘掉目标或重复做过的事，见 [上下文窗口是什么？长上下文有哪些问题](/ai/llm/04-context-window)

单个工具结果太长的处理见 [工具返回的结果太长怎么处理](/ai/tools/12-long-tool-results)，这里说的是多步累积的问题。

### 四种手段

| 手段 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 清理工具结果 | 把较早的工具结果替换成一行占位，保留调用本身 | 简单、不丢决策过程，信息损失可控 | 之后要用的话得重新调用 |
| 压缩 | 快满时让模型把历史总结成摘要，用摘要加最近几轮替换全部历史 | 能大幅缩短 | 摘要会丢细节，压缩本身也要一次调用 |
| 外部笔记 | Agent 用工具读写待办、进度、发现，存到文件或数据库 | 信息不受压缩影响，可以跨会话 | 要模型主动记录，记录质量看提示词 |
| 子 Agent | 主 Agent 把子任务派出去，子 Agent 只返回精简结论 | 主上下文保持干净，可以并行 | 子 Agent 看不到全局，结果要拼合，见 [多 Agent 协作模式](/ai/agent/05-multi-agent) |

实际系统一般组合使用：平时清理工具结果，快满时压缩，关键信息始终写在外部笔记里。

### 压缩时保留什么

摘要的质量决定压缩后 Agent 还能不能接着干。提示词里要明确列出必须保留的内容：

- **任务目标和约束**：用户原始要求，以及中途补充的要求
- **已经做出的决定和原因**，避免压缩后又推翻
- **当前进度**：完成了什么、正在做什么、还剩什么
- **关键事实**：文件路径、ID、报错信息、接口地址这类以后还要精确使用的值
- **失败过的尝试**，避免重蹈覆辙

可以丢的是原始工具输出和中间的推理过程。用户的原话和系统提示不参与压缩，原样保留。

### 和缓存的配合

前缀缓存要求请求开头不变。清理和压缩都会改写历史，改写后的那一轮缓存会失效。所以不要每一轮都改，而是累积到一定量再批量处理，让大部分轮次还能命中缓存，见 [Prompt 缓存](/engineering/deploy/04-prompt-caching)。

## 代码示例

```ts
interface Msg {
  role: 'user' | 'assistant' | 'tool'
  content: string
  toolCallId?: string
}

// 清理旧工具结果：只保留最近 keep 条原文，其余替换成占位，调用和结果的配对不变
function clearOldToolResults(messages: Msg[], keep = 3): Msg[] {
  const toolIdx = messages.flatMap((m, i) => (m.role === 'tool' ? [i] : []))
  const toClear = new Set(toolIdx.slice(0, Math.max(0, toolIdx.length - keep)))
  return messages.map((m, i) =>
    toClear.has(i) ? { ...m, content: '[早期工具结果已清理，需要时请重新调用]' } : m,
  )
}

const history: Msg[] = [{ role: 'user', content: '修复登录 bug' }]
for (let i = 0; i < 5; i++) {
  history.push({ role: 'assistant', content: `调用 read_file #${i}` })
  history.push({ role: 'tool', content: 'x'.repeat(5000), toolCallId: `c${i}` })
}
const cleaned = clearOldToolResults(history)
console.log(cleaned.filter((m) => m.content.startsWith('[早期')).length) // 2
```

## 面试官可能追问

::: details 压缩应该在什么时候触发？
一般按 token 用量设阈值，比如用到窗口的一大半时触发，要给压缩调用本身和后续几轮留出空间。也可以在自然的阶段边界压缩，比如一个子任务完成后，这时摘要最好写。
:::

::: details 外部笔记和长期记忆是一回事吗？
不完全是。外部笔记服务于当前任务，记录计划和进度，任务结束就可以归档；长期记忆跨任务保存用户偏好和经验，需要检索、去重和过期机制。两者可以用同一套存储，见 [Agent 的记忆系统怎么设计](/ai/agent/04-memory)。
:::

::: details 压缩之后 Agent 的表现变差了，怎么排查？
对比压缩前后的轨迹，看它是忘了目标、重复了已做的事，还是丢了某个精确的值。针对性地改摘要提示词，把丢失的那类信息列为必须保留；精确值最好让 Agent 写进外部笔记，不依赖摘要。
:::

## 易错点

- 只靠更大的上下文窗口解决。窗口再大，成本和注意力分散的问题都还在
- 压缩时把用户的原始要求也概括掉了，几轮之后目标就走样了
- 清理工具结果时把调用和结果的配对拆散，接口直接报错
- 每一轮都改写历史，前缀缓存几乎从不命中
