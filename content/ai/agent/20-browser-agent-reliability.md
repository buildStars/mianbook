# 浏览器 Agent 为什么容易失败？怎么提高成功率？

::: tip 一句话回答
网页是**动态、不可控**的：页面没加载完、弹窗遮挡、元素定位错、内容异步变化、需要登录或人机验证，任何一步出错都会让后面全部偏离。提高成功率靠**每步动作后校验结果**、**等待页面稳定再观察**、**把长任务拆成可检查的小步**、**有限次数的重试**，以及遇到登录、验证码、不可逆操作时**交还给人**。
:::

## 详细解析

### 常见失败

| 失败 | 表现 | 根因 |
| --- | --- | --- |
| 页面没加载完 | 找不到元素，或点了还没绑定事件的按钮 | 观察得太早 |
| 弹窗遮挡 | 点击落在 cookie 横幅、广告或引导层上 | 没有识别遮挡层 |
| 定位错 | 点了同名的另一个按钮，或在错的输入框里输入 | 元素描述有歧义，编号过期 |
| 动态内容 | 下拉建议、虚拟列表、轮播，刚看到的东西马上变了 | 观察和执行之间页面变化 |
| 以为成功 | 执行器没报错，模型就认为提交成功了 | 没有校验动作结果 |
| 登录和验证码 | 卡在登录页，或者反复尝试 | 这不是 Agent 该自己解决的问题 |
| 迷路 | 跟着链接越走越远，忘了原任务 | 步数太多，上下文里缺少进度 |

单步成功率不低的情况下，步数一多，整体成功率也会掉得很快，因为每一步的失败都会累积。所以减少步数和及时发现偏离同样重要。

### 动作后校验

点击成功只说明事件发出去了，不代表达到了目的。每个关键动作都要定义"期望发生什么"：

- URL 变成了某个模式
- 某个元素出现或消失（"保存成功"提示、表单关闭）
- 输入框的值等于刚才输入的内容
- 列表里多了一条记录

能用代码检查的就用代码检查，比让模型看截图判断更可靠。校验失败时把"期望什么、实际看到什么"告诉模型，而不是只说"失败了"。

### 等待页面稳定

不要固定 `sleep` 几秒。更好的信号是：

- 目标元素出现且可见、可点击（没有被遮挡、没有 disabled）
- 网络请求在一小段时间内没有新的
- DOM 在一小段时间内不再变化
- 页面上的加载指示消失

这几种通常组合使用，并且都要设上限超时，超时后带着当前状态交给模型决策，而不是无限等。

### 任务拆分和重试

1. 先规划成几个有明确完成标准的子目标："搜到商品 → 进入详情 → 选好规格 → 加入购物车"
2. 每完成一个子目标就校验并记录进度，上下文里始终带着"做到哪一步了"
3. 单步失败先在原地重试：重新观察页面、关掉遮挡、换一种定位方式
4. 同一步重试几次仍失败，回退到上一个已知正确的状态（重新打开页面）再试
5. 设置总步数和总时长上限，超出就停下报告

重试只适合查询、导航这类无副作用的动作。提交订单、发消息这类动作重试前要先确认上一次到底有没有生效，否则会重复提交。

### 什么时候交还给人

- **登录**：让用户自己登录，Agent 复用会话；不要让模型接触密码
- **验证码等人机验证**：这是站点拒绝自动化的信号，暂停交给用户，或改用站点提供的正式接口，不尝试绕过
- **不可逆操作**：付款、提交、删除、发送，执行前请用户确认，见 [人在回路怎么设计](/ai/agent/11-human-in-the-loop)
- **反复失败**：多次重试仍然卡住，带着截图和已尝试的方法求助，比继续乱点好

另外要遵守站点的服务条款和访问频率要求。浏览器 Agent 的安全风险见 [Computer Use 是怎么工作的](/ai/tools/14-computer-use)。

## 代码示例

一个"动作 + 校验 + 有限重试"的封装，`page` 是假的执行器：

```js
async function waitFor(check, { timeout = 3000, interval = 100 } = {}) {
  const start = Date.now()
  while (Date.now() - start < timeout) {
    if (await check()) return true
    await new Promise(r => setTimeout(r, interval))
  }
  return false
}

async function actAndVerify(name, act, verify, retries = 2) {
  for (let i = 0; i <= retries; i++) {
    await act()
    if (await waitFor(verify, { timeout: 500 })) return { ok: true, attempts: i + 1 }
    console.log(`${name} 第 ${i + 1} 次未达到预期，重新观察后重试`)
  }
  return { ok: false, reason: `${name} 重试后仍未成功，交给用户处理` }
}

// 假页面：第一次点击被弹窗挡住，弹窗关掉后才生效
const page = { popup: true, cartCount: 0 }
async function clickAddToCart() {
  if (page.popup) { page.popup = false; return } // 点在了弹窗上
  setTimeout(() => { page.cartCount++ }, 200) // 异步更新购物车
}

actAndVerify('加入购物车', clickAddToCart, () => page.cartCount === 1).then(console.log)
// 加入购物车 第 1 次未达到预期，重新观察后重试
// { ok: true, attempts: 2 }
```

## 面试官可能追问

::: details 为什么不让模型自己判断成功与否就够了？
模型看截图判断会有误判，尤其是提示一闪而过、或者成功和失败的页面长得很像的时候。能用确定性条件检查的（URL、元素、值）用代码检查，模型只负责代码判断不了的语义校验。
:::

::: details 怎么衡量和持续提升成功率？
准备一组固定的任务和环境（最好是可重置的测试站点），每次改动后批量跑，统计成功率、平均步数和失败原因分布。按失败原因归类后逐个解决，比笼统地改提示词有效，见 [Agent 怎么评测](/engineering/eval/10-agent-eval)。
:::

::: details 弹窗怎么处理？
观察时把弹窗、遮罩层单独标出来，让模型知道"当前有一个覆盖层"；常见的 cookie 横幅可以优先选拒绝非必要项的选项关闭。动作前检查目标元素是否被遮挡，被挡住就先处理遮挡层。
:::

## 易错点

- 用固定 `sleep` 代替等待条件，网络慢时失败、网络快时浪费时间
- 执行器没报错就当成功，不做结果校验
- 对提交、付款这类有副作用的动作盲目重试，造成重复下单
- 遇到验证码时让 Agent 想办法绕过，正确做法是交还给人或改用正式接口
