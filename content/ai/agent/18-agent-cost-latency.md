# Agent 的成本和延迟怎么优化？

::: tip 一句话回答
Agent 的总成本约等于**步数 × 每步 token**，总延迟约等于**每步模型耗时 + 工具耗时**的累加，而且每一步都要把越来越长的历史重新发一遍。所以优化抓四点：**减少轮次**（并行工具调用、合并步骤、确定性流程交给代码）；**分层用模型**（简单步骤用小模型，难的规划才用大模型）；**控制上下文**（裁剪工具结果、保持前缀稳定以命中缓存）；**设预算和提前终止**（最大步数、token 预算、够用就停）。
:::

## 详细解析

### 先看钱和时间花在哪

单次调用的优化见[降低调用成本](/engineering/deploy/03-cost-reduction)，Agent 的特殊之处在于多步叠加：

- **输入 token 滚雪球**：第 n 步要带上前 n-1 步的全部消息和工具结果。假设每步新增 2000 token，跑 20 步，最后一步输入就有约 4 万，累计输入是这个数的十倍左右
- **串行等待**：每一步都要等模型生成完、工具返回，再开始下一步，延迟是线性叠加的
- **无效步骤**：调错工具、重复查询、来回反思，占了不少步数

所以先用[链路追踪](/engineering/eval/07-tracing)看每个任务的步数分布、每步 token 和耗时，找出最大的那一块再动手。怎么系统地评测见[成本和延迟评测](/engineering/eval/15-cost-latency-eval)。

### 减少轮次

1. **并行工具调用**：互不依赖的查询让模型一次发出多个调用，并发执行，见[并行工具调用](/ai/tools/04-parallel-calls)
2. **粗粒度工具**：把总是连着用的"查用户 → 查订单 → 查物流"合成一个工具，少两轮往返
3. **确定性的部分写成代码**：固定步骤不用让模型每次决定，用[工作流](/ai/agent/06-workflow-vs-agent)串起来，只在需要判断的节点调模型
4. **先规划再执行**：一次生成完整计划，执行阶段少做反复思考，见[规划](/ai/agent/03-planning)

### 分层用模型

| 环节 | 适合的模型 |
| --- | --- |
| 意图分类、路由、参数抽取 | 小模型 |
| 总结工具结果、压缩历史 | 小模型 |
| 任务规划、复杂推理、最终答复 | 大模型 |
| 子任务执行 | 视难度而定，多 Agent 时子 Agent 可以用小模型 |

路由的做法见[模型路由](/engineering/deploy/11-model-routing)。换小模型前要在评测集上确认成功率没掉，成功率下降带来的重试可能比省下的还多。

### 控制上下文，提高缓存命中

- 工具结果先裁剪再进上下文：只保留需要的字段，长结果存外部，给模型摘要和引用，见[工具结果太长怎么办](/ai/tools/12-long-tool-results)
- 历史过长时压缩早期步骤，见[长任务上下文管理](/ai/agent/12-long-task-context)
- System Prompt 和工具定义放在最前面、保持不变，新内容只往后追加，这样每一步都能命中[提示词缓存](/engineering/deploy/04-prompt-caching)。中途改工具列表或在前面插入时间戳会让缓存失效
- 压缩历史会改变前缀，导致缓存失效，所以不要每步都压，攒到阈值再压一次

### 预算和提前终止

- 硬上限：最大步数、累计 token、总耗时，超了就停下返回已有结果或转人工
- 软预算：把剩余预算告诉模型，让它在资源少时收敛
- 完成判断：拿到足够信息就回答，不为"再确认一下"多跑几轮
- 失败快速退出：同一个工具连续出错或结果重复，判定陷入循环，直接中止

失控防护更完整的讨论见[怎么防止 Agent 失控](/ai/agent/07-guardrails)。

### 降低体感延迟

总时间压不下来时，让用户少等：流式输出中间状态（"正在查询订单"），先返回部分结果；能离线做的长任务改成异步，完成后通知。首 Token 延迟的优化见[延迟优化](/engineering/deploy/07-latency)。

## 面试官可能追问

::: details 多 Agent 会更省还是更贵？
通常更贵。每个子 Agent 都要带自己的提示词和上下文，协调本身也消耗 token。它的好处是子任务可以并行、各自上下文更干净。只在任务确实能拆成独立的并行子任务时用，否则单 Agent 更划算。
:::

::: details 怎么给一个任务设置合理的步数上限？
看线上数据：统计成功任务的步数分布，上限设在高分位附近并留一些余量。不同类型的任务分开设。超限的样本要单独复查，判断是任务本身复杂还是 Agent 在绕圈。
:::

::: details 推理模型思考很久，Agent 里怎么用？
只放在需要深度推理的节点，比如规划和疑难决策；执行类步骤用普通模型。很多接口支持调节思考的预算，按步骤难度给不同的预算。
:::

## 易错点

- 只算单次调用的价格，忽略多步累积的输入 token，后者往往才是大头
- 为了省钱一律换小模型，结果成功率下降、重试变多，总成本反而上升
- 每一步都改动提示词前缀，导致缓存一直不命中
- 只设最大步数，不检测重复调用，Agent 在上限内仍然空转
