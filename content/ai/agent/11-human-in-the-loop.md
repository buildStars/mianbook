# Agent 的人在回路（Human-in-the-loop）怎么设计？

::: tip 一句话回答
人在回路就是在 Agent 执行中设置**人工介入点**。常见三种：**审批**（执行高风险动作前让人确认）、**澄清**（信息不足时向人提问）、**审阅修改**（关键产出先给人看，改完再继续）。设计要点有三个：**介入点按风险选**，只拦不可逆和高影响的操作，否则用户会不看就点同意；**能暂停和恢复**，等人的时候把状态存下来，不占着进程；**确认内容要具体**，让人看到要执行的真实参数，而不是模型写的一句概括。
:::

## 详细解析

### 三种介入方式

| 方式 | 触发时机 | 例子 |
| --- | --- | --- |
| 审批 | 执行某个工具调用前 | 发邮件、付款、删除数据、合并代码前，展示参数，用户选"批准 / 拒绝 / 修改" |
| 澄清 | 模型发现信息不够 | "要订哪天的会议室？"，而不是自己猜一个日期 |
| 审阅修改 | 阶段性产出完成后 | 研究计划、文章大纲、代码改动方案，用户改完再往下执行 |

另外还有一种被动的：用户**随时可以打断**，停下 Agent 或者插一句新的指示。

### 在哪里设介入点

按"可逆性 × 影响范围"分级，和 [工具调用的权限和安全](/ai/tools/09-tool-permissions) 的风险分级是同一套思路：

- **只读操作**：不拦
- **可逆、只影响自己**：比如在沙箱里改文件，不拦，事后可以审阅
- **不可逆或影响他人**：对外发送、付款、删除、改生产配置，必须拦

拦截要在**执行层**做，由代码判断要不要暂停，而不是让模型自己决定"这个要不要问用户"。

### 暂停和恢复

人可能几分钟后才回复，也可能第二天。所以审批不能是一个阻塞等待的函数：

1. Agent 产生一个需要审批的工具调用，执行层不执行，把**完整状态**（消息历史、待执行的调用、步数和预算）存下来
2. 给用户发审批请求，进程可以退出
3. 用户回复后，读出状态，把决定写进去：批准就执行；拒绝就把"用户拒绝了，原因是 xx"作为工具结果交给模型，让它换个方案
4. 循环从断点继续

这需要 Agent 的状态可以持久化，见 [Agent 的状态持久化和断点恢复](/ai/agent/14-durable-agent)。

### 避免审批疲劳

确认请求太多，用户会不看内容就点同意，审批就失去意义。缓解办法：

- 只拦真正高风险的操作，低风险的事后汇总给人看
- 允许"本次会话内同类操作都批准"，但范围要清楚，比如只针对某个目录或某个收件人
- 把多个相关操作合成一次确认，比如"将发送以下 3 封邮件"
- 展示的是**真实参数**（收件人、金额、要执行的命令），而不是模型的描述。模型被注入时，它的描述也可能是假的

## 面试官可能追问

::: details 用户一直不回复怎么办？
给审批设超时。超时后默认按**拒绝**处理，不能默认批准；同时通知用户任务因等待审批而暂停，状态保留一段时间，用户回来还能继续。长时间不处理的任务按策略清理。
:::

::: details 用户拒绝之后，Agent 应该怎么做？
把拒绝作为工具结果返回给模型，最好带上用户给的原因，让模型调整方案或者询问用户想要什么。不要直接终止整个任务，也不要让模型换个工具绕过去做同一件事，后者要在权限层面拦住。
:::

::: details 澄清问题问多了也烦人，怎么平衡？
在任务开始时集中问一次关键问题，比中途反复打断好。对于可以合理默认的细节，让模型按常见选择做，并在结果里说明它做了哪些假设。只有答错代价高的问题才停下来问。
:::

## 易错点

- 让模型自己判断要不要请示用户。被注入或判断失误时，它会跳过确认
- 确认框里只显示模型生成的概括，用户看不到真实参数
- 用阻塞等待实现审批，进程一重启，等待中的任务全丢
- 审批超时后默认放行
