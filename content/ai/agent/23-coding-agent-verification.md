# Coding Agent 改完代码怎么验证？编辑格式、测试和回滚怎么设计？

::: tip 一句话回答
编辑格式上，**搜索替换**（给出原文片段和新片段，要求原文唯一匹配）在可靠性和成本之间比较平衡，**整文件重写**简单但大文件容易丢内容，**diff** 省 token 但行号和上下文容易写错。应用编辑时要**检测失败**（没匹配到、匹配多处）并把原因回传给模型重试。改完依次跑**格式化、类型检查、lint 和相关测试**，把**精简后的错误信息**交给模型修复，设轮数上限。用 **git 做检查点**，走偏了就回滚到上一个好的状态。
:::

## 详细解析

### 编辑格式的可靠性

| 格式 | 优点 | 常见失败 |
| --- | --- | --- |
| 整文件重写 | 实现最简单，不存在匹配问题 | 大文件输出慢、费 token，模型可能省略未改动部分（写成"其余不变"） |
| 搜索替换 | 只输出改动部分；匹配失败能被检测到 | 原文片段和文件不一致（空格、缩进、记错内容），或者匹配到多处 |
| unified diff | 紧凑，能表达多处改动 | 行号、上下文行容易写错，补丁打不上 |

搜索替换的关键是**唯一匹配**：原文片段在文件里必须恰好出现一次，否则拒绝应用。这样错误会在编辑时就暴露出来，而不是悄悄改错位置。还有一个前提：模型必须先读过这个文件，基于最新内容写原文片段。

### 编辑失败怎么处理

1. 原文没匹配到：告诉模型"没找到"，附上文件里最相似的几行，让它重读后再试
2. 匹配到多处：告诉模型匹配了几处、分别在哪一行，让它多带几行上下文
3. 文件在读取之后被改过（用户或其他工具改了）：要求重新读取
4. 同一处连续失败几次：换成整段重写或停下报告

部分实现会对空白做宽松匹配，能提高成功率，但要注意别因此匹配到不该改的地方。

### 改完之后的检查

从快到慢依次跑，前一步不过就不跑后面的：

1. **格式化**：自动修复，不需要模型参与
2. **类型检查和编译**：最便宜、最能发现问题的一步，比如调用了不存在的方法、参数类型不对
3. **lint**：未使用的变量、可疑的写法
4. **相关测试**：先跑和改动相关的测试，全部通过后再按需跑全量

检查结果回传给模型时要**精简**：只给失败的测试名、断言信息和关键的堆栈几行，去掉通过的用例和大段重复日志。几千行原始输出会淹没真正的错误，也浪费上下文，见 [工具返回的结果太长怎么办](/ai/tools/12-long-tool-results)。

修复要有**轮数上限**。达到上限还不通过，就停下来报告当前状态和失败原因。模型有时会为了让测试通过去改测试本身、删断言或跳过用例，这类改动要单独提示人审查。

### 用 git 做检查点和回滚

- 开始前确认工作区状态，记录起点（当前提交，或先暂存用户已有的改动）
- 每完成一个通过检查的小步，做一个检查点（临时提交或保存 diff）
- 修复越改越乱时，回到上一个检查点重新尝试，而不是在错误的基础上继续叠加
- 最后把整体 diff 展示给用户审查，由用户决定是否保留

注意不要破坏用户原有的未提交改动，也不要自作主张执行 `git reset --hard`、强制推送这类不可逆操作。

## 代码示例

带唯一匹配检查的搜索替换：

```js
function applyEdit(content, oldText, newText) {
  const first = content.indexOf(oldText)
  if (first === -1) return { ok: false, error: '没有找到原文，请重新读取文件后再试' }
  const second = content.indexOf(oldText, first + 1)
  if (second !== -1) {
    const lineOf = i => content.slice(0, i).split('\n').length
    return { ok: false, error: `原文匹配到多处（第 ${lineOf(first)}、${lineOf(second)} 行），请多带一些上下文` }
  }
  return { ok: true, content: content.slice(0, first) + newText + content.slice(first + oldText.length) }
}

const file = `function add(a, b) {
  return a - b
}
function sub(a, b) {
  return a - b
}`

console.log(applyEdit(file, 'return a - b', 'return a + b').error)
// 原文匹配到多处（第 2、5 行），请多带一些上下文
console.log(applyEdit(file, 'return a * b', 'x').error)
// 没有找到原文，请重新读取文件后再试
const r = applyEdit(file, 'function add(a, b) {\n  return a - b', 'function add(a, b) {\n  return a + b')
console.log(r.content.split('\n')[1]) //   return a + b
```

## 面试官可能追问

::: details 项目没有测试怎么办？
至少跑类型检查、编译和 lint；可以让 Agent 为这次改动补一个最小的测试或复现脚本，先确认改前失败、改后通过；涉及界面的改动可以启动应用实际看一眼。验证不了的部分要在报告里明确说出来。
:::

::: details 测试本身就不稳定，时过时不过怎么办？
先在改动前跑一次，记录基线：哪些用例本来就失败。改完对比基线，只关注新增的失败。不稳定的用例可以重跑确认，但不要让模型去修和本任务无关的测试。
:::

::: details 怎么防止模型通过改测试来"让测试通过"？
在指令里明确不允许修改已有测试的断言；在检查环节识别出对测试文件的改动并标注出来交给人审；评测时用模型看不到的隐藏测试来判断，[SWE-bench 这类基准](/engineering/eval/16-agent-benchmarks)就是这样做的。
:::

## 易错点

- 搜索替换不检查唯一性，匹配到第一处就改，结果改错了函数
- 把几千行的测试输出原样塞回上下文，真正的报错反而被淹没
- 修复没有轮数上限，模型在两种错误写法之间来回切换
- 回滚时用破坏性的 git 命令，把用户原本未提交的改动一起清掉
