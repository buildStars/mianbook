# Agent 的自我反思和纠错是怎么实现的？

::: tip 一句话回答
在 Agent 循环里，反思和纠错就是**每一步执行后看反馈、判断成没成、没成就带着错误信息重试或换方案**。关键是判断依据要来自**外部反馈**：工具返回的报错、测试和编译结果、Schema 或业务规则校验器、页面状态，而不是让模型凭感觉说"我做对了"。常见结构有三种：**执行-校验-修正**的内层循环、**评估者-优化者**（另一个模型或校验器打分给意见）、**Reflexion 式**（失败后写下"错在哪、下次怎么做"再重试）。工程上要配套**重试预算**和**停止条件**：同一个错误重复出现、预算用完、没有新信息时就停下，交给人处理。
:::

## 详细解析

### 反思在循环里的位置

```text
计划 ──▶ 执行工具 ──▶ 拿到反馈 ──▶ 判断：成功？
                                      │是 ──▶ 下一步
                                      │否
                                      ▼
                           分析原因（带上原始报错）
                                      │
                        ┌─────────────┼──────────────┐
                        ▼             ▼              ▼
                   改参数重试      换方案/换工具    预算用完 → 停下交给人
```

提示词层面让模型"答完自查一遍"属于另一类问题，效果和局限见 [让模型自我反思、自我修正真的有用吗](/ai/prompt/14-self-reflection)。这里讨论的是 Agent 有了执行能力之后，怎么把环境的反馈接进纠错循环。

### 判断依据从哪来

| 来源 | 例子 | 可靠性 |
| --- | --- | --- |
| 确定性校验器 | 单元测试、类型检查、编译、JSON Schema、SQL 能否执行、业务规则（金额不能为负） | 最高，还能指出错在哪 |
| 工具和环境反馈 | 接口返回 4xx 和错误信息、文件不存在、页面上没出现预期元素 | 高，但要区分"真失败"和"暂时失败" |
| 另一个模型评审 | 评估者按清单打分，打分方法同 [LLM-as-a-Judge](/engineering/eval/02-llm-as-judge) | 中，适合没有确定性检查的产出 |
| 自评 | 同一个模型在同一上下文里判断自己 | 低，只作参考 |

设计时先问：这一步有没有能自动验证的东西？有就让它决定"成没成"。典型例子是编程 Agent 的"改代码 → 跑测试 → 看报错 → 再改"，见 [编程 Agent 是怎么工作的](/ai/agent/08-coding-agent)。

### 三种结构

- **执行-校验-修正**：每次工具调用或产出后立即校验，失败就把**原始错误信息**（失败的断言、报错堆栈、校验器给出的字段路径）交给模型修正，而不是只说"失败了"
- **评估者-优化者**：生成者产出，评估者（另一个提示词、另一个模型或校验器）按明确标准给出通过与否和具体意见，循环到通过或预算用完
- **Reflexion 式**：一次完整尝试失败后，让模型写一段可执行的经验（"下次先确认文件路径再修改"），带进下一次尝试；适合能多次尝试、有明确成败信号的任务

### 重试预算和停止条件

纠错循环最常见的问题是停不下来，或者越改越差：

- **分层预算**：单个工具调用最多重试几次，单个子任务最多修正几轮，整个任务有总步数和费用上限
- **区分错误类型**：超时、限流这类暂时错误按退避重试，不需要模型反思；参数错误、逻辑错误才需要模型修正；权限不足这类重试也没用的，直接停
- **检测原地打转**：同一个错误连续出现、模型给出和上次一样的修改，说明没有新信息，再试也没用
- **保留最好的版本**：后一轮不一定更好，按校验结果选通过项最多的版本，而不是总用最后一版
- **停下时交代清楚**：带着当前最好的结果、已尝试的方案和未解决的错误交给人，见 [人在回路怎么设计](/ai/agent/11-human-in-the-loop)

## 代码示例

```ts
type Check = { ok: true } | { ok: false; error: string }

// 执行-校验-修正：校验器决定成败，预算和"重复错误"决定什么时候停
async function runWithCorrection(
  attempt: (feedback?: string) => Promise<string>,
  validate: (out: string) => Check,
  maxRounds = 3,
) {
  let feedback: string | undefined
  let lastError = ''
  for (let round = 1; round <= maxRounds; round++) {
    const out = await attempt(feedback)
    const check = validate(out)
    if (check.ok) return { status: 'ok' as const, out, round }
    if (check.error === lastError) return { status: 'stuck' as const, error: check.error, round } // 同一错误重复，停
    lastError = check.error
    feedback = `上次的输出没有通过校验：${check.error}` // 把原始错误交回去
  }
  return { status: 'budget_exhausted' as const, error: lastError, round: maxRounds }
}

const outputs = ['{"amount": -5}', '{"amount": 20}']
const result = await runWithCorrection(
  async () => outputs.shift() ?? '',
  (out) => (JSON.parse(out).amount > 0 ? { ok: true } : { ok: false, error: 'amount 必须大于 0' }),
)
console.log(result) // { status: 'ok', out: '{"amount": 20}', round: 2 }
```

## 面试官可能追问

::: details 推理模型已经会在内部检查了，还需要外部纠错循环吗？
需要，但目的不同。内部思考能减少推理上的错误，但它看不到执行结果。外部循环的价值在于引入新信息：测试结果、工具报错、校验结论，这些只有真正执行之后才能拿到。
:::

::: details Reflexion 的反思存在哪里？
单个任务内，反思放在上下文里，下一次尝试时带上。如果希望跨任务积累经验，可以把反思存进长期记忆，按任务类型检索出来；但要有筛选和过期机制，避免错误的经验一直误导后面的任务，见 [Agent 的记忆系统怎么设计](/ai/agent/04-memory)。
:::

::: details 怎么证明纠错循环真的有用？
用评测集对比开启和关闭纠错的成功率，同时看平均步数、费用和延迟。按任务类型分组看，常常只对部分类型有收益，那就只对这些类型开启，见 [怎么评估一个 Agent 的表现](/engineering/eval/10-agent-eval)。
:::

## 易错点

- 有测试、校验器这类客观信号却不用，让模型自己判断"做对了没有"
- 只告诉模型"失败了"，不把原始报错交给它
- 暂时错误和逻辑错误一视同仁，超时也让模型去反思
- 没有重试预算和重复错误检测，循环原地打转，费用失控
