# 浏览器是怎么匹配 CSS 选择器的？为什么说选择器是从右往左匹配的？

::: tip 一句话回答
在**样式计算**阶段，浏览器要为每个元素找出所有匹配的规则。对复合选择器，它从**最右边的关键选择器**开始：先看当前元素是否满足最右边那部分，满足了再**向上检查祖先**是否满足左边的部分。因为页面上绝大多数规则连最右边都对不上，**第一步就能排除**，比从左往右"先找祖先再往下搜"省得多。主流引擎（如 Blink、WebKit）还会按关键选择器的 id、class、标签**把规则分桶**，只检查可能相关的规则。现代浏览器优化得很好，选择器性能一般不是瓶颈。
:::

## 详细解析

### 匹配发生在哪一步

```text
解析 HTML → DOM 树
解析 CSS  → 样式规则
样式计算：对每个元素，找出匹配的规则 → 按层叠排序 → 得出计算样式
→ 布局 → 绘制 → 合成
```

匹配要回答的问题是"这个元素命中了哪些规则"，而不是"这条规则命中了哪些元素"。这个方向决定了从右往左更合适。完整流程见 [浏览器渲染流程](/basics/browser/01-url-to-page)。

### 从右往左的过程

以 `.nav li a` 为例，当前元素是某个 `<a>`：

1. 最右边是 `a`：当前元素是 `a` 吗？不是就直接结束
2. 是的话，向上找祖先里有没有 `li`
3. 找到 `li` 后，再从它往上找有没有 `.nav`
4. 全部满足才算匹配；向上走到根节点还没找到就失败

如果从左往右，要先找到所有 `.nav`，再遍历它们的后代找 `li`，再找 `a`，大量分支最后走不通，还要回溯。而从右往左，每个元素向上只有一条祖先链，路径是确定的。

### 分桶和其他优化

以 Blink、WebKit 为例，引擎不会拿每个元素去试所有规则（具体做法各引擎不同）：

- 按关键选择器归类：最右边是 `#id` 的放进 id 桶，是 `.class` 的放进 class 桶，是标签的放进标签桶，剩下的（如 `*`、只有属性选择器）放进通用桶
- 匹配一个元素时，只取它的 id、各个 class、标签名对应的桶，加上通用桶
- 一些引擎还用布隆过滤器之类的结构，快速判断"祖先链里肯定没有某个 class"，提前放弃向上查找
- 一些引擎会让条件相同的兄弟元素共享计算结果（样式共享）

### 哪些写法开销相对大

- 关键选择器过于宽泛：`.box *`、`div` 结尾的长选择器，几乎每个元素都要进入向上检查
- 很深的后代选择器：`.a .b .c .d span`，每个 span 都要沿祖先链反复查找
- `:has()`：根据后代或后续兄弟决定当前元素，DOM 变化时要反向判断哪些祖先受影响，浏览器为此做了专门优化，但滥用仍有代价
- 频繁改 class 引发大范围样式重新计算，比选择器本身更值得关注

### 实际影响

现代浏览器的选择器匹配非常快，大部分页面的样式计算耗时主要来自元素多、规则多、频繁触发重新计算，而不是某个选择器写法。真要排查，用 DevTools 的 Performance 面板看 "Recalculate Style" 的耗时，再针对热点处理。日常写法上，保持选择器扁平（如 BEM），本身就兼顾了可维护性和性能。

## 面试官可能追问

::: details 选择器匹配和优先级计算是一回事吗？
不是。匹配决定"哪些规则作用于这个元素"，优先级决定"多条规则冲突时谁赢"。匹配完成后才按来源、层叠层、优先级、出现顺序排序。优先级的计算见 [选择器优先级](/basics/css/03-specificity)。
:::

::: details `querySelectorAll` 也是从右往左匹配吗？
它的问题方向相反：给定选择器，找出所有命中的元素。浏览器实现上通常会遍历子树里的元素，对每个元素用同一套从右往左的逻辑判断是否匹配；对单个 id 这类简单选择器会走快速路径。具体策略各引擎不同。
:::

::: details 修改一个 class 会导致整页重新匹配吗？
不一定。浏览器会记录哪些规则依赖这个 class，只把可能受影响的元素标记为需要重新计算，比如自身和后代，或者兄弟选择器涉及的兄弟。但 `:has()` 和复杂的兄弟选择器会让受影响范围变大。
:::

## 易错点

- 从右往左说的是**一条选择器内部**的匹配顺序，不是样式表里规则的应用顺序
- 以为 id 选择器开头的长选择器更快：`#app .list span` 的关键选择器是 `span`，起点仍是所有 span
- 把选择器写法当成首要性能问题，忽略了 DOM 规模和频繁的样式失效
