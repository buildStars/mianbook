# 设计一个在线协同文档：多人同时编辑怎么解决冲突？OT 和 CRDT 有什么区别？

::: tip 一句话回答
多人同时改同一段文字，按到达顺序直接覆盖会丢内容，按下标重放会让各端结果不一致。两种主流解法：**OT（操作转换）** 由中心服务器给操作定序，再把并发操作的位置做**转换**后应用，需要中心服务器，实现复杂但在文本协同上最成熟；**CRDT** 给每个字符一个**唯一 ID**，按 ID 和固定的排序规则合并，操作可交换、任意顺序应用都**最终一致**，天然支持离线和点对点，代价是元数据、内存开销和删除留下的**墓碑**。工程上常用 Yjs 这类 CRDT 库，配 WebSocket 同步服务和"快照 + 增量"的存储。
:::

## 详细解析

### 第一步：问题和需求

- 功能：多人实时编辑富文本，看到彼此的光标和在线状态；断网后能继续编辑，联网后自动合并；历史版本
- 规模（假设值）：大部分文档同时在线 1～5 人，少数热门文档几十人；单篇文档几万字
- 核心难点：并发编辑时，**所有人最终看到同样的内容**，而且不丢任何一方的输入

为什么不能简单处理？文档是 `AB`，Alice 在位置 1 插入 `X`，Bob 同时在位置 1 插入 `Y`。Alice 本地变成 `AXB`，Bob 本地变成 `AYB`。如果各自把对方的 `insert(1, ...)` 原样应用，Alice 得到 `AYXB`，Bob 得到 `AXYB`，两端不一致。加锁或"后写覆盖"能保证一致，但会丢输入，体验也不可接受。

### 第二步：OT 怎么处理

OT 的思路是：操作发到服务端，服务端决定一个全局顺序；后到的操作如果和先到的操作并发，就**根据先到的操作调整位置**再应用。

同一个例子，假设 Alice 的操作先到服务端：

1. 服务端应用 Alice 的 `insert(1, X)`，文档变成 `AXB`
2. Bob 的 `insert(1, Y)` 和它并发，需要转换。两者位置相同，规则约定先定序的排在前面，于是 Bob 的操作右移一位，变成 `insert(2, Y)`，文档变成 `AXYB`，并广播给 Alice
3. Alice 本地是 `AXB`，收到 `insert(2, Y)`，得到 `AXYB`
4. Bob 本地是 `AYB`，收到 Alice 的 `insert(1, X)`，在客户端把它对自己未确认的 `insert(1, Y)` 做转换。Alice 的操作定序在前，位置不变，仍是 `insert(1, X)`，得到 `AXYB`

三方一致。OT 依赖中心服务器定序；插入、删除、格式化两两之间都要写转换函数，富文本操作种类多，正确实现很难，但这条路线在文本协同上历史最久、最成熟。

### 第三步：CRDT 怎么处理

CRDT 不用下标定位，而是给每个字符一个全局唯一的 ID，例如 `(客户端 ID, 本地计数器)`，并记录插入时它左边的字符是谁。

还是同一个例子：

- 原有字符：`A` 和 `B`
- Alice 插入 `X`，ID 为 `(alice, 1)`，左邻居是 `A`
- Bob 插入 `Y`，ID 为 `(bob, 1)`，左邻居也是 `A`

两个字符都要放在 `A` 后面，谁在前由一条所有端都一样的确定规则决定，例如左邻居相同时按客户端 ID 排序，`alice` 小于 `bob`，所以 `X` 在前。不管哪端先收到哪个操作，排出来都是 `AXYB`。

- 删除不能真正移除字符：别的端可能还在引用它做左邻居，所以只标记为已删除，这就是**墓碑**
- 操作满足交换律、结合律、幂等，可以任意顺序、重复应用，不需要中心服务器定序，所以支持离线编辑和点对点同步
- 代价：每个字符都带元数据，内存和存储比纯文本大；墓碑会累积，需要垃圾回收

| 对比项 | OT | CRDT |
| --- | --- | --- |
| 定位方式 | 下标，靠转换修正 | 唯一 ID 加排序规则 |
| 中心服务器 | 需要，负责定序 | 不需要，服务器只做转发和存储 |
| 离线、点对点 | 难 | 天然支持 |
| 开销 | 操作本身小，转换逻辑复杂 | 元数据多，有墓碑 |

### 第四步：以 Yjs 为例的整体架构

Yjs 是一个 CRDT 实现，数据以共享类型的形式暴露：

```js
import * as Y from 'yjs'
import { WebsocketProvider } from 'y-websocket'
import { IndexeddbPersistence } from 'y-indexeddb'

const doc = new Y.Doc()
const text = doc.getText('content') // 顶层共享类型，还有 getMap、getArray、getXmlFragment

new IndexeddbPersistence('doc-42', doc) // 本地持久化，离线也能编辑
const provider = new WebsocketProvider('wss://collab.example.com', 'doc-42', doc) // 房间名相同的文档互相同步

// 光标和在线状态走 awareness，不写进文档
provider.awareness.setLocalStateField('user', { name: 'Alice', color: '#e66' })

doc.transact(() => {
  text.insert(0, 'Hello')
  text.format(0, 5, { bold: true })
}) // 事务里的多次修改只触发一次事件

doc.on('update', (update) => {
  // update 是压缩的二进制增量，可以发给服务端存储
})
```

```text
编辑器（ProseMirror / Quill 等，绑定 Y.XmlFragment / Y.Text）
   │
Y.Doc ── y-indexeddb（本地）
   │ WebSocket（房间 = 文档 ID）
同步服务（鉴权、转发 update、广播 awareness）
   │
存储：快照 + 增量 update 日志 ── 定期合并
```

- **同步服务**：长连接用 WebSocket（见 [WebSocket](/basics/network/15-websocket)）。连接时先校验用户对文档的权限，只读用户的 update 直接丢弃。同一文档的连接要落在同一个节点，或者节点之间通过发布订阅转发
- **存储**：每个 update 追加写入日志；定期用 `Y.mergeUpdates` 或把整个文档 `Y.encodeStateAsUpdate` 成快照，清掉旧日志。新用户打开文档时加载快照加之后的增量
- **断线重连**：客户端发自己的状态向量（`Y.encodeStateVector`），服务端只回对方缺的部分，离线期间的修改同样以 update 发上去合并
- **awareness**：光标、用户名、颜色只广播、不持久化，30 秒收不到某端更新就视为离线
- **编辑器绑定**：编辑器的数据模型和共享类型双向绑定，本地编辑转成共享类型的操作，远端 update 再映射回编辑器。`Y.Text` 的 `toDelta()` 和 Quill 的 Delta 格式一致

### 第五步：扩展

- **历史版本**：定时存快照并打标签；需要恢复已删除内容时要关闭垃圾回收（`doc.gc = false`），代价是文档更大
- **评论、批注**：锚定在字符 ID 上，而不是下标，文字增删后位置不漂移
- **大文档**：按章节拆成多个子文档，按需加载

## 面试官可能追问

::: details 协同文档和 IM 消息同步有什么不同？
IM 消息只追加、互不修改，服务端定序就够了（见 [IM 系统](/basics/backend-design/04-im)）。协同文档是多人并发修改同一份数据，要解决同一位置的冲突，并保证合并后各端完全一致。
:::

::: details CRDT 的墓碑会不会让文档无限变大？
会增长，所以要有垃圾回收。Yjs 默认会回收被删除内容本身，只留下记录"这里删过东西"的少量元数据；把 `doc.gc` 设为 `false` 才会完整保留，以便恢复旧版本。实际中更容易膨胀的是不加合并的 update 日志，服务端要定期压缩成快照。
:::

::: details 撤销怎么做？
协同场景下撤销只能撤自己的操作，不能把别人的修改也撤掉。做法是记录本地事务（通过事务的 origin 区分本地和远端），撤销时生成反向操作，再作为一次新的修改同步出去。
:::

::: details 权限怎么控制？只在前端禁用编辑够吗？
不够。CRDT 的 update 可以被任意构造，服务端必须在同步服务里校验连接身份，没有写权限的连接收到 update 直接丢弃，也不广播。
:::

## 易错点

- 以为"后写覆盖"或加锁就能做协同，前者丢内容，后者体验很差
- 把 OT 的"转换"说成 CRDT 也要做，CRDT 靠唯一 ID 和确定的排序规则，不做下标转换
- 把光标、在线状态写进文档本身，导致历史里塞满光标移动
- 只存 update 日志从不压缩，打开老文档要重放海量增量
