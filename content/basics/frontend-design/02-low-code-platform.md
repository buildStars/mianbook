# 设计一个低代码可视化搭建平台：页面描述、组件物料、渲染和出码怎么设计？

::: tip 一句话回答
核心是一份 **JSON 页面描述（Schema）**：组件树、属性、样式、事件动作、数据源绑定和表达式都在里面。围绕它有四块：**物料**（组件加上描述它的元数据）、**编辑器**（画布、拖拽、属性面板、撤销重做，本质是在改 Schema）、**渲染器**（运行时递归渲染 Schema）、**出码**（把 Schema 转成源码）。难点在表达式求值的安全、物料的版本管理和低代码的边界：复杂逻辑要留**自定义组件和代码扩展点**。
:::

## 详细解析

### 第一步：目标和边界

先问清楚给谁用，这决定了灵活度：

| 场景 | 使用者 | 特点 |
| --- | --- | --- |
| 活动页、营销页 | 运营 | 组件偏展示，强调所见即所得、快速发布，逻辑很少 |
| 中后台（表单、表格、详情） | 开发 | 组件偏数据，要接接口、做校验和联动，需要写表达式甚至代码 |

规模上关注的不是 QPS，而是物料数量（几十到几百个组件）、单页节点数（几百个）、发布频率，以及运行时页面的访问量（活动页可能瞬间很高，要走 CDN）。

### 第二步：整体架构

```text
物料仓库（组件代码 + 元数据，按版本发布到 CDN）
      │
编辑器 ──读写──► Schema ──保存──► 后端（草稿、版本、权限）
  画布(iframe)                         │
  属性面板                         发布
  大纲树 / 撤销重做              ┌──────┴──────┐
                          运行时渲染器         出码
                       （加载 Schema 渲染）  （生成源码，走正常构建）
```

### 第三步：关键模块

**Schema**

```json
{
  "id": "page_1",
  "component": "Page",
  "props": { "title": "报名" },
  "dataSource": [{ "id": "userInfo", "url": "/api/user", "autoLoad": true }],
  "children": [
    {
      "id": "btn_1",
      "component": "Button",
      "props": { "text": "{{ state.userInfo.name }}，立即报名", "disabled": "{{ !state.agreed }}" },
      "style": { "marginTop": "16px" },
      "events": { "onClick": [{ "action": "request", "api": "/api/signup" }, { "action": "toast", "text": "成功" }] }
    }
  ]
}
```

- 每个节点有唯一 ID，编辑器选中、撤销、协同都靠它
- 属性值可以是常量，也可以是表达式（约定一种标记，例如 `{{ }}` 包裹）
- 事件绑定的是**动作列表**（请求、跳转、改状态、提示），而不是任意代码，这样能被可视化配置
- Schema 要有版本号，结构升级时写迁移函数

**物料**：组件本身加上元数据：可配置的属性（类型、默认值、用什么编辑器配置）、支持的事件、能放进哪些容器、能接受哪些子组件。属性面板根据元数据**自动生成**，加新组件不用改编辑器。物料独立打包，渲染时按 Schema 用到的组件按需加载；Schema 里记录组件版本，物料升级不影响已发布的页面。

**编辑器**

- 画布放在 **iframe** 里：页面的样式和脚本与编辑器隔离，互不污染；拖拽时编辑器根据坐标算出落点
- 拖拽放置时按元数据校验（表单项只能放进表单）
- 撤销重做：命令模式（每个操作记录 do 和 undo），或者每次修改存一份 Schema 快照。快照实现简单，用结构共享的不可变数据可以省内存
- 多人同时编辑同一页面会有冲突，可以先用页面锁，需要真正协同再上 [协同编辑](/basics/frontend-design/03-collaborative-editing) 的方案

**渲染器**：递归遍历 Schema，按 `component` 找到组件，把属性里的表达式求值后传进去，把动作列表转成事件处理函数。数据源请求的结果放进页面状态，表达式依赖状态，用响应式系统驱动更新（Vue 的做法见 [响应式原理](/basics/vue/01-reactivity)）。

### 第四步：难点和取舍

**表达式安全**：表达式来自用户配置，不能直接 `eval` 或 `new Function` 执行，否则搭建者可以读 Cookie、发任意请求。做法是用受限的表达式语言：自己解析成语法树，只允许访问白名单里的变量（`state`、`props`、少量工具函数），不允许访问 `window`、原型链。需要完整 JS 的场景放到独立的沙箱（iframe 或 Worker）里执行。

**运行时渲染还是出码**

| 对比项 | 运行时渲染 | 出码 |
| --- | --- | --- |
| 发布 | 改 Schema 即发布，秒级生效 | 生成代码后要构建、部署 |
| 性能 | 多一层解析和渲染器，首屏稍重 | 和手写代码一样，能做 tree-shaking |
| 后续维护 | 只能在平台上改 | 开发可以接手改代码，但改了就很难再回到可视化编辑 |
| 适合 | 活动页、频繁变化的页面 | 低代码起步、后面要深度定制的项目 |

两者可以并存：日常用运行时渲染，需要脱离平台时导出代码。

**发布和版本**：草稿和线上版本分开存，每次发布生成不可变的版本快照，回滚就是把线上指针指回旧版本；灰度按用户比例下发不同版本的 Schema。运行时 Schema 和物料都走 CDN 缓存。

**低代码的边界**：复杂交互、复杂表单联动、特殊性能要求，用配置描述会比写代码还难。平台要留扩展点：开发者注册自定义组件、写自定义动作、在指定位置插入代码，而不是不断加配置项。

### 第五步：扩展

- **模板和区块**：常用的组件组合存成区块，拖进来就是一组节点
- **数据模型驱动**：中后台根据接口或数据表结构自动生成表单和表格的 Schema
- **多端**：同一份 Schema 配不同的渲染器和物料，输出到 H5、小程序

## 面试官可能追问

::: details 编辑器为什么要用 iframe 做画布？
页面的 CSS 可能覆盖编辑器的样式，组件里的全局脚本也可能影响编辑器。iframe 天然隔离样式和全局变量，还能模拟不同的视口宽度。代价是跨 iframe 的拖拽、选中框定位要通过坐标换算和消息通信实现。
:::

::: details 撤销重做用命令模式还是快照？
命令模式内存小，但每种操作都要写正确的逆操作，操作种类多时容易出错。快照实现简单、不会出错，配合不可变数据的结构共享，没改的子树复用同一个对象，内存开销可以接受。协同场景下撤销只能撤自己的操作，这时更依赖协同数据结构自带的撤销管理。
:::

::: details 组件之间怎么联动，比如选了省份再刷新城市列表？
通过页面状态中转：省份组件的 change 动作写入 `state.province`，城市组件的数据源依赖这个状态，表达式变化时自动重新请求。不要让组件直接互相引用，否则 Schema 里会出现难以维护的依赖关系。
:::

## 易错点

- 表达式直接用 `eval` 或 `new Function` 执行，搭建者能在页面里执行任意脚本
- Schema 不记录物料版本，组件一升级，已发布的页面跟着变样
- 什么需求都加配置项，最后配置比代码还复杂，没有留自定义代码的出口
- 出码后又想回到可视化编辑，手改过的代码没法转回 Schema
