# 设计一个分布式定时任务调度系统

::: tip 一句话回答
核心是把**调度**和**执行**分开：**调度中心**负责按 cron 表达式算出下次触发时间、到点选一个执行器下发任务、记录结果；**执行器**嵌在业务服务里，只管跑任务、回报状态。要解决的关键问题有四个：多个调度节点**不能重复触发**（抢占数据库行锁或选主）；执行器挂了要**故障转移**和**重试**；大任务要能**分片**到多台机器并行；调度中心宕机期间**错过的触发**要有补偿策略。任务本身必须幂等，因为"至少执行一次"是能做到的最好保证。
:::

## 详细解析

### 第一步：澄清需求

- **场景**：每天凌晨对账、每小时生成报表、每 5 分钟同步数据、定期清理过期数据
- **和延时任务的区别**：这里是按 cron **周期性**执行、任务数量在几百到几万个；"每个订单 30 分钟后取消"这种海量一次性任务见 [延时任务系统](/basics/backend-design/07-delay-task)
- **功能**：任务的增删改、启停；cron 和固定间隔两种触发；手动触发一次；执行日志、失败告警；任务依赖（A 跑完再跑 B）
- **非功能**：秒级精度够用；同一次触发只能执行一次（或至少业务上幂等）；调度中心本身高可用

单机里用 `node-cron`、Spring 的 `@Scheduled` 就行（见 [Node.js 的定时任务](/basics/node/18-task-queue)），问题出在部署多个实例时：每个实例都会执行一遍。

### 第二步：整体架构

```text
           ┌──────────── 控制台（任务配置、日志、手动触发）
           ▼
   ┌─────────────────┐   存储：任务表、触发记录、执行日志（MySQL）
   │ 调度中心 × N     │──────────────────────────┐
   │ 扫描到期任务、选执行器 │                    │
   └──────┬──────────┘                          │
          │ RPC 下发（任务 ID、分片参数）         │ 心跳注册
   ┌──────▼──────┐  ┌─────────────┐  ┌──────────┴──┐
   │ 执行器 A-1   │  │ 执行器 A-2   │  │ 执行器 B-1   │
   │（业务服务内） │  │             │  │             │
   └─────────────┘  └─────────────┘  └─────────────┘
```

- 执行器启动时向调度中心注册，按应用名分组，定期心跳；心跳超时就从可用列表里移除
- 调度中心只发"任务 ID + 参数"，任务代码在执行器里，所以业务发版不影响调度中心
- 现成的开源方案例如 XXL-JOB、ElasticJob、PowerJob，Java 里还有 Quartz 的集群模式，思路相近

### 第三步：核心模块和数据模型

```sql
CREATE TABLE job (
  id              BIGINT PRIMARY KEY,
  app             VARCHAR(64) NOT NULL,      -- 由哪个执行器组执行
  handler         VARCHAR(128) NOT NULL,     -- 执行器里注册的任务名
  cron            VARCHAR(64) NOT NULL,
  shard_total     INT NOT NULL DEFAULT 1,
  route_strategy  VARCHAR(16) NOT NULL,      -- 轮询、一致性哈希、广播、分片
  misfire_policy  VARCHAR(16) NOT NULL,      -- 错过触发：忽略 / 补跑一次
  timeout_sec     INT NOT NULL,
  retry_max       INT NOT NULL DEFAULT 0,
  next_fire_time  BIGINT NOT NULL,           -- 下次触发时间戳（毫秒）
  enabled         TINYINT NOT NULL,
  KEY idx_next (enabled, next_fire_time)
);

-- 每次触发一条记录，(job_id, fire_time) 唯一，防止同一次触发被执行两遍
CREATE TABLE job_run (
  id         BIGINT PRIMARY KEY,
  job_id     BIGINT NOT NULL,
  fire_time  BIGINT NOT NULL,
  shard_idx  INT NOT NULL,
  executor   VARCHAR(64),
  status     VARCHAR(16) NOT NULL,           -- 等待、运行中、成功、失败、超时
  retry_cnt  INT NOT NULL DEFAULT 0,
  UNIQUE KEY uk_fire (job_id, fire_time, shard_idx)
);
```

**调度循环**：每秒扫描 `next_fire_time <= now + 预读窗口` 的任务，放进内存时间轮精确到秒触发；触发后按 cron 算出新的 `next_fire_time` 写回。

### 第四步：关键难点

**多个调度节点怎么不重复触发**：常见做法是抢数据库行锁、按 `next_fire_time` 乐观更新、用 etcd 或 ZooKeeper 选主，再用 `job_run` 的唯一索引兜底，同一次触发被下发两遍时第二次插入失败就不执行。各方案的细节和取舍见 [分布式定时任务怎么保证只执行一次](/basics/distributed/14-distributed-scheduler)。系统设计层面要多考虑一点：调度节点按任务 ID 哈希分片后，节点增减时要重新分配任务，可以靠注册中心感知成员变化后触发再平衡。

**执行器挂了怎么办**：路由时只选心跳正常的执行器；下发失败换一台重试；执行中的任务长时间没有回报，按超时标记失败，按 `retry_max` 重新调度。因为可能出现"其实执行完了只是回报丢了"，任务逻辑必须幂等。

**大任务分片**：比如每天给 1 亿用户发账单。调度中心把一次触发拆成 `shard_total` 个分片，分发给不同执行器，每台拿到 `(shard_idx, shard_total)`，只处理 `user_id % shard_total == shard_idx` 的数据。某个分片失败只重跑这一片。

**错过触发（misfire）**：调度中心宕机 10 分钟，恢复后有一批任务已经过了触发时间。按任务配置的策略处理：**忽略**，直接算下一次（适合每分钟的同步任务）；**立即补跑一次**（适合每天一次的对账）。不要把错过的每一次都补跑，会瞬间堆积大量执行。

**同一任务上次还没跑完**：配置阻塞策略：丢弃本次、排队等待，或者终止上一次。默认丢弃本次最安全，避免同一任务并发跑导致数据冲突。

### 第五步：扩展与优化

- **任务依赖**：用 DAG 描述，上游成功后触发下游；复杂的数据管道交给专门的工作流引擎
- **超时控制**：执行器侧给任务设置超时并能中断，防止卡死的任务一直占着线程
- **监控告警**：每次执行的耗时、结果、日志可以在控制台查；连续失败、执行超时、长时间未触发、执行器在线数骤降都要告警，告警按任务负责人路由
- **扩缩容**：执行器无状态，新实例注册后自动进入路由列表；分片任务按当前在线执行器分配分片，缩容前先摘除心跳、等手上的任务跑完再下线
- **时区和夏令时**：cron 要指定时区，否则跨时区部署时"凌晨 2 点"含义不同

## 面试官可能追问

::: details 为什么不直接在每个服务里加分布式锁，跑单机定时任务？
小规模可以：每个实例的定时器都触发，抢到锁的那个执行（锁的实现见 [Redis 分布式锁](/basics/redis/07-distributed-lock)）。缺点是没有统一的任务管理、执行日志、失败重试和手动触发，也做不了分片，任务多了很难运维。调度中心把这些能力集中起来。
:::

::: details cron 的秒级任务很多，调度中心扛不住怎么办？
调度中心水平扩展，按任务 ID 哈希分片，每个节点只负责自己那部分任务。扫描数据库用预读窗口加内存时间轮，避免每秒都全表扫描。真正的压力常常在执行器，执行器要有自己的线程池上限和排队。
:::

::: details 怎么保证任务"恰好执行一次"？
分布式环境下做不到严格的恰好一次，只能做到"至少一次 + 幂等"。调度侧用唯一索引避免重复下发，执行侧让任务可重入：比如对账任务按日期覆盖写入结果，发账单前先检查这个用户本期是否已发。
:::

## 易错点

- 多实例部署后直接用框架自带的单机定时器，每台都执行一遍
- 依赖"执行成功的回报"判断任务完成，回报丢失时会重复执行，所以任务必须幂等
- 调度中心恢复后把错过的触发全部补跑，瞬间压垮下游
- 同一任务上次没跑完，下次又启动，两次并发修改同一批数据
