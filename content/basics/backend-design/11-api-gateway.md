# 设计一个 API 网关

::: tip 一句话回答
API 网关是所有外部请求进入后端的**统一入口**，把每个服务都要做的事收拢到一处：**路由转发、鉴权、限流、熔断、协议转换、日志和指标**。核心是一条**插件链**：请求进来先匹配路由，再依次经过各插件，最后转发给上游服务。网关本身要做到**无状态、可水平扩展**，配置存在配置中心，变更**热加载**不用重启；它在每个请求的关键路径上，所以要特别注意性能和自身的高可用，不能把业务逻辑塞进去。
:::

## 详细解析

### 第一步：澄清需求

- **功能**：按域名、路径、Header 路由到不同服务；统一鉴权（JWT、API Key）；限流；超时、重试、熔断；灰度发布；请求和响应改写；访问日志和指标
- **用户**：只给自家前端用，还是开放平台要给第三方开发者用（要多一套应用管理、密钥、配额和计费）
- **非功能**：网关多出来的延迟要尽量小（毫秒级以内）；可用性要高于后端任何一个服务；路由和插件配置能动态变更

量级估算（假设值）：峰值 5 万 QPS，单个网关实例能扛 5000 QPS，按 50% 水位规划需要 20 个实例。

### 第二步：整体架构

```text
客户端 ──► DNS / 云负载均衡（四层）
              │
      ┌───────▼────────┐        ┌──────────────┐
      │ 网关集群（无状态）│◄──订阅──│ 配置中心 / 控制台 │
      │ 路由 → 插件链 → 转发 │        └──────────────┘
      └───┬──────┬─────┘
          │      │ 上游地址来自服务注册中心
     用户服务  订单服务 ...
          │
  日志 / 指标 / 链路 ──► 观测平台
```

- **数据面**：网关实例，只做请求处理，可以随时加减机器
- **控制面**：控制台和配置中心，管理路由、插件、上游；网关订阅变更，收到后在内存里原子替换路由表
- 常见选型：基于 Nginx 和 OpenResty 的（例如 Kong、APISIX），基于 Envoy 的，Java 生态的 Spring Cloud Gateway

### 第三步：核心模块和数据模型

**路由**：一条路由由匹配条件和目标组成。

| 字段 | 例子 |
| --- | --- |
| 匹配条件 | host = `api.example.com`，path 前缀 `/orders`，method = GET，Header `x-canary: 1` |
| 上游 | 服务名 `order-service`，负载均衡策略（轮询、最少连接、一致性哈希） |
| 插件 | `[jwt-auth, rate-limit, request-log]` 及各自参数 |
| 超时和重试 | 连接 1 秒，读 3 秒，只对幂等方法重试 1 次 |

路由很多时，路径匹配用前缀树（Radix Tree），不要线性遍历正则。

**插件链**：按阶段执行，任何一个插件都可以直接返回响应、中断链路。

1. 接入：TLS 终止、获取真实客户端 IP、请求体大小限制
2. 安全：IP 黑白名单、鉴权（校验 JWT 签名和过期时间，把用户 ID 放进 Header 传给后端）
3. 流量控制：限流（算法见 [Redis 限流](/basics/redis/10-rate-limit)）、熔断
4. 转发：选上游实例、改写路径和 Header、协议转换（HTTP 转 gRPC）
5. 响应：改写响应、统一错误格式、记录日志和指标

### 第四步：关键难点

**性能**

- 网关是 I/O 密集型，用事件驱动、非阻塞的模型，和上游保持长连接（连接池），避免每个请求都握手
- 插件里不要做同步的远程调用。鉴权尽量本地完成（JWT 本地验签），需要查远程的结果要缓存
- 请求体和响应体默认流式转发，不要整个读进内存，尤其是文件上传下载

**限流做在哪**：单机限流最快，但实例数变了总阈值会跟着变；全局限流要访问 Redis，多一次网络往返。常见折中是全局阈值按实例数拆成单机阈值，只对少数要求精确的接口（比如付费 API 配额）用集中式计数。

**高可用**

- 网关实例无状态，前面挂负载均衡，至少跨两个可用区部署
- 配置中心挂了，网关继续用内存里最后一份配置，不能因为拉不到配置而拒绝服务
- 每个上游独立的连接池和熔断，一个慢服务不能占满网关的连接和线程，拖垮其他服务的流量，原理见 [熔断和降级](/basics/distributed/09-circuit-breaker)

**配置变更安全**：一条写错的路由可能让全站 404。变更要有校验、灰度（先推一部分网关实例）、版本记录和一键回滚。

### 第五步：扩展与优化

- **灰度发布**：按 Header、用户 ID 哈希或比例把流量切到新版本上游
- **开放平台**：应用注册、AppKey 和签名校验、按应用配额、调用量统计
- **可观测性**：网关生成或透传 Trace ID，每个请求记录路由、上游、耗时、状态码
- **边界**：聚合多个接口、为某个端裁剪字段这类逻辑，放到 [BFF](/basics/node/17-bff) 里，不要放在网关；服务之间的内部调用由[服务网格](/basics/container/15-service-mesh)或 RPC 框架治理，不必绕回网关。大模型调用的专用网关见 [大模型网关](/engineering/system-design/05-llm-gateway)

## 面试官可能追问

::: details 网关做鉴权，后端服务还需要校验吗？
需要做最基本的保护。网关负责认证（你是谁），把可信的用户 ID 通过 Header 传下去；后端要确保只接受来自网关或内网的请求，否则别人绕过网关伪造这个 Header 就能冒充用户。资源级的授权（这个订单是不是你的）只有业务服务知道，仍然要在后端判断。
:::

::: details 网关的重试要注意什么？
只对幂等请求（GET、带幂等键的写请求）重试，POST 下单这类请求重试可能重复下单。重试要限制次数，并且换一个上游实例；整个调用链只在一层重试，否则每层重试 3 次，传到第三层就放大成 27 倍，把本来就慢的服务彻底压垮。
:::

::: details 怎么做到路由配置秒级生效又不重启？
网关启动时全量拉取配置，之后通过长轮询或 watch 订阅变更（例如 etcd 的 watch）。收到变更后在后台构建新的路由表，构建完成再用一次指针替换生效，正在处理的请求继续用旧表，不会出现半新半旧的状态。
:::

::: details 网关会不会成为单点和性能瓶颈？
网关无状态，可以水平扩展，单点问题靠多实例加负载均衡解决。瓶颈通常来自插件：同步调用远程服务、正则匹配过多、读完整个请求体。所以插件要轻、要能单独开关，网关自身也要有限流，防止流量洪峰打穿到后端。
:::

## 易错点

- 把业务逻辑写进网关，网关变成每次发版都要改的"大单体"，风险集中
- 只用单机限流却按全局阈值配置，实例扩容后实际总阈值翻倍
- 所有上游共用一个连接池和超时配置，一个慢服务拖垮整个网关
- 配置中心不可用时网关拒绝服务。正确做法是继续用最后一份可用配置
