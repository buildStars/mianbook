# 设计一个日志收集和查询系统

::: tip 一句话回答
链路是 **采集 → 缓冲 → 处理 → 存储 → 查询**：每台机器上的 **Agent** 读日志文件或容器标准输出，发到 **Kafka** 这类消息队列削峰；**处理层**做解析、结构化、脱敏；存储有两种思路：**全文倒排索引**（例如 Elasticsearch，什么都能搜，但写入和存储成本高）和**只索引标签**（例如 Loki，按服务、级别等少量标签定位，再暴力扫描内容，便宜得多）。日志量大，成本是核心问题，要靠**冷热分层、保留策略和采样**控制；高峰期宁可延迟、限流，也要明确在哪丢、丢什么。
:::

## 详细解析

### 第一步：澄清需求

- **用途**：线上排障（按 Trace ID、用户 ID、关键字查）、错误告警、简单统计；审计日志另外处理，要求不能丢
- **查询特征**：绝大多数查询集中在最近 1 天，必带时间范围和服务名；偶尔要查几周前的
- **延迟**：从打日志到能查到，几秒到几十秒
- **量级（假设值）**：1000 台机器，每台每秒 1000 行，每行 500 字节。约 100 万行/秒、500 MB/秒，每天约 43 TB 原始数据；压缩后可能剩几分之一，保留 30 天也是 PB 级

### 第二步：整体架构

```text
应用 ─► 文件 / stdout
          │
     采集 Agent（每节点一个，DaemonSet）
          │ 批量、压缩、断点续传
          ▼
     Kafka（按服务分 topic，削峰、解耦、可重放）
          │
     处理层（解析、加字段、脱敏、路由）
      ├──► 热存储：Elasticsearch / Loki（7 天）
      ├──► 冷存储：对象存储（30 天以上，压缩归档）
      └──► 实时告警（错误数、关键字匹配）
                │
           查询服务 / 控制台
```

- **采集**：Agent 例如 Filebeat、Fluent Bit、Vector。记录每个文件读到的偏移量，重启后接着读；文件轮转（`app.log` 改名成 `app.log.1`）要能跟住
- **缓冲**：Kafka 吸收流量高峰，下游存储变慢或升级时日志先堆在队列里，不会反压到应用（见 [消息积压](/basics/distributed/07-mq-order-backlog)）
- **处理**：把文本解析成结构化字段（时间、级别、服务、Trace ID、消息），去掉手机号、Token 这类敏感信息

### 第三步：核心模块和数据模型

日志在应用侧就打成**结构化的 JSON**，比事后用正则解析可靠得多（应用侧的写法见 [Node.js 日志和监控](/basics/node/19-logging-observability)）：

```json
{"ts":"2026-10-16T08:00:01.123Z","level":"error","service":"order","host":"node-17","trace_id":"4bf92f3577b34da6","msg":"pay callback timeout","order_id":"9021"}
```

两种存储方案对比：

| 对比项 | 全文索引（Elasticsearch 类） | 只索引标签（Loki 类） |
| --- | --- | --- |
| 索引内容 | 每个字段、每个词都建倒排索引 | 只对 service、level、host 等少量标签建索引，内容压缩成块存放 |
| 查询能力 | 任意关键字、字段组合快速检索，聚合统计强 | 先按标签和时间定位块，再扫描内容做过滤 |
| 写入和存储成本 | 高，索引可能和原始数据一样大 | 低，块可以放对象存储 |
| 适合 | 需要灵活检索、日志量可控 | 日志量巨大、查询基本都带服务名和时间范围 |

不管哪种，数据都**按时间分区**：Elasticsearch 按天建索引，过期直接删整个索引，比按条件删除便宜得多。

### 第四步：关键难点

**写入吞吐**：Agent 批量发送并压缩；处理层无状态，按 Kafka 分区水平扩展；Elasticsearch 写入用 bulk 批量提交，适当调大刷新间隔，让新数据晚一点可见、换取写入吞吐；标签方案要控制标签的取值数量，把用户 ID、Trace ID 当标签会让索引膨胀。

**高峰期的取舍**：某个服务死循环狂打日志，可能拖垮整个集群。要有限流：按服务设定速率上限，超出的部分采样或丢弃，并且打点记录丢了多少。级别低的 debug 日志优先丢，error 日志和审计日志不丢。应用侧日志写入要异步、有界缓冲，日志系统出问题不能阻塞业务线程。

**成本控制**

- 冷热分层：最近几天放在 SSD 的热节点，之后转到大容量盘或对象存储，查询变慢但便宜
- 保留策略按日志类型区分：调试日志 7 天，业务日志 30 天，审计日志按合规要求
- 成功请求的访问日志可以采样，只全量保留错误和慢请求

**查询体验**：强制带时间范围，默认最近 15 分钟；限制单次扫描的数据量和返回条数；常见查询（某服务错误数趋势）提前聚合成指标，不要每次去扫原始日志。

### 第五步：扩展与优化

- **和链路、指标打通**：日志带 Trace ID，从链路追踪的某个慢请求一键跳到它的全部日志；日志里的错误数转成指标，告警走指标系统
- **多租户**：按团队隔离索引或标签，分别计量存储和查询配额
- **日志转指标**：处理层实时统计关键字次数，比查询时再统计便宜

## 面试官可能追问

::: details 为什么中间要加 Kafka，Agent 直接写 Elasticsearch 不行吗？
小规模可以直接写。加 Kafka 的好处：吸收突发流量，存储集群慢了或在维护时日志先积在队列里；多个下游（存储、告警、归档）可以各自消费同一份数据；处理逻辑出 bug 时可以重置偏移量重新消费。代价是多维护一套组件，链路延迟也多一点。
:::

::: details 容器里的日志怎么收集？
应用把日志写到标准输出，容器运行时把它落成节点上的文件（`/var/log/containers/` 下）。每个节点用 DaemonSet 跑一个 Agent 读这些文件，同时从 Kubernetes API 拿到 Pod 名、命名空间、标签，加到每条日志上。不推荐在每个 Pod 里塞一个日志 Sidecar，除非应用只能写文件。
:::

::: details 怎么保证日志不丢？
做不到完全不丢，要看代价。Agent 记录偏移量、确认发送成功再推进；Kafka 配置副本和 `acks=all`（见 [消息不丢失](/basics/distributed/05-mq-reliability)）；消费者写入存储成功后再提交偏移量。最容易丢的环节是应用进程崩溃时内存缓冲里还没写盘的那部分。审计这类不能丢的日志，最好走单独的可靠通道，而不是和普通日志混在一起。
:::

## 易错点

- 日志打成自由文本，事后用正则解析，格式一改解析就断
- 把用户 ID、请求 ID 这类高基数的值当成索引标签，索引膨胀、查询变慢
- 应用同步写远程日志服务，日志系统一慢，业务接口跟着超时
- 只按条件删除过期日志，不按时间分区，清理本身就把集群压垮
