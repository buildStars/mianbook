# 进程调度算法有哪些？Linux 的 CFS 是怎么调度的？

::: tip 一句话回答
经典调度算法有 **FCFS（先来先服务）、SJF（短作业优先）、优先级调度、时间片轮转（RR）和多级反馈队列（MLFQ）**，区别在于怎么在吞吐量、平均等待时间和响应速度之间取舍。按能否打断正在运行的进程，又分**抢占式**和**非抢占式**。Linux 的普通进程用 **CFS（完全公平调度）**：给每个进程记一个**虚拟运行时间 vruntime**，权重越高（nice 越小）vruntime 涨得越慢，进程按 vruntime 放在**红黑树**里，每次挑 vruntime 最小的最左节点运行。实时进程走单独的调度类（SCHED_FIFO、SCHED_RR），优先级高于所有普通进程。
:::

## 详细解析

### 经典调度算法

| 算法 | 规则 | 优点 | 问题 |
| --- | --- | --- | --- |
| FCFS | 按到达顺序，跑完才换下一个 | 简单、公平 | 长作业挡住后面的短作业（护航效应） |
| SJF / SRTF | 估计运行时间最短的先跑；SRTF 是抢占版 | 平均等待时间最优 | 运行时间要预估；长作业可能饿死 |
| 优先级 | 优先级高的先跑 | 能区分重要程度 | 低优先级饿死，常配合"老化"逐步提升 |
| 时间片轮转 | 每个进程跑一个时间片，用完排到队尾 | 响应快，适合交互 | 时间片太小切换开销大，太大退化成 FCFS |
| 多级反馈队列 | 多个优先级队列，新进程进高优先级队列，用完时间片就降级 | 不用预估时长，短任务和交互任务自然优先 | 参数多，需要定期提升防止饿死 |

多级反馈队列的思路很实用：系统不知道一个进程要跑多久，就先假设它是短任务给高优先级；如果它总把时间片用光，说明是 CPU 密集型，逐级降低；经常主动让出 CPU 的 I/O 密集型进程留在高优先级，响应就快。

### 抢占和非抢占

- **非抢占**：进程只会在主动阻塞、退出时让出 CPU，FCFS 和 SJF 是典型
- **抢占**：时间片用完、更高优先级的进程就绪时，内核可以打断当前进程。现代通用操作系统都是抢占式的

抢占意味着发生上下文切换，切换本身的代价见[上下文切换](/basics/os/08-context-switch)。

### CFS：用虚拟运行时间追求公平

CFS 的目标是让每个进程"理想情况下同时拿到 1/n 的 CPU"。做法是为每个进程记录 vruntime：

```text
vruntime += 实际运行时间 × (nice 0 的权重 / 本进程的权重)
```

- nice 值范围 -20 到 19，默认 0。nice 越小权重越大，vruntime 增长越慢，于是更常被选中
- 相邻 nice 值的权重大约差 1.25 倍，设计上每差 1 级 CPU 占比差 10% 左右
- 就绪进程按 vruntime 存在红黑树里，最左节点（vruntime 最小）就是下一个要跑的，内核缓存了这个节点，找到它是 O(1)，插入和删除是 O(log n)

几个细节：

1. **没有固定时间片**：CFS 在一个调度周期里按权重给每个进程分配运行时间，进程越多每份越小，但有最小粒度下限，防止切换过频
2. **新进程和唤醒的进程**：vruntime 不是从 0 开始，而是参考队列里的最小 vruntime 设置，否则一个睡了很久的进程醒来会长时间独占 CPU
3. **I/O 密集型进程天然占优**：它们经常睡眠，vruntime 涨得慢，醒来后排在前面，交互响应好

较新的内核把普通进程的调度算法换成了 EEVDF，它仍然基于虚拟运行时间和红黑树，额外考虑了延迟要求。面试时讲清 CFS 的思路就够了。

### 调度类和实时进程

Linux 按调度类分层，高层有可运行任务时低层不会被调度：

```text
stop > deadline（SCHED_DEADLINE） > 实时（SCHED_FIFO / SCHED_RR） > 普通（SCHED_OTHER / SCHED_BATCH） > idle
```

- **SCHED_FIFO**：同优先级先来先跑，不主动让出就一直跑
- **SCHED_RR**：同优先级之间时间片轮转
- 实时优先级 1～99，和 nice 是两套体系

```bash
# 查看进程的调度策略和优先级
chrt -p 1234
# 以 nice 10 启动低优先级任务；renice 调整运行中的进程
nice -n 10 ./backup.sh
renice -n 5 -p 1234
# NI 列是 nice 值，PRI 列是内核视角的优先级
ps -o pid,ni,pri,cls,comm -p 1234
```

## 面试官可能追问

::: details 实时进程写了死循环，会把机器卡死吗？
默认不会完全卡死。内核有实时任务限流：`/proc/sys/kernel/sched_rt_runtime_us` 和 `sched_rt_period_us` 默认值是 950000 和 1000000，表示每秒最多给实时任务 0.95 秒，剩下的时间留给普通进程，让你还能登录处理。把 runtime 设成 -1 就取消限制，这很危险。
:::

::: details nice 值调低就一定跑得更快吗？
不一定。nice 只影响 CPU 竞争时的分配比例，机器空闲时 nice 19 的进程也能跑满一个核。如果瓶颈在磁盘或锁上，调 nice 没有作用。另外普通用户只能调高 nice（降低优先级），调低需要 root 或 CAP_SYS_NICE 权限。
:::

::: details 容器里的 CPU 限制和 CFS 有什么关系？
cgroup 的 CPU 限制就是 CFS 的带宽控制：在一个周期里给 cgroup 分配一定配额，用完就被限流，等下个周期。Kubernetes 的 CPU limit 就是这样实现的，所以 limit 设得太紧会出现周期性的延迟毛刺，见 [Pod 资源配置](/basics/container/08-k8s-resources)。
:::

## 易错点

- 把 nice 当成实时优先级：nice 只在普通调度类里起作用，nice -20 的进程也会被任意实时进程抢占
- 认为 CFS 有固定的时间片：它按权重和就绪进程数动态分配运行时间
- 把 vruntime 理解成真实运行时间：它是按权重缩放后的值，高权重进程的 vruntime 涨得慢
- 说 SJF 是"最好的算法"：它只在平均等待时间上最优，前提是知道运行时间，还会饿死长作业
