# fork 和 exec 是怎么创建进程的？写时复制是什么？

::: tip 一句话回答
Linux 创建新程序分两步：**fork** 复制当前进程得到子进程，它**调用一次返回两次**，父进程拿到子进程的 PID，子进程拿到 0；**exec** 用一个新程序替换当前进程的代码、数据和栈，PID 不变。Shell 执行命令就是 **fork + exec + wait**。fork 不会立刻复制内存，而是用**写时复制（COW）**：父子进程共享同一批物理页，页表都标成只读，谁先写某一页就触发缺页异常，内核才把这一页复制一份。Redis 的 BGSAVE 和 AOF 重写就靠 fork 拿到内存快照。
:::

## 详细解析

### fork：调用一次，返回两次

fork 之后有两个几乎一样的进程从同一个位置继续执行，区别只在返回值：

- 返回值 > 0：当前是父进程，返回值是子进程 PID
- 返回值 = 0：当前是子进程，可以用 `getppid()` 拿父进程 PID
- 返回值 < 0：创建失败，比如进程数达到上限或内存不足

子进程继承父进程的地址空间副本、打开的文件描述符（指向同一个打开的文件，共享偏移量）、环境变量、工作目录、信号处理设置；不继承的有 PID、父进程 ID、挂起的信号、文件锁等。多线程程序 fork 后，子进程里只有调用 fork 的那个线程，其他线程持有的锁会永远处于加锁状态，所以多线程程序 fork 后应尽快 exec。进程和线程的区别见[进程、线程和协程](/basics/os/01-process-thread)。

### exec：换掉整个程序

exec 是一组函数（`execve` 是底层系统调用，`execl`、`execvp` 等是包装），它加载新的可执行文件，替换当前进程的代码段、数据段、堆和栈，然后从新程序的入口开始执行。PID 不变，已打开的 fd 默认保留（设置了 `FD_CLOEXEC` 的会被关闭）。exec 成功就不会返回，返回了说明失败。

Shell 执行 `ls -l` 的过程：

```text
shell                     子进程
  │ fork() ──────────────▶ │ （shell 的副本）
  │                        │ 处理重定向：dup2 把 fd 1 指向文件
  │ waitpid() 等待          │ execvp("ls", ...) → 变成 ls
  │                        │ 运行，exit(0)
  │ ◀──── 回收，拿到退出码 ──┘
```

把创建进程和加载程序拆开，好处是中间可以在子进程里调整环境：重定向、管道、改工作目录、降权限，都在 fork 后、exec 前完成。父进程不 `wait` 的话，子进程退出后会变成僵尸，见[进程状态和僵尸进程](/basics/os/11-process-state-zombie)。

### 写时复制怎么工作

1. fork 时内核复制父进程的页表，不复制物理页，并把父子双方可写页的页表项都改成**只读**
2. 任何一方读这些页，正常访问共享的物理页
3. 任何一方写某一页，触发缺页异常；内核发现这是 COW 页，分配新物理页、复制内容、把写的一方的页表项指向新页并恢复可写
4. 如果某页只剩一个使用者，直接恢复可写，不用复制

这样 fork 的成本主要是复制页表，紧接着 exec 时几乎没有浪费。缺页异常的机制见[虚拟内存](/basics/os/03-virtual-memory)。镜像层的写时复制是文件系统层面的另一回事，见[镜像分层](/basics/container/02-image-layers)。

### vfork 和 posix_spawn

- **vfork**：子进程直接借用父进程的地址空间，父进程挂起，直到子进程 exec 或 `_exit`。比 fork 还省，但子进程改了内存会影响父进程，很容易出错
- **posix_spawn**：把 fork + exec 打包成一个调用，由 C 库选择高效的实现（Linux 的 glibc 用 `clone` 加 `CLONE_VM | CLONE_VFORK`）。大内存进程频繁起子进程时比 fork 合适，因为不用复制巨大的页表

### 实际影响

**Redis 持久化**：BGSAVE 和 AOF 重写时 fork 子进程，子进程看到的是 fork 那一刻的内存快照，慢慢写到磁盘；父进程照常处理请求。问题有两个：fork 本身要复制页表，内存越大耗时越长，期间主线程阻塞；写请求多时被修改的页都要复制，最坏接近翻倍，所以要预留内存。开启透明大页时，改一个字节也要复制 2MB 的大页，Redis 官方建议关闭透明大页。详见 [RDB 和 AOF](/basics/redis/04-persistence)。

**Node.js**：`child_process.fork()` 不是系统调用 fork，而是启动一个新的 Node 进程运行指定脚本，并建立 IPC 通道，子进程不共享父进程的内存状态。

## 面试官可能追问

::: details fork 之后父子进程谁先运行？
不确定，由调度器决定，程序不能依赖顺序。需要同步就用 `wait`、管道或信号。
:::

::: details 为什么 Redis 推荐 vm.overcommit_memory = 1？
fork 一个占 10GB 的进程时，按 COW 实际不会立刻用到 10GB，但在默认的启发式策略下，内核可能认为可用内存不足，导致 fork 失败。设成 1 让内核总是允许分配，Redis 的 BGSAVE 就不会因此失败；代价是内存真不够时由 OOM Killer 处理。
:::

::: details 为什么 fork 之后父进程大量写内存会变慢？
每写一个还在共享的页就触发一次缺页异常加一次页复制，这些都在内核里同步完成。父进程写得越分散，复制的页越多，延迟和内存同时上升。
:::

## 易错点

- 说 fork 会把父进程的内存完整复制一遍：现代系统都是写时复制，复制的是页表
- 以为 exec 会创建新进程：exec 不改 PID，只替换当前进程的程序
- 把 Node.js 的 `child_process.fork()` 当成系统调用 fork：它启动的是全新的 Node 进程
- 多线程程序 fork 后在子进程里继续用锁或调用非异步信号安全的函数，可能死锁
