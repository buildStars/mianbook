# 线程同步有哪些方式？互斥锁、自旋锁、信号量、条件变量有什么区别？

::: tip 一句话回答
**互斥锁**保证同一时刻只有一个线程进临界区，抢不到就**睡眠**让出 CPU；**自旋锁**抢不到就**忙等**，适合极短的临界区，省掉睡眠和唤醒的切换开销；**信号量**是一个计数器，控制**最多 N 个**线程同时访问资源；**条件变量**用来**等待某个条件成立**，必须配合互斥锁使用，被唤醒后要用 **while 重新检查**条件。读多写少时还可以用**读写锁**。
:::

## 详细解析

### 为什么需要同步

多个线程共享同一进程的内存。像 `count++` 这样的操作实际是"读、加、写"三步，两个线程交错执行就会丢失更新。需要同步的场景有两类：**互斥**（同一时刻只能一个线程改）和**协作**（一个线程要等另一个线程做完某件事）。进程之间的通信方式是另一个话题，见 [进程间通信有哪些方式](/basics/os/02-ipc)。

### 几种原语对比

| 原语 | 语义 | 抢不到时 | 适用场景 |
| --- | --- | --- | --- |
| 互斥锁 | 只有一个持有者，谁加锁谁解锁 | 线程睡眠，等唤醒 | 通用的临界区保护 |
| 自旋锁 | 只有一个持有者 | 循环检查，占着 CPU | 临界区极短、多核、不能睡眠的场合（如内核中断上下文） |
| 读写锁 | 读读并发，读写、写写互斥 | 睡眠 | 读多写少的共享数据 |
| 信号量 | 计数器，P 操作减 1，V 操作加 1，减到 0 时阻塞 | 睡眠 | 限制并发数、资源池、生产者消费者计数 |
| 条件变量 | 等待某个条件，被其他线程通知唤醒 | 睡眠，同时释放互斥锁 | 等队列非空、等任务完成 |

### 互斥锁和自旋锁怎么选

互斥锁抢不到时要陷入内核、把线程挂起，之后再被唤醒，一来一回是两次上下文切换（开销见 [上下文切换](/basics/os/08-context-switch)）。如果临界区只有几条指令，锁很快就会释放，这些切换比等待本身还贵，自旋更划算。

反过来，临界区长或者持锁线程可能被调度走时，自旋就是在白白烧 CPU。单核上自旋更没有意义，持锁的线程得不到 CPU 就没法释放锁。实际很多互斥锁的实现是混合的：先自旋一小会儿，还拿不到再睡眠，Linux 的 futex 就是这种思路的基础。

### 信号量和互斥锁的区别

- 信号量的初值可以是 N，允许 N 个线程同时进入；初值为 1 的二元信号量看起来像互斥锁
- 互斥锁有"所有者"，只能由加锁的线程解锁；信号量没有所有者，A 线程 P、B 线程 V 是正常用法，所以它能用来做线程间的通知

### 条件变量的正确用法

条件变量本身不存状态，它只负责"睡下"和"叫醒"，条件要放在被互斥锁保护的共享变量里。`wait` 会**原子地**释放锁并睡眠，被唤醒后重新拿到锁才返回。

必须用 while 而不是 if 检查条件，原因有两个：

1. **虚假唤醒**：标准允许 `wait` 在没人通知时返回
2. **被抢先**：多个等待者被 `broadcast` 一起叫醒，第一个拿到锁的已经把队列里的数据取走了，后面的再取就是空的

## 代码示例

用 POSIX 线程写一个阻塞队列的取数据部分：

```c
#include <pthread.h>

pthread_mutex_t mu = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_empty = PTHREAD_COND_INITIALIZER;
int queue[100];
int count = 0;

int take(void) {
    pthread_mutex_lock(&mu);
    // ✅ 用 while：被唤醒后条件可能又不成立了
    while (count == 0) {
        // 原子地释放 mu 并睡眠，返回前重新持有 mu
        pthread_cond_wait(&not_empty, &mu);
    }
    int v = queue[--count];
    pthread_mutex_unlock(&mu);
    return v;
}

void put(int v) {
    pthread_mutex_lock(&mu);
    queue[count++] = v; // 简化示例，省略队列满的判断
    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&mu);
}
```

## 面试官可能追问

::: details 为什么条件变量要和互斥锁一起用？
检查条件和进入睡眠必须是一个整体。如果不加锁，线程刚检查完 `count == 0`、还没睡下，另一个线程就放入数据并发了通知，这次通知就丢了，等待者可能永远睡下去。`wait` 在持锁状态下原子地释放锁并睡眠，就堵住了这个窗口。
:::

::: details 读写锁有什么问题？
读线程源源不断时，写线程可能一直拿不到锁，出现写饥饿。很多实现提供写优先选项：有写者在等时，新来的读者也要排队。读写锁本身比互斥锁复杂，读操作很短时性能未必更好，要实测。
:::

::: details 这些原语和 Java、Go 里的锁是什么关系？
语言层的锁大多建在这些原语之上。Java 的 `synchronized` 和 `ReentrantLock` 见 [synchronized 和 ReentrantLock 的区别](/basics/java/06-synchronized-lock)，Go 的 `sync.Mutex`、`sync.Cond` 见 [Go 的并发同步手段](/basics/go/08-sync-context)。跨进程、跨机器的互斥要用分布式锁，见 [Redis 分布式锁](/basics/redis/07-distributed-lock)。
:::

## 易错点

- 条件变量等待时用 if 判断条件是常见 bug，必须用 while
- 自旋锁不是"更快的互斥锁"，临界区一长就是浪费 CPU
- 信号量没有所有者，可以由其他线程释放；互斥锁只能由持有者释放
- 锁的粒度和加锁顺序没处理好会导致死锁，见 [死锁是怎么产生的](/basics/os/04-deadlock)
