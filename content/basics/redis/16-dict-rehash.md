# Redis 的字典是怎么实现的？渐进式 rehash 是怎么做的？

::: tip 一句话回答
Redis 的字典是**数组 + 链表**的哈希表，冲突用**链地址法**解决。每个字典里有**两张哈希表**，平时只用第一张；扩容或缩容时分配第二张，然后**渐进式 rehash**：不一次性搬完，而是在每次增删改查时顺手搬一个桶，再加上定时任务每次搬一小段时间，搬完后两张表交换角色。这样即使字典有上千万个 key，也不会因为一次 rehash 把主线程卡住。
:::

## 详细解析

### 结构

字典是整个数据库（所有 key）的底层结构，也是 Hash、Set 在元素多时的编码（编码切换见 [数据类型](/basics/redis/03-data-structures)）。

```text
dict
├── ht[0]: table ──> [0] -> entry(k1,v1) -> entry(k5,v5) -> NULL
│                    [1] -> NULL
│                    [2] -> entry(k2,v2) -> NULL
│                    [3] -> NULL
├── ht[1]: 平时为空，rehash 时才分配
└── rehashidx: -1 表示没在 rehash；否则表示 ht[0] 下一个要搬的桶下标
```

- 桶数组大小总是 **2 的幂**，下标用 `hash & (size - 1)` 算，比取模快
- 冲突的节点挂成单向链表，新节点插在**链表头部**，插入是 O(1)
- 哈希函数用 SipHash，能抵御针对哈希表的碰撞攻击

### 什么时候扩容、缩容

负载因子 = 已有节点数 / 桶数。

| 情况 | 触发条件 |
| --- | --- |
| 扩容 | 负载因子达到 1，且当前**没有** BGSAVE / BGREWRITEAOF 子进程 |
| 强制扩容 | 有子进程，但负载因子已经远大于 1（源码里有一个强制阈值，不同版本取值不同） |
| 缩容 | 节点数远小于桶数（填充率低到大约一成），由定时任务检查 |

为什么有子进程时尽量不扩容？子进程靠 fork 的**写时复制**共享内存，rehash 会大量改写内存页，导致页被复制，内存占用飙升。所以这时宁可让链表长一点（持久化原理见 [RDB 和 AOF](/basics/redis/04-persistence)）。

新表大小是 2 的幂，扩容时大约翻倍，缩容时缩到刚好能装下现有节点。

### 渐进式 rehash 的流程

1. 给 `ht[1]` 分配新的桶数组，`rehashidx` 置为 0，rehash 开始
2. 之后每次对这个字典做增删改查，都顺带把 `ht[0]` 第 `rehashidx` 号桶上的整条链表搬到 `ht[1]`，然后 `rehashidx++`
3. 遇到空桶会跳过，但单步最多只看有限个空桶，避免一次扫描太久
4. 服务器定时任务里也会对正在 rehash 的字典集中搬一会儿（每次约 1 毫秒），防止一个没人访问的字典永远搬不完。由 `activerehashing` 配置控制，默认开启
5. `ht[0]` 搬空后释放它，把 `ht[1]` 变成 `ht[0]`，`rehashidx` 置回 -1

### rehash 期间的读写

| 操作 | 做法 |
| --- | --- |
| 查找、更新、删除 | 先查 `ht[0]`，找不到再查 `ht[1]` |
| 新增 | 只写入 `ht[1]`，保证 `ht[0]` 只减不增，最终一定能搬空 |
| 遍历（SCAN） | 游标设计考虑了两张表并存，保证 rehash 前就存在的 key 至少返回一次，但可能重复 |

代价是 rehash 期间两张表同时占内存，查找最坏要查两张表。

## 面试官可能追问

::: details 为什么不像 Java HashMap 那样一次性扩容？
Redis 命令在单线程里执行（见 [Redis 为什么快](/basics/redis/02-why-fast)）。一个有几千万 key 的字典一次性 rehash 可能要几百毫秒甚至更久，这段时间所有请求都会卡住。渐进式把成本摊到每次操作上，每次只多花一点点时间。
:::

::: details rehash 会导致内存突然上涨吗？
会。扩容时要一次性分配新桶数组，大约是原数组的两倍，key 很多时这块内存不小。如果实例开了 maxmemory，这一下可能触发淘汰。较新的版本在内存紧张时会推迟扩容，具体策略跟版本有关。
:::

::: details SCAN 为什么可能返回重复的 key？
SCAN 的游标是按桶的高位反向递增的，这样表扩容或缩容后，已经扫过的桶在新表里对应的位置仍然被视为"已扫过"，不会漏 key。代价是缩容时几个旧桶合并成一个新桶，部分 key 会被再次返回，所以业务要自己去重。
:::

## 易错点

- 渐进式 rehash 不是"后台线程慢慢搬"，主要是**在命令执行时顺手搬**，再加主线程定时任务兜底
- rehash 期间新增只写新表，查找要两张表都查；不要说成"只查新表"
- 有子进程时不是完全禁止扩容，而是提高了触发门槛
