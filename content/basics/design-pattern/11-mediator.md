# 中介者模式是什么？和观察者模式有什么区别？

::: tip 一句话回答
中介者模式把一组对象之间**多对多的直接引用**，改成**都只和一个中介者打交道**：对象有变化就告诉中介者，由中介者决定通知谁、做什么。它把散落在各处的协作逻辑集中到一处，适合表单联动、聊天室、多个组件互相协调这类场景。和观察者模式的区别在于：观察者只负责"广播变化"，不关心谁怎么处理；中介者**知道所有参与者，并主动编排它们的行为**。风险是中介者越写越大，变成上帝对象。
:::

## 详细解析

### 解决什么问题

一个下单表单：选了"国家"要刷新"省份"，选了"配送方式"要重算"运费"，"优惠券"要看"商品金额"，提交按钮要看所有字段是否合法。如果每个字段组件直接引用其他字段：

```text
没有中介者：每个字段互相引用，N 个对象最多 N×(N-1) 条依赖
国家 ⇄ 省份 ⇄ 运费 ⇄ 优惠券 ⇄ 提交按钮（还有交叉连线）

有中介者：每个字段只认识中介者，N 条依赖
国家 ─┐
省份 ─┼─> 表单中介者 ─> 决定联动规则
运费 ─┤
提交 ─┘
```

加一个字段、改一条联动规则，只需要改中介者，各个字段组件保持独立、可复用。

### 常见例子

- **表单联动**：字段只上报 `change`，联动规则写在表单控制器里
- **聊天室**：用户不直接给别的用户发消息，而是发给聊天室，由聊天室转发、过滤、记录
- **组件协调**：一个页面的筛选栏、列表、分页、详情面板，由父组件或页面级控制器统一协调
- **航空管制**：经典比喻，飞机之间不直接通信，都听塔台的

前端里很多时候"父组件"本身就在扮演中介者：子组件通过事件上报，父组件决定要更新哪些子组件的 props。

### 和观察者、发布订阅的区别

| 维度 | 观察者 / 发布订阅 | 中介者 |
| --- | --- | --- |
| 通信方向 | 一对多，单向广播 | 多对多，经中介集中 |
| 中心是否懂业务 | 不懂，只负责分发 | 懂，包含协作规则 |
| 参与者关系 | 发布者不知道谁在听 | 中介者知道所有参与者 |
| 关注点 | 解耦"通知"这件事 | 解耦对象之间的交互逻辑 |

[观察者和发布订阅](/basics/design-pattern/02-observer-pubsub) 里的事件中心只是"邮局"，收到什么就转发什么；中介者是"调度员"，会根据谁发来什么消息，决定让谁做什么。实现上中介者内部经常用事件机制，但是否包含协作逻辑才是区分点。

### 上帝对象的风险

所有交互都集中到中介者，它会变成一个知道所有事、谁都离不开的大对象，难测试、难修改。应对办法：

- 按业务边界拆成多个中介者，比如"地址联动"和"价格计算"分开
- 中介者只做协调，具体计算逻辑放回各自模块或抽成纯函数
- 联动规则多时，用配置表描述规则，中介者只负责执行

## 代码示例

```js
class ChatRoom {
  constructor() { this.users = new Map() }
  join(user) {
    this.users.set(user.name, user)
    user.room = this
  }
  // 协作规则集中在这里：私聊、群发、屏蔽
  send(from, text, to) {
    if (text.includes('广告')) return from.receive('系统', '消息被拦截')
    const targets = to ? [this.users.get(to)] : [...this.users.values()]
    targets.filter((u) => u && u !== from).forEach((u) => u.receive(from.name, text))
  }
}

class User {
  constructor(name) { this.name = name }
  say(text, to) { this.room.send(this, text, to) } // 只认识聊天室
  receive(from, text) { console.log(`[${this.name}] ${from}: ${text}`) }
}

const room = new ChatRoom()
const [a, b, c] = ['小王', '小李', '小张'].map((n) => new User(n))
;[a, b, c].forEach((u) => room.join(u))
a.say('大家好')      // 小李、小张都收到
b.say('私聊你', '小王') // 只有小王收到
c.say('看广告')      // 小张收到系统提示
```

## 面试官可能追问

::: details Vuex、Redux 这类全局 store 算中介者吗？
有相似之处：组件不直接互相修改，而是通过 store 交互。但 store 主要是"集中的状态 + 订阅通知"，更接近观察者；组件之间的协调规则一般不写在 store 里。如果在 store 的 action 里编排多个模块的联动，那部分就有中介者的味道。
:::

::: details 中介者和外观模式（Facade）有什么区别？
外观是给一个复杂子系统提供简化的入口，通信是单向的：外部调用外观，外观调用子系统。中介者是让一组平级对象互相协作，通信是双向的：参与者会主动通知中介者，中介者也会反过来调用参与者。
:::

::: details 什么时候不该用中介者？
对象之间只有一两条简单依赖时，直接调用更清晰，加中介者只会多一层跳转。只是需要"某件事发生后通知一批人"，用观察者就够了。中介者适合交互规则多、经常变、牵涉多个对象的场景。
:::

## 易错点

- 把"有个事件中心"就当成中介者：只转发不编排的是发布订阅
- 中介者里堆满业务计算，最后谁都不敢改，要按业务边界拆分
- 参与者绕过中介者直接互相调用，模式就失去了意义
