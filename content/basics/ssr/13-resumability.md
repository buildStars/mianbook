# 可恢复性（Resumability）是什么？和水合有什么区别？

::: tip 一句话回答
水合是服务端渲染出 HTML 后，客户端**再把组件代码下载并执行一遍**，重建组件树、绑定事件，页面才能交互。可恢复性是 Qwik 提出的思路：服务端把**应用状态和事件监听的位置序列化进 HTML**，客户端不重新执行组件，只用一个很小的全局监听器等待交互，用户点了哪里才去**按需加载那一小段处理函数**。它省掉了启动时的执行成本，代价是首次交互时可能要等代码下载。
:::

## 详细解析

### 水合到底贵在哪

服务端已经把 HTML 渲染好了，但浏览器拿到的只是"死"的 DOM。框架要让它活起来，水合需要：

1. 下载整个页面用到的组件代码
2. 从根组件开始**重新执行**一遍渲染函数，重建组件树和响应式状态
3. 把生成的虚拟 DOM 和已有 DOM 对上，绑定事件监听

服务端已经做过一遍的工作，客户端又做了一遍。页面越大，下载、解析、执行的 JS 越多，"看得见但点不动"的时间越长。水合不匹配的问题见 [水合不匹配](/basics/ssr/02-hydration-mismatch)。

### 可恢复性怎么做

Qwik 的思路是：既然服务端已经执行过，就把执行的"结果"完整带到客户端，让客户端从断点**继续**，而不是从头**重放**。

- **序列化状态**：组件状态、响应式依赖关系写进 HTML 里的 JSON
- **序列化监听**：事件处理函数不在启动时注册，而是在 DOM 上记录"这个事件对应哪个代码块"
- **全局事件委托**：页面只加载一个很小的脚本，在 document 上监听事件；用户点击时，根据元素上的记录找到并下载对应的处理函数，再从 HTML 里恢复所需的状态去执行
- **细粒度拆包**：编译器把每个事件处理函数、组件拆成独立的懒加载块

```text
水合：     下载全部 JS → 执行所有组件 → 绑定事件 → 可交互
可恢复性： 加载极小的加载器 → 可交互（点击时）→ 下载这个处理函数 → 执行
```

启动成本和页面大小基本无关，只和用户实际交互的部分有关。

### 和其他方案对比

| 方案 | 核心做法 | 客户端执行什么 |
| --- | --- | --- |
| 全量水合 | 整页组件重新执行 | 所有组件 |
| 部分水合 / [岛屿架构](/basics/ssr/08-islands) | 静态部分不发 JS，只水合交互"岛" | 每个岛内的全部组件 |
| [React Server Components](/basics/react/11-server-components) | 服务端组件不发代码，客户端组件照常水合 | 所有客户端组件 |
| 可恢复性 | 不水合，交互时按需加载处理函数 | 只有被触发的处理函数 |

前三种是"减少要水合的东西"，可恢复性是"不做水合"。岛屿架构需要开发者手动标出哪些组件要交互，可恢复性由编译器自动拆分。

### 代价

- **首次交互延迟**：点击时才下载代码，网络差会感到卡顿。通常会在空闲时或通过 Service Worker 预取，缓解但不能完全消除
- **HTML 变大**：序列化的状态和监听记录都在 HTML 里
- **编程约束**：跨越懒加载边界的闭包必须可序列化，不能随意捕获函数、类实例、DOM 引用，编译器会报错提醒
- **生态**：思路比较新，和 React、Vue 的生态不能直接复用

## 面试官可能追问

::: details 为什么 React 或 Vue 很难做到可恢复？
它们的组件状态存在运行时的闭包和组件实例里，事件监听也是渲染时才知道的。不把组件重新执行一遍，客户端就无法得到这些信息。可恢复性需要编译器从一开始就把代码按序列化边界拆开，是框架层面的设计选择，很难事后补上。
:::

::: details 可恢复性和懒加载组件有什么区别？
懒加载组件（`import()` 拆包）只是推迟下载，组件一旦加载仍要执行并水合。可恢复性连执行都省了：状态从 HTML 里直接恢复，粒度细到单个事件处理函数，而不是整个组件。
:::

::: details 什么场景适合可恢复性？
内容多、交互稀疏、很在意首屏可交互时间的页面，比如电商落地页、营销页、内容站。交互密集、打开后马上要全面操作的应用（在线编辑器、后台系统），所有代码迟早都要加载，优势就不明显了。
:::

## 易错点

- 把可恢复性理解成"更快的水合"：它的核心是不在启动时重新执行组件
- 以为可恢复性没有代价：首次交互要下载代码，必须配合预取
- 把岛屿架构和可恢复性混为一谈：岛屿内部仍然是常规水合
