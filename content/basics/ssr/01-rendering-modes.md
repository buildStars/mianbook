# CSR、SSR、SSG、ISR 有什么区别？怎么选？

::: tip 一句话回答
四种模式的区别在于 **HTML 在什么时候、在哪里生成**。**CSR** 由浏览器执行 JS 生成，服务器只返回一个空壳；**SSR** 在每次请求时由服务器生成；**SSG** 在构建时一次性生成，部署成静态文件；**ISR** 是 SSG 加上"过期后在后台重新生成"，静态页面也能定期更新。选择时看两点：内容是否因人而异、多久变一次。后台系统用 CSR，文档博客用 SSG，内容站和电商列表用 ISR 或 SSR 加缓存，强个性化的页面用 SSR；主流框架都支持**按路由混合使用**。
:::

## 详细解析

### 四种模式的流程

```text
CSR：请求 → 返回几乎为空的 HTML 和 JS → 下载执行 JS → 请求接口 → 渲染出内容
SSR：请求 → 服务器取数据、渲染出完整 HTML → 浏览器显示 → 下载 JS → 水合后可交互
SSG：构建时取数据、生成所有页面的 HTML → 部署到 CDN → 请求直接返回文件 → 水合
ISR：首次和 SSG 一样 → 过期后的下一个请求先拿到旧页面，同时后台重新生成 → 之后的请求拿到新页面
```

- CSR 的首屏要等 JS 下载、执行、接口返回三步，白屏时间长，但服务器只需要托管静态资源
- SSR、SSG、ISR 在浏览器端都要**水合**：HTML 先显示出来，JS 加载完才能交互，见 [SSR 和水合](/basics/vue/18-ssr-hydration)
- ISR 的"过期后先返回旧内容、后台更新"就是 stale-while-revalidate 策略。除了按时间过期，也可以在内容变更后**按需**让某个页面失效

React Server Components 是另一个维度的问题：它决定哪些组件的代码不用下发到浏览器，可以和 SSR、SSG 组合使用，见 [Server Components](/basics/react/11-server-components)。

### 对比

| | CSR | SSR | SSG | ISR |
| --- | --- | --- | --- | --- |
| HTML 生成时机 | 浏览器运行时 | 每次请求 | 构建时 | 构建时，过期后后台重建 |
| 首屏内容 | 慢，要等 JS 和接口 | 较快，受服务端取数和渲染耗时影响 | 最快，CDN 直接返回 | 命中缓存时和 SSG 一样快 |
| 可交互时间 | JS 执行完即可交互 | 要等水合 | 要等水合 | 要等水合 |
| 服务器成本 | 低，只放静态文件 | 高，每个请求都要渲染 | 最低 | 低，只是偶尔重建 |
| SEO | 差，首次 HTML 没有内容 | 好 | 好 | 好 |
| 数据新鲜度 | 实时，客户端请求 | 实时 | 停留在构建时 | 最多延迟一个过期周期 |
| 个性化内容 | 支持 | 支持 | 只能在客户端再请求 | 只能在客户端再请求 |

### 按场景选择

- **后台管理系统、内部工具**：CSR。要登录才能用，不需要 SEO，用户会长时间停留，首屏慢一点可以接受，部署也最简单
- **文档、博客、官网、营销页**：SSG。所有人看到的内容一样、更新不频繁，构建一次放到 CDN 上，又快又便宜
- **内容站、电商商品列表和详情**：页面多、需要 SEO、内容会变但能接受几分钟的延迟，用 ISR；或者用 SSR 并让 CDN 缓存一小段时间，效果相近
- **强个性化页面**：购物车、个人中心、推荐流，每个人看到的都不一样，用 SSR 且不能进共享缓存；也可以外壳静态化，个性化部分在客户端请求

还有两个要考虑的因素：页面数量特别多（几十万个商品）时，SSG 的构建时间会很长，可以用 ISR 只预生成热门页面，其余的在第一次访问时生成；价格、库存这类实时性要求高的字段，即使页面用了 ISR，也可以在客户端单独请求。

### 同一个应用按路由混合

同一个应用里不同页面的需求不同，Next.js、Nuxt 等框架都支持按路由选择渲染方式。以 Nuxt 的 routeRules 为例：

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true }, // 构建时生成（SSG）
    '/docs/**': { prerender: true },
    '/products/**': { isr: 3600 }, // 缓存到 CDN，过期后后台重建，需要部署平台支持
    '/blog/**': { swr: 600 }, // 在服务端缓存 10 分钟，过期后先返回旧内容再更新
    '/admin/**': { ssr: false }, // 只在浏览器渲染（CSR）
  },
})
```

Next.js 会根据页面是否用到 Cookie、请求头这类请求相关的数据，以及数据请求的缓存设置，决定在构建时还是请求时渲染，规则见 [Next.js 的缓存](/basics/ssr/05-next-caching)。

## 面试官可能追问

::: details SSR 一定比 CSR 快吗？
不一定。SSR 让**首屏内容**更早出现，但首字节时间会变长，因为服务器要先取完数据、渲染完才返回；接口慢的时候，SSR 的首字节甚至比 CSR 返回空壳还慢。HTML 显示出来后还要等水合，中间可能有一段"看得见、点不动"的时间。首次加载之后的页面切换，SSR 应用通常也在客户端完成，和 CSR 一样。所以要看指标：关心 LCP 和 SEO 时选 SSR，后台系统用 CSR 更省事。
:::

::: details CSR 的 SEO 问题有哪些解决办法？
主流搜索引擎能执行 JS，但渲染有延迟，也不保证完整；社交平台抓取分享卡片的爬虫基本不执行 JS。办法有：改成 SSR 或 SSG；不方便改造时用预渲染，构建时用无头浏览器打开各个路由，把 HTML 保存成静态文件。只给爬虫返回预渲染页面的"动态渲染"属于权宜之计，Google 已经不推荐这种做法。
:::

::: details ISR 有什么缺点？
- 过期后的第一个访问者拿到的是旧页面，不适合价格、库存这类要求实时的数据
- 多实例部署时，每个实例默认有各自的缓存，按需失效只作用于收到请求的那个实例，需要配置共享的缓存存储
- 依赖框架和部署平台的支持，纯静态托管用不了
:::

::: details SSG 的页面内容怎么更新？
内容变了就重新构建、重新部署，通常由 CMS 的 webhook 触发 CI。页面很多、全量构建太慢时，换成 ISR 或者只重建变化的页面。页面上需要实时的部分（评论数、库存）在客户端请求接口。
:::

## 易错点

- SSG 不等于"没有 JS"：SSG 的页面在浏览器里同样要下载 JS 并水合，才能交互
- 带用户信息的 SSR 页面不能直接被 CDN 缓存，否则会把一个用户的页面返回给另一个用户
- ISR 和"SSR 加 CDN 缓存"效果接近，区别是前者由框架管理页面缓存和重建，后者靠 CDN 或反向代理的缓存规则
- SSR 改善的是"首屏内容出现"，不是"可交互"，两者不是同一个时间点
