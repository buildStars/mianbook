# 岛屿架构是什么？Astro 这类框架为什么首屏快？

::: tip 一句话回答
岛屿架构把页面看成一片**静态 HTML 的海洋**，只在需要交互的地方放一个个独立的**岛屿**组件。框架默认把所有组件在构建时或服务端渲染成纯 HTML，**不发送组件的 JS**；只有显式标记的交互组件才会单独加载自己的 JS 并水合，还能指定时机：页面加载时、浏览器空闲时、进入可视区时。这叫**部分水合**，和整页水合相比，浏览器要下载和执行的 JS 少得多，主线程更早空闲，首屏和可交互都更快。代价是岛屿之间相互独立，共享状态要额外处理，适合文档、博客、官网这类**以内容为主**的网站，不适合后台、在线编辑器这类**强交互**的应用。
:::

## 详细解析

### 整页水合的浪费

传统的 SSR、SSG 应用里，HTML 先显示出来，但浏览器还要下载**整个页面所有组件**的代码，把整棵组件树水合一遍。对内容网站来说，页面的大部分（导航文字、文章正文、页脚）水合之后也没有任何交互，这些 JS 的下载、解析、执行都是浪费，还会占住主线程，拖慢真正需要交互的部分。

### 岛屿怎么工作

```text
页面（静态 HTML，不带 JS）
├─ 导航栏
│   └─ [岛屿] 搜索框：浏览器空闲时水合
├─ 文章正文
├─ [岛屿] 图片轮播：进入可视区时水合
└─ 页脚
    └─ [岛屿] 评论区：进入可视区时水合

每个岛屿：先在服务端渲染出 HTML → 有自己独立的 JS 入口 → 按指令的时机加载、水合，互不阻塞
```

以 Astro 为例，`.astro` 组件只在构建时或服务端执行，输出 HTML；从 React、Vue、Svelte 等框架导入的组件，默认也只输出 HTML，加上 `client:*` 指令才变成岛屿：

```html
---
// src/pages/post.astro：这段代码只在构建时或服务端执行
import Header from '../components/Header.astro'
import Search from '../components/Search.jsx'
import Carousel from '../components/Carousel.vue'
import LikeButton from '../components/LikeButton.jsx'
---
<Header />
<Search client:idle />
<article>...</article>
<Carousel client:visible />
<LikeButton client:load />
<Carousel />
```

最后一个 `<Carousel />` 没有指令，只会输出静态 HTML，点了也不会动。

### 加载时机的指令

| 指令 | 什么时候加载并水合 | 适合 |
| --- | --- | --- |
| `client:load` | 页面加载后立即 | 首屏就要能用的：购买按钮、导航菜单 |
| `client:idle` | 页面初始加载完成、浏览器空闲时，可以设置最长等待时间 | 优先级低一些的：搜索框、客服入口 |
| `client:visible` | 进入可视区时，基于 IntersectionObserver，可以设置提前量 | 首屏以下的：评论、轮播 |
| `client:media` | 满足某个媒体查询时 | 只在小屏出现的菜单按钮 |
| `client:only` | 跳过服务端渲染，只在浏览器渲染，要写明框架，如 `client:only="react"` | 依赖浏览器 API、没法在服务端渲染的组件 |
| 不写指令 | 不加载 JS | 纯展示的内容 |

除了客户端岛屿，Astro 还有**服务端岛屿**：组件加上 `server:defer` 后会单独在服务端按需渲染，页面先用 fallback 占位。这样页面主体可以被长时间缓存，用户头像、购物车这类个性化的部分单独渲染。

### 为什么首屏快

- **下载的 JS 少**：静态部分没有组件代码，页面上没有岛屿时连框架运行时都不用加载
- **主线程空闲早**：不用水合整棵树，INP 等交互指标更好，见 [Core Web Vitals](/basics/browser/09-web-vitals)
- **岛屿并行、独立水合**：低优先级的重组件不会挡住高优先级的组件，首屏以下的岛屿可以推迟到看见时再加载
- **HTML 本身完整**：页面是 SSG 或 SSR 生成的，内容直接可见，适合放在 CDN 上

### 和整页水合、React 服务端组件的对比

| | 整页水合 | 岛屿（部分水合） | React Server Components |
| --- | --- | --- | --- |
| 下发的组件 JS | 页面上的所有组件 | 只有岛屿组件 | 只有客户端组件 |
| 应用根节点 | 整个页面一个根 | 每个岛屿各是一个独立的根 | 整个页面一个根，服务端组件部分不需要水合 |
| 默认行为 | 全部可交互 | 默认静态，显式标记交互组件 | 默认服务端组件，`'use client'` 标记交互组件 |
| 页面切换 | 客户端路由 | 默认是多页应用，整页跳转 | 客户端路由，请求新页面的 RSC payload |
| 组件之间共享状态 | 同一个应用，直接共享 | 岛屿相互隔离，要借助外部 store | 客户端组件之间可以用 Context |

两者都在减少发给浏览器的 JS，但机制不同：岛屿在**页面层面**切分出多个独立的小应用；RSC 保留一棵完整的 React 树，在**模块依赖**上划分哪些代码不下发，同时保留客户端路由和跨组件的状态共享。RSC 的细节见 [Server Components](/basics/react/11-server-components)。

## 面试官可能追问

::: details 岛屿之间怎么共享状态？
每个岛屿是独立挂载的应用，不能通过 props 或 Context 共享。常用做法是用一个和框架无关的小型 store（Astro 文档推荐 Nano Stores），各个岛屿都订阅它；也可以用自定义事件、URL 参数或者 localStorage 传递。共享的状态一多，说明这部分页面更适合做成一个完整的客户端应用。
:::

::: details 什么情况下不适合用岛屿架构？
页面大部分区域都要交互、组件之间状态联动频繁的应用，比如后台管理系统、在线文档编辑器、看板。这时"静态的海洋"很小，岛屿之间的通信反而增加复杂度，用 SPA 或 Next.js、Nuxt 这类全栈框架更合适。需要像 SPA 一样无刷新切换页面、保留页面状态的场景，也要额外处理。
:::

::: details client:only 和 client:load 有什么区别？
`client:load` 的组件会先在服务端渲染出 HTML，用户立即能看到内容，JS 加载后再水合。`client:only` 完全跳过服务端渲染，JS 加载前那里是空的（可以提供占位内容），容易造成布局偏移，只用于确实无法在服务端渲染的组件。
:::

::: details Vue、Nuxt 里能做类似的优化吗？
可以做到一部分。Vue 的异步组件支持延迟水合，可以等进入视口、浏览器空闲时再水合，Nuxt 的懒加载组件也可以直接写 `hydrate-on-visible` 这类属性，见 [SSR 和水合](/basics/vue/18-ssr-hydration)；Nuxt 的服务端组件（`.server.vue`，目前仍是实验性功能）只在服务端渲染，不下发组件代码，思路和岛屿相近。区别在于它们仍然是一个完整的 Vue 应用，而不是相互独立的小应用。
:::

## 易错点

- 以为岛屿组件不在服务端渲染：除了 `client:only`，岛屿也会先输出 HTML，再在浏览器里水合
- 给所有组件都加上 `client:load`，等于退回整页水合，失去了岛屿的意义
- 在 `.astro` 组件上加 `client:*` 指令：指令只能用在从 UI 框架导入的组件上
- 把岛屿和 React Server Components 混为一谈：目标相同，机制和适用场景不同
