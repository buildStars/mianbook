# 微信小程序的双线程架构是什么？为什么要这样设计？

::: tip 一句话回答
小程序把运行环境拆成两层：**逻辑层**用独立的 JS 引擎运行 JS，没有 `window`、`document`，不能操作 DOM；**渲染层**用 WebView 渲染 WXML 和 WXSS，每个页面一个 WebView。两层不能直接通信，数据和事件都要**经过微信客户端（Native）中转**。这样设计主要是为了**管控和安全**：开发者碰不到 DOM，就没法绕过平台随意跳转外链、改写页面，也读不到只供展示的敏感数据；同时逻辑和渲染分开跑，JS 计算不会直接卡住页面渲染。代价是每次更新都要跨线程传数据，`setData` 成了性能瓶颈。
:::

## 详细解析

### 两层各管什么

| | 逻辑层（App Service） | 渲染层（View） |
| --- | --- | --- |
| 跑什么 | 页面和组件的 JS、调用 `wx.*` API | WXML 模板、WXSS 样式 |
| 运行环境 | iOS 上是 JavaScriptCore，安卓上是 V8 | iOS 上是 WKWebView，安卓上是微信的 XWeb（基于 Chromium 内核） |
| 数量 | 整个小程序一个 | 每个页面一个 WebView |
| 能力 | 没有 DOM 和 BOM，网络请求、存储等都走 `wx.*` | 负责显示和收集用户事件，业务 JS 不在这里运行（WXS 响应事件除外） |

```text
逻辑层（JS 引擎，1 个）        Native（微信客户端）        渲染层（WebView，每页 1 个）
Page / Component 的 JS  --setData-->  中转  --数据-->  页面 A、页面 B ……
                        <--事件回调--  中转  <--用户事件--
wx.request 等 API       <---------->  网络、存储、系统能力
```

逻辑层处理完数据后发给渲染层，渲染层把用户点击、输入等事件发回逻辑层。逻辑层发起的网络请求也由 Native 代为转发。

### 为什么这样设计

- **管控和安全**：Web 技术很开放，脚本可以把页面随意跳转到别的网页、改动界面上的任何内容；平台还有一些只负责展示敏感数据的组件，开发者拿不到数据，可一旦能操作 DOM 就能把它读出来。要管住这些，就得禁用跳转页面、操作 DOM、动态执行脚本这类浏览器接口，但逐个禁用很容易漏，所以干脆让开发者的 JS 跑在一个没有任何浏览器接口的沙箱里。能做什么全由平台开放的 `wx.*` API 和组件决定，比如页面跳转要用平台的路由 API 或 `navigator` 组件，打开网页要用 `web-view` 组件并配置业务域名
- **逻辑和渲染互不阻塞**：浏览器里 JS 和渲染共用主线程，一段长任务就会让页面卡住。小程序的 JS 在单独的线程，计算再重，WebView 的滚动和已有的动画也能继续
- **多 WebView 带来接近原生的体验**：每个页面独立一个 WebView，切换页面像原生 App 一样有转场动画，返回时上一页还在，不用重新渲染。代价是内存，页面越多 WebView 越多，`wx.navigateTo` 打开的页面栈最多十层

### 代价：跨线程通信

两层之间不能共享内存，数据要先序列化，经过 Native 转发到渲染层，渲染层再算出差异去更新页面。数据量越大、调用越频繁，通信和渲染的耗时就越明显。这就是 `setData` 经常成为性能瓶颈的原因，优化方法见 [setData 为什么会卡](/basics/cross-platform/02-setdata)。

交互也受影响：手指拖动一个元素时，`touchmove` 事件先从渲染层传到逻辑层，逻辑层算出新位置后再 `setData` 传回来，一次响应要两次通信加一次渲染，动画容易跟不上手。

另外，iOS 上的 JavaScriptCore 不能开启 JIT，同等条件下运行性能比其他平台低，复杂计算要在真机上测。

### 新的渲染引擎

微信后来推出了 **Skyline** 渲染引擎：用一条单独的渲染线程负责布局、合成和绘制，原来在 WebView 里做的 DOM 树创建等工作移到逻辑层执行，也不用再为每个页面新建一个 WebView，目标是减少内存开销和卡顿，接近原生的表现。它和 WebView 渲染并存，迁移时要按官方文档检查组件和样式的支持情况。

## 代码示例

逻辑层拿不到 DOM，需要节点尺寸时，要通过 API 异步查询渲染层：

```js
Page({
  data: { list: [] },

  onReady() {
    // ❌ 逻辑层没有 document，这行会报错
    // document.querySelector('.list')

    // ✅ 通过 Native 向渲染层查询节点信息，结果异步返回
    wx.createSelectorQuery()
      .select('.list')
      .boundingClientRect((rect) => {
        console.log('列表高度', rect.height)
      })
      .exec()
  },
})
```

## 面试官可能追问

::: details 很多 npm 包为什么在小程序里用不了？
逻辑层不是浏览器，没有 `window`、`document`、`XMLHttpRequest` 这些对象。依赖 DOM 的 UI 库、直接用 `fetch` 或 `localStorage` 的工具库都跑不起来，网络和存储要换成 `wx.request`、`wx.setStorage`。纯逻辑的包（日期处理、加密、数据结构）一般没问题。
:::

::: details 拖拽、跟手动画这类高频交互怎么优化？
核心是减少跨层通信，让事件在渲染层直接处理。微信提供了 WXS 响应事件：WXS 函数绑定在组件事件上，运行在渲染层，可以直接修改组件的 `style` 和 `class`，不用每次 `touchmove` 都绕一圈逻辑层。也可以用 `movable-view` 这类内置组件，拖动由组件内部处理。
:::

::: details 双线程一定比 Web 快吗？
不一定。它避免了 JS 长任务阻塞渲染，但多了通信成本：首屏数据要从逻辑层传到渲染层才能显示，频繁的小更新也会排队。逻辑层本身是单线程的，所有页面的 JS 都在这一个线程里跑，后台页面的定时器同样会占用它。写得不好的小程序照样会卡。
:::

::: details 开发者工具里的表现能代表真机吗？
不能完全代表。开发者工具里逻辑层和渲染层的运行环境和真机不同，样式的渲染效果、JS 的执行速度、部分 API 的行为都可能有差异。官方也说明以微信客户端的实际表现为准，上线前要在 iOS 和安卓真机上都验证。
:::

## 易错点

- "双线程"指逻辑层和渲染层分开，渲染层不是只有一个线程，每个页面都有自己的 WebView
- 逻辑层和渲染层之间不是直接通信，而是经过微信客户端中转，这也是 `setData` 开销的来源
- 逻辑层能写 JS，不代表能用浏览器 API；能用什么完全取决于平台开放的 `wx.*` 接口
