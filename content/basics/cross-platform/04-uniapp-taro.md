# uni-app 和 Taro 是怎么做到一套代码多端运行的？

::: tip 一句话回答
多端框架都要解决同一个问题：各家小程序、H5、App 的模板语法、组件和 API 都不一样。思路分两类：**编译时转换**，把源码的模板和语法翻译成各端的代码，产物接近手写，但能写的语法受限；**运行时适配**，在小程序的逻辑层里实现一套精简的 **DOM 和 BOM**，让 React、Vue 照常运行，再把这棵"假 DOM"的变化通过 `setData` 同步到一套通用模板上，语法限制少，代价是额外的运行时开销。uni-app 在小程序端是"编译模板 + 小程序版的 Vue 运行时"，Taro 从早期的重编译时转向了重运行时。平台差异用**条件编译**处理。
:::

## 详细解析

### 要抹平哪些差异

| 差异 | 例子 |
| --- | --- |
| 模板语法 | 微信用 WXML 的 `wx:if`、`wx:for`，支付宝小程序用 `a:if`，H5 是普通的 HTML |
| 组件 | 小程序用 `view`、`text`、`image`，H5 用 `div`、`span`、`img` |
| API | `wx.request`、`my.request`、浏览器的 `fetch` |
| 运行环境 | 小程序逻辑层没有 DOM；App 端可能是 WebView 渲染或原生渲染 |

框架的做法是：开发者用统一的组件和 API 写（uni-app 用 `uni.*`，Taro 用 `Taro.*`），由编译器和运行时翻译到各端。

### 编译时转换

编译器把源码解析成 AST，再按目标平台生成对应的模板、样式和脚本。Taro 早期就是这种方式：用 Babel 把 JSX 翻译成 WXML，运行时只做很薄的一层适配。

- **优点**：产物和手写的小程序接近，运行时开销小
- **缺点**：JSX 太灵活，很多写法无法静态翻译成模板，比如把 JSX 存进变量再传来传去、复杂的动态渲染，只能在文档里列"不支持的写法"；每个平台都要维护一套转换规则，改一个 Bug 要同步改多份

uni-app 用的是 Vue 的模板语法，和小程序模板本来就很接近，所以模板适合在编译时转换：编译器把 `.vue` 文件拆成 WXML、WXSS 和 JS。逻辑部分则带上一个**小程序版的 Vue 运行时**，负责响应式、计算出数据变化再调用 `setData`，路由、组件和 API 基本是一一转译。

### 运行时适配

Taro 后来改成了"重运行时"：

1. 在逻辑层实现一套精简的 `document`、`window`、元素节点和事件系统
2. React 通过 `react-reconciler` 加上自定义的宿主配置，把增删改节点的操作落到这套 DOM 上；Vue 直接用它的渲染器操作这套 DOM
3. 小程序侧只有一套**固定的通用模板**：按节点类型选择对应的模板，递归渲染子节点。不管写了多少页面，模板的体积都有上限
4. 节点变化时记录"哪个路径的哪个值变了"，攒起来通过一次 `setData` 按路径更新

这样几乎能用完整的 React 或 Vue 语法，接入新框架、新平台的成本也低。代价也很明确：包里要带上 React 或 Vue 本身；逻辑层多维护一棵 DOM 树；首次渲染要把整棵节点树作为数据传给渲染层，节点多时首屏和更新都会变重。常见的优化是把频繁更新的局部放进单独的自定义组件里，缩小每次 `setData` 的范围，长列表用虚拟列表。

### 条件编译处理平台差异

再好的抽象也有抹不平的地方，比如只有微信有的开放能力、App 端才有的原生插件。这时要按平台写不同的代码：

- **uni-app**：用注释形式的条件编译，`// #ifdef MP-WEIXIN` 到 `// #endif` 之间的代码只编译进微信小程序，`#ifndef` 表示排除某个平台。JS、模板、样式和 `pages.json` 都支持，样式里要用 `/* */` 注释
- **Taro**：用 `process.env.TARO_ENV`（如 `weapp`、`h5`、`rn`）判断，编译时会删掉不属于当前平台的分支；也可以按 `xxx.weapp.js`、`xxx.h5.js` 命名多份文件，导入时不写后缀，由编译器挑选

条件编译在**编译时**生效，没被选中的代码根本不会进入产物，所以它和运行时 `if` 判断平台不同，不会增加其他平台的包体积。

## 代码示例

```vue
<template>
  <view>
    <!-- #ifdef MP-WEIXIN -->
    <button open-type="share">分享给好友</button>
    <!-- #endif -->
    <!-- #ifdef H5 -->
    <button @click="copyLink">复制链接</button>
    <!-- #endif -->
  </view>
</template>

<script setup>
// #ifdef APP
// 只在 App 端执行，例如调用原生插件（示意）
// #endif
</script>
```

```jsx
// Taro（示意，copyLink 省略）：编译时只保留当前平台的分支
import { Button } from '@tarojs/components'

function ShareButton() {
  if (process.env.TARO_ENV === 'weapp') return <Button openType="share">分享给好友</Button>
  return <Button onClick={copyLink}>复制链接</Button>
}
```

## 面试官可能追问

::: details uni-app 打包成 App 时是怎么渲染的？
App 端有两种页面：`.vue` 页面在 WebView 里渲染，逻辑层和渲染层分开，原理和小程序类似；`.nvue` 页面用原生组件渲染，原理接近 React Native。逻辑层运行在独立的 JS 引擎里，所以和小程序一样不能直接用 `window`、DOM，需要操作 DOM 的代码要放到 renderjs 这类运行在渲染层的脚本里。
:::

::: details 运行时方案为什么会比原生小程序慢？慢在哪？
多出来的工作主要有三块：React 或 Vue 自身的计算（虚拟 DOM 对比、调度）；维护逻辑层那棵模拟的 DOM 树；把 DOM 变化转换成 `setData` 的数据。首屏要传整棵节点树，数据量也比手写小程序大。大部分页面感知不明显，但在长列表、高频更新、低端安卓机上会暴露出来，这时要针对性优化或者把热点页面改成原生写法。
:::

::: details uni-app 和 Taro 怎么选？
主要看团队技术栈和目标平台。团队用 Vue、目标以小程序和 App 为主，uni-app 的生态和 App 端打包能力更顺手；团队用 React、想在多个平台上保持 React 的写法，Taro 更合适，它对 React 生态的兼容更完整。对性能特别敏感的核心页面，无论选哪个都可以保留原生小程序页面混合使用。
:::

## 易错点

- "一套代码多端运行"不等于零成本，各端的样式、组件行为和 API 能力仍有差异，条件编译和多端测试少不了
- 运行时方案不是把浏览器搬进了小程序，模拟的 DOM 只实现了框架需要的子集，直接操作 DOM 的第三方库依然可能用不了
- 条件编译是编译期的文本裁剪，不能用变量动态拼出平台名，Taro 的 `process.env.TARO_ENV` 也要完整书写，不能解构
