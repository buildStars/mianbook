# H5、小程序、React Native、Flutter 和原生开发怎么选？

::: tip 一句话回答
没有绝对的好坏，要从业务出发看几个维度：**性能和体验**、**开发效率和团队技能**、**发布和审核**、**动态更新能力**、**能调用多少系统能力**、**获客渠道**。大致的取向是：H5 迭代最快、传播最方便，体验和系统能力最弱；小程序自带**平台流量入口**，适合轻量、即用即走的服务；React Native 和 Flutter 用一套代码做 App，体验接近原生；原生体验和能力最好，成本也最高。实际项目常常是**混合方案**，比如原生外壳加 H5 活动页、原生 App 里部分页面用 React Native。
:::

## 详细解析

### 维度对比

| 维度 | H5 | 小程序 | React Native | Flutter | 原生 |
| --- | --- | --- | --- | --- | --- |
| 体验和性能 | 受浏览器和 WebView 限制，复杂交互弱 | 好于普通 H5，受平台框架限制 | 接近原生，渲染原生控件 | 接近原生，自绘、各端一致 | 最好 |
| 开发效率 | 最高，一套代码到处打开 | 高，但每个平台有差异 | 一套代码出两端 App | 一套代码出两端 App | 两端各写一套 |
| 发布和审核 | 部署即生效 | 平台审核 | 应用商店审核 | 应用商店审核 | 应用商店审核 |
| 动态更新 | 随时更新 | 审核后发布，客户端启动时检查并下载新版，一般下次冷启动生效 | JS 包可以热更新，受商店政策约束 | 官方没有提供动态更新方案 | 只能发版 |
| 系统能力 | 少，靠浏览器开放的 API | 平台开放什么用什么 | 多，可写原生模块补充 | 多，可通过平台通道补充 | 全部 |
| 安装门槛 | 无需安装 | 无需安装，有包体积限制 | 需要下载安装 | 需要下载安装 | 需要下载安装 |
| 获客渠道 | 链接、搜索引擎、社交分享 | 平台内的搜索、分享、扫码等入口 | 应用商店、广告投放 | 应用商店、广告投放 | 应用商店、广告投放 |
| 团队技能 | 前端 | 前端 | 前端加少量原生 | Dart 加少量原生 | Android 和 iOS 工程师 |

### 典型场景

- **营销活动、帮助中心、需要频繁改的页面**：H5，改完即上线，分享链接就能传播
- **线下扫码、即用即走的服务**（点餐、停车、预约）、依赖社交分享的业务：小程序，用户不用装 App，平台还能带来流量
- **需要 App、团队以前端为主、要两端同时上线**：React Native；对动画和 UI 一致性要求很高、愿意学 Dart：Flutter
- **深度使用系统能力**（音视频、相机、蓝牙、后台任务）、**性能极其敏感**的核心产品：原生
- **验证想法的早期产品**：先用 H5 或小程序跑通，验证需求后再投入 App

### 常见的混合方案

- **原生外壳 + H5 页面**：首页、交易链路等核心页面用原生，活动页、详情页用 H5，通过 JSBridge 调用登录、支付、分享等能力，见 [JSBridge 的原理](/basics/cross-platform/07-jsbridge)
- **原生 + 部分 React Native / Flutter 页面**：两者都能嵌入现有 App，按页面逐步替换，新业务用跨端写，老页面保持原生
- **小程序 + H5**：小程序里用 `web-view` 组件承载已有的 H5 页面，需要配置业务域名，部分能力受限
- **一套代码多端发布**：用 uni-app、Taro 同时产出小程序和 H5，原理见 [uni-app 和 Taro 的多端原理](/basics/cross-platform/04-uniapp-taro)

### PWA 的定位

PWA 是增强版的 H5：用 Service Worker 做离线缓存，可以添加到主屏幕、以独立窗口打开，不经过应用商店。适合想要接近 App 体验、又不想维护 App 的场景，但各平台对推送、安装等能力的支持程度不同，原理见 [Service Worker](/basics/browser/16-service-worker)。

### 面试时怎么回答

先问清楚业务，再讲取舍，不要直接报一个技术名。可以按这个顺序：

1. **用户在哪里**：用户在微信里、从扫码进来，小程序优先；需要长期留存、推送召回，就要有 App
2. **体验要求多高**：重交互、动画多的选原生或 Flutter；以内容展示和表单为主的，H5 或 React Native 足够
3. **迭代有多快**：天天改的部分放 H5，稳定的核心流程用原生或跨端框架
4. **团队是什么背景**：前端团队做 React Native 或 H5 最顺手，强行上 Flutter 要算上学习成本
5. **最后给组合方案**：例如"核心交易链路原生，活动页 H5，同时做一个小程序承接微信里的流量"

## 面试官可能追问

::: details 为什么很多 App 的活动页用 H5 而不是原生？
活动页生命周期短、改动频繁，用原生每次都要发版、等审核，用户还不一定会升级。H5 改完就生效，同一套页面还能在 App、微信、浏览器里分享打开。通过 JSBridge 补上登录、分享、支付等能力后，体验已经足够。
:::

::: details 混合开发里 H5 页面打开慢，怎么优化？
主要从三方面入手：**资源**，用离线包把 HTML、JS、CSS 提前下载到 App 里，WebView 请求时由原生直接返回本地文件；**容器**，提前初始化 WebView，或者维护一个 WebView 池，避免每次打开都冷启动；**数据**，原生在打开页面的同时并行请求首屏数据，页面就绪后直接拿来渲染，配合骨架屏减少白屏感知。
:::

::: details 已经有了 App，还有必要做小程序吗？
看获客方式。小程序的价值主要在渠道：用户在聊天里点开分享、线下扫码，不用安装就能完成一次服务，转化路径短。App 适合留存高频用户、提供完整功能。很多业务两者都做：小程序负责拉新和轻量场景，再引导重度用户下载 App。要注意小程序有自己的平台规则，类目、支付、分享方式都要符合要求。
:::

## 易错点

- 选型不能只比性能，团队技能、迭代节奏、获客渠道往往影响更大
- 小程序不只是技术方案，也是渠道选择，同时意味着要遵守平台的审核和运营规则
- 用了跨端框架也离不开原生能力，推送、支付、复杂的系统交互通常还需要原生工程师配合
