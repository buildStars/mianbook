# App 里的 H5 和 RN 页面怎么做热更新？离线包是什么原理？

::: tip 一句话回答
H5 天然能热更新，离线包解决的是它的**加载速度**：把页面的 HTML、JS、CSS 打成 zip 提前下发到手机，WebView 发请求时由原生**拦截并返回本地文件**，网络只用来拉数据。更新靠**版本比对**：App 启动或进入页面时问配置中心最新版本，有新版就下载全量包或**增量差分包**，校验后替换。RN 的热更新原理类似，替换的是 **JS bundle 和图片资源**，下次启动加载新 bundle。两者都要配合**灰度和回滚**；改动必须限于解释执行的代码，不能借热更新改变 App 的核心功能，否则违反应用商店规则。
:::

## 详细解析

### 离线包的工作流程

```text
构建：页面资源 → 打 zip + 生成清单（版本号、文件列表、哈希）→ 上传 CDN，登记到配置中心
下发：App 启动/空闲时请求配置中心 → 发现新版本 → 下载 → 校验签名和哈希 → 解压到本地目录
访问：WebView 请求 https://m.example.com/order/index.html
      → 原生拦截 → 按 URL 映射到本地文件 → 命中就直接返回
      → 未命中或校验失败 → 放行走网络（兜底）
```

拦截靠各平台 WebView 提供的请求拦截能力，例如 Android 的 `shouldInterceptRequest`，iOS 的 `WKURLSchemeHandler`。Android 上页面可以仍然用线上 URL 访问，离线包缺失时无缝回落到网络，Cookie 和同源策略也不受影响。iOS 的 `WKURLSchemeHandler` 只能注册自定义 scheme，给 http/https 注册会直接抛异常，所以 iOS 方案通常改用自定义协议（如 `app-offline://`）加载离线页面，回落网络要在 handler 里自己发请求，Cookie 和跨域也要额外处理；另一类做法是用 NSURLProtocol 私有 API 拦截，有审核风险。

离线包和 [JSBridge](/basics/cross-platform/07-jsbridge) 是两件事：JSBridge 解决 H5 调原生能力，离线包解决资源从哪里加载。它也只是 H5 提速的一部分，WebView 预热、数据预取等手段见 [跨端方案选型](/basics/cross-platform/10-cross-platform-choice)。

### 版本比对和增量更新

- 每个业务一个离线包，有自己的版本号，互相独立更新
- 客户端上报本地版本，服务端返回需要的动作：无更新、下载增量包、下载全量包
- 增量包用二进制差分工具（例如 bsdiff）由服务端对新旧两个包生成，客户端合成后校验整包哈希，不一致就丢弃并改下全量包
- 服务端只保留最近几个版本的差分，太老的客户端直接给全量包
- 更新时机：启动时检查、进入页面前检查，或由推送通知触发；下载完一般下次进入才生效，避免页面用到一半资源被换掉

### RN 的热更新

RN 页面的业务代码是一个 JS bundle，图片等资源跟着它走。流程和离线包相似：

1. 构建时打出 bundle 和资源，按平台、App 原生版本分别发布
2. App 启动时检查更新，下载新 bundle 到本地目录
3. 下次启动（或用户确认后重新加载）时，让 RN 从本地路径加载 bundle，而不是安装包里自带的那份
4. 新 bundle 启动后上报"加载成功"；连续崩溃则自动回退到上一个版本

关键约束是**和原生版本匹配**：bundle 里如果用到了新的原生模块，旧版本 App 没有这个模块就会崩溃。所以热更新包要绑定原生版本范围，涉及原生改动的必须发版。RN 的整体结构见 [RN 的架构](/basics/cross-platform/05-rn-architecture)。

### 灰度、回滚和合规

- **灰度**：配置中心按用户 ID 哈希、地区、App 版本下发新包，先给小比例用户，看崩溃率和白屏率再放量
- **回滚**：发布系统可以把"最新版本"指回旧版本；客户端也要有本地兜底，新包加载失败或启动即崩溃时自动回退
- **安全**：包要签名，客户端验签，防止被劫持替换成恶意代码；下载走 HTTPS
- **合规**：苹果审核指南 2.5.2 禁止下载、执行会引入或改变 App 功能的代码；开发者协议允许在 WebKit 里运行下载的 HTML/JS，但不能借此改变 App 的主要用途、绕过审核新增功能。热更新适合修 bug、改活动页，大的功能变化仍然要走发版

## 面试官可能追问

::: details 离线包里的接口请求也会被拦截吗？
一般不会。拦截只针对清单里列出的静态资源，接口请求直接放行走网络。有的方案会配合数据预取：原生在打开 WebView 的同时并行请求首屏接口，页面通过 JSBridge 取结果，而不是在 JS 加载完后才发请求。
:::

::: details 用户打开页面时离线包还没下载完怎么办？
走线上兜底。因为页面用的是线上 URL，拦截不到本地文件就正常从网络加载，体验和普通 H5 一样，只是没有加速。所以离线包是"锦上添花"，任何时候都不能成为页面能否打开的前提。
:::

::: details 离线包更新了，但用户一直不重启 App 怎么办？
可以在进入具体页面前做一次轻量的版本检查，或者由服务端推送更新指令。下载完成后，在下次进入该页面时切换到新包，而不是强制刷新正在浏览的页面。紧急修复可以设置"强制更新"标记，版本过低时暂不使用本地包，直接走线上。
:::

## 易错点

- 以为离线包是 H5 热更新的前提；H5 本来就能热更新，离线包解决的是加载速度
- 包不做签名校验，下载链路被劫持时会执行恶意代码
- RN 热更新不绑定原生版本，新 bundle 调用旧 App 里不存在的原生模块导致崩溃
- 认为热更新可以替代发版，用它上线大功能，踩到应用商店的审核红线
