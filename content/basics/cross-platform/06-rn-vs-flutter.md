# React Native 和 Flutter 有什么区别？怎么选？

::: tip 一句话回答
最根本的区别在**渲染方式**：React Native 用 JS/TS 写 React 组件，最终渲染成**各平台的原生控件**；Flutter 用 Dart 写，**自带渲染引擎，自己绘制每一个像素**，不使用系统控件。所以 Flutter 的界面和动画在各平台上高度一致，React Native 的界面更贴近系统原生的观感，也更容易和 Web 团队的技能、React 生态复用。选型主要看团队背景、对 UI 一致性和动画的要求、是否需要动态更新，以及和现有原生代码的集成方式。
:::

## 详细解析

### 渲染方式的差异

```text
React Native：JS 线程运行 React → Fabric 计算出视图树和布局 → 创建 Android / iOS 的原生控件
Flutter：     Dart 代码构建 Widget 树 → 布局、绘制 → 自带的渲染引擎直接画到屏幕上
```

- **React Native**：一个 `Text` 在 Android 上就是原生的文本控件，在 iOS 上是 iOS 的文本控件。系统升级带来的控件变化、无障碍能力会自然继承，但两端的细节表现可能不完全一样
- **Flutter**：按钮、列表、文字全由框架自己实现和绘制，原生系统只提供一块"画布"。两端像素级一致，但要模仿系统风格得靠框架自带的组件库，系统控件的新特性也不会自动出现

### 对比

| 维度 | React Native | Flutter |
| --- | --- | --- |
| 语言 | JavaScript / TypeScript，React 的写法 | Dart，声明式 Widget |
| 渲染 | 映射成原生控件 | 自带引擎自绘 |
| 跨平台一致性 | 外观跟随系统，细节可能有差异 | 各端一致，自定义 UI 方便 |
| 动画和复杂交互 | 简单动画没问题，复杂手势动画要借助在原生线程执行的动画库 | 自绘管线，复杂动画表现稳定 |
| 发布产物 | 原生壳 + JS 引擎 + JS 包 | 原生壳 + 渲染引擎 + 编译成机器码的 Dart 代码 |
| 调用原生能力 | 原生模块（TurboModules）、原生组件 | 平台通道（MethodChannel）、FFI 调 C 接口、平台视图嵌入原生控件 |
| 动态更新 | JS 包可以在运行时替换，技术上可行 | 发布包是预编译的机器码，官方没有提供动态更新方案 |
| 团队和生态 | 前端团队上手快，可复用不依赖 DOM 的 npm 包 | 需要学 Dart，有自己的 pub.dev 生态 |

包体积两者都要带上运行时，差异和项目规模、依赖有关，要用自己的项目实测，不要凭印象下结论。

### 和原生代码交互

- **React Native**：新架构下用 TypeScript 写模块的接口声明，Codegen 生成原生侧的接口，调用可以同步返回，见 [React Native 的架构](/basics/cross-platform/05-rn-architecture)
- **Flutter**：最常用的是**平台通道**，Dart 和原生之间异步传递消息，数据用标准编解码器序列化；需要类型安全可以用 Pigeon 生成两端代码；调用 C 库可以用 FFI 直接调 C 函数，不经过平台通道的消息编解码。地图这类很难用 Flutter 重写的控件，用平台视图嵌进来，代价是额外的合成开销

两者都支持"嵌入现有原生 App"：只把某几个页面用跨端框架写，其他保留原生。

### 动态更新：技术可行，政策受限

React Native 的业务逻辑在 JS 包里，下载新的 JS 包就能改功能，很多团队用它做线上热修复。Flutter 的发布包是提前编译好的机器码，官方没有提供开箱即用的动态更新方案，社区有第三方方案。

但能不能做，要看应用商店的规则：苹果的审核指南要求应用不能下载、安装或执行会**引入或改变应用功能**的代码，开发者协议允许下载解释执行的代码，前提是不改变应用的主要用途、不绕过签名和沙箱等系统安全机制；Google Play 要求应用只能通过 Google Play 的机制更新自身，不能从商店以外下载可执行代码（如 dex、JAR、.so 文件），在虚拟机或解释器里运行、只能间接访问 Android API 的代码（如 WebView 中的 JS）不受这条限制，但运行时加载的解释型代码同样不能违反商店政策。一般认为用热更新修 Bug、做小调整风险较低，用它上线新功能、绕过审核则可能违规甚至被下架，具体以商店当时的政策和审核结果为准。

### 怎么选

- **团队以 Web 和 React 为主、想复用前端技能、需要热修复**：React Native
- **重视品牌化的自定义 UI、动画多、要求各端完全一致**：Flutter
- **大量依赖系统控件和平台特性、追求原生观感**：React Native 更自然，或者直接写原生
- **已有原生 App**：两者都能按页面嵌入，可以先在非核心页面试点

## 面试官可能追问

::: details Flutter 自绘，是不是一定比 React Native 快？
不一定。Flutter 省掉了映射原生控件这一层，复杂动画和大量自定义绘制时优势明显；React Native 在新架构下通信成本已经降低，普通的表单、列表页面两者的体验差距不大。真正决定流畅度的往往是代码质量：不必要的重建或重渲染、长列表没做虚拟化，在两个框架里都会卡。
:::

::: details Flutter 怎么调用原生的 API？
通过平台通道：Dart 侧创建一个 `MethodChannel` 并调用方法，原生侧用同名的通道注册处理函数，执行完把结果返回。消息是异步的，参数会被序列化，支持布尔、数字、字符串、列表、Map 这类简单类型。通道名称在应用内必须唯一，一般加上域名前缀。Android 用 Kotlin 或 Java 写处理函数，iOS 用 Swift 或 Objective-C，各端写法不同。
:::

::: details 用 React Native 写的代码能直接跑在 Web 上吗？
不能直接跑，React Native 的组件是 `View`、`Text`，不是 DOM 元素。可以借助 react-native-web 这类库把这些组件映射成 DOM，实现部分代码复用，但导航、原生模块、样式细节都要单独处理。Flutter 也能编译到 Web，不过渲染方式和普通网页不同，SEO 和首屏加载需要额外考虑。
:::

## 易错点

- React Native 不是 WebView 方案，它渲染的是原生控件；Flutter 也不是，它既不用 WebView 也不用系统控件
- "热更新"是技术能力，能不能用取决于商店政策，面试时要主动说明这个限制
- 选型不要只比性能，团队现有的技术栈、招聘、维护成本往往影响更大
