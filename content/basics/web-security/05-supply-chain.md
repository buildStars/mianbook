# 前端依赖的供应链安全怎么做？

::: tip 一句话回答
一个前端项目动辄上千个间接依赖，任何一个出问题，恶意代码就会进入开发机、CI，或者被打包进产物送到用户的浏览器里。主要风险有：**恶意包和仿冒包名**、**维护者账号被盗后发布带毒版本**、**依赖混淆**（内部包名被人在公共源抢注）、**安装脚本执行任意代码**。措施分三层：安装时**提交 lock 文件、CI 用 `npm ci`、限制安装脚本、私有包用 scope 绑定私有源**；日常**审计漏洞、审核升级、减少不必要的依赖**；运行时 **CDN 脚本加 SRI**，CI 里的凭证**最小权限**。
:::

## 详细解析

### 风险

| 风险 | 怎么发生 | 后果 |
| --- | --- | --- |
| 恶意包、仿冒包名 | 包名和流行包只差一两个字母或一个连字符，手误就装上了 | 安装或运行时执行恶意代码 |
| 维护者账号被盗 | 攻击者用被盗的账号给流行包发布新版本，版本范围允许时会被自动装上 | 曾有流行包被投毒，下游大量项目受影响 |
| 依赖混淆 | 内部包没有加 scope，有人在公共源发布同名、版本号更高的包，包管理器装了公共源上的那个 | 内部构建机被控制 |
| 安装脚本 | `preinstall`、`postinstall` 在安装时自动执行，能读取环境变量、SSH 密钥、发布令牌 | 开发机和 CI 的凭证泄露 |
| 第三方运行时脚本 | CDN 上的文件被篡改，或者引入的统计、客服脚本被入侵 | 直接在用户的浏览器里执行，效果等同 XSS |
| 已知漏洞 | 依赖长期不升级 | 漏洞细节公开后被利用 |

### 安装环节

- **lock 文件 + `npm ci`**：lock 文件锁定整棵依赖树的版本和完整性哈希，版本不会悄悄漂移到刚发布的带毒版本，包内容被篡改也装不上。原理见 [lock 文件](/basics/node/10-package-managers)
- **审查 lock 文件的变更**：PR 里 lock 文件的 `resolved` 地址如果指向了陌生的源，要追问原因
- **限制安装脚本**：用 `npm ci --ignore-scripts` 或在 `.npmrc` 里设置 `ignore-scripts=true`，需要编译原生模块的包再单独处理。有的包管理器默认就不执行依赖的安装脚本，需要逐个放行，见 [Node.js 服务的安全问题](/basics/node/16-security)
- **晚一点升级**：新版本刚发布时，社区还没来得及发现问题。有的包管理器支持配置"发布满一段时间才允许安装"
- **私有包放进 scope**：内部包统一命名为 `@myco/xxx`，并把这个 scope 绑定到私有源，在公共源上也把这个 scope 注册下来，防止被别人抢占

```ini
# .npmrc
# @myco 下的包只从私有源安装
@myco:registry=https://npm.internal.example.com/
# 安装时不执行任何安装脚本（项目自己的 prepare 等也不执行）；npm run build 等命令仍会执行，但它们的 pre、post 钩子不会
ignore-scripts=true
```

### 日常维护

```bash
# CI 中：严格按 lock 文件安装，有高危漏洞时让流水线失败
npm ci --ignore-scripts
npm audit --omit=dev --audit-level=high
# 校验下载的包的仓库签名和来源证明（provenance）
npm audit signatures
```

- 用 Dependabot、Renovate 这类工具自动提升级 PR，但**不要无脑合并**：看变更记录，关键依赖要看包内容的变化，跑完测试再合
- **少引依赖**：几行代码或原生 API 能解决的，不引包。引入前看维护状态、下载量、它自己有多少依赖、有没有安装脚本
- 自己发布包时：账号开启双因素认证，用权限最小的令牌，发布时附带来源证明

### 运行时：给 CDN 脚本加 SRI

SRI（子资源完整性）让浏览器校验下载到的文件：计算文件的哈希，和 `integrity` 属性对不上就拒绝执行，CDN 上的文件被篡改也不会生效。

```html
<script
  src="https://cdn.example.com/lib@1.2.3/lib.min.js"
  integrity="sha384-（构建时计算出的哈希值）"
  crossorigin="anonymous"
></script>
```

- 哈希可以用 `openssl dgst -sha384 -binary lib.min.js | openssl base64 -A` 生成，前面加上 `sha384-`；构建工具一般有插件自动生成
- 跨源的资源必须加 `crossorigin`，CDN 也要返回 CORS 响应头，否则校验必定失败
- 支持 `<script>` 和 `rel` 为 `stylesheet`、`preload`、`modulepreload` 的 `<link>`
- 只适合内容固定的文件。地址不变、内容会更新的第三方脚本用不了 SRI

### CI 最小权限

- 安装依赖、跑测试的步骤拿不到发布令牌和云平台凭证，只有发布那一步才有
- 来自外部 fork 的 PR 不能访问密钥
- 尽量用短期凭证（比如基于 OIDC 的可信发布）代替长期有效的令牌

## 面试官可能追问

::: details 已经提交了 lock 文件，为什么还会中招？
lock 文件只保证"装的和上次一样"，不保证上次装的是干净的：新增依赖或升级时，可能正好装上了带毒的版本，lock 文件会忠实地把它锁住。CI 里用 `npm install` 而不是 `npm ci`，lock 文件还可能被改写。另外安装脚本不受 lock 文件约束，装上就会执行。
:::

::: details npm audit 没有报漏洞，是不是就安全了？
不是。`npm audit` 只对照已公开的漏洞数据库，新发布的恶意版本在被发现、上报之前，它查不出来。要配合锁版本、限制安装脚本、晚一点升级、审查依赖变更这些手段。也可以引入分析包行为的工具，检查新版本是否新增了安装脚本、网络请求、读取环境变量等可疑行为。
:::

::: details 统计、客服这类第三方脚本用不了 SRI，怎么控制风险？
能自己托管的就下载固定版本放到自己的服务器上，再加 SRI；不能的，用 CSP 限制它能加载的来源和能请求的地址（见 [CSP](/basics/web-security/01-csp)），只在需要的页面加载它，登录、支付这类敏感页面不加载。风险高的挂件可以放进单独源的 iframe 里隔离。
:::

## 易错点

- 只关注 `dependencies`：构建工具这类 `devDependencies` 同样在开发机和 CI 上运行，能偷凭证、篡改产物
- 加了 SRI 但没加 `crossorigin`，跨源资源的校验必定失败
- 关闭安装脚本后，需要编译原生模块的依赖可能装不完整，要逐个确认并单独放行
- 以为用了私有源就安全：没有 scope 的内部包名，仍然可能被解析到公共源上的同名包
