# 服务网格是什么？解决了什么问题？

::: tip 一句话回答
服务网格把微服务之间通信的**治理能力**（服务发现、负载均衡、重试超时、熔断、mTLS 加密和身份认证、指标和链路追踪）从业务代码里拿出来，交给和服务一起部署的**代理**去做。典型结构是**数据面**（每个 Pod 旁边一个 Sidecar 代理，例如 Envoy，拦截所有进出流量）加**控制面**（统一下发路由、安全策略和证书）。好处是多语言统一、业务无感知；代价是多一跳的延迟、额外的资源消耗和不小的运维复杂度。
:::

## 详细解析

### 没有网格时的问题

微服务多了以后，每个服务都要处理同一批问题：调用超时怎么设、失败重试几次、下游挂了要[熔断](/basics/distributed/09-circuit-breaker)、服务之间要加密和鉴权、要上报指标和链路。传统做法是用 SDK（比如 Java 的 Spring Cloud 一套组件），问题是：

- **语言绑定**：Go、Node.js、Python 服务各要一套 SDK，行为很难一致
- **升级难**：治理逻辑改一下，所有服务都要升级依赖、重新发布
- **侵入业务**：业务开发要理解和配置一堆治理参数

### 架构：数据面和控制面

```text
            ┌──────────── 控制面 ────────────┐
            │ 服务发现 · 路由规则 · 证书签发 │
            └──────┬─────────────────┬───────┘
                   │ 下发配置和证书   │
     ┌─────────────▼───┐       ┌─────▼───────────┐
     │ Pod A           │       │ Pod B           │
     │ 业务容器        │       │ 业务容器        │
     │   ↕ (localhost) │ mTLS  │   ↕ (localhost) │
     │ Sidecar 代理 ◄──┼───────┼──► Sidecar 代理 │
     └─────────────────┘       └─────────────────┘
```

- **数据面**：Sidecar 通过 iptables 等方式透明拦截 Pod 的进出流量，业务代码照常调用 `http://order-service`，不用改
- **控制面**：监听 Kubernetes 里的 Service 和 Pod 变化，把路由表、策略、证书推送给所有代理
- 常见实现：Istio（数据面用 Envoy）、Linkerd（自研的轻量代理）

### 能做什么

| 能力 | 例子 |
| --- | --- |
| 流量管理 | 按比例或按 Header 把流量切到新版本（金丝雀发布），超时、重试、熔断、故障注入 |
| 安全 | 服务之间自动 mTLS，证书由控制面签发和轮换；按服务身份配置"谁能调用谁" |
| 可观测性 | 代理统一产出请求量、错误率、延迟指标，传递追踪头，画出服务调用拓扑 |

这里的金丝雀比 Deployment 自带的滚动发布（见 [滚动发布](/basics/container/07-k8s-probes-rollout)）更精细：滚动发布只能按 Pod 数量比例分流，网格可以精确到 1% 的请求，或者只让内部员工的请求进新版本。

### 代价

- **延迟**：每次调用多经过两个代理（调用方和被调用方各一个）
- **资源**：每个 Pod 多一个代理容器，Pod 多了以后 CPU 和内存加起来很可观
- **复杂度**：出问题时要判断是业务还是代理，配置项多、学习曲线陡；Sidecar 和业务容器的启动、退出顺序也要处理

为了降低开销，出现了不用 Sidecar 的模式，例如 Istio 的 ambient 模式：每个节点一个共享代理负责 mTLS 和四层流量，需要七层能力时再按需部署专门的代理。也有基于 eBPF 在内核里处理部分流量的方案。

## 面试官可能追问

::: details 服务网格和 API 网关有什么区别？
API 网关管**南北向**流量，也就是外部请求进入系统的入口，关注鉴权、限流、协议转换、对外 API 管理，见 [API 网关](/basics/backend-design/11-api-gateway)。服务网格管**东西向**流量，也就是服务之间的内部调用，关注服务间的可靠性和安全。两者底层可能都是 Envoy，常常一起用：网关在入口，网格在内部。
:::

::: details 什么时候不值得上服务网格？
服务数量少、技术栈单一、团队没有专人维护基础设施时，SDK 或框架自带的治理能力就够了。网格解决的是"几十上百个多语言服务统一治理"的问题，规模不到时，增加的复杂度和资源开销往往大于收益。
:::

::: details 有了网格自动重试，业务代码还需要注意什么？
重试只对幂等请求安全，非幂等的写请求（比如创建订单）被重试可能造成重复，网格配置里要按路由区分，业务侧也要做好[幂等](/basics/distributed/06-mq-idempotent)。另外调用链上每一层都重试，次数会成倍放大，容易把下游压垮，重试最好只在一层做。
:::

## 易错点

- 把服务网格和 API 网关混为一谈，二者管的流量方向不同
- 以为 mTLS 有了就不用鉴权。mTLS 证明"调用方是哪个服务"，具体允许哪些操作还要配授权策略，用户级的权限仍然要业务判断
- 忽略 Sidecar 的资源和延迟开销，在资源很紧的集群上直接全量注入
