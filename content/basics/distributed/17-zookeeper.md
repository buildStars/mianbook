# ZooKeeper 是什么？能用来做哪些事？

::: tip 一句话回答
ZooKeeper 是一个**分布式协调服务**，对外提供一棵类似文件系统的**节点树（znode）**，每个节点能存少量数据。它的几个关键能力：**临时节点**随会话断开自动删除，**顺序节点**自动带递增编号，**Watcher** 在节点变化时通知客户端；集群内部靠 **ZAB 协议**保证写操作在多数节点上有序一致。基于这些能力，可以做**配置中心、注册中心、分布式锁、选主**。Kafka 后来用自带的 **KRaft** 替代了 ZooKeeper，减少一个外部依赖。
:::

## 详细解析

### 数据模型

```text
/
├── config
│   └── db-url            持久节点，存配置值
├── services
│   └── order
│       ├── 10.0.0.1:8080 临时节点，服务实例下线后自动消失
│       └── 10.0.0.2:8080
└── locks
    └── order-123
        ├── lock-0000000001  临时顺序节点
        └── lock-0000000002
```

| 节点类型 | 特点 |
| --- | --- |
| 持久节点 | 创建后一直存在，直到被显式删除 |
| 临时节点 | 和客户端会话绑定，会话结束（主动关闭或心跳超时）就自动删除，不能有子节点 |
| 顺序节点 | 创建时服务端在名字后追加单调递增的编号，可以和持久、临时组合 |

znode 是为存协调用的小数据设计的，单节点默认最多约 1MB，不能拿来当数据库。

### Watcher

客户端读节点时可以注册 Watcher，节点数据变化、被删除或子节点列表变化时，服务端推送一个事件。传统 Watcher 是**一次性**的，触发后要重新注册，而且事件只说"变了"，不带新数据，客户端要自己再读一次。重新注册的间隙里发生的变化不会单独通知，所以客户端要以重新读到的数据为准。

### ZAB 协议简述

集群里有一个 Leader，其余是 Follower。所有写请求都转给 Leader：

1. Leader 给写操作分配全局递增的事务 ID（zxid），作为提案发给 Follower
2. 超过半数节点写入日志并确认后，Leader 提交，再通知大家提交
3. Leader 挂了进入崩溃恢复：选出拥有最新 zxid 的节点当新 Leader，同步完数据后才对外服务

读请求可以由任何节点直接响应，所以可能读到稍旧的数据，需要最新值时可以先调用 `sync`。思路和 Raft 很像，都是"单 Leader + 多数派确认"，Raft 的细节见 [Raft 共识算法](/basics/distributed/10-raft)。因为要多数派存活，集群一般部署奇数台，5 台能容忍 2 台故障。

### 典型用途

- **配置中心**：配置写在持久节点上，各服务读取并注册 Watcher，配置变更后收到通知重新拉取
- **注册中心**：服务实例启动时在 `/services/<名字>` 下建临时节点，宕机后会话超时、节点自动删除；消费者监听子节点列表。它是 CP 型的，选主期间不能写，取舍见 [服务注册与发现](/basics/distributed/11-service-discovery)
- **分布式锁**：每个客户端在锁目录下建临时顺序节点，编号最小的获得锁；其他客户端只监听**前一个**节点，前一个删除后再判断自己是不是最小。持锁者崩溃时临时节点自动删除，不会死锁。和 Redis 方案的对比见 [Redis 分布式锁](/basics/redis/07-distributed-lock)
- **选主**：多个候选者抢着创建同一个临时节点，创建成功的就是主；主挂了节点消失，其他候选者收到通知重新抢

### Kafka 为什么不再用 ZooKeeper

Kafka 早期把 Broker 列表、Topic 元数据、Controller 选举都放在 ZooKeeper 里，带来几个问题：运维要多管一套集群；元数据变更要经过 ZooKeeper 再同步给 Broker，分区数多时 Controller 切换和元数据加载很慢，限制了集群能支持的分区规模。KRaft 模式把元数据存在 Kafka 内部的一个日志里，由几个 Controller 节点用 Raft 达成一致，元数据和消息用同一套日志机制管理。

## 代码示例

```bash
# zkCli.sh 里的基本操作
create /config/db-url "mysql://10.0.0.5:3306/app"   # 持久节点
create -e /services/order/10.0.0.1:8080 ""          # 临时节点
create -s -e /locks/order-123/lock- ""              # 临时顺序节点，返回带编号的实际路径
get -w /config/db-url                               # 读数据并注册一次性 Watcher
ls /locks/order-123                                 # 列出子节点
```

## 面试官可能追问

::: details 分布式锁为什么只监听前一个节点，不监听锁节点本身？
如果所有等待者都监听同一个节点，锁一释放所有客户端同时被唤醒去抢，大部分抢不到，这叫羊群效应，会给 ZooKeeper 带来瞬时压力。只监听前一个节点，每次释放只唤醒一个客户端，按编号排队，也是公平锁。
:::

::: details 会话超时会带来什么问题？
客户端长时间 GC 停顿或网络抖动，可能导致会话超时，临时节点被删。客户端以为自己还持有锁或还是主，其实别人已经接手了，出现两个主。业务上要监听会话状态，断开后立即停止相关操作；关键写操作可以带上递增的版本号（fencing token）让下游拒绝过期请求。
:::

::: details ZooKeeper 和 etcd 怎么选？
两者定位相近，都是 CP 的协调服务。etcd 用 Raft，提供 HTTP/gRPC 接口，是 Kubernetes 的元数据存储，云原生生态里更常见；ZooKeeper 在 Hadoop、HBase、Dubbo 等 Java 生态里用得多，客户端常配合 Curator 使用。新项目一般跟着所在生态选。
:::

## 易错点

- ZooKeeper 保证的是写操作的顺序一致，读请求默认可能读到旧数据
- 传统 Watcher 是一次性的，触发后要重新注册
- 临时节点不能有子节点；它跟随会话而不是跟随某个 TCP 连接，短暂断线重连到同一会话不会被删
- 它适合存少量协调数据，不适合存业务数据或频繁写的大数据
