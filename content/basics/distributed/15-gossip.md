# Gossip 协议是什么？适合什么场景？

::: tip 一句话回答
Gossip（流言协议）是一种去中心化的信息传播方式：每个节点**定期随机挑几个节点交换信息**，收到新信息的节点再继续往外传，像流言一样扩散。传播轮数大约随节点数**按对数增长**，没有中心节点，任意节点故障都不影响整体，但只能保证**最终一致**，传播有延迟，还会有冗余消息。它适合**集群成员管理、故障检测、元数据同步**这类能容忍短暂不一致的场景，比如 Redis Cluster、Cassandra、Consul 的成员管理；需要强一致的数据（如选主、配置提交）要用 [Raft](/basics/distributed/10-raft) 这类共识算法。
:::

## 详细解析

### 怎么传播

每个节点按固定周期执行：

1. 从已知节点里随机选几个（这个数叫扇出）
2. 和它们交换自己知道的状态（带版本号或心跳计数）
3. 双方按版本号合并，保留更新的那份

交换方式有三种：

| 方式 | 做法 | 特点 |
| --- | --- | --- |
| push | 把自己的信息发给对方 | 新信息刚出现时传得快，后期大量消息是对方已经知道的 |
| pull | 向对方要它的信息 | 后期收敛快，前期慢 |
| push-pull | 互相发送，各取所需 | 收敛最快，每次交换的数据多一些 |

从用途上还可以分为两类：**反熵**（定期全量或摘要比对，修复所有差异，保证最终一致）和**谣言传播**（只传播新消息，传了若干轮后不再传，消息量小，但有很小的概率有节点没收到）。

### 为什么收敛快

假设每轮每个已知信息的节点都告诉一个随机节点，知道的节点数大致每轮翻倍，所以全网都知道大约需要 O(log N) 轮。节点数从 100 涨到 10000，所需轮数只是增加几轮。每个节点每轮只和少数节点通信，单节点的负载不随集群规模线性增长。

### 用在故障检测

集中式心跳由一个中心节点检查所有人，中心节点本身是瓶颈和单点。Gossip 的思路是：

- 每个节点随机探测别的节点，把"我觉得某节点可能挂了"的怀疑通过 Gossip 传出去
- 多个节点都怀疑同一个节点时，才判定它下线，避免一次网络抖动就误判
- SWIM 协议还加了**间接探测**：直接探测失败后，请其他几个节点帮忙探测，排除只是自己和它之间的网络问题

### Redis Cluster 里的 Gossip

Redis Cluster 没有中心的元数据节点，节点之间通过集群总线互发 PING、PONG，消息里除了自身状态，还带上自己知道的部分其他节点的信息：

- 一个节点在 `cluster-node-timeout` 内没有响应，被标记为**疑似下线**（PFAIL）
- 这个怀疑通过 Gossip 传开，当多数主节点都认为它下线时，标记为**已下线**（FAIL）并广播，随后触发从节点故障转移
- 槽位分配、配置纪元等集群元数据也靠这种方式在节点间同步

集群模式的整体结构见 [主从复制、哨兵和 Cluster 有什么区别](/basics/redis/08-high-availability)。

### 和 Raft 对比

| | Gossip | Raft |
| --- | --- | --- |
| 结构 | 去中心化，节点地位平等 | 有 Leader，写入都经过 Leader |
| 一致性 | 最终一致 | 强一致（多数派确认后才提交） |
| 规模 | 能扩展到很多节点 | 通常 3～5 个节点，节点多了写入变慢 |
| 容错 | 任意节点故障不影响传播 | 多数派存活才能工作 |
| 典型用途 | 成员管理、故障检测、元数据扩散 | 选主、配置存储、分布式锁 |

两者经常搭配使用：Consul 用 Gossip 管理大量节点的成员和健康状态，用 Raft 在少数服务端节点之间存储需要强一致的数据。

## 面试官可能追问

::: details Gossip 有哪些缺点？
信息传到所有节点有延迟，期间不同节点看到的状态不同；同一条信息会被重复发送多次，有冗余流量；消息量和状态大小相关，节点很多时每次交换的数据会变大，需要只传摘要或部分节点的信息。另外节点之间默认互相信任，不防恶意节点伪造状态。
:::

::: details 节点状态冲突了怎么合并？
每条状态带一个版本号，比如节点自己维护的心跳计数器或者纪元号，只有节点自己能增加；合并时取版本号大的。这样不依赖各节点的物理时钟，也不会出现旧消息覆盖新状态。
:::

::: details 为什么 Redis Cluster 不用 Raft 管理元数据？
集群节点数可能比较多，而且每个节点都要知道所有节点的状态和槽位分布，用 Gossip 不需要一个中心协调者，节点增减也方便。代价是元数据是最终一致的，配置冲突靠配置纪元解决，故障转移的投票则由主节点按多数派完成。
:::

## 易错点

- 把 Gossip 当成一致性算法：它只负责传播，保证不了强一致
- 认为一个节点探测不到就判定下线：实际需要多个节点的怀疑汇总，避免误判
- 用物理时间戳合并状态，时钟不同步时会出现旧状态覆盖新状态
- 以为扇出越大越好：收敛更快，但冗余消息和网络开销也随之增大
