# Kafka 为什么吞吐量这么高？

::: tip 一句话回答
Kafka 的设计核心是把消息当作**只追加的日志**，围绕这一点做了几件事：**顺序写磁盘**，避免随机 I/O；读写都依赖操作系统的**页缓存**，不在 JVM 里自己缓存；消费时用 **sendfile 零拷贝**把数据从页缓存直接发到网卡；生产者和 Broker 都按**批**处理，批量数据还能**整体压缩**；一个 Topic 拆成多个**分区**，分布在不同 Broker 上并行读写。代价是：单分区内才有序、消息不能按条件查询和单独删除、可靠性依赖副本而不是每条都刷盘。
:::

## 详细解析

### 顺序追加写

每个分区在磁盘上是一组日志段文件，新消息只追加到当前段的末尾，不做原地修改。顺序写能充分利用磁盘的预读和合并写，对机械硬盘尤其关键，因为随机写的瓶颈在磁头寻道。消费者也是按位移顺序读，读写都是顺序的。

消息删除不是一条条删，而是按时间或大小**整段删除**旧的日志段文件，代价很低。

### 依赖页缓存

Kafka 写入时把数据交给操作系统，进入页缓存就返回，由操作系统异步刷盘；读取时如果消费者跟得上，数据大多还在页缓存里，直接从内存读。

这样做的好处：

- 不在 JVM 堆里缓存数据，避免大堆带来的 GC 压力和一份数据在堆内外各存一份
- Broker 进程重启后页缓存还在，不需要重新预热
- 操作系统的预读和回写策略本身就针对顺序访问做了优化

不每条都刷盘，可靠性靠多副本保证，见 [消息队列怎么保证消息不丢失](/basics/distributed/05-mq-reliability)。

### 零拷贝

消费者拉取消息时，Broker 要把文件内容发到网络。传统做法要把数据从内核读到用户空间再写回内核；Kafka 用 `sendfile`，数据直接从页缓存送到 Socket，省掉了用户态和内核态之间的拷贝和切换，原理见 [零拷贝](/basics/os/07-zero-copy)。

前提是 Broker 不需要改动消息内容。消息格式在生产者、Broker、消费者之间保持一致，Broker 不用解码再编码，才能直接转发文件字节。开启 TLS 后数据要在用户态加密，这条路径就用不上了。

### 批量和压缩

- 生产者把发往同一分区的消息攒成一批再发，`batch.size` 控制批的大小，`linger.ms` 控制最多等多久
- 压缩以批为单位进行（`compression.type`），重复内容越多，压缩效果越好；Broker 通常原样存储压缩后的批，消费者拉到后再解压
- 消费者一次拉取也是一批

批量把"每条消息的固定开销"分摊掉了：网络往返、系统调用、请求头都按批计算。

### 分区并行和稀疏索引

- 一个 Topic 拆成多个分区，分布在不同 Broker 上，生产和消费都能水平扩展；一个消费者组里，每个分区由一个消费者处理，见 [消费者组和 Rebalance](/basics/distributed/13-kafka-consumer-group)
- 每个日志段配有**稀疏的位移索引和时间索引**，不为每条消息建索引，而是隔一段记一条，按位移查找时先二分找到附近的位置，再顺序扫描一小段，索引文件小，能常驻内存

### 代价

| 设计 | 换来的 | 付出的 |
| --- | --- | --- |
| 只追加日志 | 顺序 I/O | 不能按条件查询、不能单独删除一条消息 |
| 依赖页缓存 | 简单高效 | 消费者严重落后时要读磁盘，可能影响同机的实时读写 |
| 批量 | 吞吐量 | 增加一点延迟（最多 linger.ms） |
| 分区 | 并行 | 只有分区内有序，见 [消息的顺序怎么保证](/basics/distributed/07-mq-order-backlog) |

## 面试官可能追问

::: details 分区越多吞吐量越高吗？
不是。分区多了，每个分区的批会变小，压缩和批量的效果下降；Broker 要管理更多文件句柄和副本同步；Leader 迁移、故障恢复和消费者 Rebalance 都会变慢。分区数要按目标吞吐量和消费者数量估算，留一些余量即可。
:::

::: details 生产者怎么调参提高吞吐量？
适当增大 `batch.size` 和 `linger.ms`，让批更大；开启压缩；`acks` 设置会影响延迟和可靠性，追求可靠时用 `acks=all` 加最少同步副本数，不要为了吞吐量牺牲可靠性。调参后要压测，因为批大了延迟也会上升。
:::

::: details 消费者落后很多时为什么会影响整个 Broker？
落后的消费者读的是早已被挤出页缓存的旧数据，只能读磁盘，同时这些读入的数据又会挤占页缓存，让正常消费者也开始读盘。积压的处理见 [消息积压了怎么处理](/basics/distributed/07-mq-order-backlog)。
:::

## 易错点

- 说"Kafka 快是因为数据都在内存里"：数据在磁盘上，快在顺序 I/O 和利用页缓存
- 把零拷贝说成"完全没有拷贝"：省掉的是用户态和内核态之间的拷贝，DMA 拷贝仍然存在
- 以为每条消息都会立即刷盘：默认交给操作系统刷盘，可靠性靠副本
- 认为分区越多越好，忽略了批量效果下降和元数据、恢复成本
