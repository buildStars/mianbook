# 分布式定时任务怎么保证只执行一次？

::: tip 一句话回答
服务部署多个实例后，每个实例里的定时器都会触发，同一个任务就会执行多次。保证"同一次触发只执行一次"的机制有三类：**数据库互斥**（按"任务名 + 计划时间"插入唯一记录，或抢行锁，Quartz 集群模式就是这样）、**分布式锁**（抢 Redis 或 ZooKeeper 的锁，ShedLock 是现成实现，关键是锁时长）、**选主**（只有主节点触发）。这三类都有边界情况：锁过期、选主切换期间双主、重试和补跑，所以最后一道防线是**任务本身幂等**。独立调度中心的整体设计见 [设计一个分布式定时任务调度系统](/basics/backend-design/13-distributed-scheduler)。
:::

## 详细解析

### 问题在哪

```text
实例 A  ── 每天 02:00 触发 ──▶ 生成日报 ┐
实例 B  ── 每天 02:00 触发 ──▶ 生成日报 ├─▶ 同一份日报生成 3 次、通知发 3 遍
实例 C  ── 每天 02:00 触发 ──▶ 生成日报 ┘
```

要做到的是：不管多少个实例同时到点，**同一次计划触发**只有一个实例真正执行。

### 三类机制对比

| 机制 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 数据库互斥 | 按"任务名 + 计划时间"插入一行（唯一索引），插入成功的实例执行；或者 `SELECT ... FOR UPDATE` 抢行锁 | 不引入新组件，唯一索引天然防重，还留下了执行记录 | 依赖数据库可用，任务多时有压力 |
| 分布式锁 | 触发时抢锁，抢到的执行 | 实现简单 | 锁时长难定：短了任务没跑完锁就过期，长了节点崩溃后要等很久 |
| 选主 | 用 ZooKeeper、etcd 或 Kubernetes 的 Lease 选出一个主节点，只有主节点触发 | 逻辑清晰，任务多时不用每个都抢锁 | 主节点压力集中；切换期间可能短暂双主 |

Java 生态里的 ShedLock 属于分布式锁这一类：用数据库、Redis 等存储一条锁记录，保证同一个任务同一时刻只在一个节点执行。它要求配置 `lockAtMostFor`（锁最长持有时间，节点崩溃后锁也会到期释放），还可以配 `lockAtLeastFor`（最短持有时间）。它只负责"不并发执行"，不负责调度、重试和分片。Redis 锁的细节见 [怎么用 Redis 实现分布式锁](/basics/redis/07-distributed-lock)。

### 锁要按"计划时间"加，而不是只按任务名

只按任务名加锁并在执行完立即释放时，如果任务执行得很快，A 执行完释放锁，B 因为时钟稍慢，晚几百毫秒触发，又能抢到锁，任务就执行了两次。两种更稳的做法：

- 唯一键里带上**本次计划触发时间**，比如 `daily_report:2026-10-16T02:00`，同一次触发只能插入成功一次
- 锁不在执行完时立刻释放，而是保持到一个**最短持有时间**之后再过期，盖住节点间的时钟差（ShedLock 的 `lockAtLeastFor` 就是这个作用）

### 选主切换期间的双主

旧主因为 GC 停顿或网络分区失联，新主被选出来，旧主恢复后还以为自己是主，两边同时触发。缓解办法：

- 主节点每次触发前确认租约仍然有效，租约快到期就不再发起新任务
- 用**单调递增的任期号（fencing token）**，执行时把任期号带给存储，存储拒绝旧任期的写入

### 兜底：幂等

锁会过期、选主会短暂双主、失败会重试、人会手动补跑，所以任务本身要能重复执行：

- 按业务主键 upsert，或者先检查"这一期是否已处理"再处理，见 [怎么实现幂等](/basics/distributed/06-mq-idempotent)
- 记录每次执行的状态和处理到的位置，失败后从断点继续，而不是从头再来

## 面试官可能追问

::: details 用分布式锁，锁的过期时间怎么定？
按任务最长执行时间再留余量；执行时间不稳定的，可以加续期。同时设置最短持有时间，防止任务很快结束后其他节点因时钟差异再执行一次。最终兜底还是任务幂等。
:::

::: details Quartz 集群模式是怎么避免重复执行的？
多个节点共用同一套数据库表（JDBC JobStore），获取即将触发的 Trigger 时通过数据库行锁协调，抢到锁的节点把 Trigger 状态改掉，其他节点就拿不到同一次触发。所以它依赖数据库，节点之间的时钟也要同步。节点崩溃时，其他节点能检测到并接手它未完成的、标记为可恢复的任务。
:::

::: details 在 Kubernetes 里跑定时任务有什么选择？
可以用 CronJob，由集群按计划创建 Pod 执行，不需要业务实例之间抢锁；通过 `concurrencyPolicy` 控制上一次没跑完时是否允许新的一次开始。但 Kubernetes 文档也说明了 CronJob 在少数情况下可能创建两个 Job 或一个都不创建，所以任务仍然要幂等。
:::

::: details 需要分片、重试、监控的话怎么办？
那就超出了"只执行一次"的范畴，要用独立的调度中心（如 XXL-JOB、Elastic-Job），由调度中心决定在哪台机器执行，并负责分片、故障转移和错过触发的补偿。设计细节见 [设计一个分布式定时任务调度系统](/basics/backend-design/13-distributed-scheduler)。
:::

## 易错点

- 只按任务名加锁并立即释放，因为节点间时钟差异，同一次任务仍可能执行两次
- 锁的过期时间小于任务执行时间，任务没跑完别人又开始执行
- 以为选主就绝对只有一个主，忽略了切换期间的双主
- 认为用了锁或调度中心就不需要幂等：锁过期、重试和手动补跑都会重复执行
