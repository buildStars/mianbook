# Kafka 的消费者组和 Rebalance 是怎么回事？

::: tip 一句话回答
**消费者组**是 Kafka 实现"队列"和"广播"两种模式的方式：同一组内，**每个分区只分给一个消费者**，组内消费者分摊消息；不同组之间互不影响，各自完整消费一遍。每个组在每个分区上的消费进度叫**位移**，提交到内部 Topic `__consumer_offsets`。组成员或订阅的分区变化时，要重新分配分区，这就是 **Rebalance**。传统的 Rebalance 期间整个组暂停消费，还可能造成重复消费；可以用**协作式重平衡**、**静态成员**和合理的超时参数来减少它的频率和影响。
:::

## 详细解析

### 分区和消费者的对应关系

```text
Topic（4 个分区）     消费者组 A（2 个消费者）     消费者组 B（1 个消费者）
P0 ──────────────▶ C1                          ┐
P1 ──────────────▶ C1                          │
P2 ──────────────▶ C2                          ├─▶ D1（4 个分区全部消费）
P3 ──────────────▶ C2                          ┘
```

- 组内消费者数 **小于** 分区数：有的消费者负责多个分区
- 组内消费者数 **大于** 分区数：多出来的消费者分不到分区，处于空闲状态
- 所以分区数决定了一个组的最大并行度，想加消费者提速，先看分区够不够

### 位移提交

位移记录的是"下一条要消费的消息"的位置，按"消费者组 + 分区"保存。提交方式决定了投递语义：

| 方式 | 做法 | 风险 |
| --- | --- | --- |
| 自动提交 | 后台定期提交已拉取的位移 | 处理到一半崩溃：已提交但没处理完的会丢，没提交的会重复 |
| 处理后同步提交 | 业务处理成功后再提交 | 崩溃时会重复消费，需要幂等 |
| 处理前提交 | 先提交再处理 | 崩溃时会丢消息，一般不用 |

大多数场景选"处理成功后提交加幂等消费"，即至少一次，幂等的做法见 [消息重复消费怎么办](/basics/distributed/06-mq-idempotent)。

### 什么时候触发 Rebalance

- 有消费者加入组，比如扩容、重启
- 有消费者离开组：正常关闭，或者心跳超过 `session.timeout.ms` 没送达
- 消费者两次 `poll` 的间隔超过 `max.poll.interval.ms`，被认为处理卡住，主动离组
- 订阅的 Topic 分区数增加，或者用正则订阅时匹配到了新 Topic

其中第三种最常见也最隐蔽：一批消息处理太慢（调用慢接口、批太大），并不是消费者挂了，却触发了 Rebalance。

### Rebalance 的代价

传统的"急切式"Rebalance 要求所有成员先放弃全部分区，再统一重新分配：

- 整个组在这段时间里停止消费，消息开始积压
- 分区换了主人，原消费者已处理但还没提交位移的消息会被新消费者再处理一遍
- 如果消费者频繁超时离组又加入，会反复 Rebalance，形成恶性循环

### 怎么减少影响

1. **协作式重平衡**：分配策略用 `CooperativeStickyAssignor`，只迁移需要变动的分区，其他分区继续消费
2. **静态成员**：给每个消费者配置固定的 `group.instance.id`，在 `session.timeout.ms` 内重启回来，不触发 Rebalance，适合滚动发布
3. **调参**：每次 `poll` 拉的条数（`max.poll.records`）别太多，保证一批能在 `max.poll.interval.ms` 内处理完；慢处理可以交给业务线程池，但要管好位移提交
4. **在分区被收回前提交位移**：注册重平衡监听器，在分区被撤销时提交已处理的位移，减少重复

消费积压的整体处理思路见 [消息积压了怎么处理](/basics/distributed/07-mq-order-backlog)。

## 面试官可能追问

::: details 想让同一条消息被两个服务都处理，怎么做？
让两个服务使用不同的消费者组。组之间的位移互相独立，各自从头到尾消费一遍，这就是 Kafka 的广播模式。同一个组里的消费者是分摊关系，不会重复拿到同一个分区的消息。
:::

::: details 消费者处理一条消息要很久，怎么避免被踢出组？
先评估能否拆小或异步化。实在耗时，就减小 `max.poll.records`、适当调大 `max.poll.interval.ms`；或者把消息交给工作线程处理，主线程继续 `poll`，但要暂停对应分区的拉取（`pause`），处理完再恢复并提交位移，否则会越拉越多。
:::

::: details Rebalance 时谁负责分配分区？
组协调者是某个 Broker，负责管理成员和心跳；具体的分配方案通常由组内选出的一个消费者（组长）按分配策略计算，再经协调者下发给所有成员。Kafka 后来还引入了由 Broker 端计算分配的新协议，减少客户端之间的协调。
:::

## 易错点

- 以为加消费者就能无限提速：组内消费者数超过分区数后，多出来的只会空闲
- 把 `max.poll.interval.ms` 超时和心跳超时混为一谈：前者是处理太慢，后者是进程或网络有问题
- 用自动提交又不做幂等，Rebalance 或崩溃后出现重复或丢失
- 滚动发布时每重启一个实例就触发一次全组暂停，却不知道有静态成员和协作式重平衡
