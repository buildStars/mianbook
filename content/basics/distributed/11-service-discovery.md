# 服务注册与发现是怎么工作的？注册中心该选 CP 还是 AP？

::: tip 一句话回答
微服务的实例会扩缩容、会重启换 IP，调用方不能写死地址。**服务注册**是实例启动时把自己的地址登记到注册中心，并通过**心跳**或**临时节点**维持存活；**服务发现**是调用方从注册中心拿到可用实例列表（通常本地缓存，并订阅变更），再用负载均衡选一个调用。注册中心选型的核心是 CAP 取舍：**CP**（ZooKeeper、etcd、Consul）保证数据一致，但网络分区时少数派一侧不可用；**AP**（Eureka、Nacos 的临时实例）分区时仍能读写，但可能返回过期的实例列表。服务发现场景通常更看重可用性。
:::

## 详细解析

### 基本流程

```text
  ① 注册 + 心跳                    ③ 订阅 / 拉取实例列表
服务提供者 ─────────▶ 注册中心 ◀────────────────── 服务调用者
                         │                               │
                         └──── ④ 实例变更推送 ──────────▶│
                                                         │ ⑤ 本地缓存 + 负载均衡
服务提供者 ◀─────────────────── ⑥ 直接调用 ─────────────┘
```

1. **注册**：实例启动后上报服务名、IP、端口、元数据（版本、机房、权重）
2. **保活**：定期发心跳，或者依赖会话（ZooKeeper 临时节点、etcd 租约），超时没续上就被摘除
3. **发现**：调用方按服务名查询实例列表，缓存在本地
4. **变更通知**：注册中心推送或调用方定期拉取，更新本地缓存
5. **下线**：正常关闭时主动注销，异常退出靠心跳超时摘除

调用方有本地缓存，注册中心短暂不可用时，已有的调用仍能继续。

### 客户端发现和服务端发现

| | 客户端发现 | 服务端发现 |
| --- | --- | --- |
| 做法 | 调用方自己查注册中心、自己做负载均衡 | 调用方只访问一个固定入口，由负载均衡器或代理去查实例 |
| 例子 | Spring Cloud 加 Nacos、Eureka；gRPC 的服务发现插件 | Kubernetes 的 Service 和 DNS，见 [Service 和 Ingress](/basics/container/06-k8s-service-ingress)；网关、Service Mesh 的 Sidecar |
| 优点 | 少一跳，负载均衡策略灵活 | 调用方简单，多语言友好 |
| 缺点 | 每种语言都要有客户端库 | 多一层代理，代理本身要高可用 |

负载均衡算法见 [反向代理和负载均衡](/basics/network/20-reverse-proxy)。

### CP 还是 AP

CAP 的含义见 [CAP 定理](/basics/distributed/01-cap-base)。

| 注册中心 | 一致性模型 | 特点 |
| --- | --- | --- |
| ZooKeeper | CP | 临时节点加 Watch；Leader 选举期间、少数派一侧不能提供服务 |
| etcd | CP | 基于 Raft，租约加 Watch，Kubernetes 用它存集群状态 |
| Consul | CP | 基于 Raft，自带健康检查和 DNS 接口 |
| Eureka | AP | 节点之间互相复制，没有 Leader；有自我保护机制 |
| Nacos | 可选 | 临时实例走 AP 协议、靠心跳保活；持久实例走 Raft、由服务端主动探测 |

为什么服务发现更看重 AP：拿到一个稍微过期的实例列表，最坏是调到一个刚下线的实例，失败后重试另一个就行；而注册中心整体不可用时，新实例注册不了、调用方拿不到列表，影响面大得多。反过来，配置中心、分布式锁、选主这类需要"所有人看到同一份数据"的场景，才更需要 CP，见 [Raft 共识算法](/basics/distributed/10-raft)。

### 健康检查和自我保护

- **心跳**只能说明进程活着，不代表能正常处理请求，可以叠加主动探测（HTTP 健康检查接口）
- **自我保护**：短时间内大量实例同时心跳超时，很可能是注册中心自己的网络出了问题，这时 Eureka 会暂停摘除，宁可保留可能已失效的实例，也不把正常实例一起删掉
- 调用方也要兜底：超时、重试、熔断，见 [熔断、降级、限流](/basics/distributed/09-circuit-breaker)

## 面试官可能追问

::: details 实例下线了，调用方多久能感知？期间请求怎么办？
主动注销时，取决于注册中心推送和调用方缓存刷新的速度；异常宕机时，还要再加上心跳超时时间。期间请求可能打到已下线的实例，所以要配合连接失败时快速重试另一个实例，以及优雅停机：先注销、等流量摘干净再退出进程。
:::

::: details ZooKeeper 做注册中心有什么问题？
它是 CP 的，Leader 选举期间和网络分区时少数派节点不能写入，可能导致新实例注册失败；传统的 Watch 是一次性的，触发后要重新注册（新版本才加入了持久 Watch）；实例很多、变更频繁时，通知风暴会给集群很大压力。它更适合做协调服务，不是特别适合大规模的服务发现。
:::

::: details 注册中心整个挂了，服务之间还能调用吗？
已经在运行的调用方有本地缓存，可以按缓存的列表继续调用；但新启动的调用方拿不到列表，实例变更也感知不到。所以客户端要把实例列表持久化到本地文件作为兜底，注册中心本身也要集群部署。
:::

## 易错点

- 把"注册中心选 CP 更可靠"当成默认答案：服务发现能容忍短暂的不一致，更怕不可用
- 只靠心跳判断健康，进程活着但已经无法处理请求的实例摘不掉
- 停机时不先注销，直接杀进程，导致下线期间出现一批失败请求
- 混淆客户端发现和服务端发现，说不清 Kubernetes 的 Service 属于哪一种
