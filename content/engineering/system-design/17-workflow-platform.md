# 设计一个可视化的 AI 工作流编排平台

::: tip 一句话回答
用户在画布上拖节点、连线，保存成一份 **DAG 定义**（节点、边、参数、变量引用），发布后不可变、带版本。执行时由**执行引擎**按拓扑顺序调度：依赖都完成的节点进队列，由 Worker 并行执行；每个节点的输入输出都**持久化**，失败按策略**重试**，中断后从**检查点**恢复。节点之间用**变量引用**传数据，如 `{{ node1.output.text }}`。平台还要提供单步调试和完整的运行日志，用**插件机制**接入模型和工具，并按租户做**配额**和隔离。
:::

## 详细解析

### 需求澄清

- 用户：业务人员和开发者，用拖拽搭建"读取文档 → 大模型抽取 → 条件判断 → 调接口"这类流程
- 节点类型：开始和结束、大模型调用、知识库检索、代码执行、HTTP 请求、条件分支、循环、并行、人工审批
- 触发方式：API 调用、定时任务、事件（Webhook）、对话
- 非功能：长流程可恢复；运行过程可追踪；多租户隔离和计费
- 和 [多租户 Agent 平台](/engineering/system-design/13-multi-tenant-agent-platform) 的区别：Agent 的步骤由模型临时决定，这里的步骤由用户预先画好，确定性更强（取舍见 [工作流和 Agent](/ai/agent/06-workflow-vs-agent)）

### 整体架构

```text
画布编辑器 ──保存──> 定义服务（DAG 校验、版本、发布）
                            │
触发器（API / 定时 / Webhook）──> 执行引擎（调度器）
                            │  读取定义，创建运行实例
                            v
               就绪节点队列 ──> Worker 池（按节点类型）
                 ^                │
                 │        ┌───────┼──────────┬───────────┐
                 │        v       v          v           v
                 │     模型网关  工具/HTTP  代码沙箱   人工审批
                 │                │
                 └── 节点完成事件 ─┘ ──> 状态存储（运行、节点执行、变量）
                                          │
                                   日志与追踪 ──> 调试面板
```

### 核心模块和数据模型

- **工作流定义**：`{ workflowId, version, nodes[], edges[], inputs, outputs }`。节点是 `{ id, type, config, inputs: { 参数名: 变量引用或常量 } }`，边描述依赖，条件分支的边带条件
- **发布校验**：检查是否有环、引用的变量是否存在且类型匹配、必填参数是否填了、引用的插件和凭证是否可用
- **运行实例**：`{ runId, workflowId, version, status, inputs, startedAt }`
- **节点执行记录**：`{ runId, nodeId, attempt, status, input, output, error, startedAt, endedAt, tokenUsage }`，既是日志也是检查点

**变量传递**：节点输出存在运行上下文里，下游用路径引用。执行节点前由引擎解析引用、做类型转换，节点本身不关心数据来源。大的输出（文件、长文本）存对象存储，上下文里只放引用，避免状态存储膨胀。

### 关键难点

**执行引擎的调度**：

1. 运行开始时，入度为 0 的节点进就绪队列
2. Worker 执行节点，结果写入状态存储，发出完成事件
3. 调度器收到事件，检查下游节点的依赖是否都已满足，满足的进队列；条件分支没走到的路径标记为跳过，汇合节点要能识别"跳过"
4. 所有终止节点完成，或者出现不可恢复的失败，运行结束

调度器本身无状态，所有状态在存储里，任何实例都能接手。也可以直接基于持久化执行引擎实现（思路见 [持久化执行](/ai/agent/14-durable-agent)）。

**并行和循环**：没有依赖关系的节点自然并行；"对列表每一项执行子流程"的节点展开成多个子执行，限制并发数，最后汇总。循环必须有最大次数，防止死循环。

**重试和恢复**：

- 节点级重试策略：最大次数、退避间隔、哪些错误可重试（超时、限流可以，参数错误不行）
- 每个节点完成后状态已持久化，Worker 或调度器崩溃后，从未完成的节点继续，已完成的不重跑
- 有副作用的节点（发邮件、写数据库）要幂等，带上 `runId + nodeId` 作为幂等键（见 [工具的幂等](/ai/tools/15-idempotent-tools)）
- 人工审批节点让运行进入等待状态，可能等几天，不占用 Worker

**调试**：

- 单节点运行：给一个节点手动填输入，只跑这一个节点
- 从某个节点重跑：复用上游节点的历史输出，修改后只跑后半段，调 Prompt 时非常省时间
- 每次运行在画布上回放：每个节点的输入、输出、耗时、token、错误，模型节点能看到完整的 Prompt（见 [链路追踪](/engineering/eval/07-tracing)）

### 扩展与优化

- **插件和模型接入**：节点类型由插件定义，插件声明输入输出的 Schema、配置表单和执行入口；模型统一走 [模型网关](/engineering/system-design/05-llm-gateway)，换模型只改配置
- **多租户**：每个租户有并发运行数、每日运行次数、token 预算的配额；就绪队列按租户公平调度；代码节点在沙箱里执行（见 [沙箱隔离](/engineering/security/06-sandbox)）
- **版本和灰度**：运行实例绑定启动时的版本，发布新版本不影响正在跑的流程；可以按比例把流量切到新版本
- **评测**：给工作流配评测集，发布前跑回归，对比新旧版本的输出

## 面试官可能追问

::: details 工作流运行到一半，用户发布了新版本，怎么处理？
正在运行的实例继续按旧版本跑完，因为它的节点结构和变量引用都基于旧版本。新触发的运行用新版本。所以定义必须不可变，运行记录里要存版本号。
:::

::: details 节点里调用的大模型输出不稳定，下游解析失败怎么办？
模型节点支持结构化输出，配置输出 Schema，平台负责校验，不合格自动带错误信息重试（见 [结构化输出](/ai/prompt/04-structured-output)）。下游节点的输入也做类型校验，问题在出错的节点就暴露出来，而不是传到很远的地方才报错。
:::

::: details 执行引擎自己写还是用现成的？
小规模、节点都很快时，自己写一个基于队列和状态表的调度器就够了。流程很长、需要等待外部事件、对可靠性要求高时，用成熟的工作流引擎或持久化执行框架更稳，平台只负责把 DAG 翻译成它的执行模型。
:::

## 易错点

- 运行实例引用"当前版本"的定义，发布新版本后正在跑的流程出错
- 节点的大段输出直接存在运行上下文里，状态存储越来越大、越来越慢
- 失败后整个流程从头重跑，已经执行过的副作用又执行了一次
- 允许无限循环，没有次数和总时长上限
