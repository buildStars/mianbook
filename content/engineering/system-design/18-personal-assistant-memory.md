# 设计一个有长期记忆的个人 AI 助理

::: tip 一句话回答
在普通对话产品上加三块：**记忆系统**、**工具集成**和**主动触发**。记忆在对话后**异步抽取**成一条条事实（偏好、身份信息、长期计划），带来源和时间存储；新对话时按相关性**检索**少量记忆注入上下文；新信息和旧记忆冲突时**更新**而不是堆积，长期不用或过期的**遗忘**。用户必须能**查看、修改、删除**自己的记忆。日历、邮件等工具通过 **OAuth** 授权，按最小权限访问，写操作要用户确认。主动提醒由定时任务和事件触发。隐私是这个产品的底线。
:::

## 详细解析

### 需求澄清

- 记住什么：用户的稳定信息（职业、家庭成员、饮食偏好）、长期目标、正在进行的事情、对助理的要求（"回答简短一点"）
- 能做什么：查日程、安排会议、总结邮件、到时间提醒
- 非功能：记忆准确，不乱编；用户完全掌控自己的数据；跨设备一致
- 记忆的原理和分类见 [Agent 的记忆](/ai/agent/04-memory)，基础的对话架构见 [对话产品设计](/engineering/system-design/02-chat-product)，这里讲整个产品怎么设计

### 整体架构

```text
客户端（App / Web / 消息渠道）
        │
    对话服务 ──> 上下文组装 ──> 模型
        │           ^   ^         │
        │   记忆检索 ┘   └ 工具结果 │ 工具调用
        │                         v
        │                工具网关（OAuth 令牌、权限、确认）
        │                   日历 / 邮件 / 待办 / 通讯录
        v
  对话结束事件 ──> 记忆抽取 Worker ──> 记忆存储（结构化 + 向量）
                                           ^
  调度器（定时 / 事件）──> 主动提醒 ───────┘ 读取相关记忆
        │
     推送服务
```

### 核心模块和数据模型

**记忆条目**：

```text
{ userId, memoryId, content, type, source: { conversationId, messageId },
  createdAt, updatedAt, lastUsedAt, expiresAt, confidence, status }
```

- `type` 区分偏好、事实、计划、对助理的指令，不同类型的检索和过期策略不同
- 保留来源，用户能看到"这条记忆是从哪次对话来的"，出错时可追溯
- 内容存一份结构化文本，同时存向量用于检索

**抽取**：对话结束或积累一定轮数后，异步用模型从对话里抽取候选记忆，不阻塞回复。只抽长期有用的信息，临时内容（"今天中午吃什么"）不记。用户明确说"记住……"时立即写入。敏感信息（健康、财务、证件号）默认不自动记，或者先问用户。

**检索和注入**：

- 少量核心记忆（名字、语言偏好、对助理的指令）每次都带上
- 其余按当前消息做语义检索，结合时间和使用频率排序，只注入最相关的几条（检索见 [混合检索](/ai/rag/05-hybrid-search)）
- 注入时标明这是记忆、记录于何时，让模型知道它可能已经过时

### 关键难点

**更新和冲突**：新抽取的候选记忆先检索相似的旧记忆，让模型判断是新增、更新、删除旧的还是忽略。例如旧记忆"住在北京"，新对话说"上个月搬到上海了"，应该更新为"住在上海"，而不是两条并存，否则助理会自相矛盾。

**遗忘**：

- 带有效期的记忆（"下周出差"）到期自动失效
- 长期没有被检索到、置信度低的记忆降权或归档
- 用户删除的记忆要真正删除，包括向量索引和缓存里的副本

**用户可控**：

- 记忆管理页面列出所有记忆，可以编辑、删除、一键清空；可以关闭记忆功能，或者开启不记录的临时对话
- 回答中用到了某条记忆时可以提示出来，用户发现不对能直接纠正

**工具授权**：

- 每个服务单独走 OAuth 授权，只申请需要的权限范围，令牌加密存放在工具网关，不进入模型上下文（见 [MCP 的鉴权](/ai/tools/13-mcp-auth) 和 [API Key 安全](/engineering/security/07-api-key)）
- 读操作直接执行，写操作（发邮件、接受会议邀请、删除日程）先给用户看草稿，确认后执行（见 [人在环路](/ai/agent/11-human-in-the-loop)）
- 邮件和日程内容是外部输入，可能带有注入指令，只当数据处理，不能触发未经确认的操作（见 [间接注入](/engineering/security/02-indirect-injection)）

**主动提醒**：

- 定时类：用户说"明天上午提醒我交报告"，解析成定时任务存进调度器
- 事件类：会议前提醒、重要邮件到达，订阅工具的变更通知或定期轮询
- 推送前再组装一次上下文，让提醒内容带上相关记忆；控制频率，允许用户关闭某类提醒

### 扩展与优化

- **隐私**：记忆按用户加密存储；明确告知是否用于训练；支持导出全部数据；日志里不记录记忆和邮件原文
- **评测**：构造多轮对话测试集，检查该记的有没有记住、该更新的有没有更新、删除后是否还会被用到
- **成本**：抽取用小模型批量处理；记忆检索结果按会话缓存

## 面试官可能追问

::: details 记忆抽取错了，比如把玩笑当真记住了，怎么办？
抽取时要求模型给出置信度，低置信的不写入或标为待确认；用到记忆时让用户看得到；用户纠正时直接修改那条记忆。保留来源也方便排查是抽取逻辑的问题还是对话本身有歧义。
:::

::: details 为什么不把所有历史对话都塞进上下文？
放不下，就算放得下也贵、慢，而且太多无关内容会让模型分心（见 [上下文窗口](/ai/llm/04-context-window)）。原始对话也不适合直接用：同一件事前后说法可能矛盾。抽取成精炼、去重、可更新的记忆，才能长期使用。
:::

::: details 多个设备同时对话，记忆会冲突吗？
记忆存在服务端，所有设备读同一份。抽取是异步的，两个对话几乎同时产生冲突的记忆时，按时间先后处理，写入时做版本检查，后到的更新基于最新的状态重新判断。
:::

## 易错点

- 只增不改，旧信息和新信息并存，助理前后矛盾
- 删除只删了数据库里的记录，向量索引里还在，仍然能被检索出来
- 把 OAuth 令牌或邮件全文放进 Prompt
- 自动记住健康、财务这类敏感信息，用户毫不知情
