# 设计一个从合同、发票里抽取结构化数据的系统

::: tip 一句话回答
链路是 **文件接入 → 解析（文本层提取或 OCR + 版面分析）→ 文档分类 → 按 Schema 抽取 → 校验 → 人工复核 → 入库**。抽取由**Schema 驱动**：每类文档定义要哪些字段、什么类型、怎么校验，模型按 Schema 输出 JSON。真正决定系统能不能上线的是后半段：**规则校验**（金额加总、日期合法、税号格式）、每个字段带**原文出处**、低置信度和校验失败的字段**转人工复核**，复核结果再回流成评测集。目标不是让模型全对，而是让错误能被发现。
:::

## 详细解析

### 需求澄清

- 文档类型：发票（格式相对固定）、合同（篇幅长、条款分散）、可能还有回单、报关单
- 输入形态：可复制文字的 PDF、扫描件、手机拍照，质量差别很大
- 输出：发票的金额、税额、开票方、日期、明细行；合同的甲乙方、金额、期限、违约条款等
- 准确率要求：财务数据错一个数字就是事故，必须有人工兜底
- 规模：假设每天上万份，允许分钟级延迟，不要求实时

### 整体架构

```text
上传 / 邮件 / 接口 ──> 文件存储 + 任务队列
                         │
                         v
       解析：文本层提取 │ OCR + 版面分析（表格、印章、手写）
                         │
                         v
                 文档分类（发票 / 合同 / 其他）
                         │
                         v
           按类型取 Schema ──> LLM 抽取（JSON + 出处）
                         │
                         v
          校验：格式 / 业务规则 / 交叉核对 ──> 置信度
                         │
            ┌────────────┴────────────┐
       全部通过：自动入库        有问题：人工复核队列
                                      │
                         复核结果入库 + 回流评测集
```

### 核心模块和数据模型

- **Schema 定义**：每类文档一个版本化的 Schema，字段有名称、类型、是否必填、校验规则、说明（说明写进 Prompt，告诉模型这个字段在文档里通常叫什么）
- **抽取结果**：每个字段存值、出处（页码、文本片段或坐标框）、置信度、校验状态
- **复核记录**：谁改了哪个字段、原值和新值，既是审计日志，也是评测数据

```json
{
  "field": "total_amount",
  "value": "12800.00",
  "source": { "page": 1, "text": "价税合计（小写）¥12,800.00" },
  "checks": ["amount_sum_ok"],
  "status": "auto_passed"
}
```

### 关键难点

**解析质量决定上限**：扫描件 OCR 错一个字，模型再强也抽不对。表格要用版面分析保留行列结构，不能简单拼成一行文本；有文本层的 PDF 优先直接提取文字。多模态模型可以直接看图片，适合版式复杂的文档，但要比较它和 OCR 方案的准确率和成本。

**结构化输出**：用 JSON Schema 约束或工具调用让模型输出固定结构（见 [稳定输出 JSON](/ai/prompt/04-structured-output)）。要求模型找不到就输出 null，不要猜一个看起来合理的值。

**出处和校验**：要求模型给出每个值依据的原文，系统再检查这段原文是否真的在文档里、是否包含这个值，这一步能挡住大部分编造。业务规则校验包括：明细金额加总等于合计、税额等于金额乘税率（允许舍入误差）、日期合法、税号符合格式；有外部数据源时做交叉核对，比如发票信息和查验接口、合同金额和订单系统。

**长合同**：几十页的合同，字段散落在不同条款。先按条款切分，用检索定位相关段落再抽取，或者分段抽取后合并（见 [超长文档处理服务](/engineering/system-design/07-document-processing)）。同一字段多处出现且不一致时（比如正文和附件金额不同），不自动选择，直接转人工。

**置信度怎么来**：模型自报的置信度不太可靠，更可靠的信号是：校验是否通过、出处是否找到、两次抽取（不同 Prompt 或不同模型）是否一致、OCR 本身的置信度。这些组合起来决定字段走自动还是人工。

### 扩展与优化

- **人工复核界面**：左边原文高亮出处，右边字段表单，有问题的字段排在前面，复核效率决定整体成本
- **持续评测**：复核过的数据就是带标注的评测集，按字段统计准确率；改 Prompt、换模型前先跑回归（见 [回归测试](/engineering/eval/05-regression-testing)）
- **固定版式走模板**：某个供应商的发票格式稳定，可以用规则或小模型处理，只把新版式和复杂文档交给大模型
- **安全**：文档里可能藏着"忽略之前的指令"之类的文字，抽取 Prompt 要把文档内容当数据处理（见 [间接提示注入](/engineering/security/02-indirect-injection)）；财务和合同数据按租户隔离、加密存储

## 面试官可能追问

::: details 新增一种文档类型要做什么？
定义 Schema 和校验规则，收集几十份样本人工标注作为评测集，调好 Prompt 跑到可接受的准确率，再上线。初期复核比例设高一些，准确率稳定后逐步放开自动通过。
:::

::: details 明细行很多的发票怎么抽？
表格的行列结构要保留好，可以让模型按行输出数组。行数多时分块抽取再拼接，用"明细之和等于合计"校验有没有漏行。
:::

::: details 为什么不直接训练一个专用的抽取模型？
数据量大、版式稳定时，专用模型更便宜更快。但新类型和长尾版式多时，大模型加 Schema 上线快、改起来也快。常见的路径是先用大模型跑起来，积累了复核数据后，再对高频类型训练或蒸馏小模型。
:::

## 易错点

- 只关注抽取 Prompt，忽略 OCR 和版面解析，表格被拍平后行列错位
- 模型输出了值就直接入库，没有出处校验和业务规则校验
- 找不到的字段让模型"尽量填"，结果编出一个格式正确的假值
- 人工复核的结果不回流，系统永远不知道自己错在哪
