# 设计一个多租户的 Agent 平台

::: tip 一句话回答
平台让很多企业（租户）在上面配置和运行自己的 Agent。核心分三层：**控制面**管 Agent 的定义和版本（Prompt、模型、工具、知识库）；**运行时**负责执行 Agent 循环，每次运行是一个可持久化、可中断的任务；**工具层**通过统一网关调用内置工具、租户自己的 API 和 MCP Server。多租户的关键是**隔离**：数据按租户隔离、凭证由平台托管不进上下文、代码执行在**沙箱**里、每个租户有独立的**配额和限流**，避免一个租户的死循环 Agent 拖垮其他人。
:::

## 详细解析

### 需求澄清

- 用户：租户的开发者或运营人员配置 Agent，租户的终端用户使用 Agent
- 能力：自定义 Prompt、选模型、挂工具和知识库、发布版本、查看运行记录
- 运行形态：对话式（实时流式）和任务式（后台跑几分钟到几小时）
- 非功能：租户之间数据绝不串；单个租户异常不影响其他租户；可计费、可审计

### 整体架构

```text
              控制台 / API
                   │
     ┌─────────────┴─────────────┐
     v                           v
 控制面                       接入层（鉴权、租户识别、限流）
 Agent 定义、版本、发布                │
 工具注册、凭证托管                    v
 知识库管理                  运行时调度 ──> 任务队列（按租户分区）
     │                                 │
     └──────── 配置 ──────────> Agent 执行器（循环：模型 ↔ 工具）
                                       │
               ┌───────────────────────┼─────────────────────┐
               v                       v                     v
          模型网关              工具网关（权限、审计）     状态存储
       （路由、配额、计量）     内置工具 / 租户 API /     （会话、检查点、
                                MCP / 代码沙箱             运行轨迹）
```

### 核心模块和数据模型

- **Agent 定义**：`{ tenantId, agentId, version, systemPrompt, model, tools[], knowledgeBases[], limits }`，发布后不可变，改动就是新版本，便于回滚和复现问题
- **运行（Run）**：`{ runId, tenantId, agentId, version, status, steps[], tokenUsage }`。每一步（模型调用、工具调用）都记下来，既是检查点也是轨迹
- **工具注册**：工具的名称、描述、参数 Schema、所需权限、凭证引用（不是凭证本身）
- **凭证**：租户的 API Key、OAuth Token 加密存放在密钥服务里，工具网关调用时才注入

### 关键难点

**租户隔离**：

- 数据层：所有表带 tenantId，查询在数据访问层强制加过滤；向量库按租户分集合或带租户过滤（见 [向量数据库怎么选](/ai/rag/03-vector-db)），高要求的租户单独部署
- 上下文层：会话、记忆、缓存的 key 都带租户，语义缓存绝不能跨租户命中
- 凭证层：模型只看到工具名和参数，真正的密钥在工具网关里注入，不会出现在 Prompt 和日志里（见 [API Key 安全](/engineering/security/07-api-key)）
- 执行层：代码执行、浏览器操作放在一次性沙箱里，限制网络和资源（见 [沙箱隔离](/engineering/security/06-sandbox)）

**运行时的可靠性**：后台任务可能跑很久，执行器会重启、扩缩容。每步完成后写检查点，失败从最近的检查点恢复，有副作用的工具调用要幂等（见 [持久化执行](/ai/agent/14-durable-agent)）。

**防失控和公平性**：每个 Agent 定义都有最大步数、单次运行 token 上限、超时；租户级有并发上限和预算（见 [Token 预算告警](/engineering/deploy/14-token-budget)）。任务队列按租户做公平调度，避免一个租户提交上万个任务把队列占满。

**工具权限和人工确认**：工具按风险分级，读操作直接执行，写操作（发邮件、改数据、付款）可以由租户配置成需要终端用户确认（见 [人在环路](/ai/agent/11-human-in-the-loop) 和 [工具权限设计](/ai/tools/09-tool-permissions)）。工具返回的内容同样可能带注入指令，要当数据处理。

### 扩展与优化

- **可观测**：按租户和 Agent 版本看成功率、步数分布、工具错误率、成本，运行轨迹可回放（见 [链路追踪](/engineering/eval/07-tracing)）
- **评测**：平台提供评测集管理，租户发布新版本前跑一遍回归
- **计费**：模型网关和工具网关统一计量，按租户出账单
- **分级部署**：普通租户共享资源池；大客户或合规要求高的租户独立部署运行时和存储，控制面仍然共用

## 面试官可能追问

::: details 租户想接入自己的 MCP Server，要注意什么？
把它当不可信的外部服务：工具描述和返回结果都可能带注入内容，要审核和隔离；调用走工具网关，统一鉴权、限流、超时和审计；连接凭证由平台托管。MCP 的结构见 [MCP 的架构](/ai/tools/06-mcp-architecture)。
:::

::: details 对话式和任务式运行在架构上有什么不同？
对话式要求低延迟，执行器直接处理请求并流式返回，状态存会话里；任务式进队列异步执行，靠检查点支持长时间运行和恢复，结果通过回调或轮询返回。两者可以共用同一套执行器和工具网关。
:::

::: details 怎么防止一个租户的 Prompt 影响其他租户？
不同租户的请求永远不会共享上下文，这是隔离的底线。另外要防的是间接影响：共享缓存命中、共享知识库检索、日志被别的租户看到。这些都靠在每一层强制带租户维度来保证。
:::

## 易错点

- 只在应用层手写 tenantId 过滤，漏一处就是数据泄露；应该在数据访问层统一强制
- 把租户的凭证放进 Prompt，让模型自己拼请求
- Agent 定义可以原地修改，线上出问题时复现不了当时的配置
- 没有租户级配额和公平调度，一个死循环拖垮整个平台
