# 设计一个 AI 图片生成平台

::: tip 一句话回答
图片生成一张要几秒到几十秒、占用整块 GPU，所以核心是**异步任务系统**：请求先过**提示词审核**和**配额检查**，进入按优先级划分的**任务队列**，GPU Worker 拉取执行，结果图再过**输出审核**，存进对象存储、经 CDN 分发，前端通过轮询或推送拿进度。成本控制靠 **GPU 调度**（批处理、按模型分池、弹性扩缩）和**产品限制**（分辨率、张数、免费额度）。审核要做**输入和输出两道**，因为无害的提示词也可能生成违规图片。
:::

## 详细解析

### 需求澄清

- 功能：文生图、图生图、局部重绘、放大；一次生成多张
- 用户：免费用户和付费用户，付费用户要更快、配额更多
- 规模：假设高峰期的请求量远超 GPU 能同时处理的数量，必须排队
- 延迟：单张几秒到几十秒，取决于模型、分辨率和步数，用户能接受排队但要看到进度
- 合规：不能生成违法内容、真实人物的不当图片，生成图要能追溯

### 整体架构

```text
客户端 ──> API 网关（鉴权、限流）──> 提交服务
                                        │ 提示词审核、配额预扣
                                        v
                         任务队列（按优先级：付费 / 免费）
                                        │
                     调度器（按模型分池、合批）
                                        │
                  ┌─────────────────────┼─────────────────────┐
                  v                     v                     v
            GPU Worker 池 A       GPU Worker 池 B         ......
                  │ 生成图片、上报进度
                  v
           输出审核 ──通过──> 对象存储 + CDN ──> 通知客户端
                  └─不通过──> 拦截、退还配额、记录
```

### 核心模块和数据模型

- **任务**：`{ taskId, userId, type, prompt, params, model, priority, status, progress, resultUrls, createdAt }`，状态有排队、生成中、审核中、完成、失败、拦截
- **调度器**：Worker 主动拉取任务，同一个模型的 Worker 只拉对应队列，避免频繁切换模型权重
- **进度推送**：Worker 按步数上报进度，写到缓存，客户端轮询或通过 SSE、WebSocket 获取；排队时显示前面还有多少任务
- **配额账户**：按用户记录剩余额度，提交时预扣，失败或拦截时退还

### 关键难点

**排队和优先级**：付费用户和免费用户分队列，调度器按权重从各队列取任务，免费队列也要保证一定的份额，不能被饿死。排队太长时直接在提交阶段拒绝或提示稍后再试，不让任务无限堆积。用户取消或关闭页面后，未开始的任务要从队列移除。

**GPU 利用率和成本**：

- **合批**：同模型、同分辨率的任务合成一批推理，提高吞吐，但会增加单个任务的等待时间，批大小要按显存和延迟目标调
- **按模型分池**：加载模型权重很慢，Worker 尽量常驻一个模型；冷门模型用少量 Worker 或按需拉起
- **弹性扩缩**：按队列长度扩缩 GPU 节点，扩容有启动和加载模型的延迟，要保留一部分常驻容量；离线批量任务可以用更便宜的可抢占实例，被回收时任务重新入队
- **产品限制**：免费用户限制分辨率、张数和高级功能，这是最直接的成本控制

**双重审核**：

- 输入审核：提示词过文本审核（见 [内容安全审核](/engineering/security/08-content-moderation)），图生图的输入图片也要审；用户可能用谐音、拆字、外语绕过，规则和分类器要持续更新
- 输出审核：生成的图片过图像分类器，判断色情、暴力、真实人物等，不通过的不返回给用户
- 记录每张图对应的用户、提示词、参数和审核结果，出了问题能追溯；有的场景还要求加可见或不可见的标识，说明是 AI 生成

**结果存储**：图片存对象存储，用 CDN 分发，链接带签名和过期时间，私有图片不能被猜到地址。中间结果和未保存的图片设置生命周期自动清理，控制存储成本。

### 扩展与优化

- **缓存**：完全相同的提示词和参数（含随机种子）结果相同，可以复用；但大多数请求带随机种子，命中率不高
- **预览优先**：先用少步数或低分辨率出预览图，用户满意再生成高清版，减少浪费
- **多模型和第三方 API**：自建 GPU 和调用第三方生成接口混用，按成本和排队情况路由（思路同 [模型路由](/engineering/deploy/11-model-routing)）
- **监控**：队列长度、排队时间、单张生成耗时、GPU 利用率、审核拦截率、每张图的平均成本

## 面试官可能追问

::: details 为什么不同步返回结果，非要做成异步任务？
生成时间长且不稳定，同步请求会长时间占着连接，网关和负载均衡还可能超时断开；高峰期排队时同步请求也没法表达"前面还有多少人"。异步任务能解耦提交和执行，支持取消、重试和进度展示。
:::

::: details Worker 生成到一半挂了怎么办？
任务被领取时设一个租约，Worker 定期续约；租约过期没完成，调度器把任务放回队列重新执行。生成本身没有副作用，重跑是安全的，只要保证结果写入和配额扣减是幂等的。
:::

::: details 输出审核误杀了正常图片怎么办？
退还配额，提供申诉入口，申诉样本进人工复核。误杀率和漏放率要一起看，阈值按场景调整：面向未成年人或公开展示的场景从严，私有创作场景可以稍宽。
:::

## 易错点

- 只审提示词不审输出，无害的提示词也可能生成违规图片
- 只有一个队列，免费流量高峰把付费用户的任务也堵住
- Worker 按任务频繁切换模型，大量时间花在加载权重上
- 图片链接是可预测的公开地址，私有图片被遍历下载
