# 设计一个会议纪要和总结系统

::: tip 一句话回答
链路是 **录音 → 语音识别（带说话人分离和时间戳）→ 转写文本清洗 → 分段总结 → 合并成纪要 → 抽取待办和决策**。要支持两种模式：**会中实时**（流式识别，滚动生成要点）和**会后整理**（拿完整录音重新识别，质量更高）。核心难点是长转写放不进上下文要**分段总结再合并**、说话人要对上真实姓名、待办要带**负责人和截止时间**，并且每条结论都能**跳回原始录音的时间点**核对。会议内容敏感，权限要跟着会议走。
:::

## 详细解析

### 需求澄清

- 输入来源：会议软件的录制、上传的音频文件、会中实时音频流
- 输出：摘要、按议题的要点、决策、待办（谁、做什么、什么时候），以及完整转写
- 规模：假设单场会议几十分钟到两三个小时，会后几分钟内出纪要
- 质量要求：不能编造没讨论过的结论；人名、数字、专有名词要准
- 合规：录音和转写的存储期限、谁能看、能否用于训练

### 整体架构

```text
音频输入 ──> 预处理（降噪、切分）──> ASR（时间戳 + 说话人分离）
                                          │
                                          v
                     转写存储（按句：说话人、起止时间、文本）
                                          │
             ┌────────────────────────────┼─────────────────────┐
             v                            v                     v
      实时要点（滚动）            会后：分段总结 → 合并          抽取：待办 / 决策
             │                            │                     │
             └──────────────> 纪要（每条带时间戳引用）<──────────┘
                                          │
                               审阅编辑 ──> 分发、同步到任务系统
```

会后流程是异步任务，放进队列执行，失败的步骤可以单独重试。

### 核心模块和数据模型

- **转写**：按句存储 `{ meetingId, seq, speaker, startMs, endMs, text }`。时间戳是后面"点击结论跳到录音"的基础
- **说话人对应**：说话人分离只能给出"说话人 A、B"，要靠会议软件的参会人信息、发言时的音轨、或者用户手动标注一次，映射成真实姓名
- **术语表**：会议所属团队的人名、产品名、项目代号，作为 ASR 的热词，也放进总结的 Prompt 里帮助纠错
- **纪要**：结构化存储摘要、议题、决策、待办，每条记录关联到引用的转写句子 seq 范围

### 关键难点

**长转写的总结**：两小时会议的转写可能有几万字。做法是按议题或按时间窗口切段（见 [长文档处理](/ai/prompt/07-long-document)），每段生成结构化的小结（要点、决策、待办），再把所有小结合并成全文纪要。合并时去重，后面推翻了前面的结论要以后面为准。直接把整段转写塞进长上下文也可以，但中间部分容易被忽略。

**不编造**：Prompt 要求每条结论给出依据的句子编号，生成后校验编号存在、内容相关；找不到依据的结论删掉或标为待确认。这也是用户信任纪要的关键：点一下就能听原话。

**待办抽取**：要输出结构化的负责人、事项、截止时间（见 [稳定输出 JSON](/ai/prompt/04-structured-output)）。负责人匹配参会人列表，"下周五"这类相对时间按会议日期换算成具体日期，拿不准就留空让人确认，不要猜。

**会中实时**：流式 ASR 的结果会修正（前面识别的字会被改），实时要点每隔一段时间基于最近的转写增量更新，不追求完美，会后再用完整版重做。

### 扩展与优化

- **成本**：ASR 按音频时长计费，总结按 token 计费；分段小结可以用便宜模型，合并和抽取用强模型（见 [模型路由](/engineering/deploy/11-model-routing)）；会后任务不着急，可以走 [Batch 接口](/engineering/deploy/12-batch-api)
- **跨会议问答**：把纪要和转写入库做检索，支持"上个月关于预算的决定是什么"，本质是一个知识库问答（见 [知识库问答系统](/engineering/system-design/01-knowledge-base-qa)）
- **权限**：纪要的可见范围默认等于参会人，分享要显式授权；检索时按权限过滤
- **评测**：人工写一批会议的标准纪要，比较要点覆盖率、待办的准确率和编造率

## 面试官可能追问

::: details 多语言或中英混说的会议怎么办？
选支持混合语言识别的 ASR，术语表里中英文都放。总结时统一输出成一种语言，专有名词保留原文。识别差的片段在转写里标出低置信度，纪要引用到这些片段时提示核对。
:::

::: details 用户修改了纪要，系统怎么利用？
保存修改前后的版本。高频被改的类型（比如人名、某类待办）说明术语表或 Prompt 有问题，可以补进术语表；修改后的纪要也可以作为评测集的标准答案。
:::

::: details 录音能不能直接给多模态模型，不经过 ASR？
可以试，有的模型能直接理解音频。但长会议的音频 token 很多，成本和延迟高，也拿不到稳定的句级时间戳和说话人信息。常见方案还是 ASR 转文本，模型处理文本。
:::

::: details 怎么处理会议里的敏感信息？
录音和转写加密存储，设置保存期限自动删除；按租户隔离；调用第三方模型时确认数据不被用于训练，敏感行业考虑私有化部署（见 [云端 API 和私有化部署](/engineering/deploy/01-api-vs-self-host)）。
:::

## 易错点

- 不保留时间戳和说话人，纪要无法核对，也无法区分谁说的
- 长转写直接截断，后半场的结论全丢了
- 待办的相对时间不换算、负责人靠模型猜，结果分发给了错的人
- 实时要点和会后纪要用同一套结果，没有用完整录音重做
