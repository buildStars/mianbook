# 设计一个 IDE 里的 AI 代码补全系统

::: tip 一句话回答
插件在用户**停顿输入**时触发补全，先做防抖和本地过滤；收集光标前后的代码、当前打开的文件、相似代码片段等上下文，按 token 预算裁剪，用 **FIM（中间填充）**格式发给一个**小而快的代码模型**；结果以灰色"幽灵文本"显示，用户按 Tab 接受。核心约束是**延迟**：用户继续输入时要**取消**旧请求，配合缓存、流式返回和就近部署。效果看**采纳率**和采纳后保留的代码量；企业场景要处理**代码隐私**和敏感文件排除。
:::

## 详细解析

### 需求澄清

- 场景：行内补全（补全当前行或几行），和对话式改代码、自主完成任务的 [编码 Agent](/ai/agent/08-coding-agent) 不是一回事，也不同于离线的 [代码审查](/engineering/system-design/03-code-review-bot)
- 规模：每个活跃开发者每分钟可能触发多次，请求量远大于对话类产品
- 延迟：补全要在用户下一次敲键盘之前出现，否则就没用了，端到端要做到几百毫秒量级
- 非功能：不能卡编辑器；代码不能泄露；企业要能管控哪些仓库可用

### 整体架构

```text
IDE 插件
  触发判断 + 防抖 → 上下文收集 → 本地缓存命中？──是──> 直接显示
                                   │否
                                   v
                     补全网关（鉴权、限流、敏感内容过滤、取消）
                                   │
                                   v
                     推理集群（小代码模型，FIM，流式返回）
                                   │
                         后处理（截断、括号配平、去重复）
                                   │
                    显示幽灵文本 ──> 采纳 / 忽略事件 ──> 埋点和指标
```

### 核心模块

**触发和防抖**：

- 输入停顿一小段时间再发请求，连续打字时不发
- 本地规则过滤：光标在注释或字符串中间、刚删除字符、文件类型不支持时不触发
- 用户继续输入时，如果新输入和当前建议的开头一致，直接截掉已输入部分继续显示，不发新请求

**上下文收集**（决定效果的关键）：

- 光标前的代码（前缀）和光标后的代码（后缀），前缀离光标近的部分最重要
- 当前文件的导入、相关类型定义；同时打开的其他文件
- 相似片段：在最近编辑和打开的文件里，按文本相似度找和光标附近代码相像的片段
- 所有上下文按优先级在 token 预算内裁剪，预算小是为了快（上下文组织思路见 [上下文工程](/ai/prompt/05-context-engineering)）

**FIM 格式**：普通生成只能接着前缀往后写，补全却常常在代码中间。FIM 训练过的模型用特殊标记把前缀、后缀、待填部分分开，模型看到后缀就知道补到哪里该停。具体的标记各个模型不同，要按模型的说明拼。

**后处理**：截断到合理的行数（单行或一个代码块）；去掉和后缀重复的内容；检查括号是否配平；过滤掉和训练数据中长段代码完全一致的结果，避免版权风险。

### 关键难点

**延迟**：

- 用小模型，部署在离用户近的区域；补全请求的输出很短，首 token 延迟决定体验（优化见 [首 Token 延迟](/engineering/deploy/07-latency)）
- **取消**：用户继续输入后，旧请求的结果已经没用了，客户端立刻中断，服务端也要停止生成，否则推理资源被大量浪费
- **缓存**：客户端按"前缀 + 后缀"的哈希缓存最近的结果，用户删了又打回来时直接命中；服务端利用前缀缓存，同一文件连续请求的前缀大部分相同
- 投机解码对补全很有效，代码里重复片段多（见 [投机解码](/ai/llm/16-speculative-decoding)）

**效果和指标**：

- **采纳率**：显示的建议中被接受的比例
- **保留率**：被采纳的代码过一段时间后还留在文件里的比例，比采纳率更能说明质量
- 展示率、延迟分布、取消率；按语言、文件类型、建议长度分组看
- 新模型和新上下文策略用 A/B 实验验证（见 [A/B 实验](/engineering/eval/09-ab-testing)）

**隐私**：

- 支持按路径、按仓库排除，`.env`、密钥文件不进上下文；网关再做一层密钥检测
- 明确告知代码是否被保存、是否用于训练；企业版默认不保留
- 对隐私要求高的客户提供私有化部署（见 [API 还是私有化部署](/engineering/deploy/01-api-vs-self-host)）

### 扩展与优化

- **仓库级上下文**：对整个仓库建索引，检索相关的函数定义和用法，补全能用上其他文件里的接口
- **多行和下一处编辑预测**：不仅补全光标处，还预测用户接下来要改的位置
- **个性化**：按企业代码库做微调，可以用 [多 LoRA](/engineering/deploy/15-multi-lora-serving) 给不同企业挂各自的适配器
- **降级**：推理服务慢或不可用时静默不显示，绝不能阻塞编辑器

## 面试官可能追问

::: details 为什么补全用小模型而不是最强的模型？
补全对延迟极其敏感，建议晚到一秒用户就已经自己打完了；请求量又很大，大模型的成本承受不了。补全的任务相对局部，小模型配合好的上下文就能做得不错。复杂的改动交给对话式或 Agent 模式用大模型。
:::

::: details 怎么判断补全应该停在哪里？
几层手段：FIM 让模型看到后缀，自己知道什么时候结束；限制最大输出长度；后处理按缩进和语法结构截断，例如单行模式下遇到换行就停，多行模式下在代码块结束处停。
:::

::: details 采纳率高就一定好吗？
不一定。建议很短（比如只补一个括号）采纳率自然高，但价值很小；也可能用户先接受再删掉。要结合采纳的字符数、保留率一起看，并和延迟、展示率放在一起权衡。
:::

## 易错点

- 每次按键都发请求，没有防抖和取消，服务端被大量无用请求压垮
- 只把前缀发给模型，补全的内容和光标后面的代码重复或冲突
- 只看离线评测分数选模型，不看线上延迟和采纳率
- 没有排除敏感文件，把密钥发给了模型服务
