# 自部署模型怎么扩缩容？冷启动慢怎么办？

::: tip 一句话回答
大模型推理的瓶颈在 GPU 显存和算力，CPU 使用率几乎反映不了负载，扩缩容要看**排队请求数**、**KV Cache 占用率**和**排队等待时间**这类推理服务自己暴露的指标。新实例启动慢，主要慢在拉大镜像、下载几十 GB 权重、加载到显存和预热，优化办法是**镜像和权重预先缓存到节点**、用更快的加载格式、保留**最小实例数**和预热池。缩容到零能省钱，但第一个请求要等完整的冷启动，只适合能接受延迟的场景。
:::

## 详细解析

### 为什么不能按 CPU 扩缩

通用的 HPA 机制见 [HPA](/basics/container/12-hpa)。推理服务的特点：

- 计算在 GPU 上，CPU 主要做调度和分词，负载很高时 CPU 也可能不高
- GPU 利用率也不好用：连续批处理下 GPU 一直很忙，利用率接近满时，服务可能还能接更多请求，也可能已经在大量排队，分不出来
- 真正的容量上限是 **KV Cache**：显存放不下更多请求的 KV 时，新请求只能排队（原理见 [KV Cache](/ai/llm/08-kv-cache)）

### 用什么指标

| 指标 | 含义 | 用法 |
| --- | --- | --- |
| 排队请求数 | 已到达但还没开始处理的请求 | 最直接的扩容信号，持续大于 0 说明容量不够 |
| KV Cache 占用率 | 已用的 KV 块比例 | 长期很高时即将排队，适合作为提前扩容信号 |
| 排队等待时间 | 请求从到达到开始处理的时间 | 和首 token 延迟目标直接相关 |
| 运行中请求数 | 正在生成的请求 | 配合单实例的最大并发看余量 |

推理框架通常会以 Prometheus 格式暴露这类指标，通过自定义指标适配器或事件驱动的扩缩容组件接入 Kubernetes。扩容阈值要考虑冷启动时间：新实例要好几分钟才能接流量，等排队严重了再扩就晚了，所以用 KV Cache 占用率这类领先指标提前扩，用排队数兜底。缩容要更保守，设置较长的稳定窗口，避免流量抖动时来回扩缩。

### 冷启动为什么慢

```text
调度到有空闲 GPU 的节点 → 拉取镜像 → 下载权重 → 加载到显存 → 初始化（编译、显存分配、预热）→ 就绪
```

- **镜像大**：CUDA 运行时、推理框架加起来就很大，节点上没缓存时拉取很慢
- **权重大**：几十 GB 的权重从对象存储下载，受带宽限制
- **加载和初始化**：反序列化权重、切分到多卡、构建计算图、分配 KV Cache、跑预热请求
- **没有空闲 GPU**：集群里没有合适的卡，要等新节点开机，这一步可能最慢

### 怎么优化

1. **镜像**：镜像和权重分开，镜像只放运行环境；在节点上预先拉取常用镜像
2. **权重本地缓存**：节点本地盘或共享的高速存储里预先放好权重，启动时直接读，不走公网或对象存储
3. **加载格式**：用支持内存映射、可以快速加载的权重格式，避免逐个张量解析
4. **预留容量**：保持最小实例数；维护一个"已加载模型但不接流量"的预热池，扩容时直接放进负载均衡
5. **按时间预测扩容**：流量有明显的早晚高峰时，按时间表提前扩，比纯靠指标反应更及时

### 缩容到零和 GPU 碎片

**缩容到零**：没有请求时不占 GPU，适合内部工具、离线任务、低频的长尾模型。代价是第一个请求要等完整冷启动，前面要有能接住请求的队列或网关，告诉客户端在加载中，不能直接返回 503。在线主流量一般不缩到零。

**GPU 碎片**：一个模型要 2 张卡，节点上剩下的空闲卡分散在不同机器，每台只有 1 张，就调度不上。办法有：按模型需要的卡数规划节点池；同类工作负载尽量紧凑调度，把整机空出来给大模型；小模型用 GPU 切分或共享技术跑在同一张卡上。调度相关见 [K8s 调度](/basics/container/11-k8s-scheduling)。

## 面试官可能追问

::: details 扩容扩上来了，但流量没有均匀分给新实例怎么办？
新实例刚加入时没有前缀缓存，如果负载均衡按缓存亲和度分配，新实例会长时间分不到流量。负载均衡要综合考虑排队长度，见 [大模型服务的负载均衡](/engineering/deploy/17-llm-load-balancing)。
:::

::: details 突发流量来了，扩容来不及怎么办？
入口做限流和排队，超出容量的请求快速返回或排队等待，而不是全部压到实例上让所有人都变慢；可以降级到更小的模型或外部 API 兜底（见 [限流和降级](/engineering/deploy/08-rate-limit-fallback)）。离线任务用低优先级队列，高峰时让路。
:::

::: details 用托管的 Serverless GPU 服务能解决冷启动吗？
能减轻，平台一般会做镜像和权重的缓存、快照恢复，但不能消除，大模型从零启动仍然要时间。选型时要实测冷启动时间，并确认是否支持保留最小实例。
:::

## 易错点

- 用 CPU 或 GPU 利用率当扩容指标，要么不扩，要么一直满载
- 扩容阈值按"现在排队了"设，没算上几分钟的冷启动时间
- 把权重打进镜像，镜像巨大，每次改代码都要重新拉几十 GB
- 在线服务缩容到零，第一个用户等了几分钟
