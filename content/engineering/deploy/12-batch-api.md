# Batch 批处理接口是什么？适合哪些场景？

::: tip 一句话回答
Batch 接口是把大量请求打包成一个任务**异步提交**，服务商在一个时间窗口内（常见上限是 24 小时，很多批次实际更快）处理完，再让你下载结果。因为不用实时响应，服务商可以把它们安排在空闲算力上跑，所以通常有**价格折扣**，也不占实时接口的限流额度。它适合**不需要马上拿到结果**的任务：离线打标签、批量生成摘要、给知识库做数据增强、跑评测集。每条请求要带自己的 **custom_id**，结果按这个 id 对回去。
:::

## 详细解析

### 工作流程

```text
准备请求文件（每行一条请求，带 custom_id）
  -> 提交批任务，拿到 batch_id
  -> 轮询状态（或等回调）：处理中 / 完成 / 过期 / 失败
  -> 下载结果文件，按 custom_id 对应回原始数据
  -> 失败和过期的条目单独重试
```

不同服务商的接口细节不一样（文件格式、窗口长度、单批上限、折扣力度），以官方文档为准，但流程大同小异。请求文件常见是 JSONL，每行一条：

```json
{"custom_id": "doc-0001", "body": {"model": "some-model", "messages": [{"role": "user", "content": "给这段文本打标签：..."}]}}
```

### 为什么能便宜

实时接口要为峰值预留算力，用户等着要结果。批任务允许延后，服务商可以拿它填平流量低谷，提高 GPU 利用率，所以愿意让利。代价是你不知道每条请求具体什么时候完成，只知道会在窗口内完成（或过期）。

### 适合和不适合

| 适合 | 不适合 |
| --- | --- |
| 离线数据打标、分类、抽取 | 用户在等的对话和搜索 |
| 批量生成商品描述、摘要 | 有严格时限的任务（几分钟内要结果） |
| 跑评测集、回归测试 | 后一步依赖前一步结果的多轮 Agent 流程 |
| 知识库入库前的文档预处理 | 请求量很少，节省的钱不值得改造 |

### 工程上要注意的

- **custom_id 必须唯一且可追溯**：用业务主键，不要用行号，结果文件的顺序不一定和输入一致
- **部分失败是常态**：结果里会有失败和过期的条目，要能只重试这些，而不是整批重来
- **幂等**：重提的批次可能和上一批的结果重复，落库时按 custom_id 去重
- **拆批**：单批有条数和文件大小上限；拆成多批也便于并行和定位问题
- **Prompt 固定前缀**：批任务里的请求往往共用同一段长指令，有的服务商在批处理时也支持 [Prompt Caching](/engineering/deploy/04-prompt-caching)，能叠加省钱
- **任务编排**：用一个任务表记录每批的 batch_id、状态和提交时间，定时轮询，不要靠一个常驻脚本等结果

## 面试官可能追问

::: details 没有 Batch 接口的话，离线任务怎么省钱？
可以自己控制并发，在业务低峰期用实时接口慢慢跑，主要是不挤占白天的限流额度；能用小模型的任务换小模型（见 [模型路由和级联](/engineering/deploy/11-model-routing)）；私有化部署的模型可以在空闲时段跑离线任务，提高 GPU 利用率。
:::

::: details 批任务的结果质量怎么检查？
和实时调用一样做校验：结构化输出先解析，失败的标记重试；再抽样人工检查，或用评审模型打分。批量任务的问题会被放大，正式跑全量前先用一小批验证 Prompt。
:::

::: details 批任务过期了怎么办？
窗口到期还没处理完的条目会被取消或标为过期，只有已完成的条目计费（以服务商文档为准），结果里会标出来。收集这些 custom_id 重新提交一批即可。如果经常过期，说明提交量超过了服务商在窗口内的处理能力，可以拆小、错峰提交。
:::

## 易错点

- 用行号对应结果，结果文件顺序和输入不一致时全部对错
- 把批处理用在用户在等的实时场景
- 一条失败就整批重跑，重复计费
- 没先用小批验证 Prompt，全量跑完才发现输出格式不对
