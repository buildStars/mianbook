# 多个微调模型怎么共用一个底座部署？

::: tip 一句话回答
用 **LoRA** 微调时，底座权重不动，每个任务只训练一对很小的低秩矩阵（适配器），体积通常只是完整模型的很小一部分。部署时显存里只放**一份底座**，多个适配器按需加载，每个请求指定用哪个适配器；推理框架可以把用不同适配器的请求放进**同一个批次**，底座部分一起算，适配器部分分别算。这样十几个微调模型只占一个底座的 GPU 成本，代价是每个请求多一点计算开销，并且所有适配器必须基于同一个底座。
:::

## 详细解析

### LoRA 为什么适合共享底座

微调的整体流程见 [训练阶段](/ai/llm/06-training-stages)，这里只看部署相关的部分。LoRA 把权重的更新量拆成两个小矩阵的乘积：

```text
原始：      y = W · x                    W 是 d × k，冻结不训练
加 LoRA：   y = W · x + B · (A · x)      A 是 r × k，B 是 d × r，r 远小于 d 和 k
```

- 只训练 A 和 B，通常只加在注意力等部分层上，适配器文件很小，可以快速加载和切换
- 部署有两种方式：把 `B·A` **合并**进 W，得到一个独立的完整模型，推理没有额外开销，但每个任务都要一份完整权重；或者**不合并**，底座和适配器分开放，这才能共享底座

### 多 LoRA 同时服务

1. 服务启动时加载底座，适配器按名字注册，请求里通过模型名或参数指定适配器
2. 调度器照常做连续批处理，同一批里可以混合使用不同适配器的请求，以及完全不用适配器的请求
3. 计算时 `W·x` 对整批一次完成；`B·(A·x)` 按每个请求对应的适配器分别算，推理框架用专门的算子把这部分也批量化，避免逐个请求循环
4. 显存里同时能放的适配器数量有上限，其余放在 CPU 内存或磁盘，按最近最少使用淘汰，冷的适配器第一次被请求时要先加载

推理框架为什么能做连续批处理见 [推理框架](/engineering/deploy/06-inference-engines)。

### 和部署多个完整模型对比

| 维度 | 多个完整模型 | 一个底座 + 多个适配器 |
| --- | --- | --- |
| 显存 | 每个模型一份权重 | 一份底座，加若干小适配器 |
| GPU 利用率 | 冷门模型的卡大部分时间空闲 | 所有任务的请求合在一起，批次更满 |
| 单请求开销 | 无额外计算 | 多一次低秩计算，批里适配器越多越明显 |
| 上线新任务 | 申请新卡、部署新服务 | 注册一个适配器文件 |
| 限制 | 无 | 必须同一个底座；适配器的秩、作用层要在框架支持范围内 |

### 适用场景

- 一个公司有很多垂直任务（客服、摘要、抽取），每个任务流量都不大，单独部署很浪费
- SaaS 平台给每个租户训练专属适配器，租户数量多但单个租户流量小
- 同一任务做多个版本的 A/B 实验，适配器可以并排上线

不适合的情况：某个任务流量极大，单独部署合并后的模型更划算；或者各任务用的底座不同，无法共享。

### 运维要点

- **适配器管理**：适配器和底座的版本要绑定，底座升级后旧适配器不能直接用，要重新训练
- **路由**：网关按租户或任务把请求映射到适配器名；适配器不在当前实例的显存里时，优先路由到已加载它的实例，减少冷加载
- **监控**：按适配器统计请求量、延迟、加载次数，加载太频繁说明显存里的适配器槽位不够或者路由不合理
- **隔离**：多租户场景下要校验请求方只能使用自己的适配器（见 [多租户隔离](/engineering/security/12-multi-tenant-isolation)）

## 面试官可能追问

::: details 一个批次里适配器很多，为什么会变慢？
底座部分不受影响，但低秩部分要按适配器分组计算，组越多，每组越小，GPU 并行效率越低，还要从显存读更多的适配器权重。所以调度时可以适当把相同适配器的请求聚在一起，并限制单批内的适配器数量。
:::

::: details 量化的底座还能挂 LoRA 吗？
可以，训练阶段就有在量化底座上训练 LoRA 的做法（如 QLoRA），推理时底座量化、适配器保持较高精度也很常见。要注意训练和推理时底座的精度最好一致，差别太大可能影响效果。量化本身见 [模型量化](/engineering/deploy/05-quantization)。
:::

::: details 多 LoRA 和前缀缓存能一起用吗？
能，但缓存要按适配器区分。同样的前缀经过不同的适配器，得到的 KV 不一样，不能跨适配器复用。缓存的键要带上适配器标识。
:::

## 易错点

- 认为 LoRA 合并后还能共享底座；合并后就是独立的完整模型了
- 用别的底座训练的适配器挂到当前底座上，形状可能对得上，效果却完全不对
- 只算显存省了多少，忽略批内适配器多时的计算开销和冷加载延迟
- 前缀缓存不区分适配器，导致不同任务之间错用缓存
