# 大模型服务的负载均衡为什么不能简单轮询？

::: tip 一句话回答
轮询假设每个请求的开销差不多，大模型请求恰恰相反：有的输入几十 token、一秒返回，有的输入几万 token、生成几分钟，**请求数均匀不等于负载均匀**。更好的做法是按实例的**排队长度**、**KV Cache 余量**这类实时负载挑实例；再考虑**前缀缓存亲和**，让相同前缀的请求落到同一个实例上命中缓存。调用多家供应商的 API 时，用**加权分配**加**健康检查**和熔断，按错误率和延迟动态调整。
:::

## 详细解析

### 轮询的问题

- **请求长度差异巨大**：输入长度、输出长度都可能差几个数量级，轮询会让某个实例碰巧接了几个长请求，排队越来越长，其他实例却很空
- **长连接**：流式请求持续很久，"最少连接数"比轮询好一些，但一个连接可能是十几 token 的小请求，也可能占满大量 KV Cache，连接数仍然不能准确反映负载
- **缓存浪费**：同一个会话的多轮请求有很长的公共前缀，被轮询打散到不同实例，每个实例都要重新计算前缀，前缀缓存几乎命中不了

通用的反向代理和负载均衡算法见 [反向代理](/basics/network/20-reverse-proxy)，这里讲大模型场景的特殊处理。

### 按实时负载调度

推理实例会暴露排队数、运行中请求数、KV Cache 占用率等指标。负载均衡器定期拉取，给每个实例算一个分数：

- 排队数越多、KV Cache 越满，分数越差
- 指标有延迟，两次刷新之间网关自己记录"刚派出去的请求"，避免所有请求瞬间都涌向同一个看起来最空的实例
- 也可以用"随机挑两个、选负载较低的那个"，实现简单，又能避免羊群效应

### 前缀缓存亲和

推理框架会缓存已经算过的前缀的 KV（API 侧的类似机制见 [Prompt Caching](/engineering/deploy/04-prompt-caching)）。命中缓存能省掉这部分预填充计算，首 token 延迟明显下降。

- 按会话 ID 或前缀的哈希做**一致性哈希**，同一会话、同一系统提示的请求优先去同一个实例
- 只按亲和分配会导致热点：某个热门前缀把一个实例压垮。所以要和负载结合，亲和的实例负载过高时，退回到负载最低的实例
- 实例扩缩容时，一致性哈希只会迁移一小部分前缀，缓存损失较小

### 多供应商 API 的负载均衡

调用外部 API 时，负载均衡的对象变成供应商或账号：

- **加权分配**：按配额、价格、延迟设权重，配额大的多分一些
- **健康检查和熔断**：统计每个供应商近期的错误率、超时率、限流次数，超过阈值就暂时摘除，过一段时间放少量请求试探
- **限流感知**：收到限流错误时，按响应里的重试提示降低该供应商的权重，而不是立刻重试同一家（见 [限流和降级](/engineering/deploy/08-rate-limit-fallback)）
- **不同于模型路由**：这里是同一个模型或等价模型之间分流量，按问题难度选模型是 [模型路由](/engineering/deploy/11-model-routing) 的事

## 代码示例

```js
// 综合负载和前缀亲和挑选实例（简化示意）
function pickInstance(instances, prefixKey) {
  const load = (i) => i.queued * 2 + i.running + i.kvUsage * 10 + i.pending
  const healthy = instances.filter((i) => i.healthy)
  // 亲和实例：按前缀哈希固定选中一个
  const hash = [...prefixKey].reduce((h, c) => (h * 31 + c.charCodeAt(0)) >>> 0, 0)
  const affinity = healthy[hash % healthy.length]
  const best = healthy.reduce((a, b) => (load(a) <= load(b) ? a : b))
  // 亲和实例不太忙就用它，否则退回负载最低的
  const chosen = load(affinity) - load(best) < 5 ? affinity : best
  chosen.pending++ // 指标刷新前，自己记一下刚派出的请求
  return chosen.id
}

const instances = [
  { id: 'a', healthy: true, queued: 0, running: 3, kvUsage: 0.4, pending: 0 },
  { id: 'b', healthy: true, queued: 4, running: 8, kvUsage: 0.95, pending: 0 },
  { id: 'c', healthy: false, queued: 0, running: 0, kvUsage: 0, pending: 0 },
]
console.log(pickInstance(instances, 'session-42'))
```

示例里的权重和阈值是随手设的，实际要按压测结果调整。示例用取模简化了亲和计算，实例数一变映射就全乱了，生产环境应该用一致性哈希。

## 面试官可能追问

::: details Kubernetes 的 Service 能直接用吗？
能用，但它在连接层面做分发，不了解请求内容和实例的 KV Cache 状态，流式长连接下分布容易不均。规模大了一般在前面加一层理解大模型请求的网关或推理感知的路由组件，按指标调度。
:::

::: details 预填充和解码分离部署时，负载均衡有什么变化？
预填充实例按输入长度和计算量调度，解码实例按 KV Cache 余量调度，两段分别做负载均衡，中间还要传递 KV。这比单一实例池复杂，适合规模很大、对延迟要求严格的场景。
:::

::: details 怎么验证新的调度策略更好？
用真实流量分布做压测，对比首 token 延迟和总延迟的高分位、吞吐、前缀缓存命中率、各实例负载的离散程度。只看平均延迟会掩盖长尾问题。
:::

## 易错点

- 认为最少连接数就能解决问题，忽略了每个连接的开销差异
- 只做前缀亲和，热门前缀把单个实例压垮
- 负载指标刷新有延迟，没有记录在途请求，导致请求成批涌向同一个实例
- 供应商被限流时还在立刻重试同一家，让限流更严重
