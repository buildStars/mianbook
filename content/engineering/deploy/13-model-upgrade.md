# 升级模型版本时，怎么灰度和回滚？

::: tip 一句话回答
模型升级要当成一次**发布**来做。线上调用**固定具体的模型版本**，不用会自动漂移的别名；新版本先跑**离线回归评测**，再用**影子流量**对比真实请求的输出，然后按比例**灰度**放量，盯住质量、格式错误率、延迟和成本。模型、Prompt、参数作为一个整体**版本化**，放在配置里由网关切换，出问题时改一个配置就能**秒级回滚**，不用重新发代码。
:::

## 详细解析

### 为什么升级模型有风险

新模型"整体更强"不等于在你的场景里更好。常见的变化有：输出风格和长度变了；对同一个 Prompt 的理解不同，原来调好的指令失效；JSON 格式偶尔不合规；拒答变多或变少；延迟和单价变了。这些在通用榜单上看不出来，只有用自己的数据测才知道。

### 版本管理

- **锁定版本**：很多服务商同时提供带日期或编号的固定版本和指向最新版本的别名。生产环境用固定版本，否则服务商一更新，你的线上行为就悄悄变了
- **配置包**：把"模型 + Prompt 版本 + temperature 等参数 + 输出解析规则"作为一个配置包整体编号。升级模型时往往要同步调整 Prompt，它们必须一起切换、一起回滚
- **集中在网关**：业务只引用"任务名"，由 [大模型网关](/engineering/system-design/05-llm-gateway) 决定实际用哪个配置包

### 发布流程

```text
离线回归评测 ──通过──> 影子流量 ──对比通过──> 灰度 1% ──> 10% ──> 50% ──> 100%
     │                    │                       │
   不通过：调 Prompt     发现差异：分析样本      指标异常：切回旧配置
```

1. **离线回归**：用评测集跑新旧两版，比较任务指标、格式合规率、拒答率，逐条看变差的样本（见 [回归测试](/engineering/eval/05-regression-testing)）
2. **影子流量**：线上请求同时发给新版本，结果只记录不展示，用评审模型或规则对比。注意它会额外花钱，也会占限流额度，通常只抽一部分流量
3. **按比例灰度**：按用户 id 哈希分桶，保证同一个用户始终落在同一个版本，体验一致，也便于做 [A/B 测试](/engineering/eval/09-ab-testing)
4. **全量后保留旧版本一段时间**，确认没有长尾问题再下线

### 灰度期间看什么

| 指标 | 说明 |
| --- | --- |
| 业务指标 | 点赞率、采纳率、转人工率、任务完成率 |
| 格式错误率 | JSON 解析失败、工具调用参数不合法 |
| 拒答和安全拦截率 | 突然上升或下降都要查 |
| 延迟 | 首 Token 延迟和总耗时的 P95、P99 |
| 成本 | 平均输入、输出 token 数和单次成本 |

提前定好回滚阈值，比如格式错误率超过旧版本若干倍就自动切回，不要等人发现了再开会讨论。线上监控的做法见 [线上监控](/engineering/eval/08-online-monitoring)。

### 回滚

回滚就是把任务指向的配置包改回旧编号。要保证：旧版本仍然可用（服务商没下线、自部署的旧模型没被删）；缓存按配置包区分（语义缓存里新版本生成的答案要能一并清掉）；会话中途切换版本不影响上下文格式。

## 面试官可能追问

::: details 服务商要下线旧版本，被迫升级怎么办？
流程一样，只是时间受限。收到下线通知就开始跑评测和调 Prompt，不要拖到最后几天。平时就把评测集和自动化回归建好，被迫升级时才能快速完成。
:::

::: details 私有化部署的模型升级有什么不同？
多了基础设施层面的风险：新模型显存占用、推理框架版本、量化方式都可能变。一般新旧两套服务并行部署，网关按比例分流；资源紧张时可以用蓝绿部署，但切换前要充分压测。
:::

::: details 新版本整体更好，但个别场景变差了，怎么办？
可以按任务分别升级：大部分任务切新版本，变差的任务暂时留在旧版本，同时针对它调 Prompt。这正是按任务管理配置包的好处。
:::

## 易错点

- 生产环境用模型别名，服务商更新后线上行为悄悄变化
- 只换模型不换 Prompt，或者 Prompt 和模型分开回滚，组合错乱
- 灰度按请求随机分流，同一个用户一会儿新一会儿旧
- 回滚时才发现旧版本已经下线或旧服务已经销毁
