# 模型路由和级联是什么？怎么让简单问题用便宜模型？

::: tip 一句话回答
线上请求难度差别很大，全部交给最强的模型是浪费。**模型路由**是在调用前判断请求该给哪个模型：按规则（功能、长度、用户等级），或者用一个小分类器预测难度。**级联**是先让便宜模型回答，再检查结果（置信度、格式校验、评审模型打分），不合格才升级到贵的模型。路由省掉了二次调用，但要求判断准；级联判断更可靠，但难题会多花一次调用和一段延迟。两者都要用评测集验证：省了多少钱，效果掉了多少。
:::

## 详细解析

### 为什么要路由

一个产品里，有的请求是"把这段话翻译成英文""这句话是什么情感"，有的是"分析这份合同的风险"。小模型处理前者效果足够，成本和延迟低得多。降本的其他手段见 [降低调用成本](/engineering/deploy/03-cost-reduction)，路由通常是收益最大的几项之一。

### 三种路由方式

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 规则路由 | 按功能入口、输入长度、是否带图片、用户套餐分流 | 简单、可解释、零额外开销 | 粒度粗，同一个功能里的难易差别照顾不到 |
| 分类器路由 | 用小模型或 Embedding 加分类头预测"小模型能不能答好" | 能按单条请求判断 | 需要标注数据训练，分错了就是效果事故 |
| 级联 | 小模型先答，校验不过再交给大模型 | 判断依据是真实的答案，最稳 | 升级的请求多一次调用，延迟变长 |

实际系统常常组合使用：规则先分大类，类内再用级联。

### 级联的"合格"怎么判断

- **结构校验**：要求输出 JSON 或固定格式，解析失败就升级，这是最便宜也最可靠的信号
- **自报置信度或拒答**：让小模型在拿不准时明确说"不确定"，比让它打分更可靠
- **评审模型打分**：用一个模型判断答案质量（见 [LLM-as-Judge](/engineering/eval/02-llm-as-judge)），判断本身也有成本
- **业务规则**：比如抽取的金额和原文对不上、引用的条款不存在

不要直接用 token 的平均概率当置信度：很多 API 不返回，而且概率高不代表答案对。

### 上线前怎么评估

1. 准备有代表性的评测集，按难度和类型分组（见 [评测集怎么建](/engineering/eval/03-eval-dataset)）
2. 分别跑"全用大模型""全用小模型""路由方案"，对比效果和成本
3. 重点看分到小模型却答错的样本，这部分就是路由的代价
4. 上线后监控升级比例和各路由分支的用户反馈；升级比例过高，说明级联反而更贵

### 放在哪一层

路由逻辑适合放在 [大模型网关](/engineering/system-design/05-llm-gateway) 里，业务方只声明"任务类型"和"质量要求"，具体用哪个模型由网关决定，换模型时业务代码不用改。

## 代码示例

```js
// 级联：小模型先答，结构校验或拒答时升级到大模型
async function cascade(prompt, { small, large, validate }) {
  const first = await small(prompt)
  if (validate(first)) return { answer: first, model: 'small' }
  const second = await large(prompt)
  return { answer: second, model: 'large', escalated: true }
}

// 校验：必须是合法 JSON，且没有声明不确定
function validateJson(text) {
  try {
    const data = JSON.parse(text)
    return data.uncertain !== true
  } catch {
    return false
  }
}
```

`small` 和 `large` 是对两个模型调用的封装，各家 SDK 写法不同。返回值里记下用了哪个模型和是否升级，方便统计升级比例。

## 面试官可能追问

::: details 路由分类器本身用什么训练数据？
最直接的是拿同一批请求分别给小模型和大模型跑，用评审模型或人工判断小模型的答案是否够好，得到"小模型能否胜任"的标签。线上的升级记录和用户反馈也可以持续补充数据。
:::

::: details 级联会不会让延迟变得不可控？
会让难题的延迟变长。可以给小模型设较短的超时，超时直接升级；对延迟敏感的场景，也可以小模型和大模型同时发，小模型合格就取消大模型请求，用一部分成本换延迟。
:::

::: details 流式输出时怎么做级联？
级联需要先看到完整结果再判断，和流式冲突。流式场景更适合调用前路由；或者只对首段内容做快速判断，不合格就中断，换大模型重新生成。
:::

## 易错点

- 只算省了多少钱，不评估分错带来的效果损失
- 级联的升级比例很高时，总成本可能比全用大模型还高
- 用 token 平均概率当置信度，以为概率高就是答对了
- 路由逻辑散落在各个业务里，换模型要改一堆代码
