# CI 太慢怎么优化？缓存、并行和只跑受影响的部分怎么做？

::: tip 一句话回答
先**度量**，找出最慢的阶段再动手。常用手段有四类：**缓存**依赖和构建产物，缓存键用锁文件的哈希；互不依赖的任务**并行**，大测试集**分片**到多台机器；monorepo 里按依赖图**只跑受影响的包**；Docker 构建调整层顺序并开启层缓存。测试按快慢**分级**，PR 只跑快的那一层，慢的放到合并后或定时跑。
:::

## 详细解析

### 先度量

不度量就优化，常常是花一天把 30 秒的步骤优化到 10 秒，真正耗时的 E2E 没动。看几样东西：

- 每个任务、每个步骤的耗时，以及最近几周的趋势
- 关键路径：并行的任务里最长的那条决定总时长
- 排队时间：Runner 不够时任务在排队，再怎么优化脚本也没用
- 重试次数：不稳定的测试导致反复重跑，也是"慢"

### 缓存：键怎么设计

缓存的对象一般是包管理器的下载缓存、构建工具的增量缓存、测试工具的缓存。缓存键的原则：

1. **内容变了，键就要变**：键里带锁文件的哈希，依赖一变就生成新缓存，不会用到旧依赖
2. **带上环境信息**：操作系统、运行时版本，原生依赖在不同系统上不能混用
3. **设置降级键**：精确键没命中时，用前缀匹配恢复最近一份旧缓存，再增量安装，比从零开始快

缓存的是包管理器的下载缓存，而不是直接缓存 `node_modules`，配合 `npm ci` 更可靠。缓存本身的上传下载也要时间，太大、命中率太低的缓存反而拖慢流水线。

### 并行和分片

- **任务并行**：lint、类型检查、单测互不依赖，拆成独立任务同时跑，只有构建和部署用 `needs` 串起来
- **测试分片**：E2E 或大型测试集按文件切成 N 份，用 matrix 起 N 台机器各跑一份，最后合并报告。分片按历史耗时均衡分配效果更好
- **取消过时的运行**：同一个分支连续推送时，取消旧的运行，别让过时的提交占着 Runner

### 只跑受影响的部分

monorepo 里改了一个包就把几十个包全测一遍很浪费。做法是：

1. 用 Git 算出相对于目标分支改了哪些文件，映射到所属的包
2. 根据包之间的依赖图，找出所有直接和间接依赖这些包的包
3. 只对这些包运行 lint、测试和构建

Nx、Turborepo 这类工具内置了这些能力，还能配合远程缓存：输入没变的任务直接取别人跑过的结果。工具本身的对比见 [monorepo](/basics/build/11-monorepo)。注意根目录的公共配置（锁文件、构建配置）改了要视为全部受影响。

### Docker 层缓存

Dockerfile 里**变化少的放前面**：先复制锁文件并安装依赖，再复制源码。这样只改代码时依赖层还能命中缓存。CI 的机器每次都是新的，本地层缓存不存在，要用 buildx 把缓存导出到仓库或 CI 的缓存服务里。再配合多阶段构建，让最终镜像只包含运行需要的东西。

### 快慢测试分级

| 层级 | 内容 | 触发时机 |
| --- | --- | --- |
| 快 | lint、类型检查、单测 | 每次推送，几分钟内反馈 |
| 中 | 集成测试、核心 E2E | PR 合并前 |
| 慢 | 全量 E2E、性能测试、跨浏览器 | 合并后或每晚 |

## 代码示例

```yaml
name: ci
on: [pull_request]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true      # 新的推送取消旧的运行

jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/cache@v6
        with:
          path: ~/.npm
          key: ${{ runner.os }}-npm-${{ hashFiles('package-lock.json') }}
          restore-keys: |
            ${{ runner.os }}-npm-
      - run: npm ci
      - run: npm test

  e2e:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]       # 4 台机器各跑四分之一
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 'lts/*'
          cache: npm
      - run: npm ci
      - run: npx playwright install --with-deps
      - run: npx playwright test --shard=${{ matrix.shard }}/4
```

## 面试官可能追问

::: details 缓存导致测试结果不对怎么办？
通常是缓存键没覆盖全部输入，比如漏了运行时版本或某个配置文件。修正缓存键，必要时手动清空缓存。原则是宁可少命中，也不能命中错的缓存。
:::

::: details 只跑受影响的包，会不会漏测？
会有风险，主要来自依赖图之外的隐式依赖，比如读取了共享的数据文件或环境变量。常见做法是 PR 只跑受影响的部分，合并到主干后或每晚再全量跑一次兜底。
:::

::: details 分片后报告怎么看？
每个分片把结果作为制品上传，最后一个任务下载所有分片的结果合并成一份报告。Playwright 支持先输出 blob 格式的报告再合并。
:::

## 易错点

- 缓存键只写死一个字符串，依赖更新了还在用旧缓存
- 直接缓存 `node_modules`，换了运行时版本后原生模块出错
- 只看单个步骤耗时，忽略排队时间和关键路径
