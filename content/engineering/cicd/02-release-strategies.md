# 蓝绿发布、金丝雀发布和特性开关有什么区别？怎么选？

::: tip 一句话回答
**蓝绿发布**是准备两套完整环境，一次性把流量从旧环境切到新环境，回滚就是切回去，代价是双倍资源。**金丝雀发布**是先让一小部分流量走新版本，看指标没问题再逐步放大，影响面小但过程慢。**特性开关**在代码里用条件判断控制功能是否生效，让"代码部署"和"功能上线"分开，可以按用户、地区灰度，关掉开关就算回滚。前两者控制**版本**，开关控制**功能**，实际经常组合用。
:::

## 详细解析

### 三者解决的问题

| | 蓝绿发布 | 金丝雀发布 | 特性开关 |
| --- | --- | --- | --- |
| 控制粒度 | 整个版本 | 整个版本，按流量比例 | 单个功能，按用户、租户、比例 |
| 在哪一层做 | 负载均衡或 DNS 切换 | 网关、Service Mesh 按权重分流 | 应用代码里 |
| 回滚速度 | 快，切回旧环境 | 快，把权重调回 0 | 最快，改开关即生效，不用部署 |
| 资源成本 | 高，两套环境同时在线 | 低，只多几个新版本实例 | 几乎没有，但代码里多分支 |
| 主要风险 | 两套环境共享数据库，表结构要兼容 | 灰度期间新旧版本并存 | 开关越积越多，变成技术债 |

在 Kubernetes 里怎么用滚动更新和探针实现，见 [K8s 滚动发布](/basics/container/07-k8s-probes-rollout)；前端静态资源的灰度见 [前端部署](/basics/build/14-frontend-deploy)。

### 蓝绿和金丝雀的共同前提

两者都会出现新旧版本同时连同一个数据库的时刻（蓝绿是切换瞬间和回滚时，金丝雀是整个灰度期）。所以表结构变更必须向后兼容，见 [不停机表结构变更](/engineering/cicd/03-zero-downtime-migration)。

金丝雀还要有**自动判断**：对比新旧两组的错误率、延迟和业务指标，超过阈值就自动回滚，而不是靠人盯着看。

### 特性开关：把发布和上线解耦

部署是把代码放到生产上，上线是让用户用到功能。有了开关，未完成的功能也能合进主干，默认关闭；运营定好时间再打开，出问题关掉就行，不用回滚整个版本。

开关按用途分几类，生命周期不同：

- **发布开关**：控制新功能上线，全量后就该删，寿命几天到几周
- **实验开关**：A/B 测试，实验结束后删
- **运维开关**：降级、熔断，比如大促时关掉推荐模块，长期保留
- **权限开关**：按套餐开放功能，长期保留，其实是业务配置

### 开关债怎么管

发布开关全量后不删，代码里就留着永远走不到的分支，几个开关组合起来还没法测试。管理办法：

1. 每个开关登记负责人和预计删除日期，到期在看板上提醒
2. 开关平台统计每个开关最近是否被读过、是否已经全量
3. 创建开关时就同时开一个"删除开关"的任务
4. 开关判断收敛到一个地方，不要在代码里散落几十处

## 代码示例

按用户 ID 哈希做稳定的百分比灰度，同一个用户每次结果一致：

```ts
import { createHash } from 'node:crypto'

type Flag = { enabled: boolean; percent: number; allowUsers: string[] }

function isOn(flag: Flag, flagKey: string, userId: string): boolean {
  if (!flag.enabled) return false                      // 总开关，出事一键关
  if (flag.allowUsers.includes(userId)) return true    // 白名单，内部先试用
  // 哈希里带上开关名，不同开关的灰度人群才不会总是同一批人
  const hash = createHash('sha256').update(`${flagKey}:${userId}`).digest()
  return hash.readUInt32BE(0) % 100 < flag.percent
}
```

## 面试官可能追问

::: details 只用特性开关，还需要金丝雀吗？
需要。开关只能保护包在开关里的代码，依赖升级、框架改动、性能退化这类问题不在任何开关后面。金丝雀保护的是整个版本，两者互补。
:::

::: details 开关的值放在哪里？改了怎么生效？
一般放在开关平台或配置中心，应用启动时拉取并在内存里缓存，通过长连接推送或定时轮询更新。平台不可用时要有默认值兜底，默认值通常是"关"。
:::

::: details 金丝雀按什么分流？
按请求随机分最简单，但同一个用户可能一会儿看到新版一会儿看到旧版。按用户 ID 哈希或 Cookie 分流更稳定，体验一致，也方便对比指标。
:::

## 易错点

- 以为蓝绿发布能随便回滚：如果新版本已经改了数据或删了列，切回旧环境也会出错
- 特性开关当成永久配置不清理，最后没人敢删
- 金丝雀只看错误率，不看延迟和业务指标，转化率掉了却判断为正常
