# 数据库表结构变更怎么做到不停机上线？

::: tip 一句话回答
核心是**扩展-收缩**（expand/contract）：先只做"加"的变更，让新旧代码都能跑；再发布新代码，必要时**双写**并**回填**历史数据；确认旧代码全部下线后，最后才做"删"的变更。任何时刻线上都可能同时跑着新旧两个版本，所以每一步的表结构都要同时兼容这两个版本。改名、删列、改类型都要拆成多次发布。
:::

## 详细解析

### 为什么不能一步改完

滚动发布、金丝雀、蓝绿切换期间，新旧代码会同时连着同一个库。如果迁移脚本把 `name` 直接改名成 `full_name`：

- 先迁移再发代码：旧代码还在查 `name`，立刻报错
- 先发代码再迁移：新代码查 `full_name`，迁移前同样报错
- 发布到一半回滚：旧代码面对已经改过的表，还是报错

所以单次发布里，表结构只能做对旧代码**无害**的变更。

### 扩展-收缩的步骤

以把 `users.name` 改名为 `full_name` 为例，拆成多次发布：

| 步骤 | 表结构 | 应用代码 | 线上同时存在的版本 |
| --- | --- | --- | --- |
| 1. 扩展 | 加 `full_name` 列，允许为空 | 不变 | 旧代码，不受影响 |
| 2. 双写 | 不变 | 写两列，读 `name` | 旧代码和双写代码 |
| 3. 回填 | 不变 | 后台任务分批把 `name` 复制到 `full_name` | 同上 |
| 4. 切读 | 不变 | 读 `full_name`，仍双写 | 双写代码之间，可随时回滚 |
| 5. 停写旧列 | 不变 | 只写 `full_name` | 确认不再回滚到第 4 步之前 |
| 6. 收缩 | 删 `name` 列 | 不变 | 只有新代码 |

每一步都可以单独回滚，只有第 6 步不可逆，所以要等观察期过了再做。

### 双写和回填的细节

- 回填要**分批**：按主键范围每次更新几千行，批次之间停顿，避免长事务和主从延迟
- 回填和双写会并发：回填时只更新 `full_name IS NULL` 的行，别覆盖双写已经写好的新值
- 回填完做校验：统计两列不一致的行数，为 0 才进入切读
- 加 `NOT NULL` 约束放在回填完成之后

大表上加列、加索引会不会锁表，取决于数据库的 Online DDL 能力，见 [Online DDL](/basics/mysql/15-online-ddl)。本题关心的是应用发布和表结构变更的配合顺序。

### 几类常见变更的安全顺序

- **加列**：先加列（可空或带默认值），再发用它的代码
- **删列**：先发不再读写它的代码，并确认 ORM 不会 `SELECT *` 后按列映射报错，最后删列
- **改类型**：按改名处理，新建一列，双写回填后切换
- **加唯一约束**：先在应用层去重并清理脏数据，再加约束
- **拆表**：新表加上，双写、回填、切读，最后删旧表的字段

### 放进流水线

1. 迁移脚本和代码一起放仓库，用迁移工具（例如 Flyway、Liquibase、Prisma Migrate）按顺序编号执行，库里有版本表记录执行到哪
2. 流水线里迁移作为单独一步，在部署新代码之前跑；预发先跑一遍，量一下耗时
3. CI 检查迁移脚本：禁止同一次发布里出现删列、改名这类破坏性语句，出现就要求拆分
4. 回滚策略以**向前修复**为主：扩展类迁移不需要回滚，代码回滚即可；收缩类迁移不可逆，要先备份

## 代码示例

第 3 步分批回填（MySQL）：

```sql
-- 每次处理一段主键范围，由任务循环推进 @start
UPDATE users
SET full_name = name
WHERE id >= @start AND id < @start + 5000
  AND full_name IS NULL;   -- 不覆盖双写已经写入的值

-- 回填结束后校验，结果为 0 再切读
SELECT COUNT(*) FROM users
WHERE NOT (full_name <=> name);   -- 空值安全比较，NULL 和非 NULL 也算不一致
```

## 面试官可能追问

::: details 迁移在部署前跑还是部署后跑？
扩展类迁移在部署新代码前跑，因为新代码依赖新列；收缩类迁移在旧代码完全下线、过了观察期之后单独发布。这也是为什么一次改名要拆成好几次发布。
:::

::: details 迁移失败了怎么办？
扩展类迁移失败一般不影响线上，因为旧代码不依赖它，修好重跑即可。所以迁移脚本最好可重复执行，比如加列前判断列是否存在。MySQL 的 DDL 会隐式提交，不能靠事务整体回滚，这点要提前想好。
:::

::: details 有没有办法避免双写那么多步骤？
如果能接受短暂停写，可以在低峰期停写、迁移、再发布，简单但不是零停机。也可以用数据库视图或生成列暂时让旧列名继续可读，减少步骤，但会引入额外复杂度。
:::

## 易错点

- 只考虑"迁移后的新代码"，忘了发布过程中旧代码还在跑
- 回填不分批，一条 `UPDATE` 锁住大量行，还造成主从延迟
- 删列太早：还有定时任务、报表脚本或别的服务在读这个列
- 以为代码回滚了表结构也会跟着回去，收缩步骤没留后路
