# 安全策略太严导致模型误拒，怎么平衡安全和可用性？

::: tip 一句话回答
误拒是把正常请求当成违规拒掉，代价是用户体验差、流失，还会让用户学会绕过规则。平衡的办法：**分级处置**（拦截、提示、放行）而不是只有拦和放两档；**按场景和用户身份**调整策略；评测时**同时看误拒率和漏拒率**，不只盯一个；再建好**申诉和反馈闭环**，持续修正规则。
:::

## 详细解析

### 误拒长什么样

- **关键词误伤**：问"怎么杀掉一个卡死的 Python 进程"、"怎么给图片加暗水印"、"小说里的反派怎么写得更可怕"被拒，只因为字面上有"杀""暗""可怕"这类词
- **领域误伤**：医疗、法律、安全研究这类专业话题，正常问题也被当成敏感内容
- **过度说教**：没有拒绝，但回答前面一大段免责声明，正文含糊其辞
- **上下文丢失**：多轮对话里一句话单独看像违规，结合上下文其实很正常

代价不只是一次体验差。用户被误拒多了，会换说法试探、转去更不受控的工具，或者干脆不用了。

### 分级处置

不要只有"拦截"和"放行"两档。按风险和置信度分成几级：

| 级别 | 适用情况 | 处理方式 |
| --- | --- | --- |
| 拦截 | 高风险且判断明确，比如违法内容 | 直接拒绝，给出简短原因 |
| 降级 | 话题敏感但有正当用途 | 给出一般性信息，不给可操作细节，建议咨询专业人士 |
| 提示 | 低风险、可能有歧义 | 正常回答，附上必要的提醒 |
| 放行 | 正常请求 | 直接回答 |

拒绝时也要好好说：说明不能做什么、能做什么、可以换什么方式，而不是一句"抱歉我无法回答"。

### 按场景和身份调整

同一句话在不同场景下风险不一样：

- **按产品场景**：儿童教育产品和面向医生的辅助工具，敏感话题的阈值显然不同
- **按用户身份**：经过认证的专业用户、企业内部员工，可以放宽相应领域的限制
- **按上下文**：审核时带上前几轮对话，而不是只看当前这一句

策略最好做成配置，按租户、场景下发，而不是写死在一个全局提示词里。整体审核链路见 [内容安全审核](/engineering/security/08-content-moderation)。

### 两个指标一起评测

- **漏拒率**：违规请求没被拦住的比例，用红队数据集测，见 [红队测试](/engineering/eval/13-red-teaming)
- **误拒率**：正常请求被拒绝或被降级的比例，用"看起来敏感但其实正常"的边界样本测

两个指标此消彼长。每次调整规则、换模型、改提示词，都要两个一起跑，确认一边下降时另一边没有明显上升。只看漏拒率，策略会越改越严；只看误拒率，又会放过风险。

### 申诉和反馈闭环

1. 拒绝回复里给出反馈入口，用户可以标记"这不该拒"
2. 线上记录每次拒绝的请求、命中的规则、所在的级别
3. 定期抽样复核，确认是误拒就修规则，并把样本加进误拒评测集
4. 规则改动走灰度，观察两个指标的变化再全量

## 面试官可能追问

::: details 误拒是模型本身的问题，还是应用层的问题？
都有可能。模型自带的安全对齐会拒一部分；应用层的关键词过滤、审核模型、系统提示词又会叠加一层。排查时先看拒绝是在哪一层发生的：被前置审核拦的，就调审核规则；是模型自己拒的，就调提示词，比如说明产品场景和用户身份，或者换模型。
:::

::: details 用关键词过滤为什么容易误拒？
关键词不看语义和上下文。"杀死进程"、"攻击面分析"这些词在技术语境里都很正常。关键词更适合做初筛，命中后交给能理解上下文的分类模型再判断，而不是直接拒绝。
:::

::: details 怎么构造误拒评测集？
收集线上被拒后用户申诉成功的请求；按领域人工写一批"带敏感词但意图正常"的问题；再加上专业场景下的真实问法。每条标注期望行为（回答、降级还是拒绝），评测时按期望行为算准确率。
:::

## 易错点

- 只统计拦截量和漏拒率，从不统计误拒率，策略会越改越严
- 把"降级回答"也当成通过：大段免责加含糊回答，对用户来说和拒绝差不多
- 放宽策略时没有身份校验：专业用户的宽松策略必须绑定在认证之后，不能靠用户自称
