# AI 接口被刷、被薅羊毛怎么防？

::: tip 一句话回答
AI 接口的每次调用都有真实的模型成本，被刷的后果是**账单失控**，所以要按"成本"来防，而不只是按请求次数。几层防线：**注册环节**提高批量注册的成本；**额度**按用户、设备、IP 和租户限制，按 **token 而不是请求数**计量；**单次请求**限制输入长度和 max_tokens；**用途约束**防止接口被当成免费的通用模型代理；**异常检测**发现集中、自动化的使用模式；最后用**全局预算和熔断**兜底，保证最坏情况下损失有上限。
:::

## 详细解析

### 和普通接口被刷有什么不同

- **成本高且不均匀**：一次请求的成本取决于输入输出的 token 数，按次数限流挡不住"少量请求、每次很长"
- **有转卖价值**：免费额度、新用户试用可以被批量注册后汇总，包装成别的服务转卖
- **能被当作代理**：一个"写周报助手"如果什么问题都回答，就等于免费的通用模型接口
- **攻击可以很慢**：大量账号各用一点，单个账号的指标都正常

OWASP 大模型十大风险把这类问题归为无节制的资源消耗，见 [OWASP 大模型应用十大风险](/engineering/security/10-owasp-llm-top10)。

### 注册和身份

免费额度挂在账号上，账号越便宜就越容易被薅。可以采取：

- 注册要验证邮箱或手机号，拦截一次性邮箱域名
- 同一设备、同一 IP 段短时间注册大量账号时触发人机验证或直接拒绝
- 新账号的额度分阶段发放，有正常使用记录后再提高
- 高价值的能力（大模型、长上下文、图片生成）需要付费或实名后才开放

### 额度和单次限制

| 层级 | 限什么 | 说明 |
| --- | --- | --- |
| 单次请求 | 输入长度、max_tokens、工具调用轮数 | 防止单次请求成本过高，Agent 要限制循环次数 |
| 用户 | 每分钟请求数、每天 token 数 | token 按"输入 + 输出"计，不同模型按价格折算成统一的点数 |
| 设备、IP | 请求数 | 拦截一人多号 |
| 租户、全局 | 每日成本预算 | 超出后降级到便宜模型或暂停免费用户 |

限流算法本身可以用 Redis 实现，见 [怎么用 Redis 实现限流](/basics/redis/10-rate-limit)。输出 token 只有生成完才知道，常见做法是请求前按 max_tokens **预扣**，结束后按实际用量退还差额。

### 用途约束和异常检测

- 限定接口能力：固定的 System Prompt、只开放业务需要的参数，不让调用方任意指定模型、温度和完整的提示词
- 用一个便宜的分类模型或规则判断请求是否在业务范围内，明显无关的请求直接拒绝
- 监控这些信号：请求时间分布像机器（全天均匀、无间隔）、大量账号的请求内容高度相似、新账号一注册就用满额度、输入几乎总是贴近长度上限
- 发现异常后分级处理：要求验证、降低额度、封禁账号，同时关联同设备、同支付方式的其他账号

### 兜底

- 在模型服务商侧也设置用量上限和告警，作为应用层失效时的最后一道线
- 服务端保存 Key，前端只调自己的后端，见 [API Key 怎么安全管理](/engineering/security/07-api-key)
- 统一走网关做计量和限流，见 [设计一个大模型网关](/engineering/system-design/05-llm-gateway)

## 代码示例

```js
// 按 token 预扣和结算的每日额度（内存版示意，生产环境放 Redis 并用原子操作）
const DAILY_POINTS = 100_000
const used = new Map() // userId -> 今日已用点数

// 不同模型折算系数是假设值，按实际价格配置
const RATE = { small: 1, large: 10 }

function reserve(userId, model, inputTokens, maxTokens) {
  const cost = (inputTokens + maxTokens) * RATE[model]
  const now = used.get(userId) ?? 0
  if (now + cost > DAILY_POINTS) return { ok: false, reason: '今日额度不足' }
  used.set(userId, now + cost) // 先按最大可能用量预扣
  return { ok: true, reserved: cost }
}

function settle(userId, model, reserved, inputTokens, outputTokens) {
  const actual = (inputTokens + outputTokens) * RATE[model]
  used.set(userId, used.get(userId) - reserved + actual) // 退还没用到的部分
}

const r = reserve('u1', 'large', 2000, 1000)
console.log(r) // { ok: true, reserved: 30000 }
settle('u1', 'large', r.reserved, 2000, 300)
console.log(used.get('u1')) // 23000
console.log(reserve('u1', 'large', 5000, 4000).ok) // false
```

## 面试官可能追问

::: details 为什么不能只按请求次数限流？
每次请求的成本差别很大：一个几十 token 的问题和一个塞满长上下文、要求长输出的请求，成本可以差几个数量级。按次数限流时，攻击者把每次请求做大就能绕过，所以计量单位要是 token 或折算后的成本。
:::

::: details 流式输出时怎么防止超额？
请求前按 max_tokens 预扣，保证这次请求最多用到预扣的量；生成过程中累计输出 token，结束或中断后按实际用量结算。用户中途断开连接时要取消上游请求，否则模型还在继续生成和计费。
:::

::: details 怎么发现"很多账号各用一点"的分布式薅羊毛？
看单个账号发现不了，要做关联分析：按设备指纹、IP 段、注册时间、支付方式、请求内容的相似度把账号聚类，聚出的大簇整体处理。同时盯整体指标，比如免费额度的消耗速度突然上升。
:::

## 易错点

- 只按请求次数限流，忽略了单次请求的 token 成本
- 只限输入不限输出，或者没限制 Agent 的工具调用轮数
- 接口参数开放过多，被当成免费的通用模型代理
- 没有全局预算和服务商侧的用量上限，应用层一旦失效，损失没有上限
