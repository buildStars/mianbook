# 推理模型的思考过程怎么流式展示？

::: tip 一句话回答
推理模型的接口会把**思考内容和正文分开**返回：有的放在增量里的独立字段，有的是独立类型的内容块。前端按类型分成两个区域，思考区默认**折叠**，只显示"思考中"和**计时**，正文开始输出时自动收起。思考可能很长，首字会变慢，要用思考摘要、进度提示来填这段空白。多轮对话时思考内容要不要回传，**各家接口要求不同**，要按文档处理，不能一律原样带回。
:::

## 详细解析

### 接口怎么区分思考和正文

模型原理见 [推理模型](/ai/llm/10-reasoning-models)，这里只讲展示。常见的两种格式：

- **增量里的独立字段**：同一条 delta 里，思考写在单独的字段，正文写在 `content`。一段时间内只有思考字段有值，之后切到正文
- **独立的内容块**：先来一个"思考"类型的块，逐段推送思考增量，块结束后再开始"文本"块；调用工具时还会穿插工具块

不同接口字段名不一样，服务端转发时最好统一成自己的事件格式，例如 `event: reasoning` 和 `event: content`，前端就不用关心上游是哪家（转发见 [服务端转发流式响应](/engineering/streaming/08-server-relay)）。有的接口默认只返回思考的摘要，或者完全不返回思考原文，前端要能处理"只有计时、没有内容"的情况。

### 前端怎么展示

```text
┌ 已思考 12 秒  [展开] ───────────┐   思考阶段：标题显示"思考中…"和实时计时
│ (折叠的思考内容，灰色小字)      │   正文开始：自动折叠，标题改成"已思考 N 秒"
└─────────────────────────────────┘
正文 Markdown 正常流式渲染……
```

- 状态分三段：`thinking`（只收到思考）、`answering`（收到第一个正文增量）、`done`。计时从发请求开始，到第一个正文增量停止
- 思考区默认折叠，展开后流式追加文本；思考内容一般只做纯文本或轻量 Markdown 渲染，正文才走完整的渲染管线（见 [流式 Markdown 渲染](/engineering/streaming/05-markdown-streaming)）
- 思考增量很密，也要像正文一样合并到一帧再更新 DOM（见 [打字机效果](/engineering/streaming/06-typewriter)）
- 用户展开了思考区，就不要在正文开始时强行收起，尊重用户的操作

### 首字慢怎么处理

推理模型的"首字"其实是思考的首字，正文要等思考结束才出来，可能要几十秒。几个办法：

1. 立刻显示"思考中"和计时，让用户知道没卡住
2. 允许看思考过程或摘要，等待时有东西可看
3. 接口支持调节思考强度或预算时，简单问题用低档（选模型见 [模型路由](/engineering/deploy/11-model-routing)）
4. 停止按钮在思考阶段也要可用（见 [停止生成](/engineering/streaming/04-abort)）

监控上把"首个思考 token 时间"和"首个正文 token 时间"分开统计，否则看不出慢在哪里。

### 多轮对话里思考要不要回传

这一点各家规定不同，有的接口在普通多轮对话里不使用上一轮的思考内容（传了也会被忽略或剔除），但一旦请求里带了工具，又要求把思考内容完整带回；有的在工具调用循环中要求把思考块（包括签名等字段）原样带回，改动或丢掉会报错。同一家不同模型的规则也可能不一样。通用做法：

- 存储时把思考和正文分开存，回传策略由服务端按模型配置决定
- 用户界面展示的历史和发给模型的历史是两份数据，不要直接把界面上的文本拼回去
- 思考内容不受系统提示的格式约束，可能包含中间推理和被否定的方案，不宜当作正式回答引用

## 代码示例

```js
// 把统一后的事件流整理成界面状态
function createReasoningState(now = Date.now) {
  const s = { phase: 'waiting', reasoning: '', content: '', startAt: now(), thinkMs: 0 }
  return {
    state: s,
    apply(evt) {
      if (evt.type === 'reasoning') {
        s.phase = 'thinking'
        s.reasoning += evt.text
      } else if (evt.type === 'content') {
        if (s.phase !== 'answering') {
          s.thinkMs = now() - s.startAt // 第一个正文增量到达，停止计时
          s.phase = 'answering'
        }
        s.content += evt.text
      } else if (evt.type === 'done') {
        s.phase = 'done'
      }
    },
  }
}

let t = 0
const st = createReasoningState(() => t)
t = 300; st.apply({ type: 'reasoning', text: '先比较两种方案…' })
t = 4200; st.apply({ type: 'content', text: '结论是' })
st.apply({ type: 'content', text: ' A。' })
st.apply({ type: 'done' })
console.log(st.state.phase, st.state.thinkMs, st.state.content) // done 4200 结论是 A。
```

## 面试官可能追问

::: details 思考内容要不要给用户看？
看产品定位。面向开发者或专业用户的工具展示思考能增加信任，也方便发现模型理解错了；面向大众的产品可以只显示计时或摘要。接口本身也可能只给摘要。无论哪种，思考内容都不能当成正式答案，也要和正文一起过内容审核。
:::

::: details 思考阶段用户点了停止，怎么处理？
和普通停止一样中断请求。区别是这时还没有正文，界面要显示"已停止"而不是空白回答；这轮对话保存时，一般只保留用户消息，或者标记为未完成，不要把半截思考当成助手的回复存进历史。
:::

::: details 思考中途调用了工具，界面怎么排？
按事件顺序渲染成时间线：思考块、工具调用块（显示工具名和状态）、工具结果、再一段思考、最后正文。每个块各自折叠，计时可以按整体算。工具调用的增量解析见 [流式工具调用](/engineering/streaming/09-streaming-structured)。
:::

## 易错点

- 把思考和正文拼进同一个字符串渲染，用户分不清哪段是答案
- 计时从第一个思考 token 开始算，漏掉了排队和网络时间，比用户的体感短
- 多轮对话把思考内容原样塞回下一轮，或在要求回传的场景里把它丢掉，都可能导致报错或效果下降
- 只监控首 token 延迟，推理模型的首 token 来得很快，正文却很慢，指标看起来正常
