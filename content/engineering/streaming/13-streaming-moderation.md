# 流式输出时怎么做内容安全审核？

::: tip 一句话回答
流式输出和审核天然冲突：审核想看完整内容，流式想尽快展示。常见做法是三层：**输入前置审核**，有问题的请求不调用模型；**输出分段审核**，服务端攒一小段（一句或几十个字）审一次，通过了再下发，用一点延迟换安全；最后保留**撤回能力**，整段审核或异步复审发现问题时，通知前端替换已展示的内容。纯"先输出后撤回"体验最好，但用户已经看到、可能已经截图，所以高风险场景要用缓冲窗口，低风险场景可以接受先展示后撤回。
:::

## 详细解析

### 为什么流式让审核变难

一次性返回时，拿到完整回答审一遍再给用户就行。流式下每个 chunk 只有几个字，单独审没有意义，违规内容往往要看上下文才能判断；而等全文生成完再审，流式就退化成了一次性返回。审核的通用做法（分类器、关键词、人工）见 [内容安全审核](/engineering/security/08-content-moderation)，这里只讲怎么和流式结合。

### 三层防线

| 层 | 时机 | 做法 | 代价 |
| --- | --- | --- | --- |
| 输入审核 | 调用模型前 | 审用户输入和上传内容，命中直接拒答 | 增加一次审核的延迟，可以和其他前置步骤并行 |
| 输出分段审核 | 生成过程中 | 服务端按句或按字数攒缓冲，审核通过再发给前端 | 展示比生成慢一个窗口 |
| 事后复审与撤回 | 生成结束后或异步 | 对全文再审一次，或抽样送人工 | 已展示的内容需要撤回 |

### 缓冲窗口怎么设计

```text
模型 chunk ──> 服务端缓冲区 ──(满一句 / 满 N 字 / 超时)──> 审核 ──通过──> 下发前端
                                                            └─不通过──> 停止生成，下发拦截事件
```

- 窗口越大，审核越准，延迟越高；按句切是常见的折中
- 审核时带上前文（已通过的部分加当前窗口），否则跨句的问题看不出来
- 审核接口要快，可以先用本地关键词和轻量分类器做第一道，复杂判断走异步复审
- 审核服务超时或出错时怎么办要事先定好：高风险业务 fail-close（不下发），一般业务可以 fail-open 并记录

### 撤回的协议

撤回需要前后端约定事件类型，不能只靠断开连接：

```json
{ "type": "moderation", "action": "retract", "messageId": "m_123", "replacement": "该回答包含不适宜内容，已被隐藏" }
```

前端收到后停止渲染这条消息，用替换文案覆盖已展示的内容。同时要处理好持久化：数据库里的这条消息也要标记为已撤回，否则刷新页面又出来了；多轮对话里，被撤回的内容也不能再作为上下文发给模型。

### 怎么取舍

- **先展示后撤回**：首字最快，适合闲聊、写作这类风险低的场景。缺点是用户已经看到，截图无法撤回
- **缓冲后展示**：多一个窗口的延迟，适合面向公众、监管严的场景
- **分级策略**：对未登录用户、敏感话题、新上线的功能用缓冲，其他走先展示后撤回

所有拦截和撤回都要记录原文、命中的规则和上下文，便于复核误杀和调整策略。

## 面试官可能追问

::: details 能不能让前端做审核？
不行。前端代码可以被绕过，审核必须在服务端。前端只负责响应服务端的拦截和撤回事件。
:::

::: details 缓冲窗口会不会让打字机效果变得一顿一顿的？
会更"成段"。前端可以对每段下发的文本再做平滑输出（见 [打字机效果](/engineering/streaming/06-typewriter)），视觉上仍然是连续的，只是整体晚了一点。
:::

::: details 模型生成到一半被拦截，已经消耗的 token 怎么办？
照样计费，这是没法避免的。拦截后要立刻中断模型调用，避免继续浪费；如果某类请求被拦截得多，应该加强输入审核，把它们挡在调用模型之前。
:::

::: details 工具调用的结果要不要审？
要。工具返回的网页、文档内容可能带违规信息或注入指令，在放进上下文或展示给用户前同样要过审核。
:::

## 易错点

- 对单个 chunk 做审核，几个字的片段既判断不准，调用次数又多
- 只做输入审核，以为输入干净输出就一定干净
- 撤回只改了前端显示，数据库和对话上下文里还保留原文
- 没有定义审核服务故障时的策略，出问题时要么全挡要么全放
