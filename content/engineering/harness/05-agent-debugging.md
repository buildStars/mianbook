# Agent 怎么调试？执行轨迹怎么记录和回放？

::: tip 一句话回答
调试 Agent 靠**完整的执行轨迹**：每一步模型看到的完整输入、模型输出、工具调用和结果、耗时，以及提示词、工具定义和模型的版本。按步查看，判断问题出在模型、工具还是上下文。复现时用**录制的工具结果做回放**，让外部环境不再变化；再从出错那一步改提示或改上下文重跑。修好的失败轨迹沉淀成测试用例。
:::

## 详细解析

链路追踪的基础设施见 [链路追踪](/engineering/eval/07-tracing)，成体系的评测见 [Agent 评测](/engineering/eval/10-agent-eval)。这里讲开发者怎么用轨迹定位和修复一次具体的失败。

### 轨迹要记什么

| 内容 | 为什么要记 |
| --- | --- |
| 每次调模型的**完整输入**（拼好后的消息、工具定义） | 模型只能根据它看到的东西做决定，只记用户问题不够 |
| 模型输出（文本、工具调用、停止原因） | 判断决策是否合理 |
| 工具调用的参数、结果、报错、耗时 | 区分是工具的问题还是模型的问题 |
| 被裁剪或压缩过的内容 | 很多"模型忘了"其实是 harness 把信息截掉了 |
| 提示词版本、工具版本、模型名、采样参数 | 回放和对比必须固定这些 |
| 权限判定和 hook 结果 | 解释"为什么这一步被拦了" |

完整输入可能很大，可以对重复的部分（系统提示、工具定义）存一份再引用。里面可能有密钥和个人信息，落盘前要脱敏，访问要有权限控制。

### 按步定位

拿到一条失败轨迹，从后往前找第一个出错的步骤，然后问三个问题：

1. **上下文对不对**：这一步模型需要的信息在不在输入里？有没有被截断、被压缩掉，或者被大量噪音淹没？
2. **工具对不对**：工具结果是否真实正确？报错信息是否足够让模型理解该怎么改？
3. **模型对不对**：信息完整、清楚，模型还是做了错误的决定，才是模型能力或提示词的问题

大部分问题落在前两类，修改 harness（工具描述、结果格式、裁剪策略）比改提示词更有效。

### 确定性回放

直接重跑一遍通常复现不了：文件变了、接口返回不同、模型采样有随机性。回放的做法是把录下的工具结果当成"桩"：

```text
录制：模型 → 工具调用 A → 真实执行 → 结果 RA（记下）
回放：模型 → 工具调用 A → 查录制表，直接返回 RA
```

- 只回放工具结果、真实调用模型：看改了提示词之后模型的决策有没有变
- 模型输出也回放：完全确定，用来复现 harness 自己的 bug，比如解析和裁剪逻辑
- 模型在回放中改走了新的工具调用，录制表里没有，就要标记出来，决定真实执行还是停下

写操作在回放时一律不真实执行，避免重复产生副作用。

### 从某一步改了重跑

不必每次从头跑。把轨迹截到出错前的那一步，修改系统提示、工具描述或某个工具结果，然后从这里继续。前面的步骤用录制结果，省时间也省钱。这依赖 harness 能从任意一步恢复状态，和 [持久化与断点恢复](/ai/agent/14-durable-agent) 用的是同一套机制。

### 失败沉淀为测试

修好之后，把这条轨迹的开头（任务、初始上下文、录制的工具结果）存成一个用例，断言关键行为：调了哪个工具、没有调哪个危险工具、最终结果满足什么条件。以后改提示词或换模型时跑一遍，防止同样的问题回来。这些用例可以并入 [回归测试](/engineering/eval/05-regression-testing)。

## 面试官可能追问

::: details 模型输出有随机性，回放还有意义吗？
有。把温度调低或固定采样参数能减少波动，但不能保证完全一致。更可靠的做法是同一步多跑几次，看出错的比例；断言写成"结果满足某个条件"，而不是"输出逐字相同"。
:::

::: details 多步之后才失败，怎么快速找到根因？
从失败点往前看，找第一个"上下文里已经有错误信息或缺失关键信息"的步骤。常见的根因是很早的某次工具结果被截断或误读，后面一路将错就错。给轨迹查看器加上"这一步上下文和上一步的差异"视图，会快很多。
:::

::: details 线上用户的轨迹能直接拿来做测试吗？
要先脱敏，去掉密钥、个人信息和业务机密，并且符合数据使用的约定。工具结果里可能夹带第三方的内容，存储和共享都要注意权限。
:::

## 易错点

- 只记用户问题和最终答复，不记每一步模型实际看到的完整输入
- 不记版本信息，回放时提示词或工具已经变了，结论不可信
- 回放时真实执行写操作，调试一次就多发了一次邮件或多扣一次款
- 把逐字相同的输出当成断言，模型稍有变化测试就失败
