# 什么是 Agent Harness？一个能上线的 Agent 除了模型还需要哪些部分？

::: tip 一句话回答
**Harness** 是包在模型外面的那一层运行框架：驱动循环、执行工具、管理上下文、控制权限、持久化状态、记录轨迹、隔离执行环境。模型决定"每一步想得对不对"，harness 决定"想对了能不能安全、稳定地做成"。同一个模型换一套 harness，表现可以差很多。
:::

## 详细解析

### 模型只是其中一块

模型的接口很简单：输入一串消息，输出文本或工具调用请求。它不会自己执行命令，不记得上次会话，也不知道哪些操作危险。把这些补上的代码就是 harness。打个比方：模型是发动机，harness 是底盘、刹车、仪表盘和方向盘。

[最小的 Agent 循环](/ai/agent/09-agent-loop) 只有几十行，[Agent 的定义](/ai/agent/01-what-is-agent) 也只要求"循环 + 工具"。但这离能上线还差很远。

### 上线需要的完整外围

| 组成 | 负责什么 | 相关题 |
| --- | --- | --- |
| 循环控制 | 调模型、解析工具调用、决定继续还是停止，限制步数和预算 | [防失控](/ai/agent/07-guardrails) |
| 工具执行 | 参数校验、超时、把错误转成模型能看懂的结果、并行调度 | [工具报错](/ai/tools/05-tool-errors) |
| 上下文管理 | 拼装系统提示和项目说明、裁剪长结果、压缩历史 | [长任务上下文](/ai/agent/12-long-task-context) |
| 权限 | 哪些操作自动放行、哪些要审批、哪些禁止 | [权限模式](/engineering/harness/02-permission-modes) |
| 扩展点 | 工具调用前后插入确定性检查和自动化 | [Hooks](/engineering/harness/03-hooks) |
| 持久化 | 检查点、断点恢复、会话历史 | [状态持久化](/ai/agent/14-durable-agent) |
| 可观测 | 记录每一步的输入输出，支持调试和回放 | [调试和回放](/engineering/harness/05-agent-debugging) |
| 沙箱 | 执行代码和命令的隔离环境 | [沙箱](/engineering/security/06-sandbox) |

另外还有子任务委派（[子 Agent](/engineering/harness/04-subagents)）、人工介入（[人在回路](/ai/agent/11-human-in-the-loop)）、项目说明加载（[项目说明文件](/engineering/harness/06-agent-instructions)）、成本统计这些配套。

### 模型和 harness 各管什么

- **模型能力**决定上限：理解任务、规划步骤、选对工具、读懂报错
- **harness 质量**决定能发挥出多少：工具描述清不清楚、报错有没有用、上下文里有多少噪音、出错后能不能恢复

很多看起来是"模型不行"的问题，其实出在 harness。工具返回几万字日志把上下文撑满，模型后面就开始忘事；工具报错只返回一个 `error`，模型只能瞎猜；没有步数上限，模型在死胡同里反复重试。换更强的模型只能缓解，根治要改 harness。

### 为什么同一个模型表现差异大

模型每一步看到的都是 harness 拼出来的上下文。同样的任务，一个 harness 给了清晰的工具说明、精简的结果和项目约定，另一个给了冗长的原始输出和含糊的工具名，模型的决策质量自然不同。所以比较 Agent 产品，不能只看它用的是哪个模型。

### 安全要靠代码，不靠提示词

"不要删除文件""不要读密钥"写进提示词，模型大多会遵守，但可能被注入内容诱导，也可能误判。权限、沙箱、步数上限这些边界要由 harness 用代码强制执行，提示词只用来表达偏好。

## 面试官可能追问

::: details Harness 和 Agent 框架是一回事吗？
有重叠，侧重不同。[Agent 框架](/ai/agent/10-frameworks) 通常是给开发者用的库，提供编排抽象；harness 强调让 Agent 在真实环境里跑起来的整套运行时，包括权限、沙箱、持久化这些产品级部分。用框架搭出来的东西，补齐这些才算完整的 harness。
:::

::: details 自己写 harness 时最容易漏掉什么？
常见的有三样：停止条件（步数、预算、重复检测）、工具结果的长度控制、失败后的恢复。前两样漏了，Agent 会又贵又笨；第三样漏了，长任务一出错就得从头再来。
:::

::: details 怎么判断问题出在模型还是 harness？
看轨迹。如果模型拿到的上下文信息完整、清楚，它还是做错了，多半是模型能力问题；如果上下文缺信息、有误导或噪音太多，就是 harness 的问题。所以完整记录每一步的输入是排查的前提。
:::

## 易错点

- 把 Agent 的效果全算在模型头上，忽略了上下文是 harness 拼出来的
- 以为最小循环加几个工具就能上线，没有权限、沙箱和停止条件
- 把安全要求写进提示词就当做完了，这些应该由 harness 用代码强制执行
