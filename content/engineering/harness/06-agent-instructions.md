# Agent 的项目说明文件怎么组织？AGENTS.md 这类文件怎么加载、怎么写？

::: tip 一句话回答
项目说明文件是放在仓库里、给 Agent 看的 Markdown，写**构建和测试命令、代码规范、目录结构、注意事项**这些新人入职要知道的东西。harness 在会话开始或进入某个目录时自动把它加载进上下文，通常分**全局、项目、子目录**多级，越靠近当前工作文件的越具体、优先级越高。它要短、要具体、随代码一起做版本管理。
:::

## 详细解析

### 解决什么问题

每次开新会话，Agent 都不知道这个项目用什么包管理器、测试怎么跑、哪些目录不能动。不写下来，它只能靠猜或者每次都去翻配置文件，既慢又容易错。项目说明文件就是把这些固定的知识写一次，每次自动带上。

AGENTS.md 是一种约定俗成的文件名，被多个编程类 Agent 支持；也有产品用自己的文件名，或者允许配置读哪个文件。格式就是普通 Markdown，没有必填字段。

### 多级加载

```text
~/.<agent>/全局说明          个人习惯：回复语言、常用工具
仓库根目录/AGENTS.md         项目通用：命令、规范、架构
packages/api/AGENTS.md       子项目特有：这个包的测试命令、约束
```

- 一般约定**离正在编辑的文件最近的那份优先**，子目录的说明覆盖根目录里冲突的部分
- 用户在对话里直接给出的要求，优先于文件里写的
- 父级和子级怎么合并（全部拼接，还是只取最近的一份），各个产品的做法不一样，要看所用工具的文档
- 子目录的说明可以按需加载：Agent 进入那个目录工作时才读，不占用其他任务的上下文

### 和其他机制的分工

| 机制 | 放什么 | 由谁维护 |
| --- | --- | --- |
| 系统提示 | Agent 的身份、通用行为、工具用法 | 产品方 |
| 项目说明文件 | 这个仓库的命令、规范、坑 | 项目团队，提交进仓库 |
| [记忆](/ai/agent/04-memory) | 跨会话积累的个人偏好和事实 | Agent 自动写或用户维护 |
| [Skills](/ai/agent/17-agent-skills) | 某类任务的详细步骤和脚本，按需加载 | 团队或个人 |
| [Hooks](/engineering/harness/03-hooks) | 必须每次执行的硬规则 | 项目团队 |

项目说明是每次都加载的，所以只放每个任务都可能用到的内容。某类任务才用的长流程放进 Skills；"提交前必须过 lint"这种必须保证的规则用 hook 强制，说明文件里写一句即可。

### 写什么

- **命令**：安装、构建、测试、单个测试怎么跑、lint 和类型检查。写成可以直接复制执行的形式
- **规范**：命名、目录约定、错误处理方式、提交信息格式
- **架构速览**：几句话说清主要目录各管什么，而不是罗列每个文件
- **坑和禁区**：生成的文件不要手改、某个目录是第三方代码、迁移要用脚本生成

### 不写什么

- 代码里一眼就能看出来的东西，比如"这是一个 TypeScript 项目"
- 冗长的背景介绍、团队历史
- 密钥、内部地址等敏感信息：文件在仓库里，也会被发给模型
- 容易过时的细节，比如具体的版本号和文件清单

文件越长，模型越难抓住重点，还每次都占上下文。写得具体比写得多重要："测试用 `npm run test -- 文件路径` 跑单个文件"比"注意写测试"有用。

### 随项目一起维护

说明文件和代码放在一起，走同样的代码评审。改了构建命令、换了测试框架，就同步改说明。发现 Agent 反复犯同一个错误，就补一条规则；规则不再适用了就删掉。

## 面试官可能追问

::: details 说明文件里的要求，Agent 一定会遵守吗？
不一定。它只是上下文的一部分，模型大多会照做，但在长任务里可能忽略，或被其他内容覆盖。必须保证的规则，要用权限规则或 hook 在 harness 层强制执行。
:::

::: details 打开一个不信任的仓库，里面的说明文件有风险吗？
有。说明文件会直接进入上下文，相当于仓库作者能给 Agent 下指令，可能借此诱导它执行危险操作，属于 [间接提示注入](/engineering/security/02-indirect-injection)。对不信任的仓库，要收紧权限模式，不要自动放行命令。
:::

::: details 多个 Agent 工具都要用，说明文件怎么共享？
用一份通用的文件（比如 AGENTS.md）作为主体，其他工具如果有自己的文件名，可以在配置里指定读这份文件，或者用很短的文件引用它，避免维护多份内容不一致的副本。
:::

## 易错点

- 把所有能想到的都写进去，文件又长又泛，真正关键的规则反而被淹没
- 以为写进说明文件就等于强制执行，没有用 hook 或权限兜底
- 在说明文件里放密钥或内部敏感信息
- 构建命令改了却没更新说明，Agent 照着过时的命令执行一直失败
