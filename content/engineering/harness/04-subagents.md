# 子 Agent 是什么？什么时候把任务委派给子 Agent？

::: tip 一句话回答
子 Agent 是主 Agent 通过一个"委派"工具启动的另一个 Agent，**有自己独立的上下文窗口**，干完活只把**摘要**返回给主 Agent。适合搜索、调研、读大量文件这类"过程很长、结论很短"的任务，以及可以并行的独立子任务。它的工具和权限可以比主 Agent 更窄。代价是更多的 token、可能丢失细节，以及任务说明要写得自包含。
:::

## 详细解析

多个 Agent 之间的协作模式见 [多 Agent 协作](/ai/agent/05-multi-agent)，上下文压缩见 [长任务上下文](/ai/agent/12-long-task-context)。这里只讲主 Agent 把子任务交出去的机制。

### 委派是怎么实现的

对主 Agent 来说，子 Agent 就是一个工具：

```text
主 Agent ──调用 delegate(任务说明, 类型)──▶ harness
                                              │
                         新建一个空的上下文，只放：
                         子 Agent 的系统提示 + 任务说明
                                              │
                         子 Agent 跑自己的循环（读文件、搜索……）
                                              │
主 Agent ◀──── 工具结果：子 Agent 的最终答复 ────┘
```

子 Agent 中间读的几十个文件、跑的几十次搜索都留在它自己的上下文里，结束后丢掉。主 Agent 的上下文只多了一次工具调用和一段结论。

### 为什么有用

- **保护主上下文**：调研过程会产生大量原始信息，主任务只需要结论。不委派的话，这些内容挤占窗口，后面的步骤会变差
- **并行**：几个互不依赖的子任务可以同时跑，比如分别调查三个模块
- **专门化**：子 Agent 可以有专门的系统提示、更窄的工具集，也可以换用更便宜的模型

### 工具和权限可以收窄

做调研的子 Agent 只给读文件和搜索工具，不给写文件和执行命令。即使它读到了带注入内容的文件，能造成的破坏也有限。子 Agent 的权限不应超过主 Agent，通常更少。一般也不允许子 Agent 无限制地继续委派，避免层层嵌套失控。

### 什么时候该委派

| 适合委派 | 不适合委派 |
| --- | --- |
| "找出所有调用这个接口的地方" | 需要和用户反复确认的任务 |
| 读一大堆文档后回答一个问题 | 几步就能做完的小任务 |
| 多个独立方向的并行调研 | 子任务之间强依赖，要频繁交换中间结果 |
| 需要不同工具集的独立环节 | 后续步骤需要过程中的全部细节 |

### 代价

- **成本**：子 Agent 要自己重新获取需要的背景，总 token 往往更多。并行能省时间，不一定省钱，见 [成本和延迟](/ai/agent/18-agent-cost-latency)
- **信息丢失**：子 Agent 只回摘要，它觉得不重要的细节主 Agent 就看不到了。可以要求它在结论里附上文件路径和行号，主 Agent 需要时再去看原文
- **协调**：子 Agent 看不到主对话，任务说明要自包含：目标、范围、已知信息、返回什么格式。说明含糊，子 Agent 就会跑偏
- **并行写冲突**：多个子 Agent 同时改同一批文件会互相覆盖。并行的最好是只读任务，要写就给每个子 Agent 隔离的工作目录

## 面试官可能追问

::: details 子 Agent 返回的结果，主 Agent 能完全相信吗？
不能。子 Agent 可能漏查或误判，也可能被它读到的外部内容影响。关键结论让它附上证据（路径、引用），主 Agent 抽查；涉及写操作的决定最好由主 Agent 确认后再做。
:::

::: details 子 Agent 和上下文压缩有什么区别？
压缩是事后把已经进入上下文的历史变短；子 Agent 是事前把过程隔离出去，原始内容从来没进过主上下文。能预见到"过程长、结论短"的子任务，用子 Agent 更干净，也不会有压缩时误删信息的问题。
:::

::: details 子 Agent 出错或超时怎么办？
harness 给子 Agent 设步数和时间上限。失败时把原因和已完成的部分作为工具结果返回，让主 Agent 决定重试、改写任务说明还是自己做，不要让主 Agent 无限等待。
:::

## 易错点

- 以为子 Agent 能看到主对话的历史，任务说明写得像在接着聊天
- 小任务也委派，结果更慢更贵
- 给子 Agent 和主 Agent 一样多的工具和权限，浪费了隔离的好处
- 把子 Agent 的摘要当成事实，不要求附证据
