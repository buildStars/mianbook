# 成本和延迟怎么纳入评测？

::: tip 一句话回答
评测时每条样本除了记录质量分，还要记录**输入输出 token 数、调用次数、总耗时和首 Token 延迟**，汇总成**单次请求平均成本**和 **P50 / P95 延迟**。比较方案时把质量和成本、延迟放在一起看，找**帕累托最优**的方案，而不是只挑分数最高的。成本和延迟也要设**门槛**放进回归测试，防止某次改动让 token 用量翻倍却没人发现。
:::

## 详细解析

### 为什么要放进评测

质量提升往往有代价：换更大的模型、加重排、多轮自我检查、给更多上下文，分数涨了，成本和延迟也涨了。只看质量分，最后上线的可能是用不起或者太慢的方案。Agent 尤其明显，一次任务调用多少轮模型并不固定（见 [Agent 评测](/engineering/eval/10-agent-eval)）。

### 每条样本记录什么

| 指标 | 说明 |
| --- | --- |
| 输入 token、输出 token | 分开记，两者单价通常不同；命中缓存的部分也单独记 |
| 调用次数 | 一次请求里调了几次模型、几次工具、几次检索 |
| 首 Token 延迟（TTFT） | 流式场景下用户感知最明显的指标 |
| 总耗时 | 从请求到最后一个 token；Agent 任务是整个任务的耗时 |
| 成本 | 按 token 数和单价算出来，加上检索、重排等其他服务的费用 |

这些数据通常已经在 trace 里（见 [可观测性](/engineering/eval/06-observability)），评测框架直接读取即可。成本的估算方法见 [一次调用的成本怎么估算](/engineering/deploy/02-cost-estimate)。

### 怎么汇总

- **成本**：看平均值和总量，也看分布。少数超长对话可能占了大头
- **延迟**：看 P50 和 P95 等分位数，平均值会被少数慢请求拉高，也会掩盖长尾
- **单位有效成本**：总成本除以回答正确的样本数，比较"每个正确回答花了多少钱"
- **按类别分组**：复杂问题耗时长是正常的，分组后才能看出哪类问题变慢了

离线评测的延迟和线上会有差别：并发、网络、缓存命中率都不一样。离线延迟更适合做版本之间的相对比较，绝对值以线上监控为准（见 [线上效果监控](/engineering/eval/08-online-monitoring)）。

### 在质量和成本之间做选择

把各方案画在"质量 - 成本"两个维度上：

```text
方案   准确率   平均成本（相对值）   P95 延迟
A      较低     1                  低
B      高       3                  中
C      略高于 B 10                 高
```

（数值仅为示意）C 比 B 只好一点，成本却高很多，通常选 B；如果有一个方案在质量、成本、延迟上都不比别人差，至少一项更好，它就是帕累托最优。最终怎么选取决于业务：客服场景延迟敏感，离线报告生成可以接受慢一点。

常见的折中手段：按问题难度路由到不同模型、对稳定的前缀用 Prompt 缓存、减少不必要的上下文（见 [降低调用成本](/engineering/deploy/03-cost-reduction)）。

### 放进回归测试

给成本和延迟设门槛，和质量分一起作为通过条件：

- 平均 token 数比基线增加超过一定比例时失败或告警
- P95 延迟超过上限时失败
- Agent 任务的平均步数超过上限时告警，可能是陷入了循环

门槛按业务的预算和体验要求定，并随基线更新（见 [回归测试](/engineering/eval/05-regression-testing)）。

## 面试官可能追问

::: details 为什么延迟不看平均值？
延迟分布通常有长尾：大部分请求很快，少数很慢。平均值既会被慢请求拉高，也看不出有多少用户等了很久。P95、P99 直接反映最慢那部分用户的体验，更适合定目标。
:::

::: details 推理模型或 Agent 的成本波动大，怎么评估？
同一条样本多跑几次，看 token 数和步数的分布，不只看一次的值。重点关注最坏情况，比如输出 token 的 P95，并给单次任务设置 token 或步数的上限，评测时统计触顶的比例。
:::

::: details 自部署模型怎么算成本？
没有按 token 计费，要按 GPU 的使用成本和吞吐折算：一段时间的机器成本除以这段时间处理的 token 数或请求数。所以吞吐对自部署的单位成本影响很大，评测时要在接近线上的并发下测。
:::

## 易错点

- 只比较质量分，选中的方案成本或延迟不可接受
- 延迟只看平均值，不看分位数
- 离线评测的延迟当成线上的真实延迟
- 输入和输出 token 不分开统计，算错成本
