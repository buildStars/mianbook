# 评测集怎么防止被刷分和过拟合？

::: tip 一句话回答
评测集被反复用来调 Prompt、选模型，分数会越来越高，但真实效果不一定提升，这就是对评测集的**过拟合**。防范办法：评测集分成**开发集**和**留出集**，日常只看开发集，留出集只在发布前用；**定期补充新样本**，尤其是线上新出现的问题；避免针对具体样本写规则；分数差异小时看**置信区间**，别把随机波动当提升。选公开模型时还要警惕**数据污染**：公开基准可能已经在训练数据里。
:::

## 详细解析

### 过拟合是怎么发生的

每次看到失败样本就改 Prompt，把这个样本修好，几十轮下来：

- Prompt 里堆满了针对个别样本的特殊说明，例如"如果用户问到退款时效，回答 7 天"
- 评测集的分数逐步上涨，但换一批同类问题，效果没有提升，甚至变差
- 评测集规模小时更明显，几十条样本，修好两三条就涨好几个百分点

本质和机器学习里在测试集上调参一样：被用来做决策的数据，就不再能公正地评价这个决策。

### 拆分数据集

| 数据集 | 用途 | 使用频率 |
| --- | --- | --- |
| 开发集 | 日常调试、看失败样本、改 Prompt | 随便看 |
| 回归集 | 每次改动自动跑，防止已修好的问题回退 | 每次提交 |
| 留出集 | 发布前做最终评估，不看具体样本，只看总分 | 偶尔，定期轮换 |

留出集的关键是"不看具体失败样本、不针对它改"。一旦根据它的失败样本改了东西，它就退化成了开发集，需要补新的留出数据。

评测集的基本构建方法见 [评测集应该怎么构建](/engineering/eval/03-eval-dataset)。

### 让评测集跟上真实分布

- **持续补充**：从线上日志、用户反馈里定期采样新问题加入（见 [反馈数据闭环](/engineering/eval/11-feedback-loop)）
- **按时间切分**：用较新时间段的数据做留出集，检查效果在新问题上是否成立
- **按类别统计**：总分之外看每个类别的分数，某类样本太少时单独补
- **同类改写**：对关键样本准备几个换说法的版本，如果只有原句能答对，说明修的是这一条而不是这一类

### 分数提升是真的吗

LLM 的输出有随机性，评测集又不大，几个点的差异可能只是波动：

- 同一配置多跑几次，看分数的波动范围
- 对比两个版本时用同一批样本做配对比较，统计"新版本赢、输、平"的样本数
- 样本量小的时候，提升要足够大才可信；可以用 bootstrap 估一个置信区间
- 用 LLM 当评委时，评委本身也有偏差和波动（见 [LLM-as-a-Judge](/engineering/eval/02-llm-as-judge)）

### 数据污染

公开基准的题目和答案可能出现在模型的训练数据里，模型在上面得分高，可能只是"记住了"。所以选模型不能只看公开基准分数，要在自己的私有评测集上测。私有评测集也不要随意外传或放进公开仓库，防止它进入以后的训练数据。

## 面试官可能追问

::: details 发现 Prompt 已经过拟合了，怎么办？
把 Prompt 里针对个别样本的规则挑出来，判断能不能合并成一般性的原则，或者移到知识库里，作为可检索的数据而不是硬编码。改完在留出集和新采样的数据上重新评估，以它的结果为准。
:::

::: details 留出集多久换一次？
没有固定周期。原则是：根据它的结果做过针对性修改，就该补新数据；业务和用户问题有明显变化时，也要更新。可以每次发布前从最近的线上数据里抽一批新样本，人工标注后作为这一轮的留出集。
:::

::: details 评测集要多大才够？
取决于要检测多大的差异和问题类别有多少。类别多、需要分组看分数时，每组都要有足够的样本。与其追求一次建很大，不如先建一个覆盖主要类别的小集合，再随线上问题持续扩充。
:::

## 易错点

- 一个评测集既用来调试又用来做最终评估，分数虚高
- 针对单条失败样本在 Prompt 里写特例规则
- 跑一次就比较两个版本，把随机波动当成提升
- 用公开基准分数代替在自己数据上的评测
