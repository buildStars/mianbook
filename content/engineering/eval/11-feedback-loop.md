# 用户的点赞点踩怎么形成数据闭环？

::: tip 一句话回答
闭环是"**收集 → 关联 → 分析归因 → 改进 → 验证**"。反馈要和这次请求的 **trace** 关联起来，才知道当时的输入、检索结果、Prompt 版本和输出；点踩的样本按原因分类（检索没找到、回答错误、格式问题、拒答过度……），对应到具体环节去改；有代表性的样本沉淀进**评测集**，改完先跑离线回归，再上线观察反馈指标。点赞点踩的数据**稀疏且有偏**，不能直接当准确率用。
:::

## 详细解析

### 反馈的来源

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| 显式反馈 | 点赞点踩、打分、选择点踩原因、填写意见 | 意图明确，但参与率低 |
| 隐式反馈 | 复制回答、重新生成、追问"不对"、马上换个问法、转人工 | 量大、覆盖面广，但含义需要推断 |
| 业务结果 | 工单是否解决、代码建议是否被采纳、是否下单 | 最接近真实价值，但延迟长、归因难 |

只靠点赞点踩，样本量往往不够。把"重新生成""转人工"这类信号也记下来，能补上大部分沉默用户的反馈。

### 先关联到 trace

只存"第几条消息被点踩"没法分析。每次回答都带一个 `trace_id`，反馈接口带上它，后台就能看到完整现场：用户问题、改写后的查询、检索到的块、Prompt 版本、模型、输出和耗时（见 [链路追踪](/engineering/eval/07-tracing)）。

存储时注意隐私：对话内容可能包含敏感信息，查看和导出要有权限，用于训练和评测前要脱敏，并符合用户协议。

### 归因和分类

点踩只说明"不满意"，不说明原因。可以：

1. 点踩后让用户选原因（不准确、没回答问题、太长、格式乱……），选项简短，选填
2. 用 LLM 对点踩样本做初步分类，标出可能的环节：检索没召回、召回了但答错、知识库本身缺失、拒答过度、违反格式要求
3. 定期人工抽检分类结果，修正分类标准

分类后按占比和影响排优先级。比如发现大量点踩来自"知识库里没有"，要补的是文档，而不是调 Prompt。

### 沉淀和验证

- 有代表性的失败样本，经过人工确认标准答案后，加入评测集（见 [评测集构建](/engineering/eval/03-eval-dataset)）
- 修改 Prompt、检索或模型后，先跑离线回归，确认修好了这批问题、没把别的弄坏（见 [回归测试](/engineering/eval/05-regression-testing)）
- 上线后用 A/B 或灰度对比点踩率、重新生成率等指标（见 [A/B 测试](/engineering/eval/09-ab-testing)）

这样每轮迭代都让评测集更贴近真实问题。

### 反馈数据的偏差

- **选择偏差**：愿意点的人是少数，而且不满意时更容易点踩
- **标准不一**：同样的回答，有人觉得太长点踩，有人觉得详细点赞
- **和正确性不完全相关**：回答错了但语气自信，用户可能也点赞
- **恶意或误操作**：要过滤刷反馈和误点

所以反馈率用来看趋势和发现问题，不能直接当成准确率；质量的结论还要靠评测集和人工抽检。

## 面试官可能追问

::: details 点赞点踩的数据能直接拿来微调模型吗？
可以作为偏好数据的来源，但不能直接用。要先清洗噪声、去掉敏感信息，确认点赞的回答确实是好的。偏好训练需要同一问题的好坏回答对，单条点赞点踩还要配对构造。多数应用层团队更常用它改进 Prompt、检索和知识库，而不是训练模型。
:::

::: details 怎么提高用户的反馈参与率？
降低操作成本：按钮放在回答末尾显眼处，点踩后的原因选项一键可选。不要频繁弹窗打扰。也可以在关键流程结束时问一个简单的问题，比如"问题解决了吗"。
:::

::: details 反馈指标突然变差，先查什么？
先看时间点前后有没有发布：Prompt、模型、知识库、检索配置的变更。再按维度拆：哪类问题、哪个入口、哪个用户群变差了。然后抽几条点踩样本看 trace，判断是哪个环节出了问题（见 [线上效果监控](/engineering/eval/08-online-monitoring)）。
:::

## 易错点

- 反馈没关联 trace，只知道哪条回答被点踩，不知道当时的上下文
- 把点赞率当准确率，忽视了参与率低和选择偏差
- 收集了反馈但没人定期分析，数据只是躺在库里
- 失败样本直接进评测集，没有人工确认标准答案
