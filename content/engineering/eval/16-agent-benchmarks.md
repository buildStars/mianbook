# SWE-bench 这类 Agent 基准是怎么构建和打分的？

::: tip 一句话回答
SWE-bench 从开源 Python 仓库里找"**有 issue、有修复 PR、PR 改了测试**"的真实案例，把 issue 描述和修复前的代码交给 Agent，让它生成补丁，再跑两组测试打分：**FAIL_TO_PASS**（修复前失败、修复后应通过，验证问题被解决）和 **PASS_TO_PASS**（修复前后都应通过，验证没改坏别的），两组全过才算解决。其他 Agent 基准思路相同：在可复现的环境里执行，**检查最终状态**而不是比对过程。看分数时要警惕数据污染、测试不充分、环境差异和 Agent 脚手架不同带来的偏差。
:::

## 详细解析

### SWE-bench 的任务从哪来

原论文的构建流程大致是：

1. 选一批流行的开源 Python 仓库，抓取已合并的 PR
2. 只保留关联了 issue、并且修改了测试文件的 PR
3. 把 PR 拆成两部分：改测试的部分作为**评测用的测试补丁**，改源码的部分作为**参考答案**
4. 在修复前的代码上执行测试，再应用参考答案后执行，找出状态发生变化的测试
5. 过滤掉没有任何测试从失败变为通过的样本，以及环境装不起来的样本

最终得到 2294 个任务，来自 12 个仓库。每个任务给 Agent 的只有 issue 文本和修复前的代码库，测试补丁对 Agent 不可见。

### 打分规则

| 测试组 | 修复前 | 修复后应该 | 作用 |
| --- | --- | --- | --- |
| FAIL_TO_PASS | 失败 | 通过 | 证明 issue 描述的问题被修好了 |
| PASS_TO_PASS | 通过 | 通过 | 证明没有引入回归 |

评测时把 Agent 的补丁应用到代码上，再应用隐藏的测试补丁，在固定的容器环境里运行这两组测试，**全部通过**才记为"已解决"，最终指标是已解决任务的比例。补丁打不上、测试超时都算失败。它不比对补丁和参考答案长得像不像，只看行为，所以不同的写法都能得分。

### 为什么要有人工筛选的子集

全量集里有不少任务本身有问题：

- issue 描述不清楚，光看描述无法知道正确行为
- 测试和参考实现绑得太紧，比如检查了特定的报错文案或函数名，正确但写法不同的修复会被判错
- 环境不稳定，测试本身时好时坏

所以出现了子集：**SWE-bench Lite** 挑了 300 个相对独立、改动较小的任务，降低评测成本；**SWE-bench Verified** 由专业开发者逐个人工审核，去掉描述不清、测试不公平的任务，保留 500 个。人工筛选提高了分数的可信度，代价是规模小、覆盖面窄，分数也更容易被针对性优化。

### 其他类型的 Agent 基准怎么打分

| 类型 | 任务形式 | 打分方式 |
| --- | --- | --- |
| 代码仓库 | 修 bug、实现功能 | 运行隐藏测试，看行为 |
| 终端操作 | 在容器里完成配置、编译、数据处理 | 任务结束后跑检查脚本，验证文件、进程、输出等最终状态 |
| 网页操作 | 在自托管的网站副本里完成购物、填表、查询 | 检查网站数据库或页面的最终状态，或比对给出的答案 |
| 工具调用和对话 | 扮演客服，用工具处理模拟用户的请求 | 对比结束时数据库状态和目标状态，常用多次运行的 pass^k 衡量稳定性 |

共同点是：环境可以重置和复现，打分看**结果状态**，不看 Agent 走了哪条路径。自己的业务怎么设计评测和 pass^k 的含义见 [Agent 评测](/engineering/eval/10-agent-eval)；模型层面的基准见 [模型基准](/ai/llm/17-benchmarks)。

### 分数为什么会有偏差

- **数据污染**：任务来自公开仓库，修复代码和讨论可能已经在训练数据里。有的基准用时间切分，只收训练截止后的新任务来缓解
- **测试不充分**：测试只覆盖了部分行为，错误的补丁也可能通过；反过来，测试过于严格会误判正确修复
- **环境差异**：依赖版本、网络、随机性都会影响结果，同一个系统在不同硬件或超时设置下分数会变
- **脚手架不同**：分数衡量的是"模型 + Agent 框架 + 提示 + 工具 + 尝试次数"的整体，不是单纯的模型能力

### 看榜单要注意什么

1. 用的是哪个子集，全量、Lite 还是 Verified，不同子集的分数不能直接比
2. 是单次运行还是多次取最好，有没有用测试结果来挑选补丁
3. Agent 能不能联网、能看到哪些信息，有没有可能看到答案
4. 成本和耗时是多少，同样的分数，花十倍预算的方案未必更好
5. 基准任务和自己的业务差距多大；最终还是要用自己的评测集验证（见 [防止评测集过拟合](/engineering/eval/12-eval-overfitting)）

## 面试官可能追问

::: details 为什么 PASS_TO_PASS 也必须通过？
只看 FAIL_TO_PASS，Agent 可以靠删掉相关逻辑、硬编码返回值让目标测试通过，同时把别的功能改坏。PASS_TO_PASS 是回归测试，保证补丁不是"修一个坏三个"。两组合在一起，才接近"真正修好了"的含义。
:::

::: details 自己要做一个类似的代码 Agent 基准，要注意什么？
任务从自己的真实工单和修复记录里取，评测用的测试对 Agent 隐藏；每个任务都要在干净环境里验证"参考答案能过、原代码不能过"；固定依赖版本，用容器隔离；最好人工审一遍描述是否充分、测试是否会误判。定期补充新任务，旧任务的分数会随着系统针对性优化而虚高。
:::

::: details 一个 Agent 在基准上分数很高，为什么接到自己项目里表现一般？
基准的任务分布、仓库规模、语言和自己的项目不一样；基准里的 issue 往往描述了明确的复现方式，真实需求更模糊；基准分数还绑定了特定的脚手架和预算。基准只能说明大致能力，选型要用自己的任务集和真实流程测。
:::

## 易错点

- 以为 SWE-bench 比对的是补丁内容，实际是看测试行为
- 忘了 PASS_TO_PASS，只把"让失败的测试通过"当作打分标准
- 不区分全量、Lite、Verified 子集，直接比较不同子集上的分数
- 把榜单分数当成纯模型能力，忽略了 Agent 框架、尝试次数和成本的影响
