# 大模型应用的红队测试怎么做？

::: tip 一句话回答
红队测试是**站在攻击者和恶意用户的角度**，主动找出应用会被诱导做出的有害行为。流程是：先**定义风险范围**（提示注入、越狱、敏感信息泄露、越权工具调用、有害内容……），再用**人工加自动化**的方式构造攻击用例，按类别统计**攻击成功率**，修复后把成功的用例沉淀成**回归测试**。它不是上线前做一次就完，模型、Prompt、工具变了都要重新测。
:::

## 详细解析

### 和普通评测的区别

普通评测关心正常用户能不能得到好回答；红队测试关心有人故意使坏时，系统会不会出事。用例来自对抗性的思路，目标是找出失败，而不是证明系统可用。

### 第一步：定义范围

先根据应用的能力和场景列出要测的风险，不同应用差别很大：

| 风险类别 | 关注点 | 相关题目 |
| --- | --- | --- |
| 提示注入 | 用户输入或外部内容覆盖了系统指令 | [Prompt 注入](/engineering/security/01-prompt-injection)、[间接提示注入](/engineering/security/02-indirect-injection) |
| 越狱 | 绕过模型的安全限制，输出有害内容 | [越狱](/engineering/security/03-jailbreak) |
| 信息泄露 | 泄露系统 Prompt、其他用户数据、内部文档 | [敏感信息泄露](/engineering/security/04-data-leakage) |
| 越权操作 | 诱导 Agent 调用不该调用的工具，或越过权限访问数据 | [工具权限](/ai/tools/09-tool-permissions) |
| 业务风险 | 做出不该有的承诺、错误的价格或政策、冒充身份 | 按业务定义 |

范围里要写清楚什么算"攻击成功"，比如"输出了系统 Prompt 的原文"或"调用了删除接口"，判定标准要具体，后面才能自动化统计。可以参考 [OWASP 大模型应用十大风险](/engineering/security/10-owasp-llm-top10) 查漏补缺。

### 第二步：构造用例

- **人工红队**：安全人员、熟悉业务的同事，或者外部的专业团队。人擅长发现新的攻击思路，尤其是结合业务逻辑的
- **已知攻击模式库**：把公开的攻击类别（角色扮演、编码混淆、多轮渐进诱导、在文档里藏指令等）整理成模板，批量生成变体
- **自动化红队**：用一个模型扮演攻击者，根据目标和上一轮回复不断改写攻击，再用评判模型或规则判断是否成功
- **多轮和间接场景**：不要只测单轮对话。要覆盖多轮逐步诱导，以及通过检索到的文档、网页、工具返回结果注入的情况

攻击用例本身是敏感数据，访问要受控，不要放在公开仓库。

### 第三步：判定和统计

- 每个用例跑多次，因为模型输出有随机性，某次没被攻破不代表安全
- 按风险类别统计攻击成功率，并按严重程度分级：泄露用户数据和输出一句不礼貌的话不是一个级别
- 判定可以用规则（比如检测输出里是否出现系统 Prompt 的特征片段、是否发生了某个工具调用）加 LLM 评判，再人工复核高危案例

### 第四步：修复和回归

修复通常不只靠改 Prompt，要在系统层面加防线：输入输出过滤、工具最小权限、敏感操作人工确认、外部内容和指令隔离。成功的攻击用例加入回归集，每次改 Prompt、换模型、加工具都跑一遍（见 [回归测试](/engineering/eval/05-regression-testing)）。上线后继续监控异常对话，新发现的攻击方式补进用例库。

## 面试官可能追问

::: details 攻击成功率降到 0 就安全了吗？
不是。它只说明在已有的用例上没被攻破，攻击者会有新的方法。所以防御要假设模型可能被攻破，用权限控制、人工确认、输出过滤等手段限制被攻破后的影响范围。
:::

::: details 红队测试会不会让应用变得过度拒答？
会。只盯着攻击成功率，容易把系统调得什么都不敢答。评测时要同时跑正常用例和"看起来敏感但其实正当"的用例，统计误拒率，两个指标一起看。
:::

::: details 什么时候要做红队测试？
上线前做一次系统的测试；之后在模型更换、系统 Prompt 大改、新增工具或数据源这类变更时重新做；日常把回归集放进流水线自动跑。高风险应用还可以定期请外部团队做。
:::

## 易错点

- 只测单轮直接攻击，漏掉多轮诱导和通过外部内容的间接注入
- 每个用例只跑一次，把"这次没攻破"当成"安全"
- 只看攻击成功率，不看误拒率
- 修复只改 Prompt，没有权限和过滤这类系统层面的防线
