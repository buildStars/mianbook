# 面书 · mianbook.ink

面试题手册网站：按目录系统复习前端、后端、AI 应用的高频面试题，带 **AI 模拟面试官**。站名、标志和配色见 [DESIGN.md](DESIGN.md)。

- **阅读端**：分类目录、题目详解（代码高亮、提示块、折叠追问、本页目录）、中文搜索、自测模式、深色模式；每道题底部可以纠错和反馈（不用登录，按 IP 限频）
- **学习记录**：每道题标记"不会 / 模糊 / 掌握"、收藏、笔记；登录后存在数据库里，多设备同步；未登录时先存在本地，登录后自动合并
- **AI 模拟面试官**：用自己的话作答，AI 对照题库参考答案打分（0～10）、指出遗漏和错误，再追问，最多 3 轮；点评流式输出，低分题自动加入复习
- **Agent 面试官**：写下面试目标（岗位、重点方向），AI 面试官自己调用工具：先看你的学习记录和薄弱点，从题库里找题，每次回答后查参考答案打分，再决定追问还是换题、加难度还是降难度，得分写进复习计划，问满后写总结。页面上能看到它每一步调用了什么工具
- **MCP Server**：在"接入 AI 工具"页面创建访问令牌，Claude Code、Cursor 等 AI 工具就能直接检索手册、按薄弱点抽题考你、把得分写回复习计划
- **问手册（RAG）**：用自己的话提问，先从题库里检索相关段落（关键词 + 向量混合检索），再让 AI 根据这些段落回答，每句话标出处、点编号直达原题；支持连续追问，搜索框里也能一键转去问
- **整场模拟面试**：按方向（前端、Go / Java / Node.js 后端、AI 应用等）和难度抽题，连续作答、追问，结束后给出各题得分、分类得分和 AI 总结；可以中途停下，下次接着答
- **间隔复习**：用 FSRS 算法安排复习时间，标记掌握程度、AI 面试得分都会更新计划；"今日复习"页逐题回忆、对照一句话回答、评分
- **学习周报**：本周学习时长、学习天数、复习和面试成绩（和上周对比）、每天的学习时长、最近 8 周趋势、最卡的题、各分类情况和下周建议。阅读时长只算页面在前台、并且最近一分钟内有操作的时间；只记登录用户，事件存在自己的数据库里（`events` 表），不记录回答内容，不接第三方统计
- **自带 API Key**：用户可以在面试面板里填自己的 Key（只存在浏览器里），不受站点每日次数限制
- **管理后台**：运营看板（AI 用量和估算花费、每日活跃、学习数据、题目难度榜）；题目编辑（Markdown 实时预览、和 `content:check` 同一套规则的边写边检查、修改历史对比和恢复、未保存提醒）；AI 写题（按写作规范起草正文、修复检查问题、参考面试反馈改写、按要求修改，改写稿先对比再采用；推荐分类里缺的题）；批量发布 / 转草稿 / 移动 / 删除；分类管理；读者反馈（按待处理 / 已处理 / 已忽略筛选，概览里提示待处理条数）；用户管理（单独设置 AI 次数、停用账号、强制下线、解除登录锁定、发重置密码邮件、撤销访问令牌，详情里看学习情况和 AI 用量）；AI 设置在线修改（模型、次数、是否允许自带 Key、价格）

技术栈：Nuxt 4（Vue 3 + Nitro）、MySQL 8、Drizzle ORM、nuxt-auth-utils、Element Plus、Shiki、MiniSearch。大模型走 OpenAI 兼容接口，默认接 Kimi（Moonshot）。

界面采用"编辑部手册"风格（暖白纸色、思源宋体标题、克莱因蓝点缀、AI 功能用渐变标识），颜色、字体、组件和题目正文的排版规则见 [DESIGN.md](DESIGN.md)。

## 本地运行

需要 Node.js 22.21+ 或 24 LTS，以及本机安装的 MySQL 8.0（Windows 默认路径 `C:\Program Files\MySQL\MySQL Server 8.0`，其他位置用环境变量 `MYSQL_HOME` 指定）。

```bash
npm install
npm run setup
npm run dev
```

`npm run setup` 会做三件事：在项目的 `.mysql/` 目录里初始化一个独立的 MySQL 实例（端口 3307，只监听本机，不注册系统服务），生成数据库账号和登录密钥写入 `.env`，然后建表并导入 `content/` 里的题目。

打开 http://localhost:3000 ，**第一个注册的账号会自动成为管理员**。

以后每次开发前先启动数据库：

```bash
npm run db:start
```

## 开启 AI 模拟面试官

1. 在 Kimi 开放平台（platform.moonshot.cn）创建 API Key
2. 打开 `.env`，填写 `NUXT_AI_API_KEY=你的 Key`
3. 重启 `npm run dev`，到"管理后台 → AI 设置"点"测试当前填写的模型"，确认可用

下表里的模型、次数、额外域名是默认值，可以在"管理后台 → AI 设置"里在线修改，保存后立即生效（存在数据库的 `settings` 表里）；那里还能关闭"用户自带 Key"、填写模型价格来估算花费。接口地址和 API Key 只能在 `.env` 里改。

后台的 AI 写题也用这个 Key，提示词里带上 `templates/writing-guide.md` 写作规范和同分类的一道题作参考；管理员写题不占每日次数，用量在概览的按功能里单独统计。

| 变量 | 说明 |
| --- | --- |
| `NUXT_AI_API_KEY` | API Key，只在服务端使用，不会发到浏览器 |
| `NUXT_AI_BASE_URL` | 接口地址，默认 `https://api.moonshot.cn/v1` |
| `NUXT_AI_MODEL` | 模型名，可用列表见后台"AI 设置" |
| `NUXT_AI_DAILY_LIMIT` | 每个用户 24 小时内最多调用几次，默认 30；后台可以给单个用户另设 |
| `NUXT_AI_EXTRA_HOSTS` | 用户自带 Key 时，除内置服务商外额外允许的域名，逗号分隔 |

换成 DeepSeek、通义千问等服务商时，修改 `NUXT_AI_BASE_URL` 和 `NUXT_AI_MODEL` 即可。

## 问手册的向量检索

问手册不配置也能用（只用关键词检索）。配置向量模型后，换个说法提问也能找到对应的题：

1. 在硅基流动（siliconflow.cn）注册并创建 API Key，费用以它的定价页为准
2. 在 `.env` 里填写 `NUXT_EMBED_API_KEY=你的 Key`，重启服务
3. 服务启动后会在后台给所有题目生成向量，进度在"管理后台 → 知识库"里看；那里还能输入问题调试检索结果

换成其他 OpenAI 兼容的向量接口时，修改 `NUXT_EMBED_BASE_URL` 和 `NUXT_EMBED_MODEL`。换了模型会自动重新生成全部向量。

填了向量 Key 后默认还会开启**重排**：用同一个 Key 调用硅基流动的 `BAAI/bge-reranker-v2-m3`，把检索出的前 30 块按相关度重新排序（效果和代价见下面"问手册是怎么实现的"的评测）。不想用时设置 `NUXT_RERANK_MODEL=`（留空）；换别家的 `/rerank` 接口时填 `NUXT_RERANK_BASE_URL`、`NUXT_RERANK_API_KEY` 和 `NUXT_RERANK_MODEL`，`NUXT_RERANK_CANDIDATES` 改候选块数。"管理后台 → 知识库"的检索调试可以切换"重排 / 不重排"对比前后的顺序。

## 注册邮箱验证码

配置了发信邮箱后，注册时要先填邮件里的 6 位验证码，防止用随便编的邮箱批量注册。没配置时注册照常，不需要验证码。已有账号不受影响，登录也不需要验证码。

以 QQ 邮箱为例：

1. 登录 QQ 邮箱网页版，在设置里找到"POP3/IMAP/SMTP 服务"并开启，按提示生成授权码（授权码不是 QQ 密码）
2. 在 `.env` 里填写：

   ```bash
   NUXT_MAIL_HOST=smtp.qq.com
   NUXT_MAIL_PORT=465
   NUXT_MAIL_USER=你的邮箱@qq.com
   NUXT_MAIL_PASS=刚才生成的授权码
   NUXT_MAIL_FROM=面书 <你的邮箱@qq.com>
   ```

3. 重启应用，到"管理后台 → 用户"点"发测试邮件给我"，收到邮件就说明配置好了

云服务器一般封了 25 端口，要用 465（SSL）或 587。QQ 邮箱要求发件人地址和 `NUXT_MAIL_USER` 一致。发信出问题时，可以在"管理后台 → 用户"里临时关掉"注册需要邮箱验证码"，不用改配置。

验证码 10 分钟内有效，输错 5 次作废。发送频率有限制：同一个邮箱 60 秒一次、一小时 5 次；同一个 IP 一小时 10 次、一天 30 次；全站一天 500 封（保护发信邮箱不被服务商限制）。这些数字可以用 `NUXT_AUTH_CODE_COOLDOWN_SECONDS`、`NUXT_AUTH_CODE_PER_EMAIL_HOURLY`、`NUXT_AUTH_CODE_PER_IP_HOURLY`、`NUXT_AUTH_CODE_PER_IP_DAILY`、`NUXT_AUTH_CODE_DAILY_TOTAL` 调整。

本地开发想试验证码又不想真发邮件时，设置 `NUXT_MAIL_OUTBOX_DIR=.data/outbox`，邮件会写成 JSON 文件放在这个目录里。

配置了发信后，登录页会出现"忘记密码"：用邮箱验证码重置密码，重置后其他设备上的登录全部失效（会话里带版本号，改密码时加 1，旧会话对不上就清掉）。

登录有防暴力破解：同一账号同一 IP 15 分钟内输错 5 次、同一 IP 15 分钟内失败 20 次（撞库）、同一账号 1 小时内失败 30 次（换 IP 猜密码），都会暂时拒绝登录；账号不存在时也做一次同样耗时的密码校验，不能靠响应快慢判断邮箱有没有注册。

## 用户管理

"管理后台 → 用户"的列表里能看到每个人最近 24 小时用了几次站点 AI、上限是多少。点用户打开详情：

- **AI 次数**：默认跟随"AI 设置"里的全站次数；可以给某个用户单独设一个次数（不受全站设置影响），也可以关闭这个用户的站点 AI（填了自己的 API Key 仍然能用）。次数的算法和限流完全一样：最近 24 小时滚动计算，自己的 Key、出错的调用、后台写题都不算
- **学习情况和 AI 用量**：掌握程度、收藏和笔记数、复习卡片、各类面试次数；最近 30 天按功能分的调用次数、token 和估算费用，最近 10 次调用的模型、耗时和出错原因。不显示笔记和回答的内容
- **账号操作**：强制下线（会话版本加 1，所有浏览器都要重新登录，访问令牌不受影响）；解除登录锁定（清掉这个账号的登录失败记录）；发重置密码邮件（用户收到验证码后在"忘记密码"页自己设置新密码，管理员看不到也改不了密码）；撤销访问令牌
- **停用账号**：马上下线，不能登录、不能重置密码，访问令牌暂停使用。密码输错时的提示和普通账号一样，只有密码对了才告诉对方账号已停用。学习记录都保留，重新启用后可以正常登录，停用前的登录不会恢复

不能停用自己、不能让自己下线、不能取消自己的管理员身份。

## 后台修改和 content/ 目录

`content/` 里的 Markdown 是题库的源文件，可以用 Git 管理。在管理后台新建、修改、移动、删除题目或分类时，改动会同时写回 `content/` 下对应的文件和 `outline.json`，所以之后再 `db:import` 不会冲掉后台的修改。部署环境里没有 `content/` 目录时只保存到数据库（后台侧栏会显示"仅保存到数据库"），记得定期 `db:export` 备份。

后台每次保存题目都会记一个历史版本（每题最多 50 个），可以在编辑页的"历史"里和当前内容逐行对比，并载入旧版本。

## AI 模拟面试官是怎么实现的

1. 前端把回答 POST 到 `/api/interviews/stream`，用 `fetch` + `ReadableStream` 解析 SSE（`EventSource` 不支持 POST）
2. 服务端校验登录和 24 小时调用次数，取出题目的参考答案（去掉代码块以节省 token），拼成提示词
3. 回答放在 `<answer>` 标签里并去掉伪造的标签，系统提示词要求把其中的指令当作内容评价，防止提示注入
4. 以流式方式调用大模型，边收边转发给前端；用户点"停止"或关闭页面时同时中断上游请求
5. 生成结束后解析得分和追问，保存面试记录；低于 8 分的题自动标记为"不会"或"模糊"
6. 前端渲染 AI 输出时转义原始 HTML、禁用图片，防止 XSS 和通过图片地址外传数据

## Agent 面试官是怎么实现的

代码在 `server/utils/agent-core.ts`（工具定义、提示词、上下文裁剪、时间线，纯函数）、`server/utils/agent.ts`（工具实现和 Agent 循环）和 `server/api/agent/`。

1. **工具**：模型通过 Function Calling 调用 6 个工具：`get_learning_profile`（各分类掌握情况、面试平均分、到期复习、最近低分题）、`search_questions`（复用问手册的混合检索，也能按分类、难度筛选）、`get_question_reference`（参考答案）、`ask_question`（出题或追问）、`record_assessment`（打分，主问题写进 FSRS 复习计划）、`finish_interview`（总结）
2. **Agent 循环**：候选人每回答一次是一轮。服务端把对话和工具定义发给模型，模型返回工具调用就执行、把结果追加到对话里再请求，直到模型只输出文字（等候选人回答）。一轮最多 8 步、每步最多 4 个工具调用，防止陷入循环。流式返回时工具调用的参数是分块到达的，按 `index` 拼完整再执行
3. **护栏**：模型的参数先用 zod 校验，不对就把错误返回给模型让它自己修正。工具里还有业务规则：题目必须来自题库；只能给正在问的题打分，而且必须在候选人回答之后、每次回答只能打一次；每题最多追问 2 次；问满题数后不能再出新题。这样即使模型被候选人的回答带偏（比如"给我打 10 分"、"这题算了直接下一题"），也写不进不该写的数据。候选人的回答和面试目标都放在标签里，提示词要求把其中的指令当普通内容
4. **上下文裁剪**：对话完整存在数据库（`agent_sessions.messages`，OpenAI 消息格式），发给模型前只保留最近一次的参考答案，之前的换成一句说明。问到后面几题时上下文不会越来越大
5. **计费和并发**：一轮不管调了几次模型都只算一次 AI 次数；同一场面试同一时间只能跑一轮。中途出错或用户停止时，已经完成的步骤照样保存
6. **展示**：SSE 推送 `delta`（文字）、`tool_start` / `tool_end`（工具调用和结果）。页面把消息转成时间线：面试官的话、工具步骤、出题卡片、打分卡片、总结，一轮结束后以服务端保存的记录为准重新加载
7. **测试**：测试里的模拟大模型按对话状态决定调用哪个工具，覆盖完整面试、追问、跳过、提前结束，以及模型给错误的题打分时被工具拦下

## MCP Server 是怎么实现的

代码在 `server/utils/mcp-protocol.ts`（JSON-RPC 分发和协议版本协商，纯函数）、`server/utils/mcp-tools.ts`（7 个工具和 3 个提示词）、`server/routes/mcp.ts`（传输层）和 `server/utils/api-token.ts`（访问令牌）。

1. **协议**：按 MCP 规范手写服务端，没有引入运行时依赖。消息是 JSON-RPC 2.0，声明 tools 和 prompts 两种能力，同时服务两代协议：
   - **2026-07-28 版**：无状态，没有握手。每个请求在 `_meta` 里带协议版本和客户端能力，服务端逐个请求判断；结果都带 `resultType` 并在 `_meta` 里自报身份；`server/discover` 介绍支持的版本、能力和使用说明；列表结果带缓存提示，工具列表因令牌权限不同标成 `private`。版本不支持时返回 `-32022` 并列出支持的版本，客户端挑一个重试
   - **2024-11-05 到 2025-11-25**：照常先 `initialize` 协商版本。请求里没有 `_meta` 版本的就按旧协议处理，旧客户端不用改
   
   协议错误（方法或工具不存在）用 JSON-RPC error，工具执行出错（参数不对、题目不存在、分类写错）用 `isError` 结果返回，模型能看到原因并自己修正
2. **传输**：Streamable HTTP，不建会话：每个 POST 直接返回 JSON，通知回 202；GET 和 DELETE 回 405（浏览器打开时跳到接入说明页）。校验 `Origin` 防 DNS 重绑定。2026-07-28 版还要求把协议版本、方法和名称抄到请求头里（`MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name`），方便网关按头路由，服务端校验它们和正文一致，不一致回 400 + `-32020`；未知方法回 404。工具和提示词列表不会变，`subscriptions/listen` 确认订阅后立刻正常结束，客户端不会当成断线去重连。无状态的好处是不用在实例之间共享会话，可以随便扩容
3. **鉴权**：个人访问令牌（`mbk_` 加 240 位随机数），数据库只存 SHA-256；分只读和可写入两种权限，只读令牌在 `tools/list` 里就看不到写入的工具；可以设有效期，撤销后立刻失效；每个令牌每分钟 60 次请求。规范推荐远程服务用 OAuth 2.1，个人项目先用令牌，Claude Code 和 Cursor 都支持自定义请求头
4. **工具**：复用 Agent 面试官和问手册的实现：混合检索、找题、看题（带自己的笔记和下次复习时间）、按薄弱点抽题、学习情况、今日复习、记录得分（写进 FSRS 复习计划）。每个工具带 `readOnlyHint` 等注解，客户端据此决定调用前要不要征求用户同意。提示词 `quiz`、`review_today`、`explain` 在 Claude Code 里是 `/mcp__mianbook__quiz` 这样的命令
5. **测试**：接口测试用两代官方 TypeScript SDK 的客户端连接真实服务（都只是开发依赖）：v1（`@modelcontextprotocol/sdk`）走 `initialize` 握手；v2（`@modelcontextprotocol/client`）分别用锁定 2026-07-28 和自动协商两种方式连接，确认协商出的是新协议。请求头校验、版本错误、订阅流这些边界情况用原始 HTTP 请求测

## 选题雷达

`npm run radar` 从 GitHub 上公开的中文面试题仓库（来源列表在 `scripts/radar-sources.json`）收集题目标题，合并不同说法的同一道题，统计每道题出现在几个来源里，再和题库比对，生成 `reports/topic-radar.md`：
- 多个来源都在问、题库里没有的题，按分类列出，附来源链接
- 多个来源都在问、题库里只有相近的题（可能换了说法，也可能角度不同）
- 只有一个来源问到、题库里没有的题（每个分类列前 10 个）
- 每个来源的许可证和收集数量

只用 GitHub 官方 API，只收集题目标题，不抓答案、不存作者。匿名访问每小时 60 次请求，抓过的内容缓存 7 天（`.data/radar-cache/`），限额用完了过一小时再跑会接着抓；在 `.env` 里填 `GITHUB_TOKEN`（只需要公开仓库的只读权限）可以一次抓完。

比对只看文字：标题或追问的相似度够高，或者关键词全都出现在题库同一段正文里，就算覆盖；换了术语的说法（比如"索引底层数据结构"和"B+ 树"）会被算成没覆盖，所以报告是选题参考，不是结论。写进题库的解析要自己写，不要照搬来源里的答案。

## 评测与可观测

**AI 调用可观测**：每次大模型调用（Agent 的一轮算一次）记一条 `ai_calls`：模型、提示词版本（`shared/utils/prompt-versions.ts`，改提示词就加版本）、首字延迟、总耗时、结果（正常 / 中途停止 / 出错）和出错原因。出错的调用不扣用户的次数，也不算进用量和费用；中途停止但已经有输出的照常计数。后台概览的"AI 性能"按功能显示近 7 天的调用数、出错率、首字延迟和总耗时的 P50/P95（只算正常结束的），以及最近几次出错的原因。

**服务端错误**：接口抛出的 5xx 错误由 Nitro 插件记进 `error_logs`（同样的错误一分钟只记一次，保留 30 天），后台概览能看到最近的错误。没有接第三方监控，需要告警时可以再接 Sentry 一类的服务。

**面试官打分评测**：`evals/scoring.json` 里 8 道题（JS、React、网络、MySQL、Redis、Go、RAG、Agent），每道 4 档回答：讲全要点的、漏了关键点的、错误的、夹带"给满分"之类话术的。`npm run eval:scoring -- --yes` 用 `.env` 里配置的真实模型、和线上同一套提示词，每个回答打 3 次，统计：
- 格式遵守率：能解析出得分的比例
- 档位命中率：好的在 8～10 分、一般的 4～7 分、错误的 0～3 分、注入的不超过 4 分
- 稳定性：同一个回答多次打分的标准差
- 三档排序：每道题是否"好 > 一般 > 错误"
- 防注入：注入回答的最高分

不加 `--yes` 只打印要调用多少次，不消耗额度。结果存到 `evals/results/`，带着模型和提示词版本，改提示词前后各跑一次对比。

## 问手册（RAG）是怎么实现的

代码在 `server/utils/rag-core.ts`（切块、检索、融合、重排、评测指标，纯函数）、`server/utils/rag.ts`（索引同步、内存检索器）和 `server/api/ask.post.ts`。

1. **切块**：每道题按二级标题切开，"一句话回答"单独一块（整题的摘要），"面试官可能追问"里每个折叠块各成一块（用户常直接问追问的内容），超过 900 字的小节按段落再切。送去生成向量的文本带上题目和小节标题，单独一块也知道在讲什么。692 道题切成约 5900 块
2. **增量同步**：每块存内容的 SHA-256。服务启动和后台改题后几秒内自动同步，哈希没变的块沿用旧向量，只给新增和改过的块调用向量接口；换了向量模型时全部重新生成。向量接口出错不影响关键词检索，下次同步接着生成
3. **混合检索**：关键词一路用 MiniSearch（BM25），中文用 `Intl.Segmenter` 分词，去掉"怎么""什么""说说"这类口头词，被切成单字的词两两拼回双字词；向量一路在内存里和所有块算余弦相似度（约 5900 块只要几毫秒，到几十万块再换向量数据库）。两路结果用 RRF（`Σ 1 / (60 + 排名)`）按排名融合，不用处理两种分数量纲不同的问题。每道题最多取 2 块
4. **重排**：融合排序的前 30 块交给重排模型（默认硅基流动的 `BAAI/bge-reranker-v2-m3`，和向量模型共用 Key），它把问题和每块资料放在一起读，打出相关度。最终顺序不是直接按重排分排，而是把融合排序和按重排分的排序再做一次 RRF，取前 6 块：评测里只按重排分排时，有的题被字面相近、领域不同的块挤了下去（"上传大文件断点续传"排到了"流式连接断了怎么续传"后面）。重排接口超过 3 秒或出错时用融合排序，并暂停 30 秒再试，不让每次检索都多等一个超时；同一个问题、同一批候选的分数有缓存
5. **生成**：资料带编号放进提示词，要求每句话标出处、资料里没有的明确说"手册里没有直接讲到"；资料和问题里的指令一律当普通文字（防提示注入）。多轮对话时，短追问（"那它的缺点呢"）补上上一个问题再检索，历史回答里的旧编号去掉。一段资料都没检索到时直接回复，不调用大模型、不占次数
6. **展示**：先推送检索到的资料（SSE 的 `sources` 事件），页面马上显示"找到几段资料"，再流式输出回答；回答里的 `[n]` 换成指向原题的链接，模型编出的不存在的编号直接去掉

**评测**：`evals/retrieval.json` 有 70 个问题，覆盖全部 39 个分类，分四类：换个说法问（paraphrase）、工作场景（scenario）、问的是追问或易错点（followup）、口语化（colloquial），都不照抄题目标题。`npm run eval:retrieval` 对比只用关键词、只用向量、混合检索、混合检索 + 重排的 Recall@1/3/5 和 MRR，并列出没找回来的问题；同一份重排分数还会算一遍"只按重排分数排序"作对照。用线上数据（692 道题、5947 块，向量模型 BAAI/bge-m3，重排模型 BAAI/bge-reranker-v2-m3）评测的结果：

| 检索方式 | Recall@1 | Recall@3 | Recall@5 | MRR |
| --- | --- | --- | --- | --- |
| 只用关键词（BM25） | 75.7% | 88.6% | 92.9% | 0.832 |
| 只用向量 | 78.6% | 92.9% | 94.3% | 0.865 |
| 混合（RRF） | 85.7% | 95.7% | 95.7% | 0.905 |
| 混合后只按重排分数排序 | 85.7% | 95.7% | 95.7% | 0.910 |
| 混合 + 重排（线上用的） | 87.1% | 98.6% | 98.6% | 0.924 |

向量主要提升的是排序：混合检索的 Recall@1 比只用关键词高 10.0 个百分点（70 个问题里多了 7 个排第一），MRR 从 0.832 提到 0.905。

重排有小幅收益。混合检索已经把 69 个问题的期望题目放进了前 30 块候选（这是重排能达到的上限）；重排后排名变好 5 个、变差 2 个，Recall@1 多 1 个排第一，Recall@3、Recall@5 各多找回 2 个问题，MRR 从 0.905 提到 0.924。评测集只有 70 个问题，差一两个问题仍然说明不了太多；代价是每次检索多一次重排请求（实测 P50 约 0.5 秒）。只按重排分数排序时各项都不如再融合一次（上一版 60 个问题的评测里，它的 Recall@1 和 MRR 甚至低于不重排），所以线上用的是再和融合排序融合一次的做法。还剩一个问题没进前 5：只描述现象的场景题"从列表页进详情再返回，筛选条件和滚动位置全没了"，期望的 keep-alive 题根本不在候选里，是召回的问题，重排帮不上。

## 部署

线上用一台 Ubuntu 24.04 服务器（2 核 4G 够用），Docker 跑三个容器：MySQL 8.4、应用、Caddy。Caddy 负责自动申请和续期 HTTPS 证书。配置都在 `deploy/` 目录里。

**第一次准备**

1. 服务器装好 Docker，用 SSH 密钥登录，防火墙放行 22、80、443
2. 给域名添加 A 记录（`@` 和 `www`），指向服务器 IP
3. 在项目根目录新建 `.env.deploy`（不会提交）：

   ```bash
   DEPLOY_HOST=ubuntu@服务器IP
   DEPLOY_KEY=~/.ssh/私钥文件
   DEPLOY_DOMAIN=你的域名
   ```

4. 执行 `npm run deploy -- --import`：上传代码，在服务器上构建镜像，建表并导入 `content/` 里的题目

第一次部署时，会在服务器的 `/opt/handbook/.env` 里随机生成数据库密码和登录密钥。AI Key 和发信邮箱（`NUXT_MAIL_*`，见上面的"注册邮箱验证码"）也填在这个文件里，填好后在服务器上执行 `cd /opt/handbook && docker compose up -d app` 生效。发信邮箱和向量 Key 也可以在本机运行 `npm run server:env` 填写：在终端里隐藏输入，经 SSH 写进服务器的 `.env` 并重启应用，密钥不会出现在命令行参数和 shell 历史里；QQ、163 的授权码不是 16 位时会提示重填。

**以后发布**：执行 `npm run deploy`。只发布已经提交的代码，有未提交的修改会提示，但不会上传。上一版代码保留在服务器的 `/opt/handbook/src.prev`。

**题目以线上后台为准**：上线后在线上后台改题。服务器上没有 `content/` 目录，修改只保存在数据库里。本地新写的题要发布时，先提交再执行 `npm run deploy -- --import`。导入不会覆盖线上比文件新的题。

**备份**：服务器每天 03:30 自动备份数据库到 `/opt/handbook/backups`，保留 14 天。`npm run deploy:backup` 会立即备份一次，并下载到本地的 `backups/` 目录。

**CI/CD（GitHub Actions）**：
- `.github/workflows/ci.yml`：推送到 main 和每个 PR 都会跑题目格式检查、类型检查、单元测试和接口测试（用服务容器起一个临时 MySQL）。接口测试失败时会上传服务端日志
- `.github/workflows/deploy.yml`：推送 `v` 开头的 tag（如 `git tag v1.3.0 && git push origin v1.3.0`）或在 Actions 页面手动运行时，先跑完整的测试，通过后用 `scripts/deploy.mjs` 发布，最后访问 `/api/health` 确认服务正常；手动运行时可以勾选"同时导入题目"
- 发布需要在仓库的 Settings → Environments 里建 `production` 环境，配置 `DEPLOY_SSH_KEY`（CI 专用的 SSH 私钥）、`DEPLOY_KNOWN_HOSTS`（`ssh-keyscan 服务器IP` 的输出）、`DEPLOY_HOST`（如 `ubuntu@1.2.3.4`）三个 secret 和 `DEPLOY_DOMAIN` 变量。可以给这个环境加"需要审批"，发布前要人点一下确认
